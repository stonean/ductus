# 088 — Rule judgments cost only what changed

A `/{project}:analyze` run judges a loaded rule afresh only when what that rule reads has changed, and its record says how many rules it judged afresh and how many stored verdicts it carried, so what rule assessment costs is read from the record rather than inferred.

## Motivation

- [082](../082-rule-assessments-converge-across-runs/spec.md) made a stored verdict stand while the sections it concerned were unchanged (its AC1 and AC7), so a run judged a rule again only against changed sections. Whether that held in practice was not known: the `analyze(…)` commit subjects reported "306 rules judged" without saying how many were judged afresh.
- **Measured** at `4cfcf172` (2026-11-25) over the 37 `analysis.md` records changed by commits after `1dc4736e`, 082's second `done`, each compared with the same path at its commit's parent: 0 advisory contradictions (082's AC3) were recorded, and 0 in the 161 records since its first `done`, `a3629a95`. `rule-verdicts` holds only rules that fired, and `write-analysis`'s `judged-rules` argument is not stored (`AnalyzeBlock` in `runtime/src/schema/primitives.rs` carries `rule_verdicts` and no `judged_rules`, an argument of `WriteAnalysisArgs` alone), so no record said how many rules its run judged afresh.
- **Derived**, by applying 082's reuse rule (its data model's Relations and `discover-rule-files`' reasons) to each prior and new record, not by reading what any run judged: 26 of the 37 runs owed a full judgment of every loaded rule, 19 because the prior record predated AC7's section digest, 5 because it carried no `rule-digest` and 2 because none existed; 7 owed a full judgment of each rule in an edited rule file (90 or 175 of 306); 4 owed judgments against changed sections only; none could carry a rule outright. Of 11,364 rule judgments owed, 2,402 (21.1%) were narrowed to changed sections. 22 commits touched `framework/rules/` after `a3629a95`.
- 082's Motivation recorded an adopter on `ductus-v0.59.11` getting 10, then 8, then 4 new rule findings over three runs on unchanged text.

## Behavior

- An analysis record states how many loaded rules its run judged afresh and how many stored verdicts it carried, so a run's rule-assessment cost is measured from the record.
- When a loaded rule file's digest differs from the one the record names, only the rules whose own text changed are judged again: the runtime reads that file at the record's `analyzed-against` commit and compares it with the current file rule by rule, so a rule whose heading, Statement and Verification are unchanged keeps its verdict. When history cannot supply the old file, as in a shallow clone, every rule in it is judged again and the result says why. A rule whose Statement or Verification names a rule judged again for either reason, or one a changed file no longer holds, is judged again too, in whichever loaded file it sits, since its verdict can rest on what the named rule says; a rule naming one only through another is not.
- A record with no `section-digest` whose `analyzed-digest` still matches its spec's design subjects gains the `section-digest` its run would have written, by a deterministic backfill shipped as a migration. A `done` spec's analysis read `spec.md` before the done flip rewrote its `status:` line, so a record also matches when `spec.md` with its `status:` set to another lifecycle status reproduces the recorded digest, and gains that text's digests. A record that matches neither way is left as it is, and gains the digest at its spec's next analysis.
- No other judgment is skipped: every loaded rule is judged unless 082's reuse or the rule above carries its verdict, and a MUST rule still gates.

## Edge Cases

- A rule file added to or removed from the loaded set is the `rule-files-changed` case it is today: every loaded rule is judged.
- A rule whose ID now sits in a different file than at `analyzed-against` is judged again, as is a rule whose ID is new; a rule removed leaves its verdict behind.
- A record with no `analyzed-against`, or one naming a commit the repository does not hold, re-judges each changed file whole, and the result names the reason.
- With `unjudged-rules`, the two counts AC1 records sum to the distinct assessable rules the loaded files define, a not-fired verdict carried counting as carried.
- When history cannot supply a changed file's copy, nothing says which rules the file held, so a rule in any loaded file naming an ID no loaded rule defines and the framework does not ship is judged again too, since the file may have held it: a rule naming a mistyped ID is then judged needlessly, a rule naming a shipped rule of a surface the project did not install is not, and no verdict resting on a removed rule is carried.

## Acceptance Criteria

- [x] AC1: `write-analysis` records, for each run, the count of loaded rules judged afresh and the count of stored verdicts carried, and a test proves both counts on a fixture run that carries one verdict and judges one rule afresh.
- [x] AC2: `discover-rule-files` with a `feature` puts in `judge` only the rules of a changed rule file whose own text differs from that file at the record's `analyzed-against`, or every rule of it when that commit's copy cannot be read, naming why, and each loaded rule whose Statement or Verification names one of those rules or one the file no longer holds; a fixture proves an edit to one rule re-judges that rule and each rule naming it alone, and one in a shallow clone re-judges the whole file.
- [x] AC3: A backfill writes `section-digest` into each `analysis.md` that carries none and whose `analyzed-digest` matches its spec's design subjects, as they stand or with `spec.md`'s `status:` set to another lifecycle status, the digests being those of the text that matched, leaving every other byte of the record as it was, and leaves each record that does not match untouched and names it; it ships as a migration ordered after every existing one, a second run writes nothing, and a fixture proves a matching record gains the digest, one matching at another status gains that text's digest, and a stale one is left as it was.

## Resolved Questions

- **A rule-file edit re-judges only the rules whose own text changed, derived from git** (the agent's recommendation, adopted by the operator, 2026-11-25). `rule-digest` held one sha256 per file, and `discover-rule-files`' description stated that "a file whose content alone changed makes only its own rules non-current", so seven of the 37 measured runs re-judged 90 or 175 of 306 rules for one edited file. Comparing the file at the record's `analyzed-against` with the current one adds nothing to a record and one `git show` per changed file per run. Rejected: a digest per rule in the record, about 11 to 25 KB more on each of the 80 records and a frontmatter schema change through the constitution; and keeping the per-file rule. **Refined (2026-11-26, below):** a rule naming a rule judged again is judged again too.
- **A rule that names a changed rule is judged again too** (the agent's recommendation, adopted by the operator, 2026-11-26). Measured at `1ffaf951` with `discover-rule-files --all --rules --verification`, a name being a loaded rule's ID in another rule's Statement or Verification: 106 of the 306 rules name a rule of their own file, and 88 one of another file, which 082's per-file digest never judged again. Of the first 12 names in `framework/rules/accessibility-frontend.md`'s rules, read in file order, 8 mark an ownership boundary the naming rule states in its own text and 4 rest on the named rule's content ("by one of the means `FE-ARIA-002` lists"). Over the 22 commits that touched `framework/rules/` after `a3629a95`, each dumped beside its parent in a clone, the per-file rule owed 1,009 judgments, a rule's own text alone 59, and its own text with each rule naming a changed one 104. Only a direct name counts: a rule naming one only through another reads that other's text, which did not change. Rejected: a rule's own text alone, which keeps the verdict of a rule whose Verification rests on a rule that changed.
- **No rule is left unjudged on a deterministic ground** (the agent's recommendation, adopted by the operator, 2026-11-25). `/{project}:analyze` keeps judging every loaded rule, narrowed only by 082's reuse and the answer above. `/ductus` installs only the rule files `[rules] surfaces` selects (`framework/bootstrap/ductus.md` §Project Configuration: "Which rule surfaces /{project}:review enforces and /ductus installs"), so an adopter's analysis already loads only its surfaces' files, and a skip by surface would save this repository's 107 frontend rules of 306 per full run (40 accessibility, 45 security, 22 performance, by rule heading in `framework/rules/*-frontend.md`) and little elsewhere. Rejected: honouring `[rules] surfaces` in analysis, which amends §rules ("never from `/{project}:analyze`") and 033's AC7, reopening 033, and leaves a spec that describes frontend behavior unjudged against frontend rules; and a skip by the paths a change touched, which needs each of the 306 rules to declare the paths it governs.
- **A current record without a `section-digest` gains one by a deterministic backfill** (the agent's recommendation, adopted by the operator, 2026-11-25, replacing the same day's answer to drain, whose recommendation had weighed scope and the release date). 50 of the 78 `analysis.md` records held none (a frontmatter scan, 2026-11-25). A record whose `analyzed-digest` still matches its spec's design subjects was judged against exactly the sections it now has, so their digests are the ones its run would have written, and those specs' next runs judge only changed sections. Rejected: letting each record gain the digest at its spec's next run, which leaves those next runs judging every loaded rule.
- **A record also matches with `spec.md`'s `status:` set to another lifecycle status** (the agent's recommendation, adopted by the operator, 2026-11-26). Measured at `1ffaf951` in a local clone, by `discover-rule-files`' `verdicts.reason` for each record as it stands and with its spec's status set by `set-status` to each other status: 49 of the 79 records held no `section-digest`, 48 of them `done`, and 31 carried the `rule-digest` without which no verdict is reused. A `done` spec's analysis ran before the done flip rewrote `spec.md`'s `status:` line, so a match as recorded writes 2 records, 1 with verdicts (036's), and a match at the status the run read writes 13, 12 with verdicts (11 analyzed at `in-progress`, and 036's) and 009's, which carries no `rule-digest`. The backfill writes only when that text hashes to the recorded digest, which proves the run read it, so it asserts no analysis that did not happen, the reason `framework/migrations/audit-record-relocate.md` gives under "Do not backfill the digests". Rejected: a match as recorded, which leaves 29 records with verdicts and no digest; and no backfill, which drops the primitive, the migration and its bootstrap run, and leaves those 12 specs' next analyses after an edit judging every loaded rule.
- **A file judged whole judges each rule naming an ID no loaded rule defines** (the agent's recommendation, adopted by the operator, 2026-11-26, in 088's review). When a changed file's copy at `analyzed-against` cannot stand in, nothing says which rules the file held, so a rule in another file naming one it removed kept its verdict, which AC2 does not allow: `RuleEdits::between` added only the file's current rules to what a naming rule is stale for. A name no loaded rule defines may be such a rule, so while a file is judged whole it stales each rule naming it; it costs one set of the loaded rules' IDs and no git read, and judges needlessly only a rule naming a mistyped ID, of which this repository's rule files held none at `42202b22`. A shipped rule's ID is left out (`shipped_rule_ids`), since one no loaded file defines sits in a surface the project did not install: without that, a single-surface adopter would judge needlessly each rule naming another surface's rule, 13 of 199, 20 of 138 or 8 of 31 (the Cost section; the agent's recommendation, adopted by the operator, 2026-11-26, once the review found the first form understated that cost). Rejected: rewording AC2 to count a removed rule only when its file's copy can be read, which carries a verdict the run cannot vouch for, signalled only by the file's `rejudged-files` entry.
