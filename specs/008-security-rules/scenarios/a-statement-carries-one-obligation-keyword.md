# A-statement-carries-one-obligation-keyword

## Context

The rule format's severity classification made a rule's Statement the source of its tier: "The Statement's RFC 2119 keyword determines the severity `/{project}:analyze` reports", MUST and MUST NOT blocking, SHOULD and SHOULD NOT non-blocking. The same table required that "Rules MUST use exactly one of the four keywords in the Statement. Mixed keywords (e.g., "MUST … SHOULD") are not permitted; split such rules into two entries" (`specs/008-security-rules/data-model.md:111`–`:120`). `specs/017-derive-dont-ask/data-model.md:75`–`:84` restated the invariant for configuration rules, and `specs/036-quality-cross-rules/data-model.md:63` for quality rules.

The shipped rule files did not hold to it. Counted 2026-09-27 over the Statement block quote of every `### {ID}` section in `framework/rules/*.md`, with MUST NOT counted as MUST and SHOULD NOT as SHOULD, 16 of 192 rules carried both a MUST-family and a SHOULD-family keyword:

- `framework/rules/security-backend.md`: `BE-AUTHN-007`, `BE-AUTHN-010`, `BE-AUTHN-014`, `BE-DEPS-001`, `BE-ERR-002`, `BE-LOG-003`
- `framework/rules/security-frontend.md`: `FE-CSP-001`, `FE-CSP-003`, `FE-PII-003`, `FE-STORAGE-002`, `FE-XSS-008`
- `framework/rules/performance-frontend.md`: `FE-FONT-002`, `FE-LOAD-001`, `FE-LOAD-002`
- `framework/rules/api-backend.md`: `BE-ERRENV-001`, `BE-PAGE-001`

Every one is a `BE-`/`FE-` ID, whose format this spec's data model governs. No check enforced the invariant, which is how 16 violations reached the shipped files. Three Statements also used MAY, which was not one of the four keywords — `BE-PAGE-001` (one of the 16), `BE-INPUT-010`, and `BE-DATA-001` — counted over the same block quotes.

Surfaced while clarifying `060-exec-analyze-assesses-each-loaded-rule`, whose exec walker reads each rule's tier from its Statement. That spec settled the walker's reading of a mixed Statement as MUST-tier, so a mixed rule is assessed once and never in both tiers. It did not settle whether the rule files or the invariant is the thing to change.

## Behavior

Every shipped rule's Statement and the rule format's severity classification agree: a reader, or a tool, takes one tier from each Statement without a precedence rule the format does not state.

- **The invariant is stated in tier terms.** A Statement's obligation keywords come from one tier: MUST and MUST NOT, or SHOULD and SHOULD NOT. MAY is permitted beside them as a permission or scope boundary and carries no tier. `specs/008-security-rules/data-model.md`, `specs/017-derive-dont-ask/data-model.md`, and `specs/036-quality-cross-rules/data-model.md` all state it that way.
- **The 16 mixed rules are reconciled.** 14 are split: each becomes a MUST rule under its existing ID and a SHOULD rule under the next free sequence number in its category, and each new rule carries its own Statement, Rationale, and Verification. A citation that meant a SHOULD half names the new ID. The other two, `BE-DEPS-001` and `FE-CSP-001`, lose a SHOULD clause their own MUST clause already implies, and no rule is minted for it.
- **The Statement field describes the shape the rules have.** The format describes a Statement as a block quote whose obligation keywords come from one tier, with MAY permitted beside them, rather than as "one sentence". 121 of 192 shipped Statements ran to two or more sentences, counted 2026-09-27 over the same block quotes as a `.`, `!` or `?` followed by whitespace and a capital, with `e.g.`, `i.e.`, `etc.`, `vs.` and code spans masked. The "one sentence" claim appears at `framework/constitution.md:381`, `specs/008-security-rules/data-model.md:75`, `specs/008-security-rules/spec.md:59`, and `specs/017-derive-dont-ask/data-model.md:60`, and each is reworded.
- **A mixed Statement cannot reach a shipped rule file.** The runtime's corpus test over the shipped rules fails on a Statement whose keywords span both tiers, and it runs in CI on any change under `framework/rules/`.

## Edge Cases

- **Splitting keeps the existing ID on the MUST half.** Under ID stability an existing ID is never renumbered or reissued, so every existing citation still resolves to a rule. A citation that meant the SHOULD half would then resolve to the wrong one, which is why the two such citations are re-pointed rather than left to resolve.
- **A headline SHOULD.** `FE-XSS-008`'s MUST clauses apply only once Trusted Types is adopted. The existing ID keeps those conditional MUSTs, and the new SHOULD rule states the adoption.
- **A split rule's shared context.** A clause that bounds or qualifies one half goes with that half: `BE-PAGE-001`'s MAY sentence bounds the cursor-based default, so it goes with the SHOULD rule. The Rationale of each half states the risk that half mitigates, not the original rule's rationale copied whole.
- **A SHOULD clause its own MUST already implies.** Splitting it off would mint a rule that cannot fail unless its MUST sibling also fails, so every such gap would be reported twice under two IDs, which cross-pass dedup does not merge. The clause is dropped instead, which removes no obligation. `BE-DEPS-001`'s "Scanning SHOULD be automated in CI/CD" was implied by its scan on every CI run. **Superseded 2026-10-19:** the owner ruled that a MUST never requires continuous integration (`specs/008-security-rules/data-model.md` §Severity classification), so `BE-DEPS-001` now requires a scan before every release and on a schedule, and automating the scan on each dependency change is its own SHOULD, `BE-DEPS-007`. That SHOULD is no longer implied by the MUST — a project can scan before every release without scanning each change — so it fails independently and is not double-reported. `FE-CSP-001`'s "SHOULD NOT be delivered via `<meta>` tag alone" is implied by its header delivery, and the reason `<meta>` falls short stays in its Rationale.
- **Single-tier Statements with two keywords.** A Statement pairing MUST with MUST NOT, or SHOULD with SHOULD NOT, is one tier and is not split. 66 shipped Statements had that shape, counted over the same block quotes.
- **A Statement with MAY and no obligation keyword.** It has no tier, so it is not assessable and fails the corpus test. No shipped Statement has that shape.
- **Adopter copies.** The security rule files ship with the `update` strategy, so an adopter's unpinned copy receives the split on the next `/ductus` run. A pinned copy does not and keeps the mixed Statements until its owner acts. No check reads it, and `/{project}:analyze` reads each of its mixed rules as MUST-tier.
- **Adopter citations and waivers.** An adopter's citation of one of the 16 IDs keeps resolving to the MUST half. A waiver on one of them keeps covering the MUST half it already silenced, and the new SHOULD rule's findings are unwaived.
- **Three data models state the invariant.** `specs/008-security-rules/data-model.md` is canonical, and `specs/017-derive-dont-ask/data-model.md` and `specs/036-quality-cross-rules/data-model.md` restate it. All three change together, or they disagree. 017 and 036 are `done`, so the edit reopens both under the meaningful-body-edit back-edge.

*None — all resolved.*

## Resolved Questions

- **Are the 16 mixed rules split into two entries each, or is the invariant relaxed to admit a SHOULD clause refining a MUST rule?** Split. Each of the 16 becomes a MUST rule and a SHOULD rule, except where the SHOULD clause is already implied by its own MUST clause: implementation found two such rules, `BE-DEPS-001` and `FE-CSP-001`, and each loses the clause rather than minting a rule (see Edge Cases). The MUST half keeps the existing ID in every case, and the SHOULD half takes the next free sequence number in its category. For `FE-XSS-008`, whose headline obligation is the SHOULD, the existing ID keeps the MUST clauses that apply once Trusted Types is adopted, and "adopt Trusted Types" becomes the new SHOULD rule. The invariant itself is restated in tier terms rather than keyword terms: a Statement's keywords come from one tier, MUST and MUST NOT or SHOULD and SHOULD NOT. Read literally, "exactly one of the four keywords" is also broken by 66 single-tier Statements that pair MUST with MUST NOT or SHOULD with SHOULD NOT, 2 of them `CFG-` rules, and it is restated in three data models rather than two: `specs/008-security-rules/data-model.md:120`, `specs/017-derive-dont-ask/data-model.md:84`, and `specs/036-quality-cross-rules/data-model.md:63`. All three change together.
  - **Why split rather than relax.** The data-model rewording is owed under either answer, so it does not separate them. What does is that the review record assumes one tier per rule ID. A waiver matches a finding on `(rule, file)` alone (`runtime/src/primitives/write_review.rs:485`–`:492`, `runtime/src/primitives/process_waivers.rs:122`), so waiving a mixed rule's SHOULD finding, the constitution's disposition for a SHOULD kept as-is, would also silence its MUST clauses on that file. Cross-pass dedup collapses findings sharing `(rule, file)` with overlapping line ranges to the highest severity (`write_review.rs:427`–`:448`), so a mixed rule's SHOULD finding beside its MUST finding would drop from the record. Relaxing would keep both hazards or need a waiver-schema change and a runtime release to close them. Splitting needs neither: the runtime already reads a split rule's tier (`RuleSection::tier`, `runtime/src/primitives/rule_sections.rs:50`), and `every_shipped_rule_is_assessable` holds as long as each new entry carries a Verification.
  - **Measured cost.** 14 new rule entries (192 → 206), each with its own Statement, Rationale, and Verification, and 16 existing Statements and Verifications narrowed to their MUST clauses. Of the 8 citation sites naming one of the 16 IDs outside its own section, two cited a SHOULD half and were re-pointed to the new ID: `framework/rules/security-backend.md:503` cited `FE-CSP-003` for the `X-Frame-Options` fallback, and `specs/008-security-rules/research.md:41` cited `BE-ERR-002` for RFC 9457. The first was later moved again, to `BE-API-012`, when `x-frame-options-carries-one-strength` gave the backend its own statement of that fallback. The other six cite MUST halves, which keep their IDs. Counted 2026-09-27 over each `### {ID}` section's first block quote in `framework/rules/*.md` for the rules, and with `git grep -w` outside each rule's own heading for the citations. Adopter citations and waivers are not measurable from this repository: a waiver on one of the 16 IDs keeps covering the MUST half it already silenced, and the new SHOULD IDs fire unwaived.
- **Does a check enforce the resolved invariant, so a mixed Statement cannot reach a shipped rule file again?** Yes, for the shipped rule files, and by the runtime's corpus test rather than by `/{project}:analyze`. A second corpus test over every shipped rule, `no_shipped_statement_mixes_tiers` (`runtime/src/primitives/rule_sections.rs:449`), sits beside `every_shipped_rule_is_assessable` and fails on a Statement whose keywords span both tiers, and a fixture test asserts the predicate in both directions, a mixed Statement caught and a MUST-with-MUST-NOT Statement passed, so the check keeps a subject once the shipped corpus is clean. `.github/workflows/runtime.yml` gains `framework/rules/**` in its pull-request and push trigger paths. That path is owed regardless of this answer: the existing corpus test already reads those files, and without it a change touching only rule files, the split itself included, never runs the test in CI. No binary behavior changes, so this ships from `main` without a runtime release.
  - **Why not an analyze integrity check.** The existing integrity checks (`framework/commands/analyze.md`, rule-file validation) make a failing file unloadable. An adopter's pinned copy of a shipped file keeps the mixed Statements until its owner acts, so a blocking check would drop every rule in that file from assessment and citation resolution: 73 rules for `security-backend.md`, 32 for `security-frontend.md`, 13 for `api-backend.md`, 10 for `performance-frontend.md`. An advisory check would raise up to 16 findings on every analyzed spec, each owing a disposition. Both cost more than the defect they would catch.
  - **What is not enforced.** A mixed Statement in a rule file a project authors, or in a pinned copy, is not checked. `/{project}:analyze` reads such a rule as MUST-tier (`framework/commands/analyze.md`, step 11), so it is assessed once rather than skipped, but the waiver and dedup behavior recorded under the question above applies to it unchanged.
- **Is MAY permitted in a Statement?** Yes, as a permission keyword with no tier. MAY states a permission or a scope boundary, never an obligation, so it neither sets nor changes a rule's tier and appears only beside a MUST-tier or SHOULD-tier keyword. The data models state this in the same edit that restates the invariant in tier terms, so it reopens nothing beyond what that edit already reopens. The three shipped uses all have this shape: `BE-DATA-001` excepts loopback traffic from its plaintext prohibition, `BE-INPUT-010` bounds its interpolation prohibition to bound variables, and `BE-PAGE-001` bounds where offset pagination may replace its cursor-based default. None is rewritten. When `BE-PAGE-001` is split, its MAY sentence goes with the new SHOULD rule, whose default it bounds.
  - **Why not forbid it.** Forbidding MAY rewrites three Statements, and `BE-PAGE-001`'s "MAY be used only for" would have to become SHOULD NOT or MUST NOT, which decides whether offset pagination on a collection with concurrent writes blocks. That is a change to the rule's strength made as a side effect of a format fix.
  - **Enforcement.** Nothing new is needed. `RuleSection::tier` reads only MUST and SHOULD (`runtime/src/primitives/rule_sections.rs:50`), so a Statement using MAY alone has no tier and already fails `every_shipped_rule_is_assessable`.
