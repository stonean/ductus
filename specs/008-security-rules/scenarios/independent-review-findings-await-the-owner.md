# Independent-review-findings-await-the-owner

## Context

On 2026-10-19 an independent reviewer re-checked, against fetched sources, the security rules changed after the second rule-file review pass. Every wording, fact, and citation fix was applied (commit 7577068c). Six findings would change what a rule requires, so they were left for the owner and are recorded here as open questions, each with the reviewer's evidence and a recommendation. A seventh and an eighth, the last two below, came from 034's review of the same day, which found `BE-API-013` and `FE-STORAGE-003` disagreeing about which tokens may travel in a URL and where. Ask them one at a time (constitution §recommendations).

## Behavior

- Each open question below is answered by the owner, the rule changes (or stays) accordingly, and the answer moves to Resolved Questions with its date.

## Edge Cases

- A finding the owner declines leaves its rule as it is; the declined option is recorded so it is not re-raised.

## Open Questions

- BE-AUTHN-001 PBKDF2 condition: the Statement allows PBKDF2 "where FIPS compliance is required" but the Verification never checks that condition. (a, recommended) flag PBKDF2 chosen without a stated FIPS requirement; or (b) make PBKDF2 an unconditional option and drop the condition, which would reverse spec.md Resolved Question 6 (PBKDF2 keeps its place as the choice where FIPS compliance is required)?
- BE-AUTHN-022 MFA changes: the current password alone can authorize removing or replacing a second factor, while the OWASP Multifactor Authentication Cheat Sheet asks for an existing enrolled factor. (a, recommended) require an existing enrolled factor or passkey for MFA changes, narrowing spec.md Resolved Question 9 ("an already-bound authenticator", which today includes the password) for MFA changes only; or (b) keep the current password as sufficient?
- BE-API-015 vs BE-API-013 on a token in the WebSocket handshake URL: BE-API-013 allows single-use short-lived values that a protocol carries in the URL by design (it names OAuth authorization codes, password-reset and email-verification tokens, and expiring pre-signed URLs, not a WebSocket ticket); BE-API-015's Verification flags any token in the handshake URL, following the OWASP WebSocket Security Cheat Sheet ("Avoid tokens in URL query strings"). (a, recommended) keep BE-API-015 stricter and say explicitly it narrows BE-API-013 for WebSockets; or (b) allow BE-API-013's single-use ticket in the handshake URL?
- BE-API-011 / FE-CSRF-001 fallback when Sec-Fetch-Site is absent: the rules allow rejection or an Origin check; OWASP's fail-open option also lists CSRF tokens or additional validation. (a, recommended) keep the Origin-only fallback (a design using tokens already complies through the token defense); or (b) add tokens and additional validation as fallbacks, extending spec.md Resolved Question 5 (reject, or check `Origin`)?
- SameSite as the sole CSRF defense (BE-API-011, FE-CSRF-001): the rules ban it; OWASP allows SameSite alone in narrow deployments meeting listed conditions, and the BE rationale already calls the ban deliberate. (a, recommended) keep the ban; or (b) allow OWASP's narrow conditions?
- BE-API-013 vs FE-STORAGE-003 on pre-signed URLs: BE-API-013's carve-out lets "single-use, short-lived values" appear in a URL and names expiring pre-signed URLs among them, and its Rationale says the carve-out covers values "whose single use and short lifetime bound the damage". A pre-signed URL is neither: AWS's S3 guide says "You can use the presigned URL multiple times, up to the expiration date and time", calls presigned URLs "bearer tokens that grant access to those who possess them", and lets the CLI and SDKs set an expiry "as high as 7 days". FE-STORAGE-003 allows a URL token only when the server invalidates it on first use, and does not name pre-signed URLs, so a page that loads an object through a pre-signed `<img src>` passes BE-API-013 and fails FE-STORAGE-003. (a, recommended) give pre-signed URLs their own MAY in both rules, bounded by scope and expiry rather than single use (a pre-signed URL for one object and one method, with an expiry the spec states), and correct BE-API-013's Rationale to match; (b) drop pre-signed URLs from BE-API-013's carve-out, so a spec serving object-storage downloads through pre-signed URLs fails both rules; or (c) leave both rules as they are? (a) is recommended because a pre-signed URL exists to carry its authorization in the URL, so (b) makes the standard object-storage download and upload pattern non-compliant, while a stated scope and expiry bound the exposure the way single use bounds a reset token's.
- BE-API-013 vs FE-STORAGE-003 on where a single-use token may sit: BE-API-013 lets its single-use values (OAuth authorization codes, password-reset and email-verification tokens) appear anywhere in a URL, while FE-STORAGE-003 allows them only in a query parameter, so a reset link of the form `/reset/{token}` passes BE-API-013 and fails FE-STORAGE-003. Both rules give the same reasons for keeping tokens out of URLs (access logs, browser history, the `Referer` header), and none of them differs between a path segment and a query string; FE-STORAGE-003's conditions, invalidation on first use and `Referrer-Policy: no-referrer` on the landing page, bound the exposure in either position. (a, recommended) allow the single-use carve-out in any URL position in both rules, keeping FE-STORAGE-003's two conditions; or (b) allow it in a query parameter only in both rules, so a path-segment reset token fails BE-API-013 too?

## Resolved Questions

- BE-AUTHN-001 parameter minimums: its Verification names only OWASP's headline settings (Argon2id 19 MiB/t=2/p=1; scrypt N=2^17), but the OWASP Password Storage Cheat Sheet lists several equivalent configurations (e.g. Argon2id 46 MiB/t=1) that analyze would wrongly flag. (a, recommended) accept any configuration OWASP lists as equivalent; or (b) keep only the headline settings? Resolved 2026-10-20 by the owner, option (a): the Verification accepts any of the minimum configurations the cheat sheet lists as equivalent — for Argon2id, with p=1, 46 MiB/t=1, 19 MiB/t=2, 12 MiB/t=3, 9 MiB/t=4 or 7 MiB/t=5; for scrypt, with r=8, N=2^17/p=1, N=2^16/p=2, N=2^15/p=3, N=2^14/p=5 or N=2^13/p=10 — each checked against the cheat sheet the same day, which calls the Argon2id settings "an equal level of defense" and the scrypt ones "a similar minimal level of defense".
