# Independent-review-findings-await-the-owner

## Context

On 2026-10-19 an independent reviewer re-checked, against fetched sources, the security rules changed after the second rule-file review pass. Every wording, fact, and citation fix was applied (commit 7577068c). Six findings would change what a rule requires, so they were left for the owner and are recorded here as open questions, each with the reviewer's evidence and a recommendation. A seventh and an eighth came from 034's review of the same day, which found `BE-API-013` and `FE-STORAGE-003` disagreeing about which tokens may travel in a URL and where. A ninth came from 008's review of 2026-10-20, which found that the narrowed `BE-AUTHN-022` leaves no compliant way to replace a lost second factor, and a tenth from that review's check of the ninth answer as applied. Ask them one at a time (constitution §recommendations).

## Behavior

- Each open question below is answered by the owner, the rule changes (or stays) accordingly, and the answer moves to Resolved Questions with its date.

## Edge Cases

- A finding the owner declines leaves its rule as it is; the declined option is recorded so it is not re-raised.

## Open Questions

*None — all resolved.*

## Resolved Questions

- BE-AUTHN-001 parameter minimums: its Verification names only OWASP's headline settings (Argon2id 19 MiB/t=2/p=1; scrypt N=2^17), but the OWASP Password Storage Cheat Sheet lists several equivalent configurations (e.g. Argon2id 46 MiB/t=1) that analyze would wrongly flag. (a, recommended) accept any configuration OWASP lists as equivalent; or (b) keep only the headline settings? Resolved 2026-10-20 by the owner, option (a): the Verification accepts any of the minimum configurations the cheat sheet lists as equivalent — for Argon2id, with p=1, 46 MiB/t=1, 19 MiB/t=2, 12 MiB/t=3, 9 MiB/t=4 or 7 MiB/t=5; for scrypt, with r=8, N=2^17/p=1, N=2^16/p=2, N=2^15/p=3, N=2^14/p=5 or N=2^13/p=10 — each checked against the cheat sheet the same day, which calls the Argon2id settings "an equal level of defense" and the scrypt ones "a similar minimal level of defense".
- BE-AUTHN-001 PBKDF2 condition: the Statement allows PBKDF2 "where FIPS compliance is required" but the Verification never checks that condition. (a, recommended) flag PBKDF2 chosen without a stated FIPS requirement; or (b) make PBKDF2 an unconditional option and drop the condition, which would reverse spec.md Resolved Question 6 (PBKDF2 keeps its place as the choice where FIPS compliance is required)? Resolved 2026-10-20 by the owner, option (a): a spec choosing PBKDF2 states the FIPS 140 requirement that makes it the choice, and analyze flags PBKDF2 chosen without one, as it flags bcrypt chosen without saying why Argon2id and scrypt are unavailable. Resolved Question 6 stands. The cheat sheet, checked the same day, says "If FIPS-140 compliance is required, use PBKDF2".
- BE-AUTHN-022 MFA changes: the current password alone can authorize removing or replacing a second factor, while the OWASP Multifactor Authentication Cheat Sheet asks for an existing enrolled factor. (a, recommended) require an existing enrolled factor or passkey for MFA changes, narrowing spec.md Resolved Question 9 ("an already-bound authenticator", which today includes the password) for MFA changes only; or (b) keep the current password as sufficient? Resolved 2026-10-20 by the owner, option (a): replacing or removing an enrolled second factor, or turning MFA off, requires a fresh verification with an enrolled second factor or passkey; the password still authorizes password, email and recovery-contact changes, and enrolling the first factor when none is enrolled. Enrolling another factor beside an enrolled one follows from that qualifier and is covered too, found by 008's review the same day: otherwise the password could enroll an attacker's factor and that factor then remove the owner's, and NIST SP 800-63B-4 §4.1.2.1 requires binding an AAL2 authenticator to take AAL2 authentication. spec.md Resolved Question 9 records the narrowing. The cheat sheet, checked the same day, says "Require reauthentication with an existing enrolled factor before allowing changes" and "Do not rely solely on the active session".
- BE-API-015 vs BE-API-013 on a token in the WebSocket handshake URL: BE-API-013 allows single-use short-lived values that a protocol carries in the URL by design (it names OAuth authorization codes, password-reset and email-verification tokens, and expiring pre-signed URLs, not a WebSocket ticket); BE-API-015's Verification flags any token in the handshake URL, following the OWASP WebSocket Security Cheat Sheet ("Avoid tokens in URL query strings"). (a, recommended) keep BE-API-015 stricter and say explicitly it narrows BE-API-013 for WebSockets; or (b) allow BE-API-013's single-use ticket in the handshake URL? Resolved 2026-10-20 by the owner, option (a): BE-API-015 keeps every token out of the handshake URL, a single-use ticket included, and both rules say it narrows BE-API-013's carve-out for a WebSocket handshake. The cheat sheet, checked the same day, says "Avoid tokens in URL query strings because they can leak into access logs" and "For browser clients using tokens, prefer sending the token in the first message over WSS", and says nothing of handshake tickets.
- BE-API-011 / FE-CSRF-001 fallback when Sec-Fetch-Site is absent: the rules allow rejection or an Origin check; OWASP's fail-open option also lists CSRF tokens or additional validation. (a, recommended) keep the Origin-only fallback (a design using tokens already complies through the token defense); or (b) add tokens and additional validation as fallbacks, extending spec.md Resolved Question 5 (reject, or check `Origin`)? Resolved 2026-10-20 by the owner, option (a): reject-or-`Origin` stays the treatment of a request without `Sec-Fetch-Site`, and each rule now says a design falling back to a CSRF token complies through the token defense; Resolved Question 5 stands. The cheat sheet, checked the same day, offers fail-safe blocking, or a fail-open "fallback to" origin verification, "CSRF tokens, and/or require additional validation" — the last names no mechanism analyze could check.
- SameSite as the sole CSRF defense (BE-API-011, FE-CSRF-001): the rules ban it; OWASP allows SameSite alone in narrow deployments meeting listed conditions, and the BE rationale already calls the ban deliberate. (a, recommended) keep the ban; or (b) allow OWASP's narrow conditions? Resolved 2026-10-20 by the owner, option (a): the ban stays in both rules, and FE-CSRF-001's Rationale now says, as BE-API-011's already did, that it does not adopt the cheat sheet's narrow exception. The cheat sheet, checked the same day, allows `SameSite` alone only when five conditions all hold, the fourth an `Origin` or `Referer` check on state-changing endpoints.
- BE-API-013 vs FE-STORAGE-003 on pre-signed URLs: BE-API-013's carve-out lets "single-use, short-lived values" appear in a URL and names expiring pre-signed URLs among them, and its Rationale says the carve-out covers values "whose single use and short lifetime bound the damage". A pre-signed URL is neither: AWS's S3 guide says "You can use the presigned URL multiple times, up to the expiration date and time", calls presigned URLs "bearer tokens that grant access to those who possess them", and lets the CLI and SDKs set an expiry "as high as 7 days". FE-STORAGE-003 allows a URL token only when the server invalidates it on first use, and does not name pre-signed URLs, so a page that loads an object through a pre-signed `<img src>` passes BE-API-013 and fails FE-STORAGE-003. (a, recommended) give pre-signed URLs their own MAY in both rules, bounded by scope and expiry rather than single use (a pre-signed URL for one object and one method, with an expiry the spec states), and correct BE-API-013's Rationale to match; (b) drop pre-signed URLs from BE-API-013's carve-out, so a spec serving object-storage downloads through pre-signed URLs fails both rules; or (c) leave both rules as they are? (a) is recommended because a pre-signed URL exists to carry its authorization in the URL, so (b) makes the standard object-storage download and upload pattern non-compliant, while a stated scope and expiry bound the exposure the way single use bounds a reset token's. Resolved 2026-10-20 by the owner, option (a): both rules give a pre-signed object-storage URL its own MAY, bounded by scope and expiry — one object and one method, with an expiry the spec states — and flag one with no stated expiry or a wider scope; BE-API-013's Rationale no longer calls it single-use, and both rules cite the Amazon S3 User Guide. AWS's guide, checked the same day, says "You can use the presigned URL multiple times, up to the expiration date and time", calls presigned URLs "bearer tokens that grant access to those who possess them", lets the CLI and SDKs set an expiry "as high as 7 days", and has each URL name one bucket, object key and HTTP method.
- BE-API-013 vs FE-STORAGE-003 on where a single-use token may sit: BE-API-013 lets its single-use values (OAuth authorization codes, password-reset and email-verification tokens) appear anywhere in a URL, while FE-STORAGE-003 allows them only in a query parameter, so a reset link of the form `/reset/{token}` passes BE-API-013 and fails FE-STORAGE-003. Both rules give the same reasons for keeping tokens out of URLs (access logs, browser history, the `Referer` header), and none of them differs between a path segment and a query string; FE-STORAGE-003's conditions, invalidation on first use and `Referrer-Policy: no-referrer` on the landing page, bound the exposure in either position. (a, recommended) allow the single-use carve-out in any URL position in both rules, keeping FE-STORAGE-003's two conditions; or (b) allow it in a query parameter only in both rules, so a path-segment reset token fails BE-API-013 too? Resolved 2026-10-20 by the owner, option (a): both rules allow the single-use carve-out in a query parameter or a path segment, and FE-STORAGE-003 keeps its two conditions, first-use invalidation and `Referrer-Policy: no-referrer` on the landing page, which bound the exposure in either position.
- BE-AUTHN-022 and a lost second factor: since the 2026-10-20 narrowing, every multi-factor change on an account with a second factor enrolled needs a fresh verification with an enrolled second factor or passkey, and the rule's one exception is a password reset through `BE-AUTHN-018`'s recovery flow. A user who has lost their only second factor therefore has no compliant way to replace it, and analyze flags any spec's factor-reset flow as a MUST violation. The OWASP Multifactor Authentication Cheat Sheet separates changing a factor ("Require reauthentication with an existing enrolled factor before allowing changes") from resetting one: "there needs to be a mechanism for them to regain access to their account if they can't use their existing MFA; however it is also crucial that this doesn't provide an attacker with a way to bypass MFA", and "Account recovery is just an alternate way to authenticate so it should be no weaker than regular authentication". NIST SP 800-63B-4 §4.2 defines account recovery as recovering "from losing control of the authenticators", after which "the subscriber can bind one or more new authenticators"; at AAL2 it requires "Two recovery codes obtained using different methods from the set (i.e., saved, issued, and recovery contacts)", or "One recovery code from the set … plus authentication with a single-factor authenticator that is bound to the subscriber account", or repeated identity proofing, and "account recovery SHALL cause a notification". (a, recommended) add a recovery exception: a user who has lost every enrolled second factor MAY bind a replacement through account recovery meeting that AAL2 bar, with the user notified out of band and `BE-AUTHN-018` governing the recovery codes as tokens; the password alone still never authorizes it. (b) count recovery codes saved at MFA enrollment as an enrolled second factor and add nothing else, so a user who saved none has no self-service path. (c) leave the rule as it is. Measured 2026-10-20: no spec in this repository outside 008 mentions MFA, second factors or recovery codes, so the answer changes only what an adopter's analyze reports. Resolved 2026-10-20 by the owner, option (a): `BE-AUTHN-022` gains a MAY under which a user who has lost every enrolled second factor binds a replacement through account recovery that takes two recovery codes obtained by different methods, one such code together with a single-factor authenticator bound to the account such as the current password, or repeated identity proofing, and notifies the user through a channel independent of the recovery. Each recovery code is generated and stored as `BE-AUTHN-018` requires of its tokens — from a CSPRNG, persisted only as a hash, invalidated once used — and an issued code expires within a bounded window; a saved code does not, since NIST SP 800-63B-4 has saved codes kept offline for future use and sets a maximum validity only for issued codes. The exception covers binding a replacement, not turning MFA off, and the password alone still never replaces a second factor. The Verification flags a lost-factor recovery on the password alone, on one recovery code alone, or without the notification.
- BE-AUTHN-022's saved recovery codes against BE-AUTHN-018: the recovery exception applied for the ninth question has each recovery code generated, hashed and invalidated once used as `BE-AUTHN-018` requires of its tokens, and has only codes issued to a recovery address or sent to a recovery contact expire. That follows NIST SP 800-63B-4 §4.2, which has saved recovery codes "maintained offline (e.g., printed or written down) and stored securely by the subscriber for future use", says "Following the use of a saved recovery code, the CSP SHALL invalidate that recovery code and SHALL issue a new saved recovery code to the subscriber", and sets a maximum validity only for issued codes. The option chosen read "`BE-AUTHN-018` governing the recovery codes as tokens", and `BE-AUTHN-018` still requires an account-recovery flow to "issue a single-use token that expires within a bounded, documented window and is invalidated once used or once a newer token is issued", and on a successful reset to invalidate "any outstanding reset or recovery tokens" — so a spec following the saved-code path fails `BE-AUTHN-018`. (a, recommended) scope `BE-AUTHN-018`'s expiry, newer-token invalidation and reset sweep to the tokens a flow issues on demand, and say a saved recovery code is generated and hashed per its (b), invalidated and replaced once used, and kept across a password reset — matching NIST, and keeping a user's printed codes usable when the phone is lost later; or (b) leave `BE-AUTHN-018` as it is and drop the saved-code exception from `BE-AUTHN-022`, so saved codes expire within a documented window, a newly issued set invalidates the older one, and every password reset invalidates them, leaving a user who reset their password without saved codes until they generate new ones. Measured 2026-10-20: no spec in this repository outside 008 mentions recovery codes, so either answer changes only what an adopter's analyze reports. Resolved 2026-10-20 by the owner, option (a): `BE-AUTHN-018`'s expiry, newer-token invalidation and reset sweep now reach only the tokens a recovery flow issues. A saved recovery code — given at MFA setup, as the replacement for one used, or at the user's request — is kept by the user for later; it is still generated and stored as (b) requires and is invalidated and replaced once used, and its Verification flags a saved code stored raw, left valid after use, or not replaced. The ninth answer's "`BE-AUTHN-018` governing the recovery codes as tokens" holds for generation, hashing and single use, with expiry left to the codes a flow issues, as NIST SP 800-63B-4 §4.2 sets it.
