# Shared-constitution-references-are-judged

## Context

A project may register a shared constitution under `.ductus/config.toml` `[constitutions.<name>]` (path `../shared/constitution.md`), and its specs cite that document's sections in the qualified form, path and anchor on one line: ``(`../shared/constitution.md` §rule-with-three-parts)``. `/{project}:analyze` step 4 runs `resolve-anchor` with `markers-path` set to the framework constitution alone. Two adopter reports, verified 2026-10-26 at HEAD c0952038 with the 0.59.11 binary:

- **Markers matching by basename.** The markers file is recognized by substring on any path token containing its basename, so `../shared/constitution.md`, `team-constitution.md` and `constitution.md.bak` all read as the markers file. A shared-constitution anchor cited after such a path — a backticked `constitution.md`, a `../<owning-repo>/constitution.md` path, an in-tree registered path, a markdown link — comes back `kind: markers`, `resolved: false`. A test landed in 2be18da6 (`a_line_citing_a_nested_markers_file_by_a_relative_path_is_not_qualified`, mutation M31 in `scripts/mutation/owner-reviews-067.py`) locks in that matching.
- **An inconsistent split by anchor.** In one file, same form: `§two-part` → `qualified`, `resolved: true`; `§rule-with-three-parts` → `markers`, `resolved: false`; a second file's `§word-word-word` anchors the same. The reporter guessed anchor hyphen count (five data points); the basename matching above may be the cause instead. With `markers-path` set to the shared constitution, every one resolves.
- **Qualified means unread.** A missing anchor cited after any other document — existing, missing, or outside the tree — comes back `qualified`, `resolved: true`, because `resolve-anchor` never reads the named document. The primitive counts these (`qualified`), but step 4 reads only `unresolved` and records no unexamined reason, so at `/{project}:analyze` an unchecked reference is indistinguishable from a checked one. A non-markdown document comes back unresolved, a false alarm. A whole path-and-section citation inside one code span is not scanned. A registered constitution that cannot be read is already unexamined (`constitution-unresolved`, 055 AC8).
- **Consequences.** Each such cite yields an advisory `anchor-resolution` finding, discarded as a false positive, one per citing spec. The stored discard is keyed by family and message text, so after the cited section was renamed the real break matched the stored discard. Authors were told to put path and section in one code span so ductus skips them, which hides every rename.

## Behavior

- Whether a reference is qualified does not depend on its anchor's shape: two references in the same form on the same kind of line classify the same way.
- The markers file is recognized by its resolved path, not by a basename substring, so a registered shared constitution, or any other file sharing the basename, is not the markers file.
- A qualified reference that names a registered `[constitutions.*]` document is judged against that document's markers, so a missing anchor there is unresolved and a present one resolves.
- A reference on a line naming another document is judged: it resolves when the text after `§` begins with a heading of a readable document its line names, a heading of the citing file, or a marker in the markers file, and one that matches none is an advisory `anchor-resolution` finding. An explicit `**§X** in` pair keeps 071's stricter rule. A code span whose whole content is a path followed by one `§` reference is a reference on that path, judged the same way; any other span holds no reference.
- What cannot be judged is recorded, never dropped: a reference whose line names only documents absent from the tree is unexamined, excluded by construction, as is one matching nothing on a line that names a file that is not markdown, which holds no section the check can read; one naming a document that exists but cannot be read, or a skipped registered entry, is unexamined as could not be read. So a `/{project}:analyze` run's record distinguishes "every cited section exists" from "these citations were not examined".
- `resolve-anchor` reads the registry itself, so step 4, its scope line and the installed-command anchor check judge references into registered documents with no argument of their own, and their prose says so.

## Edge Cases

- Minimal fixture: a shared constitution with markers `§a-b` and `§a-b-c`, and one spec citing both in the qualified form. The test asserting both classify alike is proven to fail against the current resolver before the fix.
- `resolve-constitutions` returns a `..` sibling path, which `resolve-anchor` refuses today (`parent-directory component ('..') not permitted`).
- A registered constitution that cannot be read: the run records `constitution-unresolved`, as 055 AC8 has it, and each reference naming it is unexamined as could not be read.
- A stored waiver of an `anchor-resolution` finding whose section was since renamed: falls away once registered documents are judged; what remains is 058's decision matching, with 063's primitive-decided `decision-key` as precedent.
- The constitution's Cross-document references bullet says nothing about shared constitutions or unchecked qualified references, and still says "longest-first", which AC2 says never decided a match.
- A code span holding a path and two `§` references, a markdown link, or any word besides the path and the reference: not a citation, ignored like any other span.
- A span citation whose path names a document absent from the tree: unexamined, excluded by construction, as on a line.
- A line or span naming a registered document by its registered path and also naming an in-tree document: each reference is judged against every readable document named, so it resolves when any of them carries the cited section.
- Repeat runs over unchanged inputs are byte-identical: each occurrence is one reference, judged once.
- A line naming a markdown document and a script: the reference resolves by the document's headings or a marker, and one matching neither is unexamined rather than a finding, since it may be meant for the script.
- The references the wider judgment flags today, measured at 78897161: 42 in `spec.md` files, the subject of analyze step 4, and 12 under `framework/`, the subject of Family 39, plus 90 in plans and scenarios that neither reads. Their cleanup, and the disposal of the 7 in criteria of `done` specs, is decided on this scenario's task.

## Resolved Questions

- **Is the registration the loading policy the same way the Shared Files manifest is, and does the 2be18da6 basename-matching test (and mutation M31) change with it?** Yes: `resolve-anchor` reads the `[constitutions.*]` registry itself, through `resolve-constitutions`' loader, as it reads the manifest itself, and judges a reference on a line naming a loaded document against that document's markers; a reference naming a skipped entry is not judged, and the next question records it (owner, 2026-11-11, option (a)). The registry answers the three objections `anchor-reference-kinds` raised, as the manifest did for 071: which documents load (`loaded`), the error surface (`skipped`, already recorded as `constitution-unresolved`, 055 AC8), and the root (each entry's `constitution.md`). Reading a path committed config names outside the tree is the config-sourced path boundary stated on `validate_no_traversal` in `runtime/src/primitives/mod.rs`, which `resolve-constitutions` and `resolve-references` already rely on; a host-supplied argument was rejected because a primitive may not open a caller-supplied path outside the project, and the exec walk would supply none. The test keeps its assertions, since its `../constitution.md` resolves to the markers path; M31 is re-anchored, because the basename lookup it mutates in `markers_identifiers` goes, and a new test pins that a lookalike name (`team-constitution.md`, `constitution.md.bak`, `../shared/constitution.md`) is not the markers file.
- **How does `/{project}:analyze` surface qualified references it did not check, and does an unreadable named document stay `qualified` or become unexamined?** By checking them: each is judged against the readable documents its line names, the citing file's headings and the markers, one matching none is an advisory finding, and only what cannot be judged is recorded unexamined — excluded by construction when its documents are absent from the tree, could not be read when one exists unreadable or is a skipped registered entry, so `a_mapped_source_that_cannot_be_read_stays_qualified` is rewritten to assert the latter (owner, 2026-11-11, option (j) with (y), applied by the owner's "continue with your recommendation"). Measured at 78897161 with an approximation of the primitive's rules (ATX headings outside fences and comments, a prefix match ending where a word ends, the constitution's markers as fallback): of 341 qualified references in `spec.md` files, the subject analyze step 4 reads, 284 resolve (162 constitution markers, 122 headings), 42 match none and 15 name only documents not in this tree; over every spec, plan and scenario file 646 of 843 resolve and 132 match none; under `framework/`, which Family 39 checks, 171 of 200 resolve and 12 match none. A sample of 7 that matched none were all correct references the rule cannot attribute (a section of a document the line does not name, a shortened heading, a bold label), so the cleanup rewrites each as an explicit `**§X** in` pair or names its document; 7 of the 42 sit in criteria of 5 `done` specs (010, 014, 024, 055, 064), and their disposal is decided on this scenario's task. Recording every qualified reference unexamined was rejected because only checking catches a renamed section, the failure this scenario's Context records; recording an unmatched one unexamined, because a reference checked and found broken would read as not checked. This reverses both resolved questions of `anchor-reference-kinds` for every readable document, beyond the shipped and registered ones. The owner confirmed (2026-11-11) that a reference naming a skipped registered entry is could not be read rather than excluded by construction: the config declares the document, so its absence is a gap in what the run saw.
- **What does a reference get when its line names a file that is not markdown?** That file is a document with no section the check can read: the reference still resolves by a marker or a heading, and one matching none is unexamined, excluded by construction, never a finding (owner, 2026-11-11, option (a)). Reproduced with the 0.59.11 binary: `` `.ductus/config.toml` `` before `§constitutions`, a backticked `runtime/src/main.rs` before `§Usage`, and a link to `config.toml` before `§artifacts` each came back `kind: markers`, `resolved: false`, because only a `.md` name counts as a document, so each was judged against the constitution. Measured over this corpus's spec, plan, scenario and `framework/` files: none sits where analyze step 4 or Family 39 reads, and 6 sit in plans and scenarios, each a markdown section cited on a line that also names a script, which become unexamined. Keeping the finding was rejected because an unmatched reference beside a document the check cannot read cannot honestly be called broken, the reading decided for absent and unreadable documents above; the cost is that a broken constitution reference sharing a line with a script reads as not examined.
- **Is a path-and-section citation inside one code span brought into scope by extending 071's checked form or a backticked path outside the span, rather than by scanning code spans?** By scanning: a code span whose whole content is a path followed by one `§` reference is judged like a reference on a line naming that path, and every other span stays ignored, so `an_anchor_inside_a_code_span_is_not_a_reference` still holds (owner, 2026-11-11, option (c)). After the first two questions the out-of-span form, `` `../shared/constitution.md` §rule ``, is already judged, and extending the pair form to registered documents adds no detection: a constitution's sections are markers, matched by the exact anchor token, so the pair's protection against a heading prefix does not apply. Leaving spans unscanned would keep every citation authors already wrote in a span outside every check until someone rewrote it. Measured over `specs/`, `framework/` and `docs/`, outside fenced blocks and audit records: 314 code spans hold a `§` — 243 a bare reference, 70 other content, and 1 a path and a section, a markdown link inside an example in `anchor-reference-kinds`, which the whole-content grammar excludes — so the scan adds no candidate here. An adopter span illustrating that exact form would be flagged; adopters' trees are out of reach, so that count is unmeasured.
