# 081 — Reviews and checks follow what changed

`/{project}:review` is responsible for code and `/{project}:analyze` for the project's artifacts. A reopening whose own work changed only artifacts owes an analysis and no review. A change confined to artifacts owes the artifact checks, and no build, automated test, code lint or code CI.

## Motivation

Specs reached `done` slowly because reviews and checks were owed for changes outside what the work in hand had touched.

- **Reviews owed for no code.** Measured at `6158d7df` on 2026-11-11 with `compute-review-scope` and `check-review-gate`, run from a release build of that tree: all 12 `in-progress` specs waiting only on the completion gate were blocked on a review. Ten of them (002, 010, 014, 023, 024, 036, 038, 045, 051, 058) had no commit of their own touching a path outside `specs/`. Here a commit is the spec's own when its subject's scope names the spec first. The other two, 026 and 029, had one each (`e08ea5b7`, `6cd79d85`). None of the 12 review records held a gating count or an open finding, and each had a `dispositions:` map. Three mechanisms put the reviews there:
  - **The spec's own scenario or data-model edit made its review stale.** This was the first failure for nine of the 12. One was 038's one-line edit to a scenario, adding a path to a `§` reference. The rule was [079](../079-review-and-analysis-work-converges/spec.md)'s Resolved Question of 2026-11-04: a scenario's text is the requirement, so a change to it with no code change was when the code might no longer meet it.
  - **A sweep commit touching the spec's directory brought in the commit's code wherever the spec's plan listed it.** This was the only blocker for 010, 024 and 058: 067 task 19's commit `8651d466` edited `framework/constitution.md` and `framework/commands/analyze.md`.
  - **A commit naming no spec put its code in every open spec's review.** Examples were `0afc0c00` (`framework(bootstrap)`) and `9a268a5f` (`docs(agents)`).
- **Runtime builds on spec-only pushes.** At `6158d7df`, `.github/workflows/runtime.yml` (`cargo test`, clippy, fmt, audit) was already path-filtered and did not run for a change confined to `specs/`. Two other workflows did, and each compiled the runtime: the artifact checks they ran are run by the runtime. `.github/workflows/framework-checks.yml` had no path filter. `.github/workflows/generators.yml` filtered by path only on pull requests. Both cached `runtime/target` under a key of `Cargo.lock` alone, so the crate recompiled whenever its sources had moved since the cached build. On `1cc1dd52`, a push touching only `specs/067-analyze-and-audit-checks/`, `Build the runtime` took 119 s of the generators job's 179 s and 157 s of the framework-checks job's 261 s, read from `gh run view --json jobs` for runs 43093226259 and 43093226302. `AGENTS.md` then had each run read before `done` or a tag. At that commit no Rust test read the checkout's artifacts. That was checked by reading every path a test under `runtime/` resolved from `CARGO_MANIFEST_DIR`: `runtime/tests/result_sizes.rs` builds its own corpus (`runtime/tests/common/corpus.rs`), and the rest read `framework/` or fixtures.
- **An adopter's report.** It covered a backend spec spanning three repositories, analyzed against eight rule files holding 141 rules. Closing the spec took three analyze rounds, two reviews, two follow-up tasks and about ten commits after its code was complete. The report named these problems:
  - Analyze's rule assessment surfaced new findings on each run against unchanged spec text: 10, then 8, then 4. Only findings were stored, so every run re-judged every rule. On the interactive path no primitive listed the rules, and nothing counted the rules a host left unjudged.
  - A comment-only edit to `data-model.md` forced a full review, which in turn staled the analysis.
  - The criterion-path and body-path families examined `done` specs only, so the gate's analysis was taken after flipping the spec to `done` and back. That was fixed on `main` in `63527403` and was not yet released.
  - A review rewriting `review.md` staled the analysis, since `review.md` is one of an analysis's subjects.

  The report matched `ductus-v0.59.11` (2026-10-17): its constitution still prescribed the flip, and it lacked `review-owed`. `6158d7df` was 1,083 commits past that tag (`git rev-list --count ductus-v0.59.11..6158d7df`).

## Behavior

- **The project's artifacts** are the spec root that `[paths] specs-root` names, `.ductus/`, `AGENTS.md` and `CLAUDE.md`, as paths relative to the project root. Every other path is code.
- **A review is owed for code.** A reopening whose own work changed only artifacts, a spec's scenarios and data model included, owes an analysis and no review. A review is still owed while the spec's record holds something only a review clears.
- **A spec reviews its own commits' code.** A commit whose subject names a spec has its code reviewed by the specs it names. A spec that claims it only because it touched that spec's directory reviews that directory's files and nothing else. A commit whose subject names no spec is attributed as 079 attributes it, except that one touching no spec directory claims no spec: its code leaves every open spec's scope, is listed in `excluded`, and is reviewed under the project record, `{specs-root}/review.md` (spec 084, AC6). A path a spec does not review is listed in its `excluded`.
- **The checks follow the change.** A change confined to the project's artifacts owes the artifact checks, and no build, automated test, code lint or code CI. This is the constitution's blast-radius rule made concrete, and it ships to adopters.
- **The adopter gets it.** The changes land in what a `ductus-v<version>` release ships.

> **Signpost:** [066 — Audit Records and the Completion Gate](../066-audit-records-and-the-completion-gate/spec.md)'s scenario `criteria-are-verified-in-review` owes a review while `spec.md` holds an unticked criterion, or a ticked one whose current text the last review did not judge met, whatever the window holds, so a window of artifacts alone can owe one; AC1 and AC8 say so.

## Edge Cases

- **A commit names one spec and edits another's directory.** The named spec reviews its code. The other spec owes an analysis for its own files, and a review only for what else is in its window.
- **A commit naming no spec touches no spec directory.** It leaves every open spec's window, and its code owes the project record's review, not a spec's. In this repository `framework(bootstrap)` commits are an example, and a `docs(agents)` commit touching only `AGENTS.md` owes no review at all.
- **A merge commit.** It still belongs to no spec, and what it changed itself is attributed like any commit naming no spec.
- **Uncommitted work.** Nothing can attribute it, so its code stays in the scope of the spec under review, but for a path another open spec's plan holds (spec 084, AC23), and an uncommitted artifact owes only the analysis.
- **A spec with no review record.** It still owes a review, since nothing has read its code.
- **A record holding a gating count, an open finding, the open fix-round mark, an unwaived round or no `dispositions:` map.** It still owes a review whatever changed, since only a review clears those.
- **A configured spec root, or a project in a repository subdirectory.** The artifact set is read relative to the project root and the configured spec root, as every other path rule is.
- **A runtime-source cache miss in CI.** A spec-only push that finds no runtime built from the same sources compiles one and says so. It does not run `runtime.yml`, which an edit to that data model alone does.

## Resolved Questions

- **Why split from audit-records-and-the-completion-gate:** this spec decides what owes a review, code alone and the specs a commit names, while `066-audit-records-and-the-completion-gate` owns the records, the gate and the primitives that apply that rule, so they share `compute-review-scope`, `check-review-gate`, `write-review` and the review command's files. Folding this spec into 066 would put a pipeline policy beside the record schemas it is enforced by, and 066's scenario `criteria-are-verified-in-review` changes the same rule from 066's side, recorded here in AC1 and AC8 and a signpost.
- **Does a reopening whose own work changed only a spec's scenarios or data model owe a review?** No (owner, 2026-11-11), reversing 079's answer of 2026-11-04. `/{project}:review` is responsible for code and `/{project}:analyze` for the project's artifacts. What this gives up: a requirement changed by hand in a scenario or data model, without a task, is checked against the code by nothing. A requirement added through `/{project}:amend`'s scenario route comes with a task, and that task's code change owes the review.
- **When a commit several specs claim changes code, who owes its review?** The specs its subject names (owner, 2026-11-11). A spec that only claims the commit because it touched its directory reviews only that directory's files, which owe an analysis. This narrows 079's rule of 2026-11-04, under which each claimant's review also held the commit's code that its plan listed. Measured at `6158d7df` over the 12 specs waiting on the gate, with the reversal above applied: today's rule left 10 owing a review and this one leaves 4 (023, 026, 029, 058). No code commit in those windows named two specs, so "first named" and "every spec named" agreed. How these counts were taken was not recorded: `8dd03c22`, which wrote them, states no method. What this gives up: a sibling's edit to a file this spec's plan lists is checked against this spec's contract by nothing, since the sibling's review reads it against the sibling's spec and the rules. When the subject names no spec, the entry below decides.
- **Which review owes the code of a commit whose subject names no spec?** The project record's review, under `{specs-root}/review.md`, owes the code of one that also touches no spec directory, and no spec's review does (spec 084, AC6); a commit touching spec directories is attributed by 079's plan rule. The pipeline prescribes no commit-subject convention (no line of `framework/constitution.md`, `framework/commands/` or `framework/reference/` matches `git grep -i -E 'commit (message|subject)'` or names a `type(NNN):` subject form), so an adopter's code commit usually names no spec, and plans' Affected Files need not be exhaustive (`framework/templates/spec/plan.md`: "implement-time additions surface naturally"), so reviewing it under no record, or only under the specs whose plan lists the path, would leave such code reviewed by nothing and let a spec reach `done` unread. Rejected: no review; only the specs whose plan lists the path; and plan-listed specs first, with every spec as the fallback. Measured from 2026-10-14 to 2026-11-13: 58 commits named no spec and changed code, 7 of them in the last week, with 37 specs open; how they were counted was not recorded, since `89731126`, which wrote them, states no method.
- **Which paths are the project's artifacts?** The spec root that `[paths] specs-root` names, `.ductus/`, `AGENTS.md` and `CLAUDE.md`, at the project root (owner, 2026-11-11). Every other path is code, both for whether a review is owed and for which checks a change owes. The framework fixes the set, so it is the same in every adopter and needs no setting. In this repository `framework/` is the product, so it is code, and `.ductus/reference/` is generated from `framework/reference/` (`scripts/gen-claude-commands.sh`, which the pre-commit hook runs), so it changes only with code. Measured over the commits with files since 2026-11-01 at `6158d7df` (`git log 6158d7df --since=2026-11-01 --name-only`, a commit counted when it lists a file): 664 commits, 425 confined to the spec root and 437 to this set, the 12 more being `AGENTS.md` edits. The figures first recorded here, 666, 427, 439 and 446, each ran 2 higher by a method not stated, the difference of 12 the same. What this gives up: a project's own `docs/` is code here, so it still runs code CI unless the project filters it. Rejected: the spec root alone (425), which made editing the agent files owe a build; and a configurable list of extra paths (444 with `docs/` and `README.md`), which cost a new setting.
- **Does a review that rewrites `review.md` still stale the analysis?** Yes, unchanged (owner, 2026-11-11). `review.md` is documentation, so `/{project}:analyze` checks it after it changes, and the gate already orders a reopening's review ahead of its analysis (`ductus check-review-gate --help`: the review record's checks, then the analyze record's). Measured with `measure-reopenings` over the 49 reopenings closed between 2026-11-01 and `6158d7df`: 8 of 61 analyses re-ran after a later review (029, 030, 032, 064, 071, and 078 three times). That is an upper bound, since those reviews may also have edited other subjects. Rejected: digesting only the record's gating fields, and dropping `review.md` as a subject. Each saved at most those 8; the first cost a field-level digest rule, and the second left analyze's checks of the record describing an older one.
- **Where do per-rule verdicts and a count of unjudged rules on the interactive path go?** The adopter's first problem goes in a spec of its own, 082, drafted from the report alongside this one (owner, 2026-11-11). That keeps this spec to reviews and check selection, so it reaches a release sooner. Rejected: carrying it here, which added a change to the analysis record's schema, `write-analysis`, analyze steps 11 and 12 and the constitution's audit-record table; and a scenario on 060, which widened 060's subject from the exec walker to the interactive path.
- **Why split from review-and-analysis-work-converges:** the owner chose a new spec over a scenario on 079 (2026-11-11). 079's `spec.md` was 87,348 bytes at `6158d7df` (`wc -c`), past the 50,000-byte read size, and 079 reopens either way, since its AC4 annotation names a stale digest as a reason a review is owed.
