# 069 — Accessibility rules (frontend)

`framework/rules/accessibility-frontend.md` is the frontend accessibility rule set: enforceable, citable requirements for browser-rendered UI, derived from WCAG 2.2 Level AA and installed and enforced under the **frontend** surface. This spec is its owning spec. It records the file's scope, standard baseline, category set, severity posture, and enforcement path, and it is where a later accessibility rule lands through the back-edge instead of in a spec of its own ([§rules](../../framework/constitution.md#rules), *When to write a rule*). It backfills the introducing spec the file never had.

## Motivation

`accessibility-frontend.md` shipped in commit `9ccbd0b` (2026-05-17) together with `api-backend.md` and `performance-frontend.md`. That commit bundled the three files into [024-rule-loader](../024-rule-loader/spec.md) and [025-rule-opt-out](../025-rule-opt-out/spec.md), which cover how rule files are selected and opted out of; neither recorded what this file covered. The constitution's §rules *Lifecycle* recorded the gap as a "Recorded exception (backfill)".

Without an owning spec there was no record of the file's scope, which standard it derived from and how strictly, why its six categories were the ones it declared, where its concerns stopped and a sibling rule file's began, or how a rule came to be MUST rather than SHOULD. Two consequences were visible in the file itself. Its header called WCAG 2.2 AA "the de facto baseline for public-facing web applications in regulated jurisdictions" and named four regimes, without saying which WCAG version each referenced. And `FE-KBD-002` required the §2.4.13 Focus Appearance bar at MUST, enforcing a Level AAA criterion as blocking under a Level AA baseline. A new accessibility rule also had nowhere to land: §rules routes a rule for an existing surface to that surface's owning spec, and this surface had none.

A first review in October 2026 grew the file from 13 rules in six categories to 34 in eleven, rewrote the header's baseline paragraph, and moved the §2.4.13 bar to SHOULD. A second review on 2026-10-19 added five MUST rules, bringing the file to 39 rules in the same eleven categories, 35 MUST and 4 SHOULD. It also corrected the header's regime claims from fetched sources, regrounded `FE-ARIA-001` and `FE-SEMHTML-001` after W3C discontinued *Using ARIA*, loosened four rules and tightened one to match the exceptions of the criteria and patterns they cite, and corrected success-criterion titles to WCAG 2.2's exact forms. The owner's decisions from the first review, and the questions the second answered, are under Resolved Questions.

## Standard baseline

The file's header is the canonical statement of the baseline. This section records what it commits to; each claim about an external source below was checked against that source on 2026-10-19.

- **WCAG 2.2 Level AA.** WCAG 2.2 was first published as a W3C Recommendation on 5 October 2023; the current dated version is the W3C Recommendation of 12 December 2024. W3C WAI states that ISO/IEC 40500:2025 is exactly the same as the October 2023 version. Conformance rests on the success criteria, not the techniques, which W3C states are informative.
- **Backward compatibility.** WCAG 2.2 "builds on and is backwards compatible with WCAG 2.1" and removes one success criterion, 4.1.1 Parsing, now marked obsolete. W3C adds that authors required by policy to conform with WCAG 2.0 or 2.1 "may need to continue to test and report 4.1.1", and the header carries that caveat.
- **Regimes.** The header names five regimes that mandate web accessibility (US Section 508, the US Department of Justice's ADA Title II rule, Ontario's AODA, the UK public-sector accessibility regulations through GOV.UK's guidance, and the EU European Accessibility Act) and states, for each, the WCAG version and level it references, or for the EAA, that it names none. The versions range from WCAG 2.0 to 2.2. This spec does not restate them per regime: the header is their statement, and each was checked on 2026-10-19 against the Access Board's ICT standards, ada.gov's summary of the DOJ rule, Ontario's guidance on O. Reg. 191/11, GOV.UK's guidance, and the Directive's text on EUR-Lex respectively.
- **AAA criteria.** A rule adopts a Level AAA criterion only as SHOULD, and says so. On disk, `FE-KBD-005` (§2.4.13 Focus Appearance) and `FE-MOTION-003` (§2.3.3 Animation from Interactions) adopt one each. `FE-POINTER-001` cites §2.5.5 Target Size (Enhanced), labeled Level AAA, as context for its AA §2.5.8 obligation without adopting it.
- **Rules may be stricter than the criterion.** WCAG's techniques are informative, yet several rules fix one technique as the commitment a spec or plan states. `FE-SEMHTML-002` requires a single `<h1>` and no skipped heading levels, which its Rationale states WCAG does not mandate. `FE-KBD-003` requires `Escape` to close a modal, from the WAI-ARIA Authoring Practices Guide's Dialog pattern, where §2.1.2 requires only that focus can leave by keyboard. `FE-A11YFORM-002` requires `aria-describedby` and `aria-invalid`, where §3.3.1 requires that the error be identified and described in text. Meeting this file and conforming to WCAG 2.2 AA therefore differ in both directions: the file is stricter in places, and it does not cite every Level A and AA criterion (see Open Questions).

## Rule set scope

`accessibility-frontend.md` uses the **frontend** surface: the `-frontend.md` suffix and the `FE-` ID prefix. Its categories are disjoint from the other `FE-` namespaces, those of `security-frontend.md` (`XSS`/`CSRF`/`STORAGE`/`AUTHN`/`CSP`/`DEPS`/`PII`) and `performance-frontend.md` (`VITALS`/`BUNDLE`/`IMAGE`/`LOAD`/`FONT`/`MAIN`). The header declares eleven categories. This table records them; where it and the header differ, the header governs (see Rule ID format).

| Category | Abbrev | Concern |
| --- | --- | --- |
| Semantic HTML | `SEMHTML` | native elements for interactive UI; landmarks and heading hierarchy; page language and page titles |
| Keyboard navigation and focus | `KBD` | keyboard operability; visible focus and indicator contrast; modal focus containment and restoration; focus not obscured; focus order and focus after removal; content on hover or focus; character key shortcuts; focus appearance (AAA, SHOULD) |
| ARIA usage | `ARIA` | ARIA fills gaps in native semantics rather than overriding them; accessible names; visible label within the accessible name; live regions for status messages |
| Color and contrast | `CONTRAST` | AA contrast for text and for UI components and graphics; no information by color alone |
| Accessible forms | `A11YFORM` | programmatic labels; error association, identification, and suggestion; `autocomplete` input purpose; authentication without cognitive function tests; no redundant entry; no change of context on focus or input; error prevention for legal, financial, and data submissions |
| Text alternatives and media | `A11YMEDIA` | `alt` text; captions, transcripts, and alternatives for prerecorded media; audio description and live captions for all synchronized media a page presents, embedded and user-contributed media included |
| Pointer input and target size | `POINTER` | 24×24 CSS pixel targets or equivalent spacing; single-pointer alternatives to dragging and path-based gestures; pointer cancellation (completion on the up-event) |
| Reflow, zoom, text spacing, and orientation | `LAYOUT` | reflow at 320 CSS pixels; 200% text resize (captions and images of text excepted); no zoom lock; tolerance of text-spacing overrides; no orientation lock |
| Motion, flashing, and auto-playing media | `MOTION` | pause, stop, or hide for moving and auto-updating content; audio control; three-flash limit; reduced motion (AAA, SHOULD) |
| Time limits | `TIMING` | time limits that can be turned off, adjusted, or warned about and extended |
| Accessibility testing | `A11YTEST` | automated accessibility engine gating each release (MUST) and run on every change (SHOULD); manual keyboard and screen-reader testing (SHOULD) |

### Boundaries (cross-reference, do not duplicate)

- **`autocomplete` tokens** are split by field purpose. `FE-A11YFORM-003` covers inputs that collect information about the user, under WCAG §1.3.5 and its Input Purposes list. Credential, one-time-code, and payment fields belong to `security-frontend.md` `FE-PII-002`, which `FE-A11YFORM-003` names instead of restating.
- **Credential fields in authentication flows.** `FE-A11YFORM-004` requires paste and password-manager autofill on password and one-time-code fields under §3.3.8, and cites in its Source `FE-PII-002`, which sets the `autocomplete` tokens on those fields.
- **Session timeouts** span three rules in two files. `security-backend.md` `BE-AUTHN-005` governs how long a session may live (an idle and an absolute timeout, enforced server-side). `security-frontend.md` `FE-AUTHN-002` governs the UI once a session has expired or been revoked. `FE-TIMING-001` governs the warning and the chance to extend before it expires. W3C's Understanding 2.2.1 treats a time limit added for security as set by the content, exempt only when it is essential, so the idle timeout `BE-AUTHN-005` requires is a limit `FE-TIMING-001` applies to, and so is an absolute lifetime of 20 hours or less that is not essential, as its Rationale records.
- **Performance.** No rule in this file cites a `performance-frontend.md` rule, and none there cites a rule here.

## Severity posture

- A rule grounded in a WCAG **Level A or AA** criterion is **MUST**.
- A rule adopting a **Level AAA** criterion is **SHOULD**, and its text labels the criterion Level AAA.
- A **testing-practice** rule is **SHOULD**, with one exception: the automated check that gates a release (`FE-A11YTEST-001`) is MUST. No MUST or MUST NOT requires continuous integration ([008-security-rules](../008-security-rules/spec.md) data model, *Severity classification*): whether a project runs CI, and what it runs there, is its own business, and a spec or plan cannot show it — so running the check on every change is the SHOULD `FE-A11YTEST-003`.

Checked against the file on disk: of 39 rules, 35 are MUST and 4 are SHOULD, and no Statement mixes tiers. The SHOULD rules are `FE-KBD-005` and `FE-MOTION-003` (AAA) and `FE-A11YTEST-002` and `FE-A11YTEST-003` (testing). Every MUST rule cites at least one Level A or AA criterion, with two exceptions:

- **`FE-ARIA-001`** is MUST and grounds its obligation in no WCAG success criterion. Its basis is W3C's ARIA documents: WAI-ARIA 1.2 §1.4; *ARIA in HTML*, a W3C Recommendation, at §1 (author requirements) and §3.1 and §3.2 (overriding and redundant roles); ACT rule 6cfa84 on `aria-hidden` elements in sequential focus navigation; and the Authoring Practices Guide's Read Me First. The only criterion its Source names is §4.1.2, as that ACT rule's mapping, which bears on its `aria-hidden` check and not on its fill-gaps-don't-override obligation. The first review's basis, the first rule of ARIA use in *Using ARIA*, was dropped in the second because W3C now publishes that document as a Discontinued Draft (24 February 2026). The posture above does not decide its tier (see Open Questions).
- **`FE-A11YTEST-001`** is MUST and cites no success criterion: it is the testing practice the posture names as its exception, holding each release to an automated check.

The posture maps a criterion's level to a tier; it does not bound how specific a commitment within that tier may be. The rules under Standard baseline that fix one technique (`FE-SEMHTML-002`, `FE-KBD-003`, `FE-A11YFORM-002`) carry MUST because every criterion they cite is Level A or AA.

## Enforcement

- **Design-time commitments.** The header declares that these rules verify what a spec or plan must state, not code patterns. `/{project}:analyze` loads every rule file present, regardless of stack or `[rules] surfaces`, and assesses each rule whose Verification trigger fires against the target feature's artifacts, including the code snippets a plan quotes for its affected files, which many of the Verifications name as "affected-files snippets". A rule whose trigger fires on nothing stays silent, so a project without a frontend needs no opt-out.
- **Review selection.** `/{project}:review` selects the file under the **frontend** surface. `discover-rule-files` keeps a `-frontend.md` file when `[rules] surfaces` lists `frontend`, or by stack detection when the key is unset ([024-rule-loader](../024-rule-loader/spec.md), [033-rule-surface-setting](../033-rule-surface-setting/spec.md)). A `[[review.disabled-rule-files]]` entry with its mandatory `reason` excludes it from review alone ([025-rule-opt-out](../025-rule-opt-out/spec.md)). Neither `framework/commands/review.md` nor the file's header says which review pass checks code in scope against these Statements (see Open Questions).
- **Installation.** `/ductus` installs and updates the file at `specs/rules/accessibility-frontend.md` through the `ductus`-owned Shared Files manifest in `framework/bootstrap/ductus.md`, filtered by `[rules] surfaces`. A surfaces list without `frontend` stops installation and updates and leaves an existing copy in place.

## Rule ID format

IDs follow `FE-{CATEGORY}-{NNN}` and are permanent: never renumbered, never reused. The format and the category abbreviations are governed by the file's own header. That is the second source in `framework/commands/analyze.md`'s *Which ID format governs a file*, and the place [§rules](../../framework/constitution.md#rules) names as canonical for a rule file's category abbreviations. `A11YFORM`, `A11YMEDIA`, and `A11YTEST` contain digits, which the generic `[A-Z][A-Z0-9]*` category grammar permits. The rest of the schema (the four required fields, the one-tier Statement, Source verification) is the data model of [008-security-rules](../008-security-rules/spec.md), which the header cites.

This spec deliberately has no `data-model.md`. The first source in that same resolution order is a file's introducing-spec data model, which governs ahead of the header, so a category table in a data model here would become the governing copy and demote the header the constitution names canonical. The category table under Rule set scope is descriptive: when it and the header disagree, the header is right and this spec is amended.

## Open Questions

- Is a subset of Level A and AA deliberate? Seven of WCAG 2.2's 55 Level A and AA success criteria are cited by no rule: 1.3.3 Sensory Characteristics, 1.4.5 Images of Text, 2.4.5 Multiple Ways, 2.5.4 Motion Actuation, 3.2.3 Consistent Navigation, 3.2.4 Consistent Identification, and 3.2.6 Consistent Help. The second review's new rules cite §1.4.13, §2.1.4, §2.5.2, §3.2.1, §3.2.2, and §3.3.4, and `FE-A11YMEDIA-003` now cites §1.2.3, which leaves these seven. The header says the rules derive from WCAG 2.2 AA, not that they cover it. Should the file cite every A or AA criterion a design-time commitment can address, or should the header say that meeting the file is not a WCAG conformance claim?
- Should the severity posture admit a non-WCAG W3C basis for a MUST, or should `FE-ARIA-001` cite the WCAG criterion it serves? It is MUST on the strength of WAI-ARIA 1.2, *ARIA in HTML*, and the Authoring Practices Guide; the only criterion its Source names is §4.1.2, as the mapping of the ACT rule behind its `aria-hidden` check.
- Which `/{project}:review` pass, if any, checks code in scope against these rules' Statements? `security-frontend.md`'s header assigns that to the security pass when review selects it; this file's header says only that `/{project}:analyze` enforces its rules, and none of the five passes in `framework/commands/review.md` names accessibility.

## Resolved Questions

- **Does the file get its own owning spec?** Yes. Decided by the owner 2026-10-19 for `accessibility-frontend.md`, `api-backend.md`, and `performance-frontend.md` alike: each gets its own spec, on the precedent of specs 034, 037, 038, and 039, instead of remaining under the constitution's recorded backfill exception.
- **What is `FE-KBD-002`'s MUST?** The Level AA requirement. Decided 2026-10-19: the rule had required the §2.4.13 Focus Appearance bar (Level AAA) at MUST and was loosened. Its MUST is now visible focus (§2.4.7) and a 3:1 contrast ratio against adjacent colors for an author-styled indicator (§1.4.11; W3C's Understanding 1.4.11 applies that ratio to focus indicators the author styles, and exempts the browser's unmodified default indicator from the ratio but not from being visible). The §2.4.13 bar moved to SHOULD in `FE-KBD-005`.
- **Is `FE-KBD-005` kept?** Yes. Decided 2026-10-19, as the SHOULD home of the §2.4.13 bar.
- **Is the first review's expansion kept?** Yes. Decided 2026-10-19. The first review took the file from 13 rules in six categories to 34 in eleven: five new categories (`POINTER`, `LAYOUT`, `MOTION`, `TIMING`, `A11YTEST`), and new rules in five of the original six categories, every one except `CONTRAST`. The second review's five rules, below, bring it to 39.
- **Is automated accessibility testing MUST or SHOULD?** Both, split. The owner decided 2026-10-19 that a MUST never requires continuous integration, and clarified the same day that the principle bars requiring CI, not requiring a check (008's data model, *Severity classification*). `FE-A11YTEST-001` is MUST: an automated engine checks the rendered UI before each release, and a new violation at or above the project's threshold blocks the release. Running the check on every change is `FE-A11YTEST-003`, SHOULD.
- **Should §1.4.13 Content on Hover or Focus (Level AA) become a rule, and which category owns it?** Yes, under `KBD`. The first review recorded it as a near-miss; the second (2026-10-19) added `FE-KBD-007`, which makes hover- or focus-triggered content dismissible, hoverable, and persistent.
- **Should §3.2.2 On Input (Level A) become a rule?** Yes. The first review recorded it as a near-miss; the second added `FE-A11YFORM-006`, which also covers §3.2.1 On Focus. The same review added `FE-KBD-008` (§2.1.4 Character Key Shortcuts), `FE-A11YFORM-007` (§3.3.4 Error Prevention (Legal, Financial, Data)), and `FE-POINTER-003` (§2.5.2 Pointer Cancellation), each MUST.
- **Should the header say that a project held to WCAG 2.0 or 2.1 may still need to test and report §4.1.1 Parsing?** Yes, and it now does, as WCAG 2.2's introduction says. The second review added the caveat.
- **Are the header's regime claims right?** As of the second review, yes. The first review's header said the regimes reference WCAG 2.0 or 2.1 AA; the second replaced that with the version each regime references as the header attributes it (through GOV.UK's guidance for the UK), each checked on 2026-10-19 against the sources Standard baseline lists. The EAA entry no longer says the Act references WCAG through EN 301 549: the Directive's text mentions no WCAG version and presumes conformity for products and services meeting harmonised standards whose references are published in the Official Journal of the European Union. W3C WAI notes that most organizations address the EAA with EN 301 549, whose 2026 version uses WCAG 2.2. The UK entry rests on GOV.UK's guidance, which says to meet WCAG 2.2 AA, and the AODA entry matches Ontario's guidance on O. Reg. 191/11, which requires WCAG 2.0 Level AA except §1.2.4 and §1.2.5.
- **Do the second review's loosenings weaken the baseline?** No. Each mirrors an exception in the criterion or pattern the rule cites. `FE-KBD-003` lets focus move on close to the element that continues the workflow, as the Authoring Practices Guide's Dialog (Modal) pattern does when the invoking element no longer exists or the dialog's task leads into a next step. `FE-ARIA-001` permits `role="list"` on a list whose markers are styled away, which *ARIA in HTML* §3.2 allows because some user agents otherwise suppress the list's implicit semantics. `FE-LAYOUT-001` excludes captions and images of text from 200% resize, as §1.4.4 does, and flags `user-scalable=no` and a `maximum-scale` below 2, the two expectations of ACT rule b4f0c3. `FE-POINTER-002` exempts dragging the browser determines and the author has not modified, as §2.5.7 does, and counts a keyboard equivalent only where it also offers controls a pointer can click or tap, as W3C's Understanding 2.5.7 says. The same review tightened `FE-POINTER-001`'s inline exception to §2.5.8's wording (a target in a sentence or whose size is otherwise constrained by the line-height of non-target text) and reworded `FE-KBD-004`'s MAY to follow §2.4.11's Note 2 on content the user opened.
- **Should `FE-A11YMEDIA-003` widen to all synchronized media?** Yes. Decided by the owner 2026-10-19. The rule had required audio description only for prerecorded video "the application publishes as its own content" and real-time captions only for live video "that the application publishes", while WCAG 2.2 requires that audio description be provided "for all prerecorded video content in synchronized media" (§1.2.5) and captions "for all live audio content in synchronized media" (§1.2.4). It now covers all synchronized media the application's pages present, whether produced by the application, embedded from another source, or contributed by users: §5.2.2 says conformance "cannot be achieved if part of a web page is excluded", and WCAG 2.2's definition of a web page takes in the other resources rendered together with it, "all embedded images and media" in its first example. The media-alternative-for-text exception is in the text of §1.2.3 but not of §1.2.4 or §1.2.5; it reaches those two through the definition of synchronized media, which excludes a media alternative for text that is clearly labeled as such, and the rule says so. No audio description is needed where the existing audio already provides all of the video information, per Note 3 of the audio description definition. For content outside the author's control, §5.4 offers two options: monitoring and repairing within two business days, after which a determination of conformance can still be made, or a statement of partial conformance, which W3C's Understanding Conformance calls "a statement of non-conformance"; it records the gap and does not exempt the content. The rule's Rationale also records W3C's Understanding 1.2.4, which says that criterion was intended for broadcast of synchronized media and not to require captioning of two-way multimedia calls between individuals regardless of the needs of users, and its Verification triggers the live-caption commitment on media broadcast to viewers. `FE-A11YMEDIA-002` is unchanged: its captions and transcripts already apply to all prerecorded media, and only its human-editing requirement is limited to application-authored content. 034's review of the same day then moved two of these readings into `FE-A11YMEDIA-003`'s Statement as MAY clauses, the two-way-call exclusion and W3C technique G203 for a video showing only a speaker, and gave `FE-A11YMEDIA-002` the media-alternative-for-text exception that §1.2.1 and §1.2.2 carry in their own text.
