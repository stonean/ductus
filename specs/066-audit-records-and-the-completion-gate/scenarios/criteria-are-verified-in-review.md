# Criteria-are-verified-in-review

## Context

`/{project}:implement`'s completion gate is the pipeline's only step that judges code against a spec's acceptance criteria: after `/{project}:review` and `/{project}:analyze` have recorded clean runs, it judges each criterion (`verifyCriteria`) and ticks each that holds (`mark-criterion`). Review loads the criteria, but none of its five passes returns a verdict on one, and it reads only its window, the spec's change since its last review (`compute-review-scope`). Analyze reads no code. A ticked criterion survives a reopen, so nothing re-earns it before the gate.

An adopting project reported the cost on 2026-11-18, confirmed against this repository at `0adf54ba`. On a reopened spec with 24 ticked criteria and every task done, review and analyze passed, and the gate then found three criteria that no longer held, each in code older than the reopen and outside the review window. Fixing the code owed another review, whose record stales the analysis, so the step meant to be a switch sent the spec back through both audits. An untick no longer stales the analysis (`checkbox-state-is-outside-the-analysis-digest`), but a fix still does, and the gate judges every criterion again on each run.

## Behavior

- `/{project}:review` returns a verdict, met or not met, for every acceptance criterion of the spec, wherever its code lies, with its evidence: the path and symbol that implement it and the test that proves it. Code outside the window is read for the verdict and does not join the window.
- A ticked criterion judged not met is a blocking finding, and review unticks it, except on a `done` spec, where it changes only once the owner, or an invocation told to decide, says which side is correct (spec 084; `framework/reference/review.md` §Criteria step): when the code is, the criterion's text is corrected, it stays ticked and is recorded judged met with its new text, and the spec stays `done`; when the criterion is, review unticks it and reopens the spec; with nobody to ask, as under `ductus exec`, neither changes and the record blocks. It clears only when the code is fixed and a review judges it met, or when the criterion is corrected or moved to the spec that owns the work (§implement-phase); a waiver or a deferral releases nothing, so the criterion stays unticked and holds `done`. An unticked criterion judged met is ticked by review.
- The review record states how many criteria were judged and how many met, and each criterion it judged met, by its label and a digest of its text with the tick and label normalized.
- A review is owed while `spec.md` holds an unticked acceptance criterion, or a ticked one the last review did not judge met with its current text, whatever the window holds, and its criteria pass runs even when the scope holds no code. A ticked criterion whose text a mechanical sweep alone changed since that review keeps its verdict, as §drift-prevention reads a sweep as no change; one changed by anything more, or that the committed sweep cannot vouch for, still owes a review (task 32).
- The completion gate makes no semantic judgment. `check-review-gate` blocks `done` on an unticked criterion as it does on an unchecked task, and after a clean review and a clean analysis the transition writes nothing but the spec's status.

## Edge Cases

- A criterion review cannot judge, for want of code, a test or a fetched source, is reported as not judged and counted apart from met. Review never ticks it, and a review stays owed while it is not judged met, ticked or not.
- A fixture spec with a ticked criterion that the code contradicts, in a file outside the window, is caught by review, and the same fixture with the code corrected passes. The check is proven to fail before it is trusted.
- An unticked criterion on an `in-progress` spec whose tasks are all ticked is held by the gate's tick check. Since 079's AC28 a review cannot record while a box in `tasks.md` is open, so no review that ran before the last task can leave one unjudged.
- A tick or untick refused because `spec.md` changed under it (`mark-criterion`'s changed-since-read refusal) leaves the criterion as it was and is reported beside its verdict; a review stays owed while the criterion is unticked or not judged met with its current text.
- A review record written before the record kept each criterion's verdict holds none, so a spec's first reopening after this lands owes a review whatever its window holds.
- A criterion with no `AC{n}:` label is recorded by its digest alone, so its verdict holds while its text does.
- A spec with no criterion never reaches review: `check-artifacts`' spec-integrity family blocks one at `clarified` or later.

## Resolved Questions

- **When a criterion is added to a `done` spec, or unticked by a correction, with no code changed, what judges it?** A review is owed while `spec.md` holds an unticked acceptance criterion, whatever the window holds: `compute-review-scope` reads `review-owed: true` then, so the gate holds `done` ahead of every analyze check until that review's record is committed, and its criteria pass runs even when the scope holds no code (the agent's recommendation, adopted by the operator, 2026-11-18). Today `review-owed` is false when the record holds nothing only a review clears and the scope holds no code (`compute-review-scope`'s description), so such a criterion would have no judge once the gate makes none. A criterion-only reopening then takes one review and one analysis, in that order. The rule contradicts two ticked criteria, which this work annotates: 079's AC4 (such a reopening reaches `done` with no review run of its own) and 081's AC1 and AC8 (a window holding only artifacts reports `review-owed: false` when the record holds nothing only a review clears); each is an artifact-only edit owing one analysis. Rejected: `/{project}:implement` keeping a narrowed `verifyCriteria` for criteria no review judged, which reopens nothing else but leaves the gate a semantic step in exactly this case, where a not-met verdict still sends the spec back.
- **What judges a ticked criterion whose text is rewritten after the review that ticked it?** The review: its record keeps each criterion it judged met, by label with a digest of its text, the tick and label normalized, and `compute-review-scope` reads `review-owed: true` while a ticked criterion's text differs from what the last review judged met, or the record holds no verdict for it (the agent's recommendation, adopted by the operator, 2026-11-18). Without it, a reworded ticked criterion with no code changed owes no review under the answer above, and the gate, which no longer judges, would pass it; `reviewed-digest` covers only `scenarios/*.md` and `data-model.md` (066's Record freshness). Relying on the author to untick a reworded criterion depends on diligence (§design-principles). Rejected: a separate `check-review-gate` check naming `/{project}:review`, which needs the same field and leaves `/{project}:review`'s first step reading `review-owed: false` and stopping.
- **How does a ticked criterion judged not met clear?** Only by a code fix a review then judges met, or by correcting the criterion or moving it to the spec that owns the work; a waiver or a deferral releases nothing (the agent's recommendation, adopted by the operator, 2026-11-18). §implement-phase has a criterion that no longer holds edited, corrected or consolidated away, never left ticked, and the gate's tick check holds `done` while it is unticked, as 079's AC26 does for a `done` spec, so a waiver or deferral would hold the spec short of `done` with no way out. Rejected: keeping "fixed, deferred or waived as any blocking finding is", which contradicts the gate's tick check. On a `done` spec the owner is asked first which side is correct, and only a criterion the code fails to bear out is unticked; one whose code is correct is corrected and stays ticked, so its spec stays `done` (spec 084; the agent's recommendation, adopted by the operator, 2026-11-24).
