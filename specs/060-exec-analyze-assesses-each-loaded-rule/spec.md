# 060 — Exec analyze assesses each loaded rule

A `ductus exec` `/{project}:analyze` assesses each rule in the tier the rule carries and counts each verdict once, and its record names every loaded rule it did not ask the host about.

## Motivation

Steps 11 and 12 of `/{project}:analyze` request a semantic assessment for every loaded MUST-tier and SHOULD-tier rule whose Verification trigger fires against the spec. Interactively the host walks each rule. The exec walker sent one `assessSpecQuality` request per step, although [022](../022-deterministic-runtime/spec.md) defines that extension point as per-rule Verification reads, and `resolve_assessed_rule` (`runtime/src/interpreter/payload.rs:883`) filled it with one rule: the first cited rule whose Verification resolved, else the first rule in the loaded files that carried one. The request's tier came from the step's prose (`severity_from_step_prose`, `runtime/src/interpreter/payload.rs:867`), not from the rule.

Both steps therefore asked about the same rule, once as `must` and once as `should`: the `analyze-basic` golden's `req-1` and `req-2` both carry `CFG-CONST-001`. [058](../058-findings-route-at-discovery/spec.md)'s task 41 made the exec record count the host's verdicts (`AnalyzeTally::record_assessment`, `runtime/src/interpreter/analyze_tally.rs:181`), and 058's fifth review found two consequences:

- One rule's verdict counted twice. An exec run over `analyze-basic`, whose one rule both steps assess, recorded `blocking-findings: 1` and `advisory: 1` for that single rule.
- The other loaded rules went unasked and unrecorded. This repository's 11 rule files held 192 rule sections with a Verification paragraph (counted 2026-09-26). An exec run asked the host about one rule per step, never evaluated which rules' triggers fire, and named none of the rest in `unexamined-by-reason`, so the record read as though steps 11 and 12 had examined every rule. That is the overstatement `QUAL-CLAIM-001` forbids.

058's task 48 had already recorded a request carrying no rule under `rule-assessments-not-checked` rather than counting its verdict. That covered a step with no rule to ask about, not a step with more rules than its one request could carry.

Line references in this Motivation and in the Resolved Questions are to the tree at `33a5c302`, before this spec changed the walker.

## Edge Cases

- **No rule loaded.** When the rule-file directory is absent, cannot be listed, or holds no rule file, steps 11 and 12 send no request and each records one target under `rule-assessments-not-checked`, as before this spec (`runtime/tests/parity.rs:460`). With no rule in the run, "no rule applies" and "nothing was checked" would otherwise render alike.
- **One tier empty while the other is not.** Nothing is recorded for the empty tier: every loaded rule was asked about, so the run examined its whole subject. The `analyze-basic` fixture, one MUST-tier rule once its Statement carries a keyword, is this case at step 12.
- **A rule file that cannot be read.** Its rules cannot be enumerated, so the file is recorded in `unexamined-by-reason` under a could-not-be-read reason rather than dropped from the walk's subject, as the single-rule resolver this spec replaced, `resolve_assessed_rule`, dropped it silently (`runtime/src/interpreter/payload.rs:909` at `33a5c302`).
- **A rule with no Verification, or whose Statement carries no RFC 2119 keyword.** It is not asked about and is recorded unexamined. No rule shipped in this repository is either — the runtime's corpus test `every_shipped_rule_is_assessable` holds every one to it — but an adopter-authored rule file can be.
- **A deprecated rule.** It is asked about like any other: a deprecated rule binds until it is removed (§rules, Lifecycle), and steps 11 and 12 make no exception for one. This repository's rule files carry no deprecated rule.
- **Request order.** Requests go out in a fixed order: rule files in the sorted order `list_rule_files` returns (`runtime/src/primitives/discover_rule_files.rs:151`), rules in heading order within a file, MUST-tier rules at step 11 and SHOULD-tier rules at step 12. Request ids, and so the goldens, are reproducible.
- **A malformed response or an interrupted walk partway through the rules.** A response that fails validation halts the walk with `error: schema-mismatch`, as any extension response does (`Walker::validate_llm_response`, `runtime/src/interpreter/mod.rs:770`). Because `write-analysis` runs at step 20, a halted or interrupted walk writes no record, never a partial one counting only the rules answered so far.

## Acceptance Criteria

- [x] AC1: An exec analyze assesses each rule in the tier the rule itself carries, never in a tier taken from the step alone, so no rule is assessed in both step 11 and step 12
- [x] AC2: Each rule an exec analyze assesses contributes its verdict to the record at most once
- [x] AC3: Every loaded rule an exec analyze did not ask the host about is recorded in `unexamined-by-reason`, under a reason `framework/commands/analyze.md`'s Unexamined targets and 066's data model classify, so the record never reads as though steps 11 and 12 examined a rule they did not
- [x] AC4: An exec run over `analyze-basic` counts `CFG-CONST-001`'s verdict once, and a test with two or more loaded rules shows each one either assessed or recorded unexamined
- [x] AC5: An exec analyze sends one `assessSpecQuality` request for every loaded rule that carries a tier and a Verification, whether or not the rule's trigger fires against the spec, each request carrying that one rule in its `rule` object, beside the basenames of the rule files the run loaded
- [x] AC6: An exec analyze reads a rule's tier from the RFC 2119 keyword in its Statement: MUST or MUST NOT makes it MUST-tier, SHOULD or SHOULD NOT with no MUST makes it SHOULD-tier, and a Statement carrying neither is recorded unexamined rather than assessed
- [x] AC7: A rule file an exec analyze cannot read is recorded in `unexamined-by-reason`, and a walk with no rule loaded records one `rule-assessments-not-checked` target at each of steps 11 and 12
- [x] AC8: `framework/commands/analyze.md` steps 11 and 12 and the `assessSpecQuality` section of `specs/022-deterministic-runtime/data-model.md` state that an exec run leaves trigger evaluation to the host, which answers a rule whose trigger does not fire with `passed: true`
- [x] AC9: 066 records the per-rule exec walk: the `rule-assessments-not-checked` description in `specs/066-audit-records-and-the-completion-gate/data-model.md` counts rules rather than requests, and 022's body or a scenario under it links back to this spec, discharging the `cross-spec-impact:` entry this spec declares on it

## Resolved Questions

- **Does the walker send one request per rule, or one per step?** One per rule. An `assessSpecQuality` step sends one request for each loaded rule it assesses, each carrying that one rule in the request's existing typed shape. This does not change 022's extension-point contract; it is what that contract already says. 022 defines `assessSpecQuality` as `/ductus:analyze`'s "per-rule Verification reads", with a request carrying one `rule` (`specs/022-deterministic-runtime/spec.md:170`, `specs/022-deterministic-runtime/data-model.md:1275`), and defines single-shot as one round trip per invocation as opposed to a multi-turn user-mediated exchange (`specs/022-deterministic-runtime/spec.md:203`), not as one invocation per step. What is new is walker machinery: before this spec every extension step emitted exactly one request (`Walker::handle_extension`, `runtime/src/interpreter/mod.rs:364`), so the walker gains a way to issue one marker step's request once per item of a list. The `analyze-basic` golden does not decide it, since AC4 moves its counts under every option (`runtime/tests/parity.rs:429` asserts two requests and `:436`–`:437` one blocking and one advisory finding). Measured on this repository at `33a5c302` (192 loaded rules, every one carrying a Verification; median tracked `spec.md` 17.5 KB over 58 specs), one request per rule sends up to 192 requests carrying about 3.4 MB of spec text and assesses every rule. One request per step sends 2 and would record 190 rules unexamined on every run. Batching a tier's rules into one request assesses every rule in 2 requests but changes both the request and response schemas and asks one call to judge up to 167 rules, a quality effect nobody has measured. The rejected options are the second and the third.
- **Where does the walker read a rule's tier?** From the RFC 2119 keyword in the rule's Statement block quote, which is where the rule-format data models already put it: "The Statement's RFC 2119 keyword determines the severity `/{project}:analyze` reports" (`specs/008-security-rules/data-model.md:111`–`:120`, restated at `specs/017-derive-dont-ask/data-model.md:75`–`:84`), and `framework/commands/review.md:49` holds review to the same reading. A Statement containing MUST or MUST NOT is MUST-tier and assessed at step 11; otherwise one containing SHOULD or SHOULD NOT is SHOULD-tier and assessed at step 12. A Statement carrying both is MUST-tier, since it states a blocking obligation, and the host can still report a failure of only its SHOULD clause as advisory, because the tally counts a finding in its own severity before the request's (`runtime/src/interpreter/analyze_tally.rs:189`). A Statement carrying neither is not assessed: the rule is recorded in `unexamined-by-reason` under a reason in the could-not-be-read class, never sent with an unspecified tier, whose failure without a finding would count in no tier (`runtime/src/interpreter/analyze_tally.rs:192`). Measured over this repository's 192 rules at `33a5c302`, 151 Statements carry MUST alone, 25 SHOULD alone, 16 both, and none neither, so 167 rules are MUST-tier and 25 SHOULD-tier. The `analyze-basic` fixture's `CFG-CONST-001` Statement and the rule in `an_exec_analyze_records_the_assessments_it_receives` (`runtime/src/interpreter/mod.rs:1397`) carried no keyword, so both gained one; otherwise AC4's single count could not hold. Rejected: a structured tier field in the rule format, a second authored statement of the tier that must be kept in step with the Statement across three data models, 192 rules, and every adopter-authored rule file; and sending no tier for the host to decide, which leaves the tier to the host where AC1 requires the rule's own.
- **Does the exec walker evaluate a rule's Verification trigger, or ask about every loaded rule?** It asks the host about every loaded rule that has a tier, and the host judges whether the trigger fires as part of the assessment. A trigger is prose — `CFG-CONST-001`'s opens "Any spec or plan that introduces a value used by more than one module" (`framework/rules/configuration-cross.md`) — and whether it applies to a spec is semantic judgment, which the runtime may not make: §runtime-boundary principle 2 names per-rule Verification reads among the work that stays out of it. Each request already carries the rule's whole Verification phrase, trigger included, and the response carries only `passed` and `finding` (`specs/022-deterministic-runtime/data-model.md:1275`), so a rule whose trigger does not fire is answered `passed: true` and counts in no tier. That is a true result rather than a gap: the rule was examined and nothing was found. Rejected: a mechanical trigger filter, which needs a structured trigger field in the rule format (three data models, 192 rules, and every adopter-authored rule file), since a keyword heuristic over the prose would skip rules that do apply without recording that it did; and a first pass asking which triggers fire before assessing those, which adds an extension point to 022's closed set to save a number of requests that cannot be computed without measuring how many triggers fire across real specs.

**Why split from deterministic-runtime:** [022](../022-deterministic-runtime/spec.md) is the runtime's protocol contract as a whole; this spec changes one behavior of the exec walker — how steps 11 and 12 assess the loaded rules and count their verdicts. The overlap Family 7 sees, `framework/commands/analyze.md` and 022's `data-model.md`, is where any change to the analyze walker lands, and this spec discharged its impact on 022 through task 6 under its `cross-spec-impact:` declaration. Folding it into 022 would bury one walker change, its acceptance criteria, and its golden fixtures inside the record of the whole runtime. The pair surfaced when the 2026-10-19 rule-file review reopened both specs at once.
