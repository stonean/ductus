# 034 — Backend performance rules

Introduce `framework/rules/performance-backend.md`, the backend counterpart to `performance-frontend.md`: an enforceable rule set covering server-side performance concerns the framework should govern across features. The file follows the canonical rule schema and is installed and enforced under the **backend** surface.

## Motivation

The constitution names **performance** a governance-recognized cross-cutting category (§rules), and when this spec was written the frontend surface already shipped `performance-frontend.md` (Core Web Vitals, bundle size, image/font discipline) while the backend surface had no performance rule set at all — only `security-backend.md` and `api-backend.md`. Backend performance failures that recur across features — N+1 queries, missing indexes, unbounded caches, exhausted connection pools, oversized responses, slow work on the request path — had nowhere to be promoted to the rules tier; each was re-litigated per feature or caught only in production.

This spec closes the asymmetry: a backend performance rule set citable by ID (`BE-{CATEGORY}-{NNN}`) that `/ductus:analyze` checks against specs and plans and `/ductus:review` checks against code.

## Rule set scope

`performance-backend.md` uses the **backend** surface (`-backend.md` suffix, `BE-` ID prefix), with NEW performance categories that stay disjoint from every other `BE-` namespace — the category sets declared in the headers of `security-backend.md`, `api-backend.md`, and the backend rule files added since. The category set (resolved at clarify):

| Category | Abbrev | Concern |
| --- | --- | --- |
| Query efficiency | `QUERY` | N+1 avoidance; indexes for filtered/sorted/joined columns (or primary-key / unique-constraint coverage); bounded reads (a cap, pagination, or bounded-batch iteration by keyset or cursor); batched, chunked bulk writes, with no single unbounded transaction on a live system |
| Caching | `CACHE` | TTLs / invalidation plus an enforced size bound; cache keys (scope-complete); stampede protection (coalescing or early refresh, jittered TTLs); an explicit HTTP `Cache-Control` policy with validators for conditional revalidation |
| Connection pooling | `POOL` | pooled or shared multiplexed connections, with a bounded maximum set by a named constant; bounded acquisition timeout; release on all paths; pool maximum × instance count kept within the backend's connection limit; no transaction or checked-out connection held across a call to another service or other uncontrolled wait |
| Payload budgets | `PAYLOAD` | response size caps (pagination for collections that can exceed a small fixed maximum), field selection (including a field mask or a view enumeration), negotiated compression (with `Vary: Accept-Encoding` and the BREACH carve-out), streaming large bodies |
| Async offloading | `ASYNC` | move slow or unbounded work — including side-effect-only third-party calls — off the synchronous request path; a third-party call the response depends on may stay synchronous, bounded by `BE-TIMEOUT-001` |

### Severity posture

Performance rules default to **SHOULD** (advisory; thresholds are context-dependent). A rule is **MUST** only when its absence is a denial-of-service or resource-exhaustion risk *regardless of scale* — unbounded queries, per-item (N+1) queries, never-expiring or unbounded caches, per-request connections, pools with no maximum size, unbounded pool waits, connections leaked on an error path, unbounded response sizes, request-blocking slow work. Tunable efficiency trade-offs (index choice, bulk-write chunking, HTTP caching policy, pool sizing against backend capacity, field selection, compression, streaming) stay SHOULD, as does keeping a transaction or checked-out connection out of a call to another service (`BE-POOL-005`).

### Boundaries (cross-reference, do not duplicate)

- **Pagination** is already `api-backend.md` §BE-PAGE — `performance-backend.md` cites it, never restates it.
- **Unbounded-input DoS bounds** are `security-backend.md` `BE-INPUT-006` — the perf rules cite it for request-size limits rather than re-deriving them; `BE-PAYLOAD-004` governs only how a within-limit body is handled.
- **Authorization and sensitive-response caching** are `security-backend.md`'s: `BE-AUTHZ-002` / `BE-AUTHZ-005` (tenant isolation) and `BE-AUTHZ-003` (no cross-request permission caching) behind `BE-CACHE-002`, and `BE-API-001` (`no-store`) behind `BE-CACHE-004`, which governs only the responses `BE-API-001` leaves cacheable. Build-emitted frontend assets and the HTML documents that reference them are `performance-frontend.md`'s where that file is also loaded, and `BE-CACHE-004`'s otherwise.
- **Operator-tunable values** (the *configuration* of timeouts, pool sizes, batch sizes) are `configuration-cross.md` `CFG-CONST-*` / `CFG-ENV-*` — perf rules require the value to exist and be bounded; the config rules govern how it is named and validated.
- **Server-side deadlines, downstream-call timeouts, retries, circuit breakers, and bulkheads** are **out of scope** here: they are as much reliability as performance and live in `reliability-backend.md` (spec 039), which the file header names. The one timeout this file owns is connection-pool acquisition (`BE-POOL-002`), which `BE-TIMEOUT-001` defers to. This keeps `performance-backend.md` focused on throughput and latency efficiency.
- **Atomic commit-and-publish** is `concurrency-backend.md` `BE-COORD-003` (spec 038): a database commit that also publishes an event or writes a second datastore goes through a transactional outbox or equivalent. `BE-POOL-005` moves a call to another service out of the transaction and cites that outbox when the call must stay consistent with the commit; it owns only the connection and lock occupancy, not the atomicity requirement.
- **Observing offloaded work** is `api-backend.md` `BE-LRO-001` (the status-monitor contract) — `BE-ASYNC-001` requires a way to observe completion and cites it for the shape.
- **Latency objectives (SLOs)** are out of scope — see Resolved Questions.

## Resolved Questions

- **Exact category set and abbreviations.** Resolved: five categories — `QUERY`, `CACHE`, `POOL`, `PAYLOAD`, `ASYNC`. `DEADLINE` (the originally-proposed sixth) is dropped from this set (see next question).
- **Deadlines/timeouts here vs. a future reliability set.** Resolved: **moved out.** Server-side deadlines, downstream-call timeouts, retries, and circuit breakers go in `reliability-backend.md` (a separate Task-9 rule set, since landed by spec 039), not here. `performance-backend.md` stays purely about throughput/latency efficiency; this avoids a perf/reliability scope blur and keeps each set coherent. Connection-pool acquisition is the one timeout kept here (`BE-POOL-002`): it bounds a wait on this service's own pool, not a downstream call, and `BE-TIMEOUT-001` defers to it.
- **Do latency objectives (SLOs) belong in this rule set?** Resolved (owner decision, 2026-10-19): **no — SLOs do not belong in rules.** The 2026-10-19 rule-file review briefly added an `SLO` category to `performance-backend.md`; the owner removed it, so the category set stays five. Latency objectives are operational policy set at the service/ops layer, not a per-feature design commitment `/ductus:analyze` can check against a spec or plan — the reasoning spec 037's Resolved Questions recorded when it deferred SLOs and alerting. Considered and excluded; do not re-propose them.
- **Must every third-party call leave the request path (`BE-ASYNC-001` scope)?** Resolved (owner decision, 2026-10-19): **no.** Slow or unbounded work, and a third-party call made only for its side effects, MUST be offloaded with an asynchronous acknowledgment. A third-party call whose result the response depends on MAY stay synchronous when bounded by a timeout per `BE-TIMEOUT-001` (and, for a failure-prone dependency, a circuit breaker per `BE-BREAKER-001`): offloading it only moves the wait into client polling. As first delivered the rule offloaded all third-party-dependent work; the 2026-10-19 review narrowed it, and the owner kept the narrowing. The acknowledgment is owed when the request's own outcome waits on the job: 034's later 2026-10-19 review found that, read literally, the clause made a signup that offloads its welcome email answer `202` where `BE-STATUS-001` requires `201`, and scoped it so. The decided scope above is unchanged.
- **MUST vs SHOULD default.** Resolved: default **SHOULD**; **MUST** only when absence is a DoS/exhaustion risk regardless of scale (unbounded queries/caches/payloads, per-request connections, unbounded pool waits, request-blocking slow work). Tunable efficiency trade-offs stay SHOULD. Recorded as the **Severity posture** above.
- **Verification style for N+1 / index rules.** Resolved: **design-time commitments** targeting specs/plans (e.g., "any plan that introduces a list-rendering endpoint MUST state its query strategy and the indexes it relies on"), not code-pattern detection — consistent with `/ductus:analyze` auditing artifacts rather than source.
- **Threshold values.** Resolved: **qualitative.** Rules require a budget to *exist and be bounded*; the concrete number is deferred to each project's named constants per `CFG-CONST-003`. No rule hard-codes a numeric threshold.
