- [ ] bug: `check-orphaned-references` is structurally blind to the stale form a migration chain actually produces, and reports clean without saying so. `managed_roots` (runtime/src/primitives/check_orphaned_references.rs) returns only the **current** managed roots — `.ductus/`, `.githooks/`, and the configured spec root — and `managed_paths_in` matches a reference only when it starts with one of them. But the orphan a chain leaves is a reference to the **pre-migration** path, which by definition carries a pre-migration root: after the generators moved root `scripts/` -> `.govern/scripts/` -> `.ductus/scripts/`, the stale reference reads `scripts/gen-spec-deps.sh`, whose `scripts/` prefix is in no root list, so the check cannot see it. The pre-rename `.govern/` prefix is likewise absent. Observed 2026-08-17 during a real adopter bootstrap (048 AC10): the primitive returned clean across the adopter's `CLAUDE.md`, `AGENTS.md`, `README.md` and `.githooks/pre-commit`, while the adopter's `AGENTS.md` carried a stale bare `scripts/gen-spec-deps.sh` path orphaned by that very chain. The operator found it by reading the file; nothing in the pipeline did. The `examined` field is good practice and quantifies which *referrers* were read, but no field declares which *reference forms* were recognized, so a clean result reads as "no orphans" when it means "no orphans among current-root paths" — `QUAL-CLAIM-001` at the level of scope rather than subject. Two candidate fixes, both cheap: include historical managed roots (`.govern/`, and the pre-042 bare `scripts/`) in the match set, since a reference to a path that does not exist is reportable whatever its prefix; and have the result name the prefixes it matched so a caller can see the boundary of the claim. Relates to `027-bootstrap-migration-registry`'s `migration-chain-reference-integrity`.
- [ ] bug: a skipped migration becomes permanently unreachable, because `[migrations].last_applied` is a watermark rather than an applied-set. Observed 2026-08-17 during a real adopter bootstrap (048 AC10) on a pre-042 subject. Six migrations were pending; the run applied five and never processed `workflows-sunset` (its own completion summary lists five and omits it). Its step 4 deletes `workflows/registry.json` at the project root when it exists unpinned, and step 1 exits silently only when **none** of its four targets exist — but the adopter's root `workflows/` held exactly that file (2956 bytes), the active config carried no `[pinned]` section, and the other three targets were absent, so it had work to do. The file survives byte-unchanged with its pre-run mtime. The unrecoverable part is the gate: the bootstrap selects entries whose `introduced_in` is **greater than `last_applied`'s** (`framework/bootstrap/ductus.md:448`), and the config stores only that one watermark string — now `runtime-store-path` (0.28.0). Since `workflows-sunset` is 0.23.0, no future `/ductus` run can ever select it again. The adopter is left with a file the framework intended to remove and no pipeline path to remove it; recovery means deleting it by hand or editing `last_applied` backwards. The general defect is the state model: a watermark cannot represent "entry N was skipped", so any migration missed for any reason — host error, a silent no-op, a batch interrupted partway — is silently and permanently forfeited the moment a later entry lands. An applied-set (or a per-entry record) would make the hole detectable and re-runnable; the watermark makes it invisible and terminal. This is `QUAL-CLAIM-001` in the registry's state: an advancing pointer asserts every earlier entry converged, and nothing verifies that.
- [ ] bug: the crates.io publish does not depend on the SBOM job, so a release can ship its crate with no SBOM attached. In `.github/workflows/runtime-release.yml` the `publish` job declares `needs: [audit, build, release-assets, acquire]` and omits `sbom`, while `sbom` itself only `needs: release-assets`. The two are siblings, so an SBOM failure cannot stop the publish. Observed on `ductus-v0.29.9`, 2026-08-17: the SBOM upload step hit a transient GitHub `HttpError: No server is currently available to service your request` after the SBOM had been generated, the job failed, and the crates.io publish proceeded regardless — the release sat with its ten platform assets and checksums but neither `ductus.cdx.json` nor its sidecar until the failed job was re-run by hand. `BE-DEPS-003` requires every production build artifact to be accompanied by a machine-readable SBOM generated during the build and retained for the artifact's lifetime, so a published crate with no SBOM violates it, and the run's overall conclusion of `failure` was the only signal — nothing tied the missing SBOM to the artifact that shipped without it. This is the same shape `AGENTS.md` §Design Principles already records for this workflow, where `release-assets` needed only `build` so the self-audit gated the crates.io publish while the binaries adopters download shipped regardless: a job whose name implies it gates something that does not depend on it. Fix: add `sbom` to `publish`'s `needs`, so the artifact and its bill of materials ship together or neither does. Worth checking the same question of every other job in that file rather than only this pair — the failure mode is structural, not specific to the SBOM.
