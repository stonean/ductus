- [ ] bug: `workflows-sunset` was recorded as applied while its only applicable target survived untouched. Observed live 2026-08-17 during a real adopter bootstrap (048 AC10) on a pre-042 subject. `framework/migrations/workflows-sunset.md` step 4 deletes `workflows/registry.json` at the project root when it exists and is not pinned; step 1 exits silently only when **none** of the four targets exist. On this adopter target 3 did exist — root `workflows/` held exactly one file, `registry.json`, 2956 bytes — the active config carried no `[pinned]` section at all, and the other three targets (the scaffolded `{config_dir}/commands/{project}/workflows/` and `skills/` directories, and a `[workflows]` config section) were absent. So the idempotency check should not have fired and step 4 should have deleted the file and reported `removed (workflow registry): workflows/registry.json`. Instead the file was left byte-unchanged with its pre-run mtime, and `[migrations].last_applied` advanced past `workflows-sunset` (0.23.0) to `constitution-relocate` (0.24.0) and then `criterion-label-backfill` (0.28.0). Nothing errored. This is `QUAL-CLAIM-001` applied to the migration registry: `last_applied` asserts a migration ran, and an adopter cannot distinguish a migration that converged its subject from one that skipped it, because the only record is the pointer that advanced. Worth fixing on two levels — the miss itself, and whether a migration should have to report what it changed (or that it changed nothing, and why) rather than being trusted on the strength of a counter.
