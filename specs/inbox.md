- [ ] `/implement` hard-errors on an uncommitted spec directory instead of returning a domain outcome: `derive-boundary` computes the write boundary by diffing against the spec dir's *first commit*, so on a spec whose directory is untracked it fails with `no commits found that touch specs/{feature}` — an operational error that halts the walk at step 2, before any task runs. Nothing upstream catches it: `/specify`, `/clarify`, and `/plan` all complete and advance status on an uncommitted spec dir, so the pipeline reaches `planned` and only then discovers it cannot start. Observed 2026-07-30 on `046-scenario-open-question-visibility`, freshly created and planned in one session with no commits. Two candidate fixes, not exclusive: (a) make `derive-boundary` return an empty-boundary domain outcome with guidance ("commit the spec directory, or seed a write-boundary in the session") rather than erroring, matching how the rest of the runtime treats provable-vs-unknowable states; (b) have `/plan`'s validation gate check that the spec directory is committed before advancing `clarified → planned`, so the gap surfaces at the gate that creates it rather than one command later. Per §design-principles "never depend on human diligence", (b) is the closer fit; (a) makes the failure legible either way. Note the fail-closed rule is correct and not the defect — the defect is that the precondition is discovered late and reported as a crash rather than as a next-step.
- [ ] Spec 046's `done` gate does not model a **deferred-by-design** scenario question, so it will call a correctly-`done` spec incomplete. 046's rule is binary: a spec MUST NOT be `done` while any scenario carries an unresolved open question. That fits the case it was written from (svc-zmc-api 033 — a wire-contract decision that genuinely blocked implementation), but not the case found in this repo on 2026-07-30 by 046's own first working surface: `026-framework-self-audit` is `done` and carries three scenario questions (`audit-ci-hard-gate` ×1, `family-10-migration-coverage` ×2) that are **waiting on conditions, not on decisions** — each states its own answer and its trigger ("Default: one PR after all three clear … resolve by inspection when the third family closes"; "Defer until …"; "once that's committed, Family 10's CHANGELOG parser can be implemented against a real example"). The shipped work is complete; these are future refinements. Note this is NOT an argument for the grandfather exemption 046 deliberately omits — grandfathering would hide genuinely-blocking questions too, and these three are arguably just misfiled (a question resolved as "deferred until X" belongs in `## Resolved Questions` with its trigger recorded, or in the inbox as future work). Two candidate directions: (a) treat it as an authoring convention — document that a deferred question is resolved-with-a-condition, not open, and sweep existing ones; (b) give the gate a way to distinguish blocking from deferred (a marker, or a `## Deferred Questions` section), which is more machinery and more room to hide real blockers in. (a) is the smaller change and keeps one meaning for "open". Decide before 046 reaches `done`, since its edge-case list currently promises no exemption and task 4 will revert 026 on the strength of that.
