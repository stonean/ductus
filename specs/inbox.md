- [ ] `mark-task`'s checkbox-form done-when reconciliation is tick-only, never untick — decide whether that asymmetry should stand. Scenario `unchecked-done-when-clause-tally` (022, task 71, landed 2026-07-31) specifies only the completion direction: once every real subtask of a task is checked, an unchecked `- [ ] Done when: …` clause ticks with it. The inverse is unimplemented, so *unchecking* a subtask on a previously-complete task leaves the clause ticked — a ticked clause sitting above an unchecked subtask, the mirror image of the incoherence the scenario exists to remove. Deliberate at implementation time (the scenario named one direction, and inventing the other would have been unspecified behavior), and low-impact today because the `/gov:implement` walk only ever marks *checked* — unchecking is a manual edit. Two candidate resolutions: (a) make it symmetric — the clause tracks "every real subtask checked" in both directions, which is the coherent reading of the scenario's own purpose ("the file a human reads agrees with the tally a machine computes"); (b) leave it tick-only and say so explicitly in the scenario's Edge Cases, framing the clause as a completion marker rather than a live mirror. Prefer (a) unless the surprise-diff cost of rewriting a line the user just hand-edited is judged worse than the incoherence.
- [ ] **Generators assert "in sync" for specs they never examined.** `gen-spec-deps.sh` line 181 prints `No changes (all specs in sync)` whenever its rewrite count is zero — but zero means "I rewrote nothing", not "everything is in sync". Untracked specs are never examined, so the message makes a positive claim about files the generator cannot vouch for. `gen-cross-service-refs.sh` has the **same defect** — it enumerates through the same `list_specs()` and prints "all references in sync". `gen-help-tables.sh` ("help.md in sync") and `gen-configure-mcp.sh` ("mcp-allow blocks in sync") share the *message shape* but do **not** use `list_specs()`; they regenerate from fixed sources, so whether their zero-count can ever mean "did not examine" is unassessed — check before assuming a uniform fix applies to all four. **Adopter report (2026-08-01, external project):** running `gen-spec-deps.sh` manually right after `/gov:specify` printed "No changes (all specs in sync)" while `dependencies` stayed `[]`; after `git add`, the same run correctly derived `[001-server-foundation, 002-authentication, 004-notes-api]`. The reporter's mechanism diagnosis is exact — `list_specs()` in `.govern/scripts/lib/specs-root.sh` enumerates via `git ls-files`, which only sees tracked files. **Correction to that report's verdict:** the exclusion is NOT a bug and must not be reverted. It is specified behavior — spec 017's `tracked-specs-not-worktree` scenario — and it exists because the original worktree-glob implementation would rewrite an untracked draft's frontmatter on any unrelated commit, force-`git add` it into that commit, and (with a circular link in a half-written draft) fail the cycle check under `set -e` and block the unrelated commit entirely. Skipping untracked drafts is the fix for a worse problem; only the *reporting* is wrong. Fix shape is a counting change, not a behavior change: `No changes (N tracked specs in sync; M untracked spec(s) skipped — git add to include)`, preserving 017's exclusion exactly while dropping the false claim. Practical impact is low (the pre-commit hook stages before running, so committing always resolves it) but the legibility cost is real — the reporter lost time and the tool pointed away from the answer. **Routing:** a scenario under 017-derive-dont-ask (which owns `tracked-specs-not-worktree` and would extend it), or under 022 if the rule is framed as the broader convention "a generator must not assert what it did not examine" across all four scripts. Note this is the same defect class as two runtime bugs fixed 2026-08-01 under QUAL-STUB-001 reasoning — `diff-cross-spec` returning bare empty lists that contractually read as "no cross-spec impact" when the window was unknowable, and `derive-boundary` crashing rather than reporting an underivable boundary — which argues for the shared-root-cause scenario (tools deriving truth from git history without accounting for work not yet in it) rather than a fourth point fix.
