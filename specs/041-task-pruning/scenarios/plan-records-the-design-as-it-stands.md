# Plan-records-the-design-as-it-stands

## Context

This spec classified `tasks.md` as ephemeral and left `plan.md` beside `data-model.md` as "the design record" ([§tasks-phase](../../../framework/constitution.md#tasks-phase)). That settled what a plan *is*. It said nothing about what a plan must not *become*, and that gap has a measured cost.

An adopter spec spanning three repositories grew its `plan.md` to 3,622 lines (308 KB). Counted by section line ranges, the design record — Overview, Technical Decisions, Affected Files, Trade-offs — held the first 1,350 lines. The other 2,272 (63%) accreted after planning, in sections the template does not have: *Implementation notes* (251 lines), *Verification evidence* (about 1,730 lines, 42 per-task entries), and two review-triage sections (about 290 lines). Read entry by entry, the accretion held seven kinds of content, and only two of them were durable:

| Kind | Durable? | Where it belongs |
| --- | --- | --- |
| Test-run evidence — commands, pass counts, mutation proofs, walkthroughs | No — true of one commit | The commit that lands the task |
| A design decision that changed during implementation | Yes | The Technical Decisions entry it changes, edited in place |
| Contributor knowledge — how to run the suites, environment traps | Yes | Routed by population ([§drift-prevention](../../../framework/constitution.md#drift-prevention), *Shared knowledge stays in git*) |
| An out-of-scope finding and the decision on it | The decision only | Where the finding was dispositioned ([§brownfield-inbox](../../../framework/constitution.md#brownfield-inbox), Finding dispositions) |
| A review triage | No | Dispositions in the review record; tasks for the fixes |
| Handoff state — what is owed, in what order, what is left on disk | No | `tasks.md`, then nowhere |
| Release steps | No | A task |

**The size was not the harm; the design record going false was.** Technical Decisions said a start-up check ran before the database connection opened. An *Implementation notes* entry 1,277 lines further down said it ran after, and only the second was true. A requirement found in end-to-end testing — a key rotation must advance each re-encrypted row's update timestamp, or a mirrored cache keeps ciphertext under the retired key — existed only as a task entry about 2,500 lines below the Rotation decision it amends. One other decision *had* been corrected in place, so the practice was known, just not reliable. Meanwhile `/{project}:implement` reads the whole plan at setup (`framework/commands/implement.md`, §Progressive context loading), so every run loaded 308 KB, most of it spent evidence.

The file named its own causes. Its review triage opened with *"`review.md`'s body is regenerated on every run, so the dispositions live here"* — a reading of [§implement-phase](../../../framework/constitution.md#implement-phase)'s *nothing durable goes in a review record's body*, whose "whatever must survive belongs on the artifact it describes, in the spec body" names no home for a triage, which is not durable at all. Its notes section opened with *"Re-read a line before relying on it"*, and its last task entries were instructions to the next session. This repository shows the same shape at a smaller scale: `057-analyze-artifact-and-record-relocation`'s plan carries a *Resuming from here* section describing itself as "the part `tasks.md` cannot hold: the order, the mechanics, and the two things a fresh session would otherwise measure again". Of this repository's 60 plans and 29 more in other adopter corpora, counted by `##` heading, four carry journal-shaped sections: *Implementation notes*, *Resuming from here*, *Post-split measurement*, and *Implementation Status (resume context)*.

Nothing pushes back. `plan.md` sits outside the review digest, so appending to it never stales a review. `/{project}:analyze` checks a plan's factual claims for grounding but not what the plan contains. And the template says what goes in a plan, never what stays out.

## Behavior

**`plan.md` records the design as it currently stands — never the history of how it got there.** Its content is the design record: the approach, the technical decisions with their rationale and rejected alternatives, the affected files, and the trade-offs. When implementation changes a decision, that decision's entry is edited in place to say what is now true, and the plan never gains an entry recording that it changed. Git history is the record of what the plan said when, exactly as it is for a spec body ([§spec-lifecycle](../../../framework/constitution.md#spec-lifecycle)).

**The design record is the plan template's own `##` sections.** Overview, Technical Decisions, Affected Files and Trade-offs are always present; Data Model, Open Questions Resolved and Cross-spec impact are optional, each marked in the template to be omitted when it does not apply. Headings are compared case-insensitively. A `##` section under any other heading is outside the record. The template is the one source for the set: the runtime compiles it from the framework template, as `prune-tasks` compiles the tasks reset body, so an adopter who customizes the template sees their own set only on the markdown-only path — the same bounded divergence AC11 records for `--reset`.

**Only the design record carries a plan's claims.** A section outside it is not something the spec relies on: anything durable found in one is moved into the record, or to its own home, before the section goes (`prune-reduces-the-spec-directory`). That premise is what lets removing such a section be judged from the diff alone — its heading is visibly outside the set, and no claim leaves with it.

**Everything else implementation produces has a named home, and none of them is the plan:**

- **Verification evidence** belongs to the commit that lands the task — its message, or the pull request carrying it. Evidence is a claim about one commit, and the commit is the artifact pinned to it; in a plan it is stale by the next task. The lasting form of a test proven to fail is the test itself.
- **Contributor knowledge** routes by population under [§drift-prevention](../../../framework/constitution.md#drift-prevention)'s *Shared knowledge stays in git*.
- **A finding** is dispositioned in the run that surfaced it, and its decision is stored where [§brownfield-inbox](../../../framework/constitution.md#brownfield-inbox)'s Finding dispositions stores it.
- **A review triage is not a record.** Each finding is dispositioned in the run; a finding still awaiting a decision is recorded as undispositioned and re-detected by the next run; and the fixes a triage plans are tasks. [§implement-phase](../../../framework/constitution.md#implement-phase)'s rule on review bodies says so, so it can no longer be read as sending a triage to the plan.
- **Handoff state** — what is owed, in what order, with what mechanics — belongs to `tasks.md`, as prose in the body of the pending task it concerns. `tasks.md` is ephemeral, which is exactly right for handoff: keep-pending keeps a pending section verbatim and drops a spent one whole, so a note lives as long as the work it describes. Two placement rules follow from how prune segments the file (`data-model.md` §Segmentation). An ordering constraint goes on the task that must wait — *blocked on tasks 18, 19 and 23* — never in the preamble or under a free-standing heading, which are structure that keep-pending always preserves, so a note there would outlive its work until a `--reset`. And a note is prose, never a checkbox line, since a checkbox in it would count toward its task's classification. The shipped tasks template's guidance comment says a task body may carry working notes and states both rules.

**The rule is detected, not remembered** ([§design-principles](../../../framework/constitution.md#design-principles)). Three surfaces carry it, beside the tasks template's handoff sentence above:

- **The constitution.** [§plan-phase](../../../framework/constitution.md#plan-phase) states the rule. [§tasks-phase](../../../framework/constitution.md#tasks-phase) said `/{project}:prune` removes none of what the durable artifacts assert, and that a decision it moves home from a plan section is edited into the design-record entry it amends, which reopens a `done` spec; `050-constitution`'s cut to one read left that to `prune-reduces-the-spec-directory`. [§implement-phase](../../../framework/constitution.md#implement-phase)'s review-body rule gains the triage clause above.
- **The shipped plan template.** It gains Trade-offs and the three optional sections, so it names every section `/{project}:plan` fills, and its guidance comment says what stays out of a plan and where each kind goes instead.
- **`/{project}:analyze`.** Each `plan.md` section outside the design record is reported as an **advisory** finding on a `planned` or later spec. It blocks nothing, and like every finding it is dispositioned: fixed by folding and removing the section (`prune-reduces-the-spec-directory`), or discarded with its reason when the section is deliberately part of that plan's design — which stores the decision, so neither the next analyze nor any prune asks again.

## Edge Cases

- **A section that is design under a name the record does not list** — a *Known limitations*, a *Classification*. The advisory fires, and discarding it with its reason is the answer; the stored decision keeps it quiet. The heading set is a detector, not a verdict, which is why nothing removes a section without a confirmed judgment.
- **A decision reversed during implementation whose old form is cited elsewhere.** Editing the entry in place changes a claim, so [§drift-prevention](../../../framework/constitution.md#drift-prevention)'s prose-claim sweep applies to whatever pointed at the old form.
- **A `done` spec whose plan is corrected.** The correction is a plan edit, which takes no back-edge ([§spec-lifecycle](../../../framework/constitution.md#spec-lifecycle); `a-plan-edit-does-not-reopen-a-done-spec`): the spec stays `done`, and neither its review nor its analysis goes stale.
- **Evidence the project must keep for audit.** The commit or pull request is where it survives beside the change it proves. A plan is the wrong home for an audit trail precisely because it is rewritten whenever the design changes.
- **A journal nested inside a design section** — a `### Task 7 notes` under Technical Decisions. The detector reads `##` sections only, so it does not see this. The rule still applies, and this is the half of it no heading test reaches; the detector's coverage is stated here rather than implied to be complete.
- **A design heading spelled differently** — *Tradeoffs*, *Trade offs*. The comparison ignores case, not punctuation or spacing, so the section is outside the record and the advisory fires. Renaming it to the template's spelling is the fix; nothing is lost either way.
- **A plan with no section outside the record, or no `##` sections at all.** The advisory is silent. A plan missing a required section is not this rule either, and is only partly checked elsewhere: `/{project}:analyze`'s artifact completeness asks only that `plan.md` exist, and its plan consistency that Technical Decisions hold a decision with its rationale and Affected Files list specific paths, so nothing reports a missing Overview or Trade-offs.
- **A handoff note on a task with no checkbox.** Prune never classifies a checkbox-free section as spent, so such a note outlives its work exactly as a preamble note does. A handoff note goes on a task that carries its work as checkboxes.
- **A handoff note that turns out to be durable** — a trap the next contributor will also hit. It is routed by population before its task is checked, because checking the task hands the note to the next prune.

## What this does not do

It does not clean up an existing plan — that is `prune-reduces-the-spec-directory`. It does not change what goes in `data-model.md`, `research.md`, or the review and analysis records. The runtime half of the advisory is `prune-plan`'s preview, which `/{project}:analyze` calls as a step of its own — not a `check-artifacts` family, whose registry lives in `067-analyze-and-audit-checks`'s data model — so this spec owns it, as it owns `prune-tasks`.

## Resolved Questions

- **Which sections are the design record?** The plan template's own `##` headings — option (b) of three, the others being a closed set compiled into the runtime independently of the template (a) and semantic judgment with no heading test (c). Overview, Technical Decisions, Affected Files and Trade-offs are always present; Data Model, Open Questions Resolved and Cross-spec impact are optional and omitted when they do not apply; headings compare case-insensitively; the runtime compiles the set from the framework template. The measurement that decided it, over the 89 plans in Context by `##` heading: all 89 carry Overview, Technical Decisions and Affected Files; 78 carry Trade-offs, which `framework/commands/plan.md` §Create the plan step 2 fills although the template then omitted it, as it omitted the Data Model that step also fills; Open Questions Resolved (21), Cross-spec impact (11, in two casings) and Data Model (10) recur as design content; the rest are one-off headings, split between design and journal. (a) would be a second copy of the plan's structure beside the template, free to drift from it; (c) leaves the runtime nothing deterministic to detect, which is the diligence dependency [§design-principles](../../../framework/constitution.md#design-principles) rejects. (b) makes the template the one source, closes the existing command/template mismatch as a side effect, and keeps the first corpus-wide analyze from flagging the 32 recurring design sections — only one-off headings fire, and a legitimate one costs a single stored discard. Resolved 2026-09-29.
- **Is `tasks.md` the whole handoff home, or does handoff need an artifact of its own?** `tasks.md` — option (a) of three, the others being a separate ephemeral file per spec (b) and a home outside the spec directory (c). `057-analyze-artifact-and-record-relocation`'s plan says `tasks.md` "cannot hold the order, the mechanics", and prune's own segmentation answers it (`data-model.md` §Segmentation): a task section runs to the next heading at or above the task level, so prose in a task's body belongs to that task, and keep-pending keeps a pending section verbatim and drops a spent one whole — a handoff note already gets exactly the lifetime of its work, with nothing new built. The same segmentation sets the two placement rules in Behavior: the preamble and free-standing headings are structure that keep-pending always preserves, so an ordering note placed there would outlive its work, and a checkbox inside a note would change its task's classification. What 057 met was a missing permission in the template, which the tasks template's guidance comment now grants. (b) is a new artifact needing its own lifetime rule, prune support and analyze checks to reproduce what keep-pending gives for free; (c) is invisible to the next contributor, and handoff has to be committed state. Resolved 2026-09-29.
