# A-path-argument-resolves-inside-its-base

## Context

`BE-INPUT-004`, rewritten 2026-10-19, says filesystem operations "MUST resolve the canonical path and verify it falls within the expected base directory before opening the file", and its Verification asks for "path canonicalization followed by a containment check that compares whole path components". The runtime's check is `validate_no_traversal` (`runtime/src/primitives/mod.rs`). It works on the text alone: it refuses an empty, absolute, rooted, drive-prefixed or `..` path, and it does not follow a symlink. A symlink inside the project that points outside it, either tracked in a cloned repository or created locally, therefore passes the check, and the primitive then reads, writes, deletes or runs whatever is on the other side.

Probed 2026-10-20 through the release binary, with a scratch project whose links point to a directory outside it:

- `set-status` on a feature directory that is a symlink to an outside directory rewrote that outside directory's `spec.md`.
- `create-scenario` on a feature whose `scenarios/` is a symlink to an outside directory wrote the new scenario there and reported it as `specs/001-x/scenarios/s.md`.
- `mark-task` on a `tasks.md` that is a symlink to an outside file read the outside file's content. It wrote nothing outside: `write_atomic_bytes` renames a tempfile over the link, so the link was replaced by a regular file inside the project carrying the edited content.
- `merge-managed-block` on a `CLAUDE.md` that is a symlink to `AGENTS.md` in the same project replaced the link the same way, so the block landed in a new, separate `CLAUDE.md` and `AGENTS.md` was left without it. `/ductus` calls `merge-managed-block` on both files (`framework/bootstrap/ductus.md` §Shared constitution imports).
- `std::fs::canonicalize` returns `NotFound` for a path that does not exist yet, and on macOS it maps `/tmp/…` to `/private/tmp/…`.

The 42 production call sites of `validate_no_traversal`, counted 2026-10-20, fall into three groups:

- 32 take a feature argument, a feature name joined to the spec root or a feature path joined to the project root, in `interpreter/mod.rs` and 29 primitives. 16 of those primitives write or delete, by a token count of their write, rename, create and remove calls.
- 7 take a file or directory path that is opened, in 6 primitives: `apply-manifest`'s source and destination, `enforce-manifest`'s cleanup directory, `merge-managed-block`, `merge-permissions`, `migrate-session-file`, and `run-generator`, which passes its script to `bash`. Every one of these primitives writes, deletes or executes. The paths `/ductus` passes them are the **Shared Files** manifest destinations (`.ductus/constitution.md`, `specs/rules/*.md`, `specs/templates/*.md`, `.githooks/*`, each agent's command directory), the per-agent `ductus` install path, `.gitignore`, the active config file, and the native rules files `CLAUDE.md` and `AGENTS.md`.
- 3 record a path in a session file and never open it: `write-session`'s `path` and `scenario-path`, and `retarget-sessions`' loop over the same two. `BE-INPUT-004`'s trigger, a file opened based on input, does not fire on these.

Eight primitives never called `validate_no_traversal`, so the count above missed them, and 022's re-review found them on 2026-10-21 (022 task 9). Until then each took a host- or LLM-supplied path with no check: `validate-frontmatter`, `resolve-anchor`, `check-rule-ids` and `check-promotion-coverage` read files their arguments named, resolved through `resolve_path`, which accepts an absolute path; `lint-markdown` handed its paths to markdownlint-cli2, which rewrites what they match under `fix`, follows a linked directory it meets while expanding a glob, expands a directory to everything under it, and resolves a `:`-prefixed path literally; `resolve-feature` read a spec's status and a scenario's section through the feature directory its identifier matched; and `fetch-archive` and `extract-archive` wrote wherever their staging paths pointed. Every shipped caller passes the first six a project-relative path or a feature name, and the bootstrap passes the two archive primitives its `{tempdir}`, which `mktemp -d -t` makes under `$TMPDIR` or `/tmp` on Linux and, on macOS, in the per-user temp directory whatever `$TMPDIR` says.

The `writeCode` write boundary (`validate_write_code_boundary`, `runtime/src/schema/extensions.rs`) matches each edit path against glob patterns after a lexical screen. The runtime never opens those paths: the host applies the edits. So the boundary is a containment decision the host relies on, not a check before the runtime opens a file.

067 already settled a symlink question for the files `check-artifacts` opens through a sibling link, and settled it without canonicalization (`specs/067-analyze-and-audit-checks/scenarios/sibling-symlink-trust-boundary.md`). Its `traverses_symlink` (`runtime/src/primitives/check_artifacts.rs`) uses `symlink_metadata` to ask whether any component below the base is a link, never where it points. A linked target is skipped as `target-unparseable` and the run continues. The reason it gives is the repeat-run determinism 045's AC8 requires: canonicalization "fails on a legitimately-missing target and makes the answer depend on where a link points". Two more 067 scenarios resolve lexically for the same reason (`link-adjacent-drift-family`, `adopter-corpus-link-integrity`). This repository tracks no symlinks.

## Behavior

- One shared check in `runtime/src/primitives/mod.rs` decides containment, after the existing lexical screen. It canonicalizes the path joined to its base and accepts it only when the result lies inside the canonicalized base, compared by whole components (`Path::starts_with`), never by string prefix. A path that leaves its base through a symlink is refused, and a symlink that stays inside the base is followed and accepted.
- The base is the directory each primitive names: the project root for a feature argument and for a project path, and `apply-manifest`'s `source-root` and `target-root` for its source and destination. A staging directory outside the project is a legitimate `source-root`.
- A refused path is an `InvalidPath` error naming the argument and the link that took it outside. The error comes before the primitive reads, writes, deletes or runs anything.
- After the check passes, the primitive keeps using the path it was given and keeps naming it that way in results and errors.
- The `writeCode` boundary matches each edit path against its globs twice, as given and where the path lands once its symlinks are resolved, and refuses one that lands outside the project or through a link that cannot be resolved, so a boundary of `runtime/**` does not admit `runtime/link/x` when `runtime/link` points into `framework/`. It judges where the edit lands, which is where the host writes, so a path that leaves through one link and returns through another is admitted when it lands inside the boundary.
- The three session-file sites keep the lexical check alone, because they open nothing.
- Every call site that opens a path goes through the check: the 32 that take a feature argument and the 7 that take a file or directory path, and the eight primitives that never called `validate_no_traversal`, below.
- `validate-frontmatter`, `resolve-anchor`, `check-rule-ids` and `check-promotion-coverage` check every path argument against the project root before reading any, refusing an absolute one as the other sites do. `lint-markdown` checks each of its paths the same way, and walks the directory before a glob's first glob character and any directory a path names, `.` among them, because markdownlint-cli2 follows a linked directory it meets and expands a directory to everything under it. It refuses the forms the check does not model: a leading `:` (markdownlint-cli2's literal path), `!` or `#` (its negations), a brace, parenthesis or `|` (brace expansion, extglobs and regex groups, which can spell a `..` or an absolute alternative), and a backslash, which markdownlint-cli2 turns into `/` except before one of `$()*+?[]^`, where it is an escape that Rust on Windows would read as a separator. `resolve-feature` checks the feature its identifier matches, with the walk, before reading its status or a scenario.
- `fetch-archive`'s destination and `extract-archive`'s archive and destination are staging paths. Each must be absolute and lie strictly inside the system temp directory, where `/ductus` makes its `{tempdir}`: the directory the runtime's `std::env::temp_dir()` names, standing for `/tmp` on Unix other than macOS when an empty `$TMPDIR` leaves it empty, or on macOS also the per-user temp directory, where `mktemp -d -t` puts it whatever `$TMPDIR` says. Either is accepted as spelled or in its canonical form, and the rest goes through the check against it, so a link on it that leaves the temp directory is refused. A relative staging path is refused, since `/ductus` never passes one, and so is the temp directory itself, which on Linux is the shared `/tmp`.
- A call that takes a feature argument also lists the feature directory recursively, following a link only when it stays inside the project, and is refused when any link in it resolves outside the project. This covers the files the primitive then opens beneath the directory under fixed names (`spec.md`, `tasks.md`, the `scenarios/` listing).
- `check-artifacts` checks its feature argument but is exempt from the walk, because 067's `sibling-symlink-trust-boundary` has it skip a linked sibling as `target-unparseable` and keep running. It can still read a fixed-name file through a link that leaves the project.

## Edge Cases

- A path that does not exist yet (a new scenario, an `apply-manifest` destination) is judged by canonicalizing its deepest existing ancestor and appending the remaining components, because `canonicalize` fails on a missing path.
- A dangling symlink is judged by where its target would resolve, through the target's deepest existing ancestor. One that would land outside the base is refused. One that would land inside is left to the primitive's existing handling, such as `check-artifact-size` skipping it as `artifact-unreadable`.
- Both the base and the candidate are canonicalized, so a project reached through a symlink (macOS `/tmp` is `/private/tmp`) is accepted, and on Windows both sides take the `\\?\` form.
- An in-project link on a path the runtime writes, such as a `CLAUDE.md` that links to `AGENTS.md`, passes the check. The write then replaces the link with a regular file, as it does today, so the check neither refuses that layout nor preserves it.
- A project in a repository subdirectory (059) is contained by its project root, not by the work tree's root, so a link to a sibling directory in the same repository is refused.
- The resolver follows at most 40 links itself across one resolution, from one budget for the whole of it as the kernel keeps one per lookup; each `canonicalize` it calls stops at the platform's own limit. A path that needs more, a loop or a chain of links that each name the next more than once, is refused as a link that cannot be resolved.
- A symlink created between the check and the open is not caught. The check runs once at the start of each call.
- The walk checks only what it can list. A directory that is traversable but not readable is left to the primitive, so a link inside it is not seen; git carries no directory modes, so only a local change of mode can arrange it.
- A path that climbs out of a missing directory and back onto a link, such as a dangling `missing/../out` where `out` leads outside, is judged where `out` leads, as the kernel resolves it once `missing` exists. One `apply-manifest` call can create that directory with an earlier entry before a later one is written.
- A primitive that walks the corpus without a path argument (`derive-dependencies`, a sibling spec read from frontmatter by `traverse-deps` or `diff-cross-spec`) opens nothing based on input, and this scenario does not change it.
- A corpus walk that reaches one of the checked call sites once per feature is refused as a whole when any feature it reaches fails the check: `prune-plan` and `prune-tasks` with `all`, and `dashboard`, which resolves every spec's references through `resolve-references`. So `/{project}:status` fails, naming the link, in a project where any spec directory is or holds a link that leaves the project.
- `extract-archive` skips symlink entries, so a staging `source-root` holds none.
- On Windows `/ductus` makes `{tempdir}` with Git Bash's `mktemp`, which prints a path such as `/tmp/ductus-XXXXXX` with no drive letter. Handed over MCP, the runtime reads that as a relative path and refuses it, so such a run is likely to halt at the archive fetch, naming the path. Passed to the CLI from Git Bash, as a State B run does, MSYS converts the argument to a Windows path first, which may then lie inside the runtime's temp directory. Neither is measured on Windows; both are read from how the two sides spell a path.

## Resolved Questions

- **Which paths outside the 39 sites go through a check?** Resolved 2026-10-21 by the owner: (a), all eight, the readers, `lint-markdown` and `resolve-feature`'s matched feature against the project root and the two archive primitives against the system temp directory. The question as put, in 022's `tasks.md` task 9, counted them as nine; it named eight: (a) all of them, as resolved; (b) the same for the readers, `lint-markdown` and `resolve-feature`, with the two archive primitives recorded as an exclusion, so a destination an LLM supplies can still write anywhere the operator can; or (c) all of them recorded as an exclusion, the finding waived. Measured that day: a probe refusing an absolute path at those primitives failed 36 tests, 27 of them the readers', and the 9 of `extract-archive` lie under the temp directory. Recommended: (a), with the reason that it leaves a host- or LLM-supplied path only the system temp directory outside the project. That reason initially overstated it: `apply-manifest`'s `source-root` and `target-root` were absolute-capable bases by this scenario's own design, so a `target-root` a caller supplied could still name a directory outside the project. 022 task 17 (the owner's answer (a), 2026-10-24) then bounded both roots by the working directory — `target-root` inside it, `source-root` inside it or strictly inside a staging directory, as `extract-archive` takes its paths — so the reason now holds: a host- or LLM-supplied path reaches outside the project only into the system temp directory.

- **How does the check decide that a path leaves its base?** Resolved 2026-10-20 by the owner: (a), canonicalize and compare. The question as put: Measured 2026-10-20. (a) **Canonicalize and compare.** Canonicalize the joined path and accept it only when it lies inside the canonicalized base, compared by whole components (`Path::starts_with`). For a path that does not exist yet (a new scenario, an `apply-manifest` destination), canonicalize its deepest existing ancestor and append the rest. A dangling link is judged by where its target would resolve. Both sides are canonicalized, so macOS's `/private/tmp` and Windows' `\\?\` forms compare equal. A link that stays inside the base is accepted, so `merge-managed-block` keeps replacing an in-project `CLAUDE.md -> AGENTS.md` link with a separate file, as probed today. The answer depends on where a link points, the property 067 avoided for its check results. It matches `BE-INPUT-004`'s wording, so the plan statement needs no further argument. (b) **Refuse any link.** Move 067's `traverses_symlink` into `mod.rs` and refuse a path when any component below its base is a symlink, wherever it points. No destination is read, so the answer depends only on whether a link is present, which is 067's determinism property. There are no missing-path, dangling-link or platform canonical-form cases. With `..`, absolute and rooted paths already refused and no link below the base, the path as given is its own canonical form under the base. The plan statement has to make that argument, because `BE-INPUT-004` names canonicalization. It also refuses links that stay inside the project: `/ductus` would halt at §Shared constitution imports for a project whose `CLAUDE.md` links to `AGENTS.md`, where today it silently splits the two files. How many adopting projects carry an in-project link on one of the paths above cannot be counted from this repository. Only an adopter report or a survey of adopting projects would settle it. Recommended: (a). It refuses everything (b) refuses that leaves the project and nothing that stays inside, so it adds no new refusal for an adopter layout. The population that would decide against it is the one that cannot be measured here. Its costs are the missing-path and platform cases, and an answer that depends on link destinations, which matters for a containment refusal less than for 067's reported results.
