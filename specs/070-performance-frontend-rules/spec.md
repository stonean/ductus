# 070 — Performance rules (frontend)

The owning spec of `framework/rules/performance-frontend.md`, the enforceable rule set for browser-rendered UI performance: Core Web Vitals budgets and measurement, bundle size, image delivery, resource loading, web fonts, and main-thread work. The file follows the canonical rule schema, identifies its rules as `FE-{CATEGORY}-{NNN}`, and is installed and enforced under the **frontend** surface. It is the frontend counterpart of `performance-backend.md`, which [034-performance-backend-rules](../034-performance-backend-rules/spec.md) introduced. Unlike 034, this spec did not design its file: the file shipped first, so the spec records the file's scope, category set, severity posture, boundaries, and the decisions behind them. In the brownfield sense of [011-brownfield-process](../011-brownfield-process/spec.md), it captures an artifact that already existed.

## Motivation

`performance-frontend.md` landed in commit `9ccbd0b` (2026-05-17), together with `api-backend.md` and `accessibility-frontend.md`. All three were bundled into [024-rule-loader](../024-rule-loader/spec.md) and [025-rule-opt-out](../025-rule-opt-out/spec.md) instead of each getting an introducing spec. The constitution's §rules → Lifecycle required a rule file that ships with `ductus` to be introduced by its own feature spec. It recorded the three as a backfill exception: in active use, ID grammar reconciled, retained as-is.

That left the file with no owning spec. Its category set, its MUST/SHOULD split, and its seams with sibling rule files were recorded nowhere. §rules routed a new rule on an existing surface to that surface's owning spec through the back-edge, so a new frontend performance rule had no spec to land in. The first 2026-10-19 review of the file showed the cost. One MUST, `FE-BUNDLE-001`, required the build to fail when a bundle exceeded its budget, which was a CI behavior that no spec or plan could show. There was also no spec in which to record the decision that replaced it, or the new `MAIN` category the review added. The same day, the owner decided that each of the three backfilled files would get its own spec, following the precedent of 034 and its sibling backend rule specs.

## Rule set scope

`performance-frontend.md` uses the **frontend** surface (`-frontend.md` suffix, `FE-` ID prefix). Its categories are the six its header declares. They are disjoint from the other `FE-` namespaces: `security-frontend.md` (`XSS`/`CSRF`/`STORAGE`/`AUTHN`/`CSP`/`DEPS`/`PII`) and `accessibility-frontend.md` (`SEMHTML`/`KBD`/`ARIA`/`CONTRAST`/`A11YFORM`/`A11YMEDIA`/`POINTER`/`LAYOUT`/`MOTION`/`TIMING`/`A11YTEST`).

| Category | Abbrev | Concern |
| --- | --- | --- |
| Core Web Vitals budgets and measurement | `VITALS` | published LCP/INP/CLS budgets at the 75th percentile, segmented by mobile and desktop; real-user (RUM) measurement, with synthetic runs only complementary |
| JavaScript/CSS bundle size | `BUNDLE` | per-route or per-entry-point JS and CSS budgets published in `specs/system.md`, in transferred bytes; route-level code splitting; an automated budget check |
| Image delivery | `IMAGE` | modern formats (AVIF/WebP); declared intrinsic dimensions; resolution matched to rendered size |
| Resource loading, prioritization, HTTP and back/forward caching, and layout reservation | `LOAD` | lazy-loading non-critical resources but never the initial viewport; a documented critical rendering path with non-blocking scripts; CSP-compatible critical CSS; LCP resource discovery and priority; cache policy for hashed static assets and HTML; reserved space for late content; no `unload` listeners, with page-exit work on `visibilitychange` or `pagehide` so pages stay eligible for the back/forward cache (bfcache) |
| Web font discipline | `FONT` | a `font-display` value that keeps text visible; WOFF2; subsetting |
| Main-thread work | `MAIN` | CPU-heavy work moved to a worker or chunked with yields; a DOM-size bound for unbounded collections |

### Severity posture

The header states only the mapping every rule file shares: **MUST** / **MUST NOT** are errors and **SHOULD** / **SHOULD NOT** are warnings. It states no criterion for when a rule is MUST. `performance-backend.md` and `observability-backend.md` each state one in their headers. After the second review on 2026-10-19, which added `FE-LOAD-009`, the file carries 22 rules, 11 MUST-tier and 11 SHOULD-tier, and no Statement mixes tiers. Whether the file should adopt an explicit posture is open (see Open Questions).

One severity constraint is already settled. Under [008's data-model §Severity classification](../008-security-rules/data-model.md#severity-classification), a MUST never requires continuous integration — neither that a project run CI nor that a check run in it — so the MUST states the outcome, and a recommendation to run a check automatically on every change is a SHOULD of its own. `FE-BUNDLE-001` and `FE-BUNDLE-003` are that pair here (see Resolved Questions).

### Boundaries (cross-reference, do not duplicate)

- **`performance-backend.md`.** `FE-LOAD-007` owns the cache policy for build-emitted static assets (content-hashed URLs with a long-lived `immutable` lifetime) and for the HTML documents that reference them. `BE-CACHE-004` owns the cache policy for other responses to safe requests, and its Rationale defers build-emitted frontend assets to this file. Compressing those assets is `BE-PAYLOAD-003`'s concern, which `FE-LOAD-007` cites instead of carrying a frontend compression rule.
- **`security-frontend.md`.** `FE-LOAD-004` shapes its inline critical CSS and async-CSS mechanism to work under the nonce- or hash-based policy that `FE-CSP-002` requires, and never relaxes that policy: the critical-CSS `<style>` carries the page's nonce or its content matches a hash the policy lists, and no inline `onload` handler is used. HTML that displays sensitive data stays `Cache-Control: no-store` per `FE-PII-003`, which takes precedence over the `no-cache` that `FE-LOAD-007` recommends for HTML. The same precedence holds against `FE-LOAD-009`'s back/forward-cache concern. Its Rationale notes that a page served `no-store` may be ineligible for the bfcache, which `FE-LOAD-007`'s `no-cache` avoids, and it keeps a page displaying sensitive data on `no-store` per `FE-PII-003`. Such a page gives up bfcache restoration, not its `no-store`.
- **`api-backend.md`.** `BE-PAGE` bounds what the server returns for a list. `FE-MAIN-002` bounds what the client keeps in the DOM, and cites `BE-PAGE` for the server side.
- **`accessibility-frontend.md`.** Neither file cites the other, and no rule overlaps. The nearest contact is `FE-A11YMEDIA-001`, which requires `alt` on every `<img>`. It applies to the same elements that `FE-IMAGE-001` through `FE-IMAGE-003` govern for format, dimensions, and resolution, but those are separate attributes. That file's `FE-LAYOUT` covers reflow, zoom, text spacing, and orientation. Reserving layout space against shift (CLS) belongs here, in `FE-IMAGE-002` and `FE-LOAD-008`.

## Enforcement

The rules verify **design-time commitments**, meaning what a spec or plan must state, not code patterns. The file's header says so. `/ductus:analyze` enforces them against feature artifacts. That includes code snippets a plan quotes for its affected files, such as an `<img src="*.jpg">` with no modern-format source, an `@font-face` rule with no `font-display`, or an external classic `<script src>` with no `defer` or `async`. MUST-tier findings are blocking and SHOULD-tier findings are advisory, per 008's severity classification. `/ductus:analyze` loads every rule file present, regardless of stack or `[rules] surfaces`. A rule fires only on a spec or plan that meets its Verification trigger.

`/ductus` installs the file from its Shared Files manifest (`framework/bootstrap/ductus.md`) to `specs/rules/performance-frontend.md` in an adopting project. `/ductus:review` selects it under the **frontend** surface. The `-frontend.md` suffix classifies it (024), and a `[rules] surfaces` list without `frontend` stops both installation updates and review selection ([033-rule-surface-setting](../033-rule-surface-setting/spec.md)). A `[[review.disabled-rule-files]]` entry excludes it from review alone (025). Listing it under `[pinned] files` only stops updates from overwriting a customized copy.

## ID format

Rule IDs follow `FE-{CATEGORY}-{NNN}`. The grammar, the `[A-Z][A-Z0-9]*` category format, and the ID-stability invariants (never renumbered, never reused) are those of [008's data-model](../008-security-rules/data-model.md). `scripts/lint-rule-ids.sh` checks grammar and per-file uniqueness.

The category abbreviations are governed by the file's own header, per the constitution's §rules: "The specific category abbreviations a given rule file uses are declared in that file's own header." This spec adds no `data-model.md` with a category table. A second table would become a governing copy, competing with the header and drifting from it. The Rule set scope table above describes the header's categories and does not govern them.

- [ ] AC2: Every rule ID in the file matches `FE-{CATEGORY}-{NNN}` with a declared category, and none of the six categories appears in the category declaration of `framework/rules/security-frontend.md` or `framework/rules/accessibility-frontend.md`. `scripts/lint-rule-ids.sh` passes.
- [ ] AC3: Every rule conforms to [008's data-model](../008-security-rules/data-model.md). It also carries a `**Source:**` paragraph. Every claim it makes about an external standard, specification, or product behavior, in any field, matches the cited document's current text when fetched.
- [ ] AC4: `FE-VITALS-001` names the three current Core Web Vitals (LCP, INP, CLS, with no budget keyed on FID), and its default budgets and measurement basis match what web.dev publishes. On 2026-10-19, web.dev's "Web Vitals" and "Defining the Core Web Vitals metrics thresholds" gave "good" as LCP ≤ 2.5 s, INP ≤ 200 ms, and CLS ≤ 0.1, assessed at the 75th percentile of page loads segmented across mobile and desktop.

- [ ] AC7: Rules whose concern meets a sibling rule file cite it and do not restate it. `FE-LOAD-007` cites `BE-CACHE-004`, `BE-PAYLOAD-003`, and `FE-PII-003`. `FE-LOAD-009` cites `FE-PII-003`. `FE-LOAD-004` cites `FE-CSP-002`. `FE-MAIN-002` cites `BE-PAGE`. `BE-CACHE-004` in `framework/rules/performance-backend.md` defers build-emitted frontend assets to this file.

## Open Questions

- **Should the header state an explicit severity posture?** `performance-backend.md` states 034's posture: MUST only when absence is a denial-of-service or resource-exhaustion risk regardless of scale. `observability-backend.md` states its own. This file states none, so its 11 MUST-tier rules (as of the second 2026-10-19 review) have no stated test to be measured against. A frontend posture might be "MUST only when absence is a resource-exhaustion or user-blocking risk regardless of scale." Invisible text (`FE-FONT-001`), parser-blocking scripts (`FE-LOAD-002`), and a lazy-loaded LCP image (`FE-LOAD-005`) read as user-blocking under that test. Modern image formats (`FE-IMAGE-001`) and WOFF2 (`FE-FONT-002`) read as payload-efficiency trade-offs of the kind 034 kept SHOULD (`BE-PAYLOAD-003`, compression), so they would need re-examining. Changing a rule's tier keeps its ID. Should the file adopt such a posture, and with what wording? The answer becomes an acceptance criterion, plus a header sentence if a posture is adopted.
- **Where do the Web Vitals budgets live?** `FE-BUNDLE-001`'s first clause requires the bundle budgets to be published in `specs/system.md`. `FE-VITALS-001` requires "documented performance budgets" and encourages stricter project-specific ones, but names `specs/system.md` only as the place to justify a looser budget. A project that adopts stricter Web Vitals budgets therefore has no named home for them, and `/ductus:analyze` has no named artifact to check a UI spec's commitment against. Should `FE-VITALS-001` name `specs/system.md`, as `FE-BUNDLE-001` does?

## Resolved Questions

- **Does `performance-frontend.md` get a spec of its own?** Resolved 2026-10-19 (owner): **yes.** Each of the three files bundled into `9ccbd0b` gets its own owning spec, following 034 and its sibling backend rule specs. This is that spec for `performance-frontend.md`. Future frontend performance rules land here through the back-edge (§rules, "When to write a rule"), not in specs of their own.
- **Category set.** Resolved in the first 2026-10-19 review: **six categories, `VITALS`, `BUNDLE`, `IMAGE`, `LOAD`, `FONT`, and `MAIN`**, as the header declares. The review added `MAIN` for main-thread work: long tasks (`FE-MAIN-001`) and DOM size for unbounded collections (`FE-MAIN-002`). Both reach INP, and none of the five original categories covered them. It also widened `LOAD`'s declared scope to prioritization, caching, and layout reservation, to match `FE-LOAD-006` through `FE-LOAD-008`. The second review the same day added `FE-LOAD-009` (no `unload` listeners, for bfcache eligibility) under `LOAD`, and the header now names its caching as "HTTP and back/forward caching". The set stayed at six.
- **May a MUST require CI?** Resolved 2026-10-19 (owner): **no.** A MUST never requires continuous integration — neither that a project run CI nor that a check run in it; it states the outcome a project's releases are held to. The owner clarified the same day that the principle bars requiring CI, not constraining what a build uses. A spec or plan cannot show how a project's CI behaves, so `/ductus:analyze` has nothing to verify such an obligation against. This is codified in [008's data-model §Severity classification](../008-security-rules/data-model.md#severity-classification). Before the review, `FE-BUNDLE-001` required the build to fail on an over-budget bundle. It now states the outcome: a bundle that exceeds its budget does not ship until the budget is raised in `specs/system.md`. `FE-BUNDLE-003` (SHOULD) recommends an automated budget check, following the `BE-SCHEMA-003`/`BE-SCHEMA-004` pattern that the data-model names.
- **Should `FE-BUNDLE-001` keep numeric default budgets?** Resolved 2026-10-19 (owner): **no; the default budgets stay out of the MUST.** The rule had shipped defaults of ≤ 170KB compressed JS for the initial route and ≤ 50KB compressed CSS, and a check of the cited sources on 2026-10-19 found that neither default matched how its source presents it. Addy Osmani's "Start Performance Budgeting" gives 170KB as an example mobile device-class budget ("e.g. < 170KB JS (min/gzip) for mobile"), not as a default starting budget, which the Statement called it. The 50KB CSS figure came from the desktop-on-WiFi example row of web.dev's "Your first performance budget", but the rule paired it with a JS default taken from a mobile example. The MUST to publish budgets already does the normative work. The Statement now requires JavaScript and CSS budgets for each route or entry point, published in `specs/system.md` and measured as transferred bytes, and an over-budget bundle does not ship until its budget is raised there. It sets no figure. The Rationale keeps published figures only as attributed examples: Osmani's 170KB mobile example, and the 170 KB critical-path total and example rows of "Your first performance budget". The 50 KB CSS figure now appears only in the desktop-on-WiFi row it comes from. The Source line names each web.dev article where it had said only "web.dev Performance Budgets". 034's "qualitative" resolution of threshold values is the precedent. The decision covers `FE-BUNDLE-001` only. `FE-VITALS-001`'s default budgets are web.dev's published "good" thresholds, which the Acceptance Criteria check against their source.
- **Do SLOs belong in this rule set?** Resolved 2026-10-19 (owner): **no; SLOs do not belong in rules.** [037-observability-backend-rules](../037-observability-backend-rules/spec.md) had already kept SLOs and alerting out of the backend observability set, as operational policy rather than per-feature design commitments. `FE-VITALS-001`'s budgets resemble an objective, a threshold at the 75th percentile, but the rule does not set one up. The project publishes the budgets, and what the rule asks of each spec or plan that introduces or modifies user-facing UI is a commitment to maintaining them, plus a `specs/system.md` justification for any looser threshold. `/ductus:analyze` can find that commitment in the artifact. `FE-VITALS-002` asks for RUM emission to a monitored backend, which is an instrumentation commitment. Neither rule defines an error budget, an alert, or an operational response to a breach.
