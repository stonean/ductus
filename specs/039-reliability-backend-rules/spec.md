# 039 — Backend reliability rules

Introduce `framework/rules/reliability-backend.md`, an enforceable rule set covering server-side reliability concerns — deadlines, timeouts, retries, retry-exhausted messages, circuit breakers, graceful shutdown, backpressure, and graceful degradation. The file follows the canonical rule schema and is installed and enforced under the **backend** surface. This is a rule-introducing feature spec — the same path [008-security-rules](../008-security-rules/spec.md) used — and one of the three Task-9 backend sets that follow [034-performance-backend-rules](../034-performance-backend-rules/spec.md).

## Motivation

The constitution calls the system to be **Reliable** ("graceful degradation and automatic recovery when components fail"). [034-performance-backend-rules](../034-performance-backend-rules/spec.md) deliberately scoped *out* server-side deadlines, downstream-call timeouts, retries, and circuit breakers — "as much reliability as performance" — and forward-references a future `reliability-backend.md`. Landing this spec resolves that forward-reference and gives reliability concerns a home at the rules tier.

Reliability failures that recur across features — an unbounded downstream wait that exhausts threads, a retry storm that amplifies an outage, a deploy that drops in-flight requests because nothing drains on shutdown — had nowhere to be promoted when this spec was written. Each was re-litigated per feature or surfaced only when a dependency degraded.

This spec closes that gap: a backend reliability rule set citable by ID (`BE-{CATEGORY}-{NNN}`) that `/ductus:analyze` checks against specs and plans (design-time reliability commitments).

## Rule set scope

`reliability-backend.md` uses the **backend** surface (`-backend.md` suffix, `BE-` ID prefix), with NEW categories disjoint from every category the other `-backend.md` rule files declare in their headers (`security-backend.md`, `api-backend.md`, `performance-backend.md`, and the rest). Category set (resolved at clarify — five categories ship; `DEADLINE` is folded into `TIMEOUT`; see Resolved Questions):

| Category | Abbrev | Concern |
| --- | --- | --- |
| Timeouts & deadlines | `TIMEOUT` | every outbound call or blocking wait on another process or host has a bounded timeout (no unbounded waits); an end-to-end request deadline is set and propagated to downstream calls; a datastore query is bounded on the server — by the datastore's own statement time limit, no longer than the caller's deadline, or by a client timeout that cancels it — not only by the caller's wait |
| Retries & dead-lettering | `RETRY` | bounded retries with backoff + jitter, idempotent ops only (cross-ref `BE-IDEMP`); no retry storms; only transient failures are retried, waiting at least a server-supplied `Retry-After`; retries happen at one layer of a call path; a message that exhausts its redelivery bound is dead-lettered where the responsible team can review and redrive it, or halts its strictly ordered stream with the halt recorded |
| Circuit breakers | `BREAKER` | breaker around failure-prone downstreams, opening on a failure count or rate; fail fast when open |
| Graceful shutdown | `DRAIN` | drain in-flight work on shutdown within a grace period that fits the platform's kill deadline; stop accepting new work; honor termination signals; leave routing and keep serving for a bounded propagation delay before closing intake |
| Backpressure, bulkheads & graceful degradation | `BULK` | bulkheads / bounded queues / load shedding to isolate failures; a failing non-critical dependency degrades the response rather than failing the whole operation |

### Severity posture

Reliability rules default to **SHOULD** where the approach is contextual. A rule is **MUST** only when its absence is an availability or cascading-failure risk *regardless of scale* — an unbounded downstream wait (no timeout), an unbounded/un-jittered retry (retry storm), a poison message redelivered forever or silently dropped (no dead-letter or halt disposition), no graceful drain (dropped in-flight requests on every deploy).

### Boundaries (cross-reference, do not duplicate)

- **Connection pooling** (including bounded acquisition timeout) is `performance-backend.md` `BE-POOL-001`/`BE-POOL-002` — reliability cites them where pool exhaustion interacts with timeouts (`BE-TIMEOUT-001`, and `BE-TIMEOUT-003` for a pooled connection an abandoned query keeps checked out) and bulkheads (`BE-BULK-001`); it does not re-derive pooling. Holding a transaction or connection across a call to another service is `BE-POOL-005`, which `BE-TIMEOUT-003` cites to separate it from bounding the query itself.
- **Idempotency** is `api-backend.md` `BE-IDEMP` — `BE-RETRY-001` cites it (retries apply only to idempotent operations).
- **Async offloading** is `performance-backend.md` `BE-ASYNC` — reliability cites it where backpressure governs offloaded work.
- **Operator-tunable values** (timeout durations, request deadlines, server-side query time limits, retry counts and backoff parameters, retry budgets, redelivery bounds, breaker thresholds, shutdown grace periods, routing-propagation delays, bulkhead bounds) are `configuration-cross.md` `CFG-CONST-*` / `CFG-ENV-*` — ten rules cite `CFG-CONST-003` for them.
- **Duplicate-safe delivery and ordering scope** are `concurrency-backend.md` `BE-COORD-002` and `BE-COORD-004` — `BE-RETRY-001` and `BE-RETRY-005` cite `BE-COORD-002`, and `BE-RETRY-005` cites `BE-COORD-004` for the ordering scope a consumer relies on where it halts a strictly ordered stream rather than dead-lettering out of it; the `RETRY` rules own the retry mechanics and the disposition of a retry-exhausted message.
- **Status codes and rate limiting** are `api-backend.md` `BE-STATUS-001` and `security-backend.md` `BE-API-004` — `BE-RETRY-003` cites both, and so does `BE-BULK-001`: `BE-STATUS-001` for the overload status a shed request gets, and `BE-API-004` for the `429` it gets where the limit is a per-client rate.
- **Readiness and saturation signals** are `observability-backend.md` `BE-HEALTH-001` and `BE-METRIC-002` — `BE-DRAIN-002` cites readiness as one way to leave routing, `BE-BULK-002` limits readiness gating to critical dependencies, and `BE-BULK-001` cites the saturation metrics.

## Resolved Questions

- **Exact category set and abbreviations.** Resolved: **five categories — `TIMEOUT`, `RETRY`, `BREAKER`, `DRAIN`, `BULK`**, each disjoint from the existing `BE-` category sets. `DEADLINE` is folded into `TIMEOUT` (per-call timeout and end-to-end deadline propagation are the same concern — bounding the wait — at two scopes, carried as two rules in one category) rather than a separate category. **Updated 2026-10-19:** the rule-file review widened two categories rather than adding a sixth — `RETRY` is now *retries and dead-lettering* and carries `BE-RETRY-005`'s disposition of a message that exhausts redelivery, and `BULK` is now *backpressure, bulkheads, and graceful degradation* and carries `BE-BULK-002`. Five categories still ship.
- **Backpressure/bulkheads (`BULK`) in scope or deferred?** Resolved: **kept in scope.** Bulkheads, bounded queues, and load shedding are the canonical graceful-degradation pattern (the constitution's reliability principle) and prevent one slow dependency from consuming all resources (cascading failure). It fits the design-time-commitment model and cites `performance-backend.md` `BE-ASYNC`/`BE-POOL-*` where it touches offloaded-work and pool concerns rather than re-deriving them.
- **MUST vs. SHOULD default.** Resolved: **default SHOULD; MUST only when the absence is an availability or cascading-failure risk regardless of scale.** Mirrors 034/037/038. The three MUSTs at launch: an unbounded downstream wait (no timeout), an unbounded or un-jittered retry (retry storm), and no graceful drain on shutdown (dropped in-flight requests every deploy). Contextual choices (timeout durations, breaker thresholds, retry budgets, which downstreams warrant a breaker) stay SHOULD. **Updated 2026-10-19 (owner-confirmed):** a fourth MUST, `BE-RETRY-005` — a message that still fails when its redelivery bound is exhausted goes to a retained dead-letter destination where the responsible team can review and redrive it, or halts its strictly ordered stream with the halt recorded, and is never redelivered indefinitely or discarded silently (as first written it also required the destination to be monitored and the halt to alert; see the next question). It meets the same bar: a single poison message blocks every message behind it on an ordered queue or partition and burns consumer capacity on an unordered one, regardless of scale. The review's other additions — `BE-RETRY-003`, `BE-RETRY-004`, `BE-BULK-002` — are contextual and ship SHOULD, and so does `BE-TIMEOUT-003`, added by that day's owner decisions: the scale-independent cascade, a caller waiting without bound, is already `BE-TIMEOUT-001`'s MUST, while what a query left running after its caller gave up costs depends on the query's weight and on whether the driver already cancels it.
- **Does `BE-RETRY-005` require the dead-letter destination to be monitored, or a halted stream to alert?** Resolved (owner decision, 2026-10-19): **no — alerting does not belong in rule files.** This applies the ruling observability-backend's spec 037 records as a Resolved Question, reaffirmed the same day, under which SLOs and alerting are operational policy rather than per-feature design commitments; `security-frontend.md` `FE-CSP-005` was reworded on the same basis to keep reports "where the team responsible for the CSP can review them". `BE-RETRY-005` stays MUST and keeps its obligation — bound redelivery, never loop forever, never discard silently — but now requires only that a retry-exhausted message is kept in a retained dead-letter destination where the responsible team can review and redrive it, or, for a strictly ordered stream, that processing halts and the halt is recorded with the message that caused it rather than the message being skipped. How the team watches either is its own operational choice.
- **Confirm the perf/reliability boundary.** Resolved: **confirmed.** All four concerns 034 deferred — request deadlines, downstream-call timeouts, retries, and circuit breakers — land here (`TIMEOUT`/`RETRY`/`BREAKER`), resolving 034's forward-reference. `performance-backend.md` `BE-POOL-002` (bounded pool-acquisition timeout) remains in the performance set and is cited here where pool exhaustion interacts with timeouts (`BE-TIMEOUT-001`) and bulkheads (`BE-BULK-001`); it is not moved.
