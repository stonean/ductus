# 079 — Review and analysis work converges

A spec's `/{project}:review` and `/{project}:analyze` work ends in a bounded number of runs, and one spec's run does not create work for another spec. This is the efficiency work `078-review-fix-rounds-are-re-read-within-a-bound` was meant to be.

## Motivation

`078-review-fix-rounds-are-re-read-within-a-bound` bounded one loop: the fix rounds inside a single `/{project}:review` run, re-read by an independent agent within a budget of two re-reads. That loop worked; 078's second review ran two rounds and one re-read. The cost the owner was losing time to was the outer loop: a review deferred part of what it found into the spec it reviewed, or into a sibling, so another implement → review → analyze cycle followed, and that review found more. No criterion of 078 measured an outcome, so its reaching `done` could not have shown whether reviews converged.

The corpus showed it. Each figure was measured on 2026-11-04 at `d62e72f3`, before this spec existed:

- **Status.** 37 specs were `in-progress`, 34 `done` and 5 `draft`, read from each `specs/NNN-*/spec.md`'s `status:`. 10 of the 37 had no unchecked `- [ ]` line in their `tasks.md`, so they waited only on review, analysis or the completion gate: 015, 016, 029, 034, 037, 039, 045, 055, 061 and 078. Eight more had exactly one.
- **Runs per spec.** Counted from commit subjects that start `review(NNN)` or `analyze(NNN)`, over all history; a run recorded under another subject, or two runs in one commit, are not counted.
  - `done` specs: review runs median 2, maximum 7, and 11 of 34 took more than two (006, 013, 019, 023, 025, 040, 042, 043, 046, 051, 062). Analyze runs median 1, maximum 5.

## Behavior

- **A spec's review and analysis converge.** Each reopening of a spec, one pass from `in-progress` to `done`, holds at most one `/{project}:review` run and one `/{project}:analyze` run, and a second of either only after the earlier run left a gating finding. A reopening that changed neither the spec's code nor its scenarios or data model owes an analysis and no review, and the pre-`done` gate holds any other until its review's record is committed, naming the review ahead of the analysis.
- **A run creates work only where it is owed.** A review or analysis run adds a task or scenario, to its own spec or another, only to dispose of a gating finding, and an observation showing the spec's own code breaks its contract counts as gating. Any other observation is fixed in the run when mechanical and otherwise waived with its reason.
- **A run reads its own spec's work.** What a review or analysis reads, and what its fix rounds re-read, is the spec's own change, so another spec's commits in the same tree neither enter it nor wait on it. A later review in the same reopening starts where the earlier one ended.
- **A behavior is stated once.** Each primitive has one description, compiled into the binary, and every other shipped place points at it, so a change edits one sentence rather than seven. Spec text cites a primitive by name, and existing spec text that is still true changes only when it is next edited.
- **The bound is measured, not asserted.** The outcome this spec targets is computed from the repository's history by the method its Resolved Questions record, and the measurement reports each reopening over the bound, each it could not count, and how many `in-progress` specs have no unchecked task. `/{project}:status` shows those counts on every run, and this spec closes only after real reopenings meet the bound.
- **A run waits for the work.** A review or an analysis runs once the spec's implementation is complete, since nothing can say whether a task still open would change what it reads, and no task list schedules one.
- **Adopters get it.** Each change to how the pipeline behaves lands in what a release ships, so an adopter's review and analysis converge too, and the measurement runs in an adopter's project over its own history.

## Edge Cases

- **A reopening that cannot be counted.** One with no recorded run, or a record that does not parse, is reported as not counted, never as within the bound. A history too shallow to hold its status commits reports that it cannot measure, and no closed reopening yet reports nothing to compare; each is a distinct state.
- **No earlier review.** With no earlier review, or a last review commit older than the reopen, the window starts at the reopen. A record not yet committed, or one the gate holds until a review runs, AC14's open mark among them, does not move the start.
- **A trip through draft.** It never reaches `done`, so it stays in one reopening: the window, `diff-cross-spec`, `check-stuck` and the measurement start where the spec last left `done` or, never `done`, where it first entered `in-progress`, and a clean review on each side of the trip is over the bound.
- **Unusual commits.** A subject naming a number no spec has claims nothing. A merge commit contributes only what it changed itself, and a squashed commit touching several spec directories follows the several-specs rule. A commit no spec claims counts whole in every window holding it, so no path goes unread.
- **An unchecked box on `done`.** A box under an unnumbered or suffixed heading counts as one under a numbered task does, and a comment's or fence's does not. A `tasks.md` new since the base counts each box it holds. A release step left as a box holds `done`, so it is ticked or removed first.
- **An untick on `done`.** `/{project}:analyze` reports it as blocking drift and its `--fix` reverts the spec, with no grandfather rule, and `classify-spec-edit` reads it as `reopens`. A tick stays a `correction`, so a criterion ticked by mistake and corrected the same way costs a reopen.
- **Rename, revert and shallow clone.** A slug changed mid-reopening keeps its window, a commit restoring an older record starts the window at the run it restores, and a shallow clone whose history stops inside the reopening or short of a fold's commits errors, or gives `diff-cross-spec` and `check-stuck` guidance, rather than answering as if history were whole.
- **A mechanical edit.** A token swept across files in a contract, or a cross-service reference added, removed or rewritten, reads `mechanical`; the same token changed in one file reads `reopens`, as does prose beside a reference. A real change made with the same token in two files reads as a sweep, as it does for the gate's staleness.
- **A stored finding the run did not read.** A waiver or decision that did not fire on a file still on disk that the run's scope does not hold stays, since nothing read that file; one on a file the scope holds, or gone from disk, expires. A scope that cannot be read retains each and says so. A key naming no file expires as before, though no stored key has that shape (all 1,075 at `f2e8c70a` name a file, `research.md`), and an analysis has no window, so its decisions are untouched.
- **A fold.** A staging spec folded below `done` brings the paths of every commit it claimed into its target's next scope, wherever the window starts: a target reopened by the fold starts after them, and no review has read them. One that reached `done` had its code read by its own review, so it brings nothing, and a commit touching its directory stays excluded, named by its number, as a consolidated spec's does. A commit that only named a spec gone from disk reads as no spec's.
- **One path, two commits.** A path changed both by a commit that belongs to the spec and by one that does not stays in scope, and in a fix round a path a fix and another spec's commit both changed stays in the round. A commit this spec or no spec claims stays in the round too.
- **Another session's uncommitted edits.** They cannot be told apart from the run's own, so they stay in scope and in the round; `git worktree` isolates sessions.
- **`--since`.** It moves only the window's start, and the scope rule still applies.
- **A finding outside the next window.** The next scope holds what the record at `HEAD` lists in `open-findings`, wherever the window starts, a path another spec's commit changed included. A file since deleted, or a path leaving the project, is not read. A listed path in another spec's directory is read and is no change of this spec's. A record from before the list names nothing, and an empty-scope write refuses over one counting a finding.
- **A broken contract.** A person's waiver, a fix a later run finds, or a deferral to another spec's work still to do clears it. A deferral to the spec's own task, or to an external work item alone, holds until then, and a break left open must name its file.
- **A reopening that owes no review.** The test is a scope with no path outside a spec's directory and no edit to this spec's scenarios or data model, whose digest the gate still compares, and a record the gate does not hold until a review runs. A path in another spec's directory is that spec's change, and its review reads it. A review run anyway is allowed, only not owed.
- **The open mark.** A run with `re-reads-off` or a budget stop still clears it on its last write. A run that halts leaves it, and the gate's message names `/{project}:review`.
- **What is not a correction.** A diff that also touches a scenario, a data model, a criterion, an open question or an unchecked task reopens as before. A stale `analyzed-digest` on a `done` spec fires no check, and the next analysis reads the text.
- **A rule-decided disposition.** A person's stored decision wins and the rule does not re-decide it, and the rule's stored waiver does not dispose of an observation later judged a broken contract. An observation that cannot be judged mechanical is waived with its reason, unless it shows a broken contract. A security observation is listed first in the report, as §brownfield-inbox asks. With no operator, a gating finding or a broken contract is recorded undispositioned and blocks.
- **Size.** Splitting a reference file to fit one read does not lower the total, and a new reference file counts toward it.
- **The sample for `done`.** A reopening holding no run, such as a correction's, does not count toward the 10. If fewer than 10 can close, `done` waits, and changing the number is the owner's, through `/{project}:amend`.
- **A primitive that fails.** It reports an error and a non-zero exit, and the run treats the affected check as not run, never as passed.

## Resolved Questions

- **When do a spec's review and analysis run?** Once its implementation is complete, every box in `tasks.md` ticked (owner, 2026-11-07), since whether a task in a long list would stale a run cannot be determined, so a rule asking someone to judge it fails when it matters, against §design-principles' filter on diligence. Both writers refuse while a box is open, by the gate's test, and both commands stop at their first step, saving the run's cost; no task list schedules a run, as §tasks-phase already has handoff state in prose. Measured at `347c3f70` by each record commit's `tasks.md`, a `- [ ]` line outside a fence counting: of the 313 runs since 2026-10-01, 236 were on `in-progress` specs and 77 on `done` ones, none earlier; 41 ran with a box open, 21 reviews and 20 analyses, and 12 of those 41 were followed by another run of the same kind before the spec reached `done`. That count took any `- [ ]` line outside a fence, so it also counted the five commented example boxes the tasks template left in four lists (019, 026, 052 and 058), which AC27's test does not: there, 15 of the 22 commits before `347c3f70` that wrote a `last-run` held only those (this spec's 2026-11-09 review), so the 41 and the 12 overstate the runs that test finds with a box open. A pattern search found 21 boxes in 18 task lists scheduling a run or holding a note as a box, of which 17 lists were rewritten as prose and 4 boxes in 4 lists are work that only mentions a run; task 26 found 3 more the search missed, 1 in 022's task 10 and 2 in 047's task 7, now prose too. It starts no reopen, since each list is an `in-progress` spec's and a task-list edit is a correction.
