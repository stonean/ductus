## Overview

One shared reader, `runtime/src/primitives/departures.rs`, parses a spec's departure entries under `## Applicable Rules`, validates their structure, and derives each entry's `decided-by` and `decided-at` from git history. Four consumers call it, so none restates the grammar or the attribution rule: a new primitive `check-departures` (AC1, and the host's list of entries), `write-analysis` and the exec walker's tally (AC2 to AC4), and `write-review` with `process-waivers` (AC5, AC8).

At analyze, a rule an entry names is still judged for whether its trigger fires, as any rule is, but a fired outcome is recorded as a third rule-verdict shape, `waived`, never `finding`, so no finding exists to count or to refuse. At review, `write-review` turns each entry into per-file waivers for the files its rule fires at, marked as departures so that `process-waivers` expires them when the entry is gone.

## Technical Decisions

### The entry grammar is a nested bullet

Decided by the owner, 2026-11-12, of three options (nested bullets, one line, a fenced YAML block); the grammar is **§Departure entry** in `data-model.md`. An entry is a list item under `## Applicable Rules` whose text is the literal key `departs:` and one backticked rule ID. Its children are `reason:` (required, non-empty) and `cited:` (optional, one `§anchor` reference); any other child key is malformed. HTML comments and fenced code are skipped, so the template's commented example is no entry and passes by default (§drift-prevention, its template-rule alignment). A `§` citation, not a markdown link, keeps the entry from creating a `dependencies:` edge (§text-first-artifacts). Measured 2026-11-12: 9 of the 76 specs carry `## Applicable Rules`, holding 20 bullets, all `` - `ID` — reason ``; none opens with `departs:`, so no existing citation reads as a departure.

### One reader, one attribution rule, four consumers

`departures.rs` exposes the entry parser (rule, reason, cited, line, structural problems) and the attribution. One module follows the pattern where a shared predicate is the only decision several callers consult: `runtime/src/primitives/rule_verdicts.rs` (its header states the callers must not disagree) and `runtime/src/primitives/commit_attribution.rs`. Repository access goes through `ProjectRepository::discover` with `to_git` and `to_project`, since the project root is not the work tree's root. The module is `pub mod` with `pub` items taking the project root as a `&Path`, as the primitives' `run` functions do, so no consumer-less item reads as dead code before task 2 calls it and the pub(crate) `ProjectRepository` stays inside it. `parse(content)` returns `entries` (the well-formed ones, so a malformed entry waives nothing) and `problems` (a line and a kind: no rule ID, a second rule ID, no or empty `reason:`, another or a repeated child key, and a rule two entries name). **A rule two entries name is reported by the reader**, as `DuplicateRule` on the later entry, with both entries kept in `entries`; `check-departures` turns each problem into its Blocking finding and so owns no second duplicate check. A `cited:` child with no text names no citation. A reason wrapped onto a continuation line, indented or lazily unindented as CommonMark renders it, is joined with a space; a lazy line is one directly after the child's text, with no blank line between, that opens no block: a bullet, an ordered item (one to nine digits, then `.` or `)`), a blockquote, a heading or a thematic break (`---`, `***`, `___`, three or more of one mark, spaces or tabs allowed) ends the child instead; a `---` directly under the child's text is CommonMark's setext underline, which also closes that paragraph. These openers are recognized only on an unindented line: an indented line is read as the child's continuation before they are consulted, so an indented `---`, `***`, `>` or `1.` joins the text, where CommonMark would end the paragraph. `attribute(project_root, spec_rel, rules)` returns each rule's `Attribution`, `Attributed{decided_by, decided_at}` or `Unattributed`; the walk follows first parents from `HEAD`, so a merge's side branch is not part of the run, and a blob already read is not parsed again.

### Attribution is the first commit of the entry's unbroken run

`git blame` names the commit that last touched a line, and the Edge Cases keep an edited entry's introducing author and date. The reader walks commits from `HEAD` (`revwalk`), parses each revision of `spec.md` (`tree.get_path`), and takes, per rule, the oldest commit of the unbroken run ending at `HEAD` in which an entry for that rule exists; an entry removed and added back is introduced by the re-adding commit. `decided-by` is the commit author's email, the identity `write-review` already records as `waived-by` from `git config user.email`; `decided-at` is the author time in UTC to the second.

`decided-by: unattributed`, a state of its own with `decided-at` absent, when the repository is shallow (`Repository::is_shallow`, as `paths_in_history` in `runtime/src/primitives/check_artifacts.rs` refuses to answer on one, and as `oldest_bullet_date` in `runtime/src/primitives/inbox_standing.rs` documents a shallow boundary reading as a confident answer), when there is no repository, when the entry is absent from `HEAD`'s `spec.md` (not yet committed), or when a revision cannot be read. A spec directory rename is followed with `Diff::find_similar` on the commit that adds `spec.md`, and only within one spec: the renamed-from directory must parse (`parse_feature_dir`) to the same `FeatureForm` as the new one, since similarity detection pairs any deleted spec with a similar added one and a spec number is never reissued. Where none is found, or the pair is another spec, the add is the introduction. The walk follows first parents, so an entry brought in by a merge is introduced by the merge commit and its side branch's authors are not named. Fixtures in `departures.rs` prove each.

### `check-departures` is a new primitive, owned by this spec

`write-analysis` refuses a `blocking-findings` count below the MUST-tier `Finding` verdicts the record holds (`derive_rule_fields` in `runtime/src/primitives/write_analysis.rs`), so the host must know which rules carry an entry before it answers steps 11 and 12, and `check-artifacts`' result carries findings and skipped targets, never a list of entries (`CheckArtifactsArgs`, `CHECK_ARTIFACTS`). `check-departures` takes `feature` and returns `entries` (rule, tier, reason, cited, decided-by, decided-at), `findings` (family `departure-entries`, tier, message, path) and `unexamined` (a citation it could not judge, reason `anchor-target-unjudgeable` or `anchor-target-unreadable`, never a pass). It judges each `cited:` through `resolve_anchor::run` with `markers-path` set to `paths::constitution_path(repo)`, as the exec walker already resolves the constitution (`runtime/src/interpreter/mod.rs`), keeping the results on entry lines. A feature-specific primitive lives with its feature (AGENTS.md). Step 5.1 of `framework/commands/analyze.md`, a nested sub-step of the `check-rule-ids` step whose rule IDs an entry names, dispatches it, so no step is renumbered: a step dispatches exactly one primitive and the other steps, specs and goldens cite step numbers. `AnalyzeTally` counts its findings by their `tier`, so under `ductus exec` a Blocking entry finding reaches `blocking-findings`, and counts none of its `unexamined` entries: a target is recorded once, and each of those repeats one a step over the whole spec records. `check-rule-ids` (step 5) scans every rule ID token in the body, an entry's backticked one included (`citation_regex`), so its `not-installed` and, with no rule file read, its `rule-citations-not-checked` count cover the entry's rule; `resolve-anchor` (step 4) scans every `§` reference on every line outside marker comments and code spans, and `judge_citations` is that same call over the same `spec.md` and markers, so its `anchor-target-unjudgeable` and `anchor-target-unreadable` cover each `cited:` line. The primitive still returns the entries, so a standalone caller sees what it could not judge; step 5.1's prose and the tally leave them to steps 4 and 5. Step 14 collects the rule IDs under `## Applicable Rules` and skips a departure entry's: the entry stays the record of the decision whether or not its rule fires. That collection is command prose only, since the exec walker no-ops step 14 (`applicable-rules-not-checked`) and no runtime code implements it. It is registered at the seven sites `docs/developing-ductus.md` §Adding or removing a runtime primitive lists, with its name in `framework/runtime-tools.txt`.

### Finding tiers

Decided by the owner, 2026-11-12: an entry missing a required field (no rule ID, no or empty `reason`), a malformed entry (a second rule ID, another or a repeated child key), an unknown or retired rule ID, and a rule two entries name are **Blocking**; a deprecated rule and an unresolvable citation are **Advisory**. A retired rule is one the spec's `retired-rules:` lists that no loaded rule file defines, and an unknown one is in neither; both come from `check-rule-ids`' reading of every rule file in the directory (`discover-rule-files` under `all`). This matches step 5 of `framework/commands/analyze.md` (`check-rule-ids`: a missing ID blocks, a deprecated one is advisory) and step 4 (an unresolved `§` reference is advisory). An entry naming a rule the project never installed (`check-rule-ids`' `not-installed`) is recorded unexamined under `rule-not-installed`, as step 5 records the citation. With no rule file loaded (`check-rule-ids`' `examined` is 0) nothing is known of any rule, so none is unknown, retired, deprecated or not installed: no finding of those kinds is raised, and each entry's rule is recorded unexamined under `rule-citations-not-checked`, as step 5 records its citations, while the structural findings and the `cited:` judgments are raised as usual. A malformed entry waives nothing, so its rule is assessed as any other. A `cited:` that is not exactly one `§anchor` reference (none, or two or more) is unresolvable too, since the reader accepts any text and the grammar takes one, and a reference `resolve-anchor` did not judge is recorded unexamined, as its own `unjudged` reason says.

`check-rule-ids` scans every ID token in the body (`citation_regex` in `runtime/src/primitives/check_rule_ids.rs`), so it reports an entry's unknown or deprecated ID too, and one defect yields two findings, one naming the ID and one the entry. Both are fixed by one edit; teaching `check-rule-ids` to skip entry lines would add a file and a grammar copy for no change in what blocks.

### `waived` is a third verdict shape, which the host cannot fabricate

`RuleVerdict` (`runtime/src/schema/primitives.rs`) is `Addressed{cite}` or `Finding{tier, at, message}`; it gains `Waived{reason, decided-by, decided-at?, cited?}`. The host supplies the bare `{verdict: waived}` for a rule `check-departures` listed whose trigger fired, since firing is the host's semantic judgment (steps 11 and 12). `write-analysis` fills the fields from the entry, refuses `waived` for a rule with no entry, and refuses `finding` or `addressed` for a rule with one: a refused write leaves no record, so the host corrects it, and nothing depends on its remembering (§design-principles). The exec walker does the same in `AnalyzeTally::record_assessment` (`runtime/src/interpreter/analyze_tally.rs`), told by `load_rules` (`runtime/src/interpreter/payload.rs`) which rules the feature's spec holds an entry for: for such a rule, any fired answer, a failure or a pass citing `addressed-by`, records the bare `Waived` and counts into no tier, and a plain pass records nothing, as 082's data model defines a rule that does not fire. The fields come from one function, `fill_waived` in `rule_verdicts.rs`, over the entries `departures::parse` returns (a rule two entries name is waived by the first, the second being `check-departures`' blocking finding), so the host's verdict and the tally's are both filled by `write-analysis`. A rule that fires and is addressed is still `waived` (Edge Cases).

A stored `waived` verdict is reused like any fired verdict while its subjects are unchanged (`Currency::Fired` in `rule_verdicts.rs`), and `spec.md` is a subject, so an entry edit makes every verdict stale. Attribution depends on history rather than on a digest, so `write-analysis` recomputes a carried `waived` verdict's fields on every write: a record written `unattributed` before the commit is attributed after it. A carried `waived` whose entry is gone cannot be refilled, so it is recorded unjudged, not kept; an entry edit already makes it stale through `spec.md`'s digest, which leaves this the guard for a record the digests misreport. Every exhaustive match on `RuleVerdict` gains an arm: `rule_verdicts.rs` (the currency and `contradiction`), `interpreter/mod.rs` (the reused-findings filter), `write_analysis.rs` (the record's `rule-verdicts` renderer; the finding floor reads `Finding` verdicts with `if let`, so `Waived` floors nothing and needs no arm) and `analyze_tally.rs`.

### The record and the report list waived rules apart

`write-analysis` renders a `## Waived rules` section in `analysis.md`'s body, between the findings sections and `## Contradictions` and absent when no rule is waived. MUST-tier rules come first (the tier from `AssessableRule` in `rule_verdicts.rs`), then every other, each in rule-ID order, so the order is the same on every run. A line is ``- {rule} ({MUST|SHOULD}) — {reason} — decided by `{decided-by}`[ at `{decided-at}`][ — cited `{cited}`]``, the record's other body lists' dash-and-em-dash form. The reason is the spec's text on one line and nothing more, since it comes from a line that already passes the markdown lint; the email, the time and the citation come from git or the entry and sit in code spans, because a bare email fails `MD034` in a committed record, which §markdown-standards requires to pass. `at` is absent for an `unattributed` rule and `cited` for an entry without one. A tier is always MUST or SHOULD: a verdict is held only for a loaded assessable rule (a supplied one for any other is refused, a carried one is read from the standing), so the list walks the loaded rules. Its result gains `waived` (rule, tier, reason, decided-by, decided-at, cited, in that order) and `waived-count`, bounded as `contradictions` is: `bounded_lists::place` keeps `waived-count` inline and, past the read size, moves `waived` with `contradictions` into the one file `lists-file` names. Both are derived from the record's verdicts after `fill_waived`, so the section, the list and `rule-verdicts` cannot disagree. Step 22 of `framework/commands/analyze.md` reports it before the passed rules and the advisory findings. No count field joins the record (Resolved Questions). A waived rule is not a finding, so `dispositions.waived` is untouched and 058's AC30 and the refusal of a waiver on a blocking finding stand.

### Review: `write-review` derives the waivers, `process-waivers` expires them

`new_waiver_entries` (`runtime/src/primitives/write_review.rs`) already turns a `--waive` (`NewWaiver{rule, reason}`) into one entry listing the files the rule fires at that no waiver holds. It gains a second source: each well-formed entry, of any tier, becomes a new waiver for its rule, so AC8's SHOULD takes the same path as a MUST. The stored waiver carries `waived-by` and `waived-at` from the entry, its `reason`, and `departure: true` in the open-schema `extra` map, which survives verbatim (`framework/reference/review.md` §Waivers). Each path still applies, expires and is retained on its own, so a file added later where the rule fires is covered with no second decision; 020's rule that a waiver never extends to another location gains one exception sentence, that a departure is bounded by the spec's own scope. An `unattributed` entry stores `waived-by: unattributed` and `waived-at` the run's own time, since `process-waivers` treats a blank `waived-at` as malformed (`REQUIRED_FIELDS` in `runtime/src/primitives/process_waivers.rs`). `write-review` reads `spec.md` once, for the entries and for its frontmatter check alike. A malformed entry derives no waiver, and the run names it in the result's `malformed-departures` (`spec.md line N: what is wrong`); a rule two entries name is derived once, from the first, and the second is named there too. A rule firing at no file stores nothing and refuses nothing, since an entry is the spec's standing decision, unlike a `--waive`, which is a request of this run. Every file the rule fires at is anchored, so a run's second write, which finds the waiver stored, still counts its findings waived; only a file no waiver holds, this run's hand `--waive` included, is stored.

Without the marker, a removed entry would leave its waivers applying while the rule fires, which the Edge Case "an entry removed" forbids. `process-waivers` reads the entries through `departures.rs`, whatever wrote the marker (a hand-written `departure: true` is expired or classified by the same test, and a non-boolean value fails the call naming the field), and expires a marked waiver whose rule has no well-formed entry, with its existing `waiver expired:` notice, on every run, and reads the spec only when a waiver carries the marker: a dimension-restricted run holds back a rule's silence, not the removal of the entry that waived it. A hand `--waive` on the same rule and file stays the first claim (`framework/reference/review.md` §Malformed and duplicate waivers).

## Data Model

[data-model.md](data-model.md) defines the entry grammar, the `waived` verdict, `check-departures`' result and the review waiver's `departure` marker. 082's data model and 066's record schema carry the verdict shape in the record (**§The analyze waiver** in `spec.md`); 073's data model owns the entry and the primitive's result and points at them.

## Trade-offs

- **A primitive rather than a `check-artifacts` family**: seven registration sites and a generated allow entry against about three files, chosen because the host needs the entries before steps 11 and 12 and `check-artifacts` returns none.
- **`write-review` derives the departure waivers**: the host has no step to forget, at the cost of `write-review` reading `spec.md` and history, which it already reads for scope.
- **The `departure` marker** is the one state that lets an entry's removal expire its waivers: one open-schema field per waiver.
- **The double report** of an entry's unknown or deprecated ID (above) is accepted.
- **Known limits**: a rename `find_similar` does not detect reads as creation, attributing the renaming commit's author; a squash or rebase attributes to its author, which no check can see; `decided-by` is who committed the entry, who accepted it for the spec, not necessarily who decided the departure, which a `cited:` document records.
- **Measured, 2026-11-13:** `attribute` over a temporary repository of 5,000 first-parent commits, the entry present from the first commit, in a release build, one run each: 324 ms when `spec.md` is unchanged in every commit, 826 ms when every commit rewrites it (parsed each time). Wall time of the one call, on the author's machine; the worst case, since a walk ends at the first commit without the entry. Re-derive with the ignored test `attribution_over_5000_first_parent_commits` in `runtime/src/primitives/departures.rs`: `cargo test --release --lib -- --ignored --nocapture attribution_over_5000_first_parent_commits`.
- **Not measured**: the compile time a `cargo test` step would add to `framework-checks`, whose `timeout-minutes` is 15; the script step avoids it.

## Open Questions Resolved

- *Settled before any finding exists* (Resolved Questions 1): `waived` is a verdict the runtime fills and the host cannot turn into a finding, so 058's AC30 stands.
- *Every file in review scope* (2): `write-review` derives per-file waivers each run from the run's own findings.
- *008 unchanged* (3): no tier is added.
- *`decided-by` from history* (4): `departures.rs`' attribution, `unattributed` as its own state, the test in `framework-checks`' full-depth job.
- *No count field* (5): `waived-count` is the result's derived figure, not a record field.
- *SHOULD rules too* (6): the review path is tier-agnostic, and AC8's fixture proves a SHOULD.
