# 082 — Rule assessments converge across runs Plan

Implements [082 — Rule assessments converge across runs](spec.md).

## Overview

`write-analysis` stores each fired rule's verdict beside the loaded rules the run left unjudged, a digest of the rule files it loaded, and a digest of each heading's section of the design subjects. A later run reuses a stored verdict while the sections it concerns, the rule's file and the set of loaded rule files are unchanged, and judges a quiet or addressed rule against the changed sections alone (AC7). One shared library, `rule_verdicts`, decides currency for three callers: `discover-rule-files` (the interactive host's list), the exec walker (which skips current rules) and `write-analysis` (which carries current verdicts forward, derives the unjudged list and detects contradictions). The data shapes are in [data-model.md](data-model.md).

## Technical Decisions

### The record holds four fields

`rule-verdicts` maps each rule that fired to its verdict (`addressed`, `finding`, or `waived` since spec 073), `unjudged-rules` lists each assessable loaded rule the run neither judged nor reused, `rule-digest` maps each loaded rule file to a digest of its rules' text, and `section-digest` maps each section of the design subjects to a digest of its text (AC7). A loaded rule in neither of the first two did not fire, as the spec's Resolved Questions decide. `rule-digest` is a field the spec did not name. A not-fired verdict leaves no entry to hold a rule-text hash, so without it a rule edited after a not-fired judgment would never be judged again, which is AC5's failure for most rules. Fields are written by `render_analysis` in `runtime/src/primitives/write_analysis.rs` and typed on `AnalyzeBlock` in `runtime/src/schema/primitives.rs`. A map or list that does not parse then makes `load_analyze_record` return `RecordLoad::Unreadable`, which `validate_record` in `validate_frontmatter.rs` reports as a hard fail: the record is undeterminable, never empty (Edge Cases).

### A stored verdict is current while four things match

1. **Design subjects.** The prior record's `analyzed-digest` entries for `spec.md`, `plan.md`, `data-model.md` and `scenarios/*.md` equal a fresh digest of those paths, with the same key set, and neither side lists one under `analyzed-unreadable`; or, where they differ, the sections the verdict concerns are unchanged (below). An `is_design_subject` predicate beside `is_analyze_subject` in `runtime/src/primitives/analyze_subjects.rs` selects them, and `subject_digest` takes it, as it takes `is_analyze_subject` and `is_review_contract` already. `tasks.md` and `review.md` stay in `analyzed-digest` for the gate and are ignored here (Resolved Questions). `spec.md` keeps `without_criterion_ticks`, so a tick moves nothing. A prior record with no `section-digest`, written before AC7, falls back to the whole files: any design-subject edit then makes every stored verdict stale (`subjects-changed`), as does an unreadable design subject on either side.
2. **Rule text.** The prior `rule-digest` entry for the rule's file equals the file's digest now: SHA-256 over each rule's ID, Statement and Verification in heading order, from the `RuleSection` fields in `runtime/src/primitives/rule_sections.rs` (`parse_rule_sections`, the one reading of what a rule is, which the exec `load_rules` in `runtime/src/interpreter/payload.rs` already uses). A rationale edit moves nothing. The granularity is the file, not the rule: see Trade-offs, where the per-rule alternative is costed.
3. **The rule was judged.** It is not in the prior `unjudged-rules`, and the prior record carries a `rule-digest` at all. A record without one predates this spec and yields no reusable verdict, as `freshness_of` treats a record with no digest as undeterminable rather than a match.
4. **The loaded rule-file set.** The rule files loaded now are exactly those the prior `rule-digest` names, or nothing is reusable and `verdicts.reason` is `rule-files-changed`: a Verification can yield to another rule "where `X` is also loaded", so a verdict turns on which files are loaded as well as on its own file (`BE-CACHE-002`; the owner's choice at this spec's review, 2026-11-12). `specs/system.md`, which 27 of the 308 rules' Verifications name, is not an input (the spec's Resolved Questions).

A rule file the prior `rule-digest` lacks, or one it names that is no longer loaded, changes the set (4), so every rule is judged. A stored verdict naming a rule no loaded file defines is dropped: `write-analysis` writes the map whole from the current rules, so a removed or disabled rule's verdict is never carried (Edge Cases). A citation into a deleted or renamed subject needs no check of its own, since its section is a changed one.

### A section is a heading's own text (AC7)

`section-digest` keys each section `<path>#<Heading>`: the heading's own text, from its heading line to the next heading of any level, by `heading_lines` in `runtime/src/primitives/resolve_anchor.rs`, so a heading in a fence or comment is content. The text before a file's first heading, frontmatter included, is keyed `<path>` alone, so every design subject has a key and its addition or removal shows. Headings of one file that read alike share one key, digested together in order, the equality `cite_resolves` already compares by. `spec.md` is read through `without_criterion_ticks`, as its whole-file digest is. Each digest is the first 16 hex characters of SHA-256: it detects change, and no reader trusts it for integrity. A section's own text, not the section with its subsections, because a subsection's edit would otherwise change every heading above it, the file's title among them, and one edit would mark the whole file changed. `section_digest` in `analyze_subjects.rs` takes the digests over the walk `subject_digest` makes, so the two read one subject set.

The changed sections are the keys added, removed or digesting differently since the prior record. A location (`cite`, `at`) is at an **unchanged section** when it names `<path>#<Heading>`, with a heading, whose key both digests hold alike; a location naming no section of both is never unchanged. With some section changed, each rule whose file is current and which the prior run judged stands as its verdict says:

- **Not fired:** judged again against the changed sections only, and still not fired when that judgment finds nothing.
- **`addressed`:** judged against the changed sections; the verdict carries forward when its `cite` is at an unchanged section and the judgment does not replace it, and otherwise the rule is not fired unless the judgment says it is.
- **`waived`:** judged against the changed sections, carried forward likewise, since its departure entry decides it (spec 073).
- **`finding`:** stands, unjudged, while its `at` is at an unchanged section; otherwise its rule is judged in full, since a finding cleared no other section (the spec's Resolved Questions, 2026-11-21).

A rule judged against the changed sections that the run does not judge is unjudged, never carried: the changed text is what nobody judged.

### A finding at an unchanged section holds nothing (AC7)

`rule_verdicts::demoted` decides it, for `write-analysis` and the exec tally alike: a `finding` passed for a rule whose prior verdict is not fired or `addressed`, current or judged against the changed sections, at an unchanged section. It is recorded as a contradiction alone, never stored as a finding and counted in no tier, and the rule keeps the verdict it carries, if any. A finding whose location is at no unchanged section counts, whatever the prior verdict: demotion needs proof that the text was judged before. On the interactive path the host knows the unchanged sections before it counts, since every section `verdicts.changed-sections` does not name is one, so it counts no such finding and passes it in `rule-verdicts`; under `ductus exec` `AnalyzeTally::record_assessment` asks `demoted` before counting. AC3's contradiction that also counts is what remains: a finding against a current not-fired or `addressed` verdict at a location that names no section.

### `rule_verdicts` is one library

`runtime/src/primitives/rule_verdicts.rs` (new, not a primitive) holds the currency decision, the citation check and the contradiction comparison, so the three callers cannot disagree. This is the arrangement `freshness_of` in `analyze_subjects.rs` gives the gate and `/{project}:review`'s `analyze` row: one function, two surfaces.

### Where the decision is made: a library, reached through an extended `discover-rule-files`

The currency decision is deterministic, so it belongs to the runtime (§runtime-boundary principle 2), not the host. The interactive host learns it from `discover-rule-files`, which step 5 and the Rules section of `framework/reference/analyze.md` already call with `all`, `rules` and `verification`. It gains an optional `feature` argument and, when set, a `verdicts` result block: `reusable` (each current fired verdict with its rule ID and verdict, a `waived` one also its attribution (spec 073), a `finding` also its stored `tier`, `at` and `message`, an `addressed` its `cite`), `judge` (the rule IDs to judge in full), `rejudge` (those to judge against the changed sections only), `changed-sections` (each changed section's key, in key order) and `reason` when the prior verdicts cannot be reused (`no-prior-verdicts`, `subjects-changed`, `rule-files-changed`, `record-unreadable`). The host judges the rules in `judge` in full and those in `rejudge` against `changed-sections`, and re-reports each `reusable` finding as any finding; a `reusable` `addressed` or `waived` verdict whose rule is also in `rejudge` stands unless that judgment replaces it, so the fired set step 14 reads keeps it. `reusable`, `judge`, `rejudge` and `changed-sections` grow with the rule library or the spec, so they go through `bounded_lists::place` as `process_decisions.rs`' lists do. The extension adds no registration site, where a new primitive costs the seven in `docs/developing-ductus.md` (registry, description, `#[tool]`, `dispatch_primitive` arm, `Command`, `runtime-tools.txt`, `result_sizes` case) and a regenerated allow block for every agent in `framework/bootstrap/configure/`.

Under `ductus exec` the walker calls `rule_verdicts` as a library, as `load_current_task` in `runtime/src/interpreter/payload.rs` already calls `read_tasks::compute`. `Walker::handle_assessments` in `runtime/src/interpreter/mod.rs` drops each rule whose verdict is current from `asked`, so AC1 holds on both paths, and keeps each rule in `judge` or `rejudge`. `LoadedRules` gains the reusable verdicts, and the walker emits a progress line naming how many it reused, so a skipped rule is visible in the stream. A reused finding still counts in the tier counts: `AnalyzeTally` adds a `record_reused` that counts it in its stored tier. The `assessSpecQuality` request is unchanged: it carries `spec.md`, and the tally places every finding there, so a finding at a section of `spec.md` unchanged since its rule's not-fired or `addressed` verdict counts in no tier (Trade-offs).

`verdicts` is computed only with `all`, `rules` and `feature`. Review's `discover-rule-files` walk binds `feature` from the context too, so a `feature` without `all` is not an error: it reads nothing and `verdicts` is absent, which a caller sees. A record that does not parse is reason `record-unreadable` with a notice, and `judge` holds every assessable rule, so it is never read as holding no verdicts and the call does not fail (`validate-frontmatter` hard-fails the record at step 2). One `place` call covers `rule-files`, `reusable`, `judge`, `rejudge` and `changed-sections`, so past the read size the file holds all five, `verdicts.reusable-count`, `verdicts.judge-count`, `verdicts.rejudge-count` and `verdicts.changed-sections-count` stay inline, and the nested block carries no top-level `-count` key.

### The exec response says whether a fired rule was addressed

`AssessSpecQualityResponse` in `runtime/src/schema/extensions.rs` gains an optional `addressed-by`, a `path#Heading` citation. `passed: true` with it is `addressed`, `passed: true` without it is not fired, and `passed: false` is a finding whose `message` and `location` the tally stores; for a rule the spec departs from, spec 073 records any fired answer as `waived` instead (see [073](../073-decided-rule-departures-are-recorded/spec.md)). The field is additive, so a host that sends none records every `passed: true` as not fired, which is the walk before this spec. `AnalyzeTally` keeps `verdicts` and `judged` and `bind`s them as `write-analysis`' `rule-verdicts` and `judged-rules`.

### `write-analysis` derives the rest

`WriteAnalysisArgs` gains `rule-verdicts` (this run's newly judged fired rules, CLI `--rule-verdicts-json FILE` as `findings` is) and `judged-rules` (every rule the run judged, not-fired ones included, repeatable `--judged-rule`). From them and the rule files it discovers itself, `write_analysis::run` derives:

- **The universe.** Every assessable rule in the directory `resolve_rules_dir` and `list_rule_files` give, under `all`, the set the exec walker's `derive_analyze_seeds` binds. A host that treats a file as unloadable still leaves its rules in the universe, so they are named unjudged: the failure is visible, never a shorter list.
- **Carried-forward verdicts.** Each prior verdict still current under the rule above is carried into the new map unless this run judged that rule, so a host cannot drop a reusable `finding` by not passing it. A rule judged against the changed sections keeps its carried `addressed` or `waived` verdict when the run passes none for it, or passes one `demoted` refuses to store.
- **`unjudged-rules`.** The universe less `judged-rules` less the carried-forward rules, plus each rule this run's `addressed` verdict cited badly; a rule owed a judgment against the changed sections that the run did not judge is among them. Its count is added to `rule-assessments-not-checked` in `by_reason`, as `count_constitution_gaps` adds the unresolved constitutions, so a caller cannot supply a total that contradicts the list. The count's meaning widens as the spec decides: it keeps 060's rules the walker could not ask about, and also counts the rules not judged.
- **`section-digest`.** `section_digest` over the feature directory at write time, as `analyzed-digest` is taken there.
- **A tier-count floor.** The run is refused when a tier's supplied count (the re-check's, before any release) is below its number of `finding` verdicts of that tier, since each stands for at least one live finding. The tier is the one stored on the verdict, the tier the finding was counted in, which the rule's text tier does not always give: a rule carrying MUST and SHOULD is MUST-tier by its Statement and can fail on its SHOULD clause alone, counted advisory, as 060 requires, so a floor on the text tier would refuse that record (owner, 2026-11-12). Under `ductus exec`, `AnalyzeTally::record_assessment` counts a finding in its rule's tier unless the Statement carries both keywords, where the host's severity stands, so a mislabelled single-tier finding is counted where its rule can fail rather than aborting the walk at the write (this spec's review). The stored tier is checked against the rule at write, so a floor cannot be met by mislabelling: a `finding` whose tier differs from its rule's text tier is refused, naming the rule and both tiers, unless the Statement carries both MUST and SHOULD, where either is accepted. Reused findings are the host's to count in their stored tier, and the exec tally does; the floor keeps an omission from dropping a failure from the count it was made in (`QUAL-CLAIM-001`).

A bare `unexamined` total, passed with no `unexamined-by-reason` as `framework/commands/analyze.md` step 21 passes it, is recorded under `unclassified` before the derived reasons are added, so the derived counts never replace the host's own unexamined targets and the total stays the breakdown's sum (`QUAL-CLAIM-001`, this spec's review); every bare total takes it, so one host input writes one record shape. The reason keys more than one module writes are constants in one place, the `REASON_*` constants of `runtime/src/primitives/write_analysis.rs`, which `runtime/src/interpreter/analyze_tally.rs` imports (`CFG-CONST-001`).

A verdict naming no assessable loaded rule, or a `finding` with a blank message, is refused before any write. A rule with a verdict is judged whether or not it is in `judged-rules`. A prior record whose rule fields do not parse reuses nothing and is overwritten, so every rule is judged or named unjudged, and its decisions are read as before; one whose frontmatter does not parse is refused, since its decisions could not be read (spec 058). The rule files the runtime itself could not read count under `rule-file-unreadable` at most once beside the host's count, taking the larger, since a walk counts the same files. The body's `## Contradictions` section follows `## Deferred to other specs`, and the Unexamined targets section names each rule left unjudged.

The write stays whole and atomic, and it is guarded against a lost update (`BE-TXN-002`): `write-analysis` takes a `ReadSnapshot` of `analysis.md` before any helper reads the decisions and rule verdicts it keeps, and renames the new record over it only while the file still holds those bytes, so of two concurrent runs the second to write fails with `changed-since-read`, writes nothing and is run again (066's data model, *The write is guarded*; Edge Cases).

### An `addressed` citation is checked by `write-analysis`

A citation is `path#Heading`: a design subject of the feature and a heading it contains. `rule_verdicts` resolves it with `heading_lines` in `runtime/src/primitives/resolve_anchor.rs`, the heading reader `resolve-anchor` and `read-section` share, compared by equality as `section_range` compares, since an explicit pair marks where the name ends. The host supplies the path, so it is contained before anything is opened: it names a design subject of the feature by normal path components only, never a `..`, root or absolute component, and a symbolic link or a file that is not regular is not followed, so a citation can reach nothing outside the spec's own design subjects (`BE-INPUT-004`). A citation naming a non-design subject, a file that is missing or unreadable, a heading the file lacks, or no citation at all is not stored as `addressed`: the rule joins `unjudged-rules`. The closed unexamined-reason set gains nothing (Resolved Questions). The check runs against the files as they are at write time, which `write-analysis` already treats as what the run read (`analyze_subjects::subject_digest` is taken there for the same reason).

### A contradiction is derived from the prior record

When this run judges a rule whose prior verdict is not fired or `addressed`, current or owed a judgment against the changed sections, `write_analysis::run` compares them. A new `finding` at an unchanged section is a contradiction alone (AC7, above). A new `finding` against a current one at a location naming no section is a contradiction too, and the finding is recorded in its tier as any finding is (AC3). The result gains `contradictions`, each with its rule, earlier verdict, `at`, `message` and `counted` (whether the finding also counts), bounded through `bounded_lists::place` as the other result lists are, its count inline in both forms (`BE-PAYLOAD-001`, this spec's review), and the body a `## Contradictions` section, `*None.*` when empty, so step 22 reports it. The contradiction itself holds nothing and appears in no count (Resolved Questions). One arises only when a judgment reaches text the run did not ask it to, which needs a host that judges outside `judge`, or outside `changed-sections` for a rule in `rejudge`, so no flag forces a re-judge here.

### The completion gate holds `done` while a loaded rule is unjudged

An unjudged rule is an obligation nobody has verified, and an edit to the section a stored MUST finding names, followed by a run judging nothing, would otherwise move that finding out of `blocking-findings` into `unjudged-rules` with nothing gating it. `check-review-gate` blocks with `unjudged-rules` (`unjudged_rules_block` in `runtime/src/primitives/check_review_gate.rs`) when `analysis.md` names any rule there. The block follows `analyze-stale`, since a stale record is re-run first, and names the rules with guidance to run `/{project}:analyze`, which judges only them while the rest of the verdicts are current. A record with no `unjudged-rules` field, written before this spec, blocks on nothing new; an unreadable one is undeterminable already. 066 owns the gate, so its data model lists the check (owner, 2026-11-12).

### Primitive interface changes, classified under `BE-COMPAT-001`

The runtime is pre-1.0 (`runtime/Cargo.toml`'s `version`), so a breaking change ships in a minor release, as 057, 058 and 063 did.

- **Additive.** `discover-rule-files`' optional `feature` and its `verdicts` block, returned only with `all`, `rules` and `feature`, and the block's `rejudge`, `changed-sections` and their counts (AC7). `write-analysis`' optional `rule-verdicts` and `judged-rules`, and its result's `contradictions`, each with `at`, `message` and `counted` since AC7, `form`, `contradictions-count` and `lists-file`. The `assessSpecQuality` response's optional `addressed-by`. The record's four fields, and the `unexamined-by-reason` key `unclassified`, for a reader that keys the map rather than enumerating it.
- **Breaking, within major version zero.** `check-review-gate`'s new `blocked-by` value `unjudged-rules`, and `verdicts.reason`'s `rule-files-changed`, for a consumer that matches either set exhaustively. `write-analysis`' new refusals: a verdict naming no assessable loaded rule, a blank `finding` message, a tier count below its `finding` verdicts, and a `finding` in a tier its rule cannot fail in. And behavior changes of existing calls: a host that passes no `judged-rules` now writes a record naming unjudged every assessable rule whose verdict is not current, which holds `done` at check 13 until a run judges them; and since AC7 a design-subject edit no longer stales every verdict of a record carrying `section-digest`, `subjects-changed` arising only for one without it or an unreadable subject, and a `finding` at an unchanged section is no longer stored or, under `ductus exec`, counted.

### The constitution pays about 160 bytes

The four fields cost the Analyze record row of `framework/constitution.md` about 160 bytes, against `scripts/lint-governing-size.sh`'s 50,000-byte ceiling: the first three about 113 (49,616 bytes then, `wc -c`, 2026-11-12), and `section-digest` 45 (49,021 to 49,066 bytes, `wc -c`, 2026-11-21), leaving 934. No cut is needed.

## Trade-offs

- **Rule text is hashed per file, not per rule.** The Resolved Questions name a hash of the rule's own text, and a not-fired rule has no entry to hold one. A per-rule hash for every loaded rule costs `(ID + 12 hex)` each: about 8.8 KB per record at this repository's 310 rules, about 640 KB across its 73 records, against 1,074 bytes and 78 KB for 12 file digests (measured 2026-11-12 over `framework/rules/` and `specs/*/analysis.md`). That is the cost the Resolved Questions rejected for a verdict-per-rule map. The price of the file digest is that editing one rule judges that file's rules again in full, not only it, and since AC7 a design-subject edit judges each rule against its changed sections only, so a rule edit is the one input that judges a whole file's rules in full. It is the rarer input: from 2026-10-22 to 2026-11-21, 60 commits touched `framework/rules/*.md` against 1,260 touching a design subject under `specs/` (`git log --format=%h` over each path set, counted 2026-11-21), and of the release tags in that window only `ductus-v0.60.0` changed a rule's Statement or Verification, before any record carried a `rule-digest`; between it and `2844f328` none changed, compared rule by rule, so a per-rule hash would have spared no judgment there.
- **`finding` verdicts store their message and location.** AC1 forbids asking about a rule with a current `finding`, and the next run must still report it in its tier, so the message and the tier it counted in stay in the record. The spec's 26 to 61 bytes per fired rule held for `addressed`; a `finding` entry carries about 100 more.
- **A fix re-judges every rule against the sections it edited.** A chore fix edits a design subject, so the re-check (step 20) judges every quiet or addressed rule against the changed sections, and a finding's rule in full when the fix touched its section. Skipping the first pass's verdicts there would judge a fix's own effects against stale text.
- **Under `ductus exec` a rule owed a judgment against the changed sections is asked about whole.** The `assessSpecQuality` request carries `spec.md` and no section list, so its host judges `spec.md` whole and the tally counts no finding at an unchanged section. A `changed-sections` field on the request would narrow what that host reads, at the same request count, and would change 022's request shape for it; the walk asks about the same rules either way. A rule whose changed sections all lie outside `spec.md` is still asked about, since the walker cannot tell what its host reads beyond the request.
- **`section-digest` grows with the headings, not the rules.** Measured 2026-11-21 over the 76 feature directories under `specs/`, counting for each the keys `file_sections` would write over `spec.md`, `plan.md`, `data-model.md` and each scenario (one per file and one per distinct heading text outside fences and comments, by a script replicating its rules) and the bytes of the rendered block (key quoted, two-space indent, 16-hex digest): a median of 38 keys and 2,404 bytes a record, at most 666 keys and 53,030 bytes in one, 350,908 bytes in all. `check-artifact-size` does not measure `analysis.md` (`FIXED_SUBJECTS` in `runtime/src/primitives/check_artifact_size.rs`), and the runtime's `load_analyze_record` parses it whole. The alternative, a digest per verdict of the sections it read, would need the judge to report what it read, which a not-fired verdict does not.
- **The `rule-assessments-not-checked` count can overlap.** A step whose prose names no tier still records its one target under 060's rule, beside the unjudged rules `write-analysis` now names. The state is a defect, and removing the walker's call would change 060 for no reader.
- **The fired-rule fraction is bounded, not measured.** Measured 2026-11-12 with the release binary, from a scratch copy of this repository under its own `git init`, `ductus exec analyze` over three `done` specs (`001-system-spec-templates`, `021-runtime-boundary`, `034-performance-backend-rules`), a script answering `passed: true` to each request, since no LLM host was available. Denominator, the rules the walk loaded: 310 asked of 310 in 12 files (228 MUST-tier, 82 SHOULD-tier); the second walk of each asked 0 and said it reused 228 and 82. The records came to 2,603 to 2,904 bytes in all, with 12 `rule-digest` lines (64-hex digests, about 1.1 KB) and no verdict: the cost when nothing fires. How many rules fire needs a host's judgments and is unmeasured. Its bound is the 73 `analysis.md` records in the tree at that commit: `blocking-findings` plus `advisory` per record has median 0, mean 1.73 and maximum 20, 46 of 73 at 0, counted after dispositions, so a finding fixed in the run is missing, and counting findings no rule raised, so it bounds neither side exactly. At about 100 bytes a `finding` entry, 20 is about 2 KB, and the map would approach a full one only with rules fired in the hundreds. The count of `addressed` verdicts stays unmeasured, since no record stores one.
- Rejected: a new `assess-rules` primitive, for the registration sites above; letting the host assemble the list from `discover-rule-files` and a stored map, which leaves the currency rule to every host and every session.
