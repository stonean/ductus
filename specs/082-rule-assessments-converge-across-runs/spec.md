# 082 — Rule assessments converge across runs

`/{project}:analyze` records a verdict for each loaded rule it assesses, against the subjects it judged. A later run re-judges a rule only when its subjects changed. A record that judged fewer rules than were loaded says so on every path, not only under `ductus exec`.

> **Signpost:** [073 — Decided rule departures are recorded](../073-decided-rule-departures-are-recorded/spec.md) adds a third verdict shape, `waived`, to the rule-verdict map for a rule the spec's departure entry names; the data model carries it.

## Motivation

An adopter reported that analyze's rule assessment did not converge. The spec was a backend feature spanning three repositories, assessed against eight rule files holding 141 rules. Three analyze runs over spec text that had stood unchanged for weeks found 10 new rule findings, then 8, then 4. Each would have fired on the first run. Each round cost a follow-up task, spec and plan edits, owner approvals, a commit, a review and another analysis. The third converged only because the host listed every rule's Verification by hand and judged them all in one pass. Nothing in the command or the record required that. The report arrived beside the one [081](../081-reviews-and-checks-follow-what-changed/spec.md) answers, and the owner moved this part here on 2026-11-11.

Read at `6158d7df`, the framework had these gaps:

- **Only findings were stored.** Steps 11 and 12 of `framework/commands/analyze.md` asked the host to judge every loaded MUST-tier and SHOULD-tier rule whose Verification trigger fired against the spec. `write-analysis` stored deferred and waived findings under `decisions:`, and `process-decisions` matched those alone. A rule judged not to fire, or to fire and be addressed already, left no trace, so every run re-judged every rule, and a different session could judge differently over the same text.
- **Exhaustiveness was unchecked on the interactive path.** `write-analysis` took `unexamined` from the caller. `rule-assessments-not-checked` counted only the rules steps 11 and 12 could not ask about: one with no Verification, or with no MUST or SHOULD keyword. A host that judged 30 of 141 rules wrote the same record as one that judged all 141. Under `ductus exec`, [060](../060-exec-analyze-assesses-each-loaded-rule/spec.md) had the walker send one request per loaded rule. Interactively nothing listed the rules for the host, although `discover-rule-files` with `rules` and `verification` could, since spec 080.

> **Signpost:** a miss deferred here. Spec 081's reopening closed at `6d583778` over spec 079's AC1 bound, with one review and two analyses (`measure-reopenings --since 2026-11-11` at `932d10e0`). Its first analysis judged a keyword-filtered subset of the 310 loaded rules' Verification triggers and missed `BE-PAYLOAD-001`, and its record could not say so. The owner deferred the miss's cause to this spec on 2026-11-11, since AC2 would have recorded each rule left unjudged. 079 records the miss as its task 34.

## Acceptance Criteria

- [x] AC1: A fixture spec analyzed twice with no edit between the runs records identical rule verdicts. The second run asks the host about no rule whose stored verdict's subjects are unchanged.
- [x] AC2: A run that judges fewer rules than were loaded records a non-zero `rule-assessments-not-checked` naming each rule left unjudged, on the interactive path as under `ductus exec`. A run that judges every loaded rule records zero, and a fixture proves both directions.
- [x] AC3: A verdict that changes from not firing, or from addressed, to a finding while its subjects are unchanged is recorded as a finding of its rule's tier and also reported as a contradiction naming the earlier verdict; the contradiction alone holds nothing. **Superseded in part (AC7, owner, 2026-11-21):** such a verdict at a section unchanged since the earlier one is recorded as the advisory contradiction alone, never as a finding.
- [x] AC4: Each new analysis-record field is in the constitution's audit-record table (§text-first-artifacts) and in 066's data model, which the record `write-analysis` writes follows; no analysis template exists to carry it.
- [x] AC5: A verdict stored before its rule's Statement or Verification changed is judged again, and a fixture that edits a rule between two runs over an unchanged spec proves it.
- [x] AC6: An `addressed` verdict whose citation does not resolve is recorded among the rules left unjudged, never as `addressed`, and a fixture proves it.
- [x] AC7: A stored verdict is current while the sections it concerns are unchanged: `analysis.md` records a digest of each heading's section of every design subject; a run judges a rule whose verdict is not-fired or `addressed` again only against the sections changed since that verdict, and a verdict citing a section again when that section changes, a `finding` in full, while a `finding` whose section is unchanged stands unjudged; and `write-analysis` records a finding at a section unchanged since that rule's not-fired or `addressed` verdict as an advisory contradiction that holds nothing. A fixture that edits one section of `plan.md` between two runs leaves a not-fired verdict current, and fails with the section digests removed.

## Edge Cases

- **A rule no longer loaded** (its file removed or disabled): its stored verdict is dropped, never carried as a judgment of a rule nobody loaded, and since the loaded rule-file set changed, every other rule is judged again (Resolved Questions).
- **A rule newly loaded**: it has no stored verdict, so the run judges it or names it unjudged; a new rule file also changes the loaded set, so every rule is judged again.
- **A design subject added or removed** (a first `plan.md`, a deleted scenario): its sections are added or removed, so every rule is judged again against them, as against any changed section.
- **A citation into a subject later deleted or renamed**: its section is changed, so the verdict resting on it is not carried forward, and the rule is unjudged until judged again.
- **A verdict map or unjudged list that does not parse**: the record is undeterminable, as any unparseable audit record is (§text-first-artifacts), never read as holding no verdicts.
- **Two runs writing the record**: `write-analysis` writes it whole and atomically, and only while `analysis.md` still holds the bytes it read, so a run whose record another run replaced after it read is refused with `changed-since-read`, writes nothing and is run again; the record that stands is what the next run reads (066's data model, *The write is guarded*).

## Resolved Questions

- **Which subjects does a verdict's digest cover?** The spec's design subjects whole, `spec.md`, `plan.md`, `data-model.md` and each scenario, never `tasks.md`, `review.md` or `analysis.md`, by the record's existing per-path `analyzed-digest` entries for them, together with a hash of the rule's own text (its Statement and Verification), kept per rule file, so a rule an upgrade edits is judged again with the rest of its file: a not-fired rule has no entry to hold a hash of its own, and a hash for every loaded rule would cost about 8.8 KB a record at 310 rules, where the twelve files cost about 1 KB (the plan's Trade-offs; the owner, 2026-11-12). A stored verdict is current while all of them match and the set of loaded rule files is the one the record's digests name, since a Verification can yield to another rule "where `X` is also loaded" and so turn on which files are loaded: adding or removing a rule file re-judges every rule once (`BE-CACHE-002`, the owner, 2026-11-12, at 082's review). `specs/system.md`, which 27 of the 308 rules' Verifications name (each rule's `**Verification:**` paragraph in `framework/rules/*.md`, counted 2026-11-21), is not part of the key: an edit there would otherwise judge every rule of every spec again, since AC7 against its changed sections only, while keeping it out leaves those 27 rules' stored verdicts current over an edited `system.md` until their rule file or the loaded rule-file set changes. That part of the finding is waived with this reason (the same decision, kept by the owner with the corrected count, 2026-11-21). Any design-subject edit re-judges every rule, which is what every run does before this spec. Rejected: the sections a verdict cites, since a `not fired` verdict, the bulk of them, cites none and would fall back to whole files anyway, at a second digest mechanism; and every `.md` under the feature, since a `tasks.md` tick or a `review.md` rewrite would then re-judge every rule (the agent's recommendation, adopted by the owner, 2026-11-12). **Superseded (AC7):** a verdict is current while the sections it concerns are unchanged, each heading's section of a design subject digested on its own, and a run judges a rule only against the sections changed since its verdict. An adopter reported that its third analysis judged a sentence its plan had held unchanged through two earlier analyses a MUST and sent the spec back to `/{project}:implement` (the adopter's report; its repository is out of reach); every task between those analyses had edited the plan elsewhere, and any design-subject edit judged every rule again. The objection above, that a `not fired` verdict cites no section, is answered by judging a rule against the changed sections rather than against the sections its verdict cites (the agent's recommendation, adopted by the owner, 2026-11-21). It reverses spec 079's research decision of 2026-11-16 that a reopening judges every rule again, annotated there: of the two real MUST findings that decision cites, 080's `CFG-CONST-004` lay in a `plan.md` unchanged between its two records and would now be a contradiction alone (the owner kept AC7, 2026-11-21). **Superseded in part (spec 088; the agent's recommendations, adopted by the operator, 2026-11-25 and 2026-11-26):** a rule file whose content changed has its rules compared one by one with its copy at the record's `analyzed-against`, so only the rules whose own text changed, and each rule naming one, are judged again, while the record keeps its hash per file.
- **Does a `done` flip cost a spec its stored verdicts?** Only for an analysis run while the spec is `done`. `spec.md`'s digest covers its frontmatter, `status:` included, and normalizes only the criteria's ticks (`subject_digest` in `runtime/src/primitives/analyze_subjects.rs`), so an analysis of a spec that is `done` reports `subjects-changed` and judges every rule again, as one of 073 would after `878e8b3c`. A reopen by `set-status` restores the bytes the analysis read, so its verdicts are current again: 073's `spec.md` with `status:` set back to `in-progress` is byte-identical to the copy its analysis read at `1c8d281d` (sha256 of both `d7832739…`, measured 2026-11-13), and a reopen by a criterion, scenario or data-model edit changes the subjects anyway. No gate requires an analysis of a `done` spec, so the digest keeps `status:`; the cost lands on a run that analyzes one anyway, as `/{project}:analyze --all` does every feature directory: it judges all 310 rules again for each `done` spec analyzed before its done flip, 40 of them on 2026-11-13. Rejected: normalizing `status:` out as the ticks are, which changes every stored digest at once, staling each in-progress spec's current analysis and every stored verdict with it, for a reuse only such a run asks for (the agent's recommendation, adopted by the owner, 2026-11-13, and kept by the owner when this cost was corrected the same day). **Since AC7:** the flip changes only `spec.md`'s text before its first heading, so such a run judges each rule against that section alone.
- **How is a stored `finding` judged once sections change?** It stands, unjudged, while the section its `at` names is unchanged, and when that section changes its rule is judged in full: a not-fired or `addressed` verdict cleared every other section, but a finding cleared none, since the judge reports one location per rule, so a rule failing in two sections stores one. A second failure of the same rule is then found at that full judgment, the run its fix needs anyway. Rejected: judging it against the changed sections like any other rule, which, once the stored location is fixed, never judges a second failure in an unchanged section again; and judging it in full on every run in which any section changed, a full judgment a run per standing finding (13 in this repository's 37 records holding verdicts, at most 2 in one, counted 2026-11-21) that lets a finding move or vanish over unchanged text (the agent's recommendation, adopted by the owner, 2026-11-21).
- **Does an `addressed` verdict cite what addresses the rule?** Yes, and `write-analysis` checks it: each `addressed` verdict names the section or anchor of a design subject that addresses the rule, and one whose citation does not resolve, as `resolve-anchor` resolves it, is not stored as `addressed` but recorded among the rules left unjudged, so the closed unexamined-reason set gains nothing. An uncited `addressed` is a judgment a later run cannot test and a different session can flip. Rejected: an optional citation, which leaves that flip; and a required but unchecked one, a check that cannot run looking like one that passed (the agent's recommendation, adopted by the owner, 2026-11-12). It depends on the record naming a missing verdict rather than being refused (the last question).
- **Does a contradiction block `done`?** No, it is advisory, and it never replaces the finding: a verdict that turns from not firing, or from `addressed`, to a finding while its subjects are unchanged joins its rule's tier as any finding does (a MUST Blocking, a SHOULD Advisory), and the report and the record's body add a contradiction note naming the earlier verdict. With current verdicts reused, a contradiction arises only when a host judges a rule whose verdict is current, which neither path asks of it: the exec walker sends no request for such a rule, and no flag forces a re-judge, so AC3's case reaches `write-analysis` only from a host that judges outside `discover-rule-files`' `judge` list. Rejected: a contradiction as a Blocking finding of its own, which would hold `done` on a judge's changed answer over unchanged text rather than on a defect in it, at an analysis run per occurrence; and a note replacing the finding, which would drop a MUST failure from `blocking-findings` (the agent's recommendation, adopted by the owner, 2026-11-12). **Superseded in part (AC7):** a finding at a section unchanged since that rule's not-fired or `addressed` verdict is the advisory contradiction alone and counts in no tier, so text a run has judged is not judged into a blocker by a later one; a finding at a changed section counts as before (the agent's recommendation, adopted by the owner, 2026-11-21).
- **Where do the verdicts live?** In `analysis.md`'s frontmatter, as a map of the rules that fired, each with its verdict (`addressed` with its citation, or `finding` with its message and location, so a current finding is reported again without re-judging, about 100 bytes more an entry; the owner, 2026-11-12), beside a list naming each loaded rule left unjudged; a loaded rule in neither did not fire. The record so grows with what fired, not with the rule library: about 26 to 61 bytes per fired rule (an ID averages 11.75 characters over this repository's 310), and 14 per unjudged one. Measured at `94e5b151`: the largest record is 19,901 bytes and the 73 records total 226,920; `check-artifact-size` does not measure `analysis.md` (`FIXED_SUBJECTS` in `runtime/src/primitives/check_artifact_size.rs`). How many fire per spec, counted at `b7b07500` as the entries under `rule-verdicts:` in each spec's `analysis.md` frontmatter, over the 36 of 76 records that carry the key: 1 at least, 10 at the median, 12.4 on average and 58 at most (022's, of the 310 rules it judged), so the map stays far from a full one. Rejected: a map of every loaded rule, about 590 KB more across this repository's 73 records at 26 bytes for 310 rules, for what absence already says; the record's body, which would put state the next run reads where the body stays prose (§text-first-artifacts), unlike `decisions:`; and a sibling file, a third record kind (the agent's recommendation, adopted by the owner, 2026-11-12).
- **Does `write-analysis` refuse a record missing a verdict for a loaded rule?** No: it records each loaded rule left unjudged, as AC2 says, since a refused write leaves no record at all and a partial run must read as partial (`QUAL-CLAIM-001`). The count stays `rule-assessments-not-checked` in `unexamined-by-reason`, a reason-to-count map (066), and the names go on the unjudged-rules list beside the verdict map. Under `ductus exec`, where the walker asks about every loaded rule without a current verdict (060, as this spec narrows it), the count keeps its meaning, the rules it could not ask about; on the interactive path it also counts the rules the host did not judge (the agent's recommendation, adopted by the owner, 2026-11-12).
- **Does the finding tier's wording in `framework/reference/analyze.md` §Stored rule verdicts need rewording?** No, and the observation is waived with this reason. Twice a rule judge recorded a MUST rule's finding at `should`, reading "the tier it is counted in (`must` for Blocking, `should` for Advisory, the finding's own severity)" as leaving the tier to the judge: `BE-PAYLOAD-001` in 057's first pass, which `3ed84fe1` fixed, and `CFG-CONST-004` in 080's run recorded at `2d5ca882`. `write-analysis` refuses a `finding` whose tier a Statement carrying one keyword cannot fail in, tested both ways (`a_finding_labelled_in_a_tier_its_rule_cannot_fail_in_is_refused`), so no record holds the mislabel, and each costs a refused write and a corrected tier; analyze step 11 already says a rule's tier is its Statement's keyword. Rejected: reopening this spec to reword the sentence, which owes a review, a pre-done verification and an analysis judging all 310 rules for what the refusal already enforces (the agent's recommendation, adopted by the owner, 2026-11-16).
- **Why split from 060-exec-analyze-assesses-each-loaded-rule:** 060 makes the exec walker ask about each loaded rule; this spec makes a verdict persist and converge across runs on both paths, which adds the analysis record's verdict fields, `write-analysis`'s derivation and the constitution's audit-record row. The owner placed it in a spec of its own on 2026-11-11, rejecting a scenario on 060 because it widened 060's subject from the exec walker to the interactive path (081's Resolved Questions). The two share the exec walker's request and tally code, which this spec's `cross-spec-impact:` on 060 covers.
