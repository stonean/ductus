# 029 — Bootstrap Runtime Auto-Detect and Wire

`/ductus` should detect the `ductus` runtime at the start of a bootstrap run, wire its MCP server into the project when the binary is present but unregistered, and tell the user that doing so reduces token use. The goal is to stop first-time adoptions from exhausting their token budget on the markdown-only reference path when a deterministic path was actually available.

> **Signpost (post-031, post-032, post-048):** the State-B auto-wire described here rested on two assumptions that no longer hold — that every agent discovers a project-committed MCP file, and that writing one aborts the run. `framework/bootstrap/ductus.md` §MCP registration is the canonical record of the first; this spec points at it rather than restating it.
>
> - [031-agent-mcp-wiring](../031-agent-mcp-wiring/spec.md) made MCP discovery a **per-agent** property rather than a layout-derived one, and split State-B registration on a `mechanism` column: a `write-file` agent gets its MCP file written, a `surface-instruction` agent gets **no** file and a one-line registration command surfaced instead.
> - [032-opencode-agent](../032-opencode-agent/spec.md) added OpenCode as a **second** `write-file` agent, so neither side of that split is a single agent any more — `write-file` is Claude, OpenCode and, since `064-pi-host-support`, Pi, whose file is an extension bridge rather than an MCP config; `surface-instruction` is Auggie and Antigravity.
> - [048-govern-acquired-runtime](../048-govern-acquired-runtime/spec.md) removed State B's abort; its scenario `state-b-continues-in-session` is where that decision lives. The **Post-completion note** at the foot of this spec carries the rest of 048's amendment.
>
> The permission write is unchanged. The detection mechanism's binary probe changed under 048, and State A gained a version check (Post-completion note).

## Motivation

On a first-time adoption, the bootstrap walks the markdown-only reference path — `curl`, `tar`, byte-compares, and a hand-authored scaffold script — because the [ductus runtime](../022-deterministic-runtime/spec.md) is not registered for the agent session. The model interprets a ~20k-token procedure step by step and can run out of tokens before the install finishes. This was observed with the [antigravity layout](../028-antigravity-agent/spec.md).

The failure is not that `ductus` is missing — the binary may already be installed globally and on `PATH`. The failure is that [`/ductus`](../003-bootstrap-automation/spec.md) deliberately does **not** scaffold the MCP wiring (it is documented as a separate, manual install), so the agent session starts with no `ductus` MCP tools and has no deterministic path to take even though one was one config file away.

MCP servers are loaded at session start. Writing the wiring file mid-run therefore cannot help the running session — only the next one. So the fix is not "use the runtime now"; it is "wire the runtime, tell the user, and let the next session run cheaply." This is the same shape as the existing **ductus.md Self-Update Check**, which already writes a fresh file and aborts with a "start a new session and re-run" instruction. Both are restart-requiring pre-flight concerns, so this feature unifies them into a single pre-flight phase (see **Pre-flight Phase**) — the user restarts at most once even when both fire.

As 029 shipped, the markdown-only path stayed first-class per [§runtime-boundary](../021-runtime-boundary/spec.md) when `ductus` was absent; 048 removed that state (Post-completion note), and a missing binary is now acquired.

## Pre-flight Phase

`ductus` detection and the existing **ductus.md Self-Update Check** run as a single pre-flight phase — after the cheap **Permission Setup** seed (so the binary probe is pre-authorized) and before pre-run migrations and the archive fetch. Both checks can independently require the session to restart: the self-update check to load a fresh `ductus.md`, ductus detection to load the MCP server. The pre-flight phase runs both checks and accumulates every restart-requiring write (a fresh `ductus.md` and/or the ductus wiring and permission entries) into a pending-restart set. `048-govern-acquired-runtime` then made the set's two contributors **non-equivalent**, and they are now inspected separately: a stale `ductus.md` aborts immediately, because the run must not proceed on instructions it has just replaced, while State-B wiring does **not** abort — the binary is on disk and every remaining primitive is reachable through the CLI, so the run continues and the wiring notice rides the **Closing restart** at the end. If neither check requires a restart, the run proceeds past pre-flight normally. The user still restarts at most once regardless of how many pre-flight concerns fired, except a never-wired Pi adopter whose run aborts on a stale `ductus.md`: Pi's bridge is written only after the archive is extracted, which the aborted run never reaches, so that adopter restarts once more after the run that writes it (`064-pi-host-support`).

Within pre-flight, `ductus` detection resolves to exactly one of three states.

### Detection mechanism

Two independent probes resolve the state:

- **Tool-inventory introspection (State A).** The agent inspects its own available-tool inventory for any `ductus`-namespaced MCP tool — `mcp__ductus__*` on Claude Code, `mcp:ductus:*` on Auggie and Antigravity, a `<server>_<tool>` name under the `ductus*` prefix on OpenCode (`032-opencode-agent` verified the prefix glob and deliberately left the exact separator unpinned), and a `ductus__*`-prefixed extension-bridge tool on Pi (`064-pi-host-support`) — counting deferred or lazily-loaded tool names as present. This needs no shell and no permission; the agent always knows its own tools. Any match is State A.
- **Binary probe (State B vs. State C).** Only when introspection finds no `ductus` tool, a shell probe runs. As 029 shipped it was a `command -v ductus`-equivalent that distinguished an installed-but-unregistered binary (State B) from an absent one (State C); since `048-govern-acquired-runtime` it is the store probe `~/.ductus/bin/ductus --version`, and a missing binary is acquired (Post-completion note). There is no non-shell way to detect this — a tool that could answer "is ductus installed" would itself put the session in State A. The probe is seeded into the **Permission Setup** pre-grant so routine runs do not prompt for it, on every agent whose seed grants the runtime CLI; Antigravity's seed carries no CLI entry.

As 029 shipped, a probe the host could not run, or the user denied, classified the run as State C. A false State C was harmless — it cost nothing beyond the behavior before 029 (no auto-wire; manual wiring stayed documented) — so the gate never hard-failed on a locked-down host. Since 048 such a run classifies as State B and acquires (Post-completion note).

### State A — runtime live this session

The `ductus` MCP tools are callable in the current session. The bootstrap takes the deterministic primitive path for the rest of the run and emits no detection message.

A host that lists MCP tool schemas lazily (e.g., Claude Code surfaces tool names in a deferred-tool reminder before exposing their schemas) is still in State A — the runtime is registered. The gate must treat lazily-listed `ductus` tools as live, not absent, and fetch the schema through the host's mechanism rather than falling through to a lower state.

### State B — binary present, not wired

No `ductus` MCP tools are available to the session. As 029 shipped, State B also needed a `command -v ductus`-equivalent probe to find the binary; since 048 a missing binary is acquired first. The bootstrap, in order:

1. Registers the runtime per the agent's MCP `mechanism`, writing a `write-file` agent's file additively (see **MCP Wiring**). As 029 shipped this was a per-layout file; since 048 the run first acquires the binary and materializes its pointer (`framework/bootstrap/ductus.md` §State B — runtime not live: acquire, wire, restart).
2. Adds the permission entries the agent needs to call the `ductus` tools (see **Permission Setup**).
3. Contributes a notice that **names every file it wrote** (the wiring file and the settings file), telling the user that `ductus` was wired and that it reduces token use. As 029 shipped, that notice rode a single pre-flight abort; `048-govern-acquired-runtime` moved it to the **Closing restart** emitted after the run's work completes, and the restart it asks for is for the MCP tool surface rather than for unfinished work. On a run a stale `ductus.md` aborts, which never reaches the Closing restart, the abort carries the notice instead.
4. The run **continues**. `048-govern-acquired-runtime`'s scenario `state-b-continues-in-session` established why: the binary is on disk and the CLI is permission-seeded, so every remaining primitive is reachable as `.ductus/bin/ductus <primitive>` and stopping here would defer the archive fetch, the migrations and the scaffolding to another session for nothing. A stale `ductus.md` is the only pre-flight contributor that still aborts.

The only writes State B performs are the additive MCP-wiring entry and the additive permission entries (`048-govern-acquired-runtime` added the store acquisition and the pointer alongside them). State B never triggers a restart mid-run: when a stale `ductus.md` aborts in the same phase, its notice carries State B's file list too, and otherwise the wiring notice waits for the Closing restart.

State B issues **no separate consent prompt** before writing. The writes are additive and idempotent, and silent like the **Permission Setup** writes, matching the procedure's no-extra-prompts rule; the notice's file list is the disclosure, and the user reverses any change through git (for tracked files) or by deleting the additive `ductus` entry. There is no opt-out flag for auto-wiring — it is deliberately out of scope for this spec.

### State C — binary absent

The `command -v ductus`-equivalent probe fails — or cannot run because the host grants no shell or the user denies it. As 029 shipped, the bootstrap proceeded on the markdown-only path and emitted one tip line pointing at the README Runtime section; 048 removed this state (Post-completion note).

## MCP Wiring

The wiring target is **per-agent, not layout-derived** — `framework/bootstrap/ductus.md` §MCP registration is the canonical table, and §Derived values deliberately carries no MCP row (`031-agent-mcp-wiring`). Only a `write-file` agent has a file written: `.mcp.json` at the repo root for Claude, the `mcp` block of the committed root `opencode.json` for OpenCode (`032-opencode-agent`), and for Pi the `.pi/extensions/ductus.ts` extension bridge, copied from the framework archive once it is extracted (`064-pi-host-support`). A `surface-instruction` agent — Auggie and Antigravity, whose MCP config lives outside the repo — gets **no** file; `/ductus` surfaces a one-line registration command for the user to run once per machine. Where an MCP config is written, the entry registers the server as `ductus` running the runtime's MCP subcommand; Pi's bridge spawns that subcommand itself.

The write **updates an existing configuration in place — it never replaces or truncates the file.** It is additive and idempotent:

- An existing wiring file with other `mcpServers` entries keeps every one of them, and every other top-level key; only a missing `ductus` entry is added under `mcpServers`.
- An existing wiring file that already contains a `ductus` entry is left unchanged — re-running does not duplicate or overwrite it.
- An existing wiring file that has no `mcpServers` key gets the key added with just the `ductus` entry, preserving all other top-level keys.
- A missing wiring file is created containing just the `ductus` entry.
- An existing wiring file that is **not valid JSON is left untouched** — the gate skips wiring, warns the user to repair it, and the run continues through the CLI; the next run wires it once the file parses. A hand-maintained config is never clobbered.

Reversal of the wiring follows the written file's tracking status. The two `project-committed` targets — Claude's repo-root `.mcp.json` and OpenCode's root `opencode.json` — are committed repo files, so `git restore` applies to either. Pi's bridge is `project-local` and gitignored, so deleting it reverses it, and the next `/ductus` run writes it again. A `surface-instruction` agent has nothing to reverse here, because `/ductus` wrote no MCP file: the user undoes the registration they ran themselves, in their own home config.

Because the write is idempotent, State B is self-limiting: once it has run, the next session is either State A (the entry took effect) or — if the binary was removed between runs — State B again, which re-acquires it.

Wiring is triggered by the binary's presence alone; the gate performs **no version-compatibility check**. This follows [spec 022 §Versioning enforcement](../022-deterministic-runtime/spec.md), which deliberately rejects startup version comparison and refuse-on-mismatch in favor of lockstep tagged releases plus the runtime's own parse-error path. A too-old wired `ductus` surfaces through that runtime parse error on the next session, and any failing primitive falls back to that step's shell specification — so the gate has no reason to second-guess the binary's version. **Superseded in part by `048-govern-acquired-runtime`:** a run now compares the runtime with the framework's pin before it wires. Acquisition replaces a store binary at another version, State A re-acquires a live runtime that is stale, and a `[runtime] path` at another version is wired with a warning, so a too-old store binary no longer reaches a session. Spec 022's decision still governs the runtime itself, which compares no versions at startup.

## Permission Setup

In State B the agent's settings must also grant permission to call the `ductus` MCP tools, whether or not a wiring file was written (`framework/bootstrap/ductus.md` §State B step 4 makes the write the same for every `mechanism`; Pi has no permission entries), so the next session can use the deterministic path without a permission prompt per tool. These entries are added to the same per-layout settings file the existing **Permission Setup** section manages, using the additive rules of its merge step: add only missing entries, never remove, reorder, or overwrite entries the user or `/{project}:configure` previously added.

Separately, the binary probe used by pre-flight detection is added to the bootstrap's existing pre-grant seed of bootstrap shell commands, so the probe does not prompt on routine runs: as 029 shipped a `command -v ductus`-equivalent, and since 048 the store probe `~/.ductus/bin/ductus --version`, on each agent whose seed grants the runtime CLI. This seed runs before pre-flight (see **Pre-flight Phase**).

## Documentation

As 029 shipped, the README Runtime section, which had framed the runtime as an entirely separate manual install that `/ductus` does not touch, was updated to state that `/ductus` auto-wires `ductus` into the project when the binary is detected, and kept the manual binary-install instructions. Both have since moved: `/ductus` acquires the binary (`048-govern-acquired-runtime`), and the README states that it acquires and wires the runtime in other sections (AC17).

## Resolved Questions

These record what was decided when 029 was built, and each reasons inside the three-state (A / B / C) model of the time. `048-govern-acquired-runtime` collapsed that model to two states and removed State B's abort — see the **Post-completion note** at the foot of this spec for what each change means. The decisions themselves still hold, except **Version compatibility**, which 048 superseded in part. The mechanisms they name have moved: the single combined abort of **Compounding restarts** is the stale `ductus.md`'s alone (AC15), and the `command -v` probe and State C of **Detection mechanism across hosts** became the store probe and State B (Post-completion note).

- **Compounding restarts.** *Resolved:* unify `ductus` detection and the ductus.md self-update check into a single **pre-flight phase** that batches every restart-requiring write (a fresh `ductus.md` and/or the ductus wiring + permissions) into one combined abort. Ordering alone cannot fix the compounding — a stale + unwired adopter hits two independent write-and-abort points regardless of order — so the paths are merged, not reordered. Worst case drops from three sessions (wire → update → run) to two (pre-flight writes both → run). On a genuine first run the just-curled `ductus.md` is already current, so self-update does not abort and only the ductus restart fires; the compounding only ever affected an existing adopter on a stale `ductus.md` who had never wired ductus.
- **Consent to modify agent config.** *Resolved:* no separate consent prompt. State B writes the wiring and permission entries additively and idempotently — silent like the **Permission Setup** writes, and consistent with ductus.md's "no extra prompts" procedural-fidelity rule — and the pre-flight abort message names every file written as the disclosure. The user reverses any change via git or by deleting the additive `ductus` entry. An opt-out flag for auto-wiring is explicitly out of scope for this spec.
- **claude-style `.mcp.json` location.** *Resolved:* repo-root `.mcp.json` is correct — it is Claude Code's documented project-level MCP config and was already the value ductus.md carried for Claude; this spec activates it rather than inventing a path. (That value now lives in ductus.md §MCP registration, per `031-agent-mcp-wiring`, and is Claude's row rather than a layout's.) Coexistence with an existing config is the additive/idempotent in-place update: preserve all existing servers and top-level keys, add only a missing `ductus` entry, add the `mcpServers` key if absent, leave an existing `ductus` entry unchanged, and never clobber a malformed-JSON file (skip + warn + degrade to markdown). Reversal is per written file — `git restore` for the tracked `.mcp.json`. (Antigravity's half of this answer no longer applies: `031-agent-mcp-wiring` made it a `surface-instruction` agent and `/ductus` writes it no MCP file, and its config is the home-level `~/.gemini/config/mcp_config.json` rather than anything under `.agents/`.) The JSON-merge implementation was left here to `/ductus:plan` and has since been settled permanently: it is **always host-side**, because State B is by definition the case where the runtime is not live, so no primitive is available to perform it — ductus.md §MCP wiring states this.
- **Version compatibility.** *Resolved:* presence of the binary is sufficient to wire — the gate performs no version check. `runtime-tools.txt` carries only tool names (no version floor), and §runtime-boundary's Versioning subsection already rejected startup version comparison and refuse-on-mismatch in favor of lockstep tagged releases plus the runtime's parse-error path. A too-old wired `ductus` is surfaced by that runtime parse error and degrades to the markdown fallback, so the bootstrap gate is the wrong layer to enforce a version floor. **Superseded in part by `048-govern-acquired-runtime`:** the bootstrap now compares the runtime with the framework's pin and re-acquires on a mismatch (see **MCP Wiring**); the runtime itself still compares no versions.
- **Detection mechanism across hosts.** *Resolved:* two independent probes. State A is reached by the agent introspecting its own tool inventory for a `ductus`-namespaced MCP tool (`mcp__ductus__*` on Claude, `mcp:ductus:*` on Auggie/Antigravity, a `ductus*`-prefixed `<server>_<tool>` name on OpenCode since `032-opencode-agent`), counting deferred/lazy names as present — no shell, no permission. The State B vs. State C split needs a `command -v ductus`-equivalent shell probe (the only way to detect an installed-but-unregistered binary; anything queryable via a tool would already be State A), reached only when introspection finds no tool. The probe command is seeded into the existing Permission Setup pre-grant so it does not prompt. If the probe cannot run or is denied, the run is classified as State C — a harmless false negative (no auto-wire; manual wiring stays documented), so detection never hard-fails on a locked-down host.

## Post-completion note — three detection states collapse to two

> Amended by [048 — Ductus-Acquired Runtime](../048-govern-acquired-runtime/spec.md).

Spec 048 makes acquisition `/{project}`'s job, which removes the condition State C described.

- **State C — binary absent** is gone. It existed to report a missing binary and suggest the adopter install one; a missing binary is now work to perform, so the former State C path acquires the runtime and then wires and permissions it exactly as State B does, joining the same pending-restart set. An adopter with no runtime reaches the deterministic path in one run plus one restart, with no manual install in between.
- **State B no longer aborts.** 048's scenario `state-b-continues-in-session` is the record. After acquisition the binary is on disk and the CLI is permission-seeded for each subcommand a remaining step runs, so each of those primitives is reachable as `.ductus/bin/ductus <primitive>` (the seed names each such subcommand rather than the whole CLI since [022](../022-deterministic-runtime/spec.md)'s task 18, without a prompt on Claude and OpenCode, and on Auggie for every subcommand but `merge-managed-block`, whose multi-line block its bounded rules cannot match; Antigravity's seed carries no CLI entry), and the abort bought nothing the CLI could not already give that run. The pending-restart set's two contributors are now inspected separately: a stale `ductus.md` still aborts, because the run must not continue on instructions it has just replaced, while State-B wiring carries its notice to the **Closing restart** after the work completes. That restart is for the MCP tool surface, and the message says so, to stop an operator re-running `/ductus` expecting it to do more.
- **The binary probe** changed from a `PATH` lookup (`command -v ductus` / `which ductus`) to a filesystem check on the ductus-owned store. `PATH` is not consulted at all — an adopter's own `ductus` on `PATH` is ignored, not warned about, not removed.
- **A probe that cannot run** used to classify as State C, a harmless false negative that skipped auto-wiring. It now classifies as State B and acquisition proceeds; acquisition is idempotent, so the false negative costs a version comparison rather than a redundant download.
- **The State C post-scaffolding tip** ("installing `ductus` cuts token use") lost its audience on the happy path and is reserved for the degraded case — acquisition attempted and failed.

**State A keeps its binding execution contract**: detecting the runtime and then walking the prose path anyway remains the failure this spec exists to prevent. It gained a version check (048's scenario `state-a-version-checks-the-pin`): a live runtime at another version than the pin is re-acquired, and the rest of the run calls it through `.ductus/bin/ductus <primitive>` rather than through the stale server's tools.
