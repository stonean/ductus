# 068 — Backend API contract rules

`framework/rules/api-backend.md` is the backend rule set for API contract quality: the shape, stability, and documentation of the HTTP and RPC interfaces a project exposes to clients outside its own process. This is its owning spec. Where [034-performance-backend-rules](../034-performance-backend-rules/spec.md) and the backend sets after it introduced their rule files, this spec takes ownership of a file that already ships and is in use — an existing feature captured after the fact, as `011-brownfield-process` describes, and given precision by the work that touches it. It records the file's scope, its category set, its boundaries with the sibling backend rule files, how it is enforced, and the decisions taken on it. A new API contract rule lands here through the back-edge (constitution §rules, *When to write a rule*).

## Motivation

`api-backend.md` shipped in commit `9ccbd0b`, together with `accessibility-frontend.md` and `performance-frontend.md`. The commit bundled the three files into the specs that were then making rule-file selection derived and opt-out-able — [024-rule-loader](../024-rule-loader/spec.md) and `025-rule-opt-out` — which treated them as files the loader had to select, not as rule sets in their own right. No spec owned `api-backend.md`. The constitution requires a rule file that ships with `ductus` to arrive through its own feature spec (§rules, *Lifecycle*), and it recorded the three files as a backfill exception instead.

What the file lacked was not a category declaration — its header listed its categories from the start — but the record behind one: why those categories and not others, where contract quality ended and the HTTP-surface security of `security-backend.md` began, and what made one rule MUST and another SHOULD. A new contract rule had no owning spec to land in, and a change to the file — such as the two 2026-10-19 reviews, which took it from 15 rules in seven categories to 23 in eleven and changed the policy of several rules — had no spec in which to record its decisions.

> **Signpost:** [050-constitution](../050-constitution/spec.md)'s task 44 removed the recorded-backfill sentence from the constitution's §rules *Lifecycle* on 2026-10-29, by the owner's decision, to offset the routing text 075 adds, so AC11's first half already holds; pointing §rules at this spec is still this spec's to do.

## Rule set scope

`api-backend.md` uses the **backend** surface (`-backend.md` suffix, `BE-` ID prefix). Its rules apply to any project that exposes a programmatic interface — REST, JSON-RPC, gRPC, GraphQL — to clients outside its own process, and they govern **contract quality**: what a client can rely on. A rule phrased in HTTP methods, status codes, or headers reaches an RPC protocol carried over HTTP only as far as its own text says, as the file's header states; `BE-APIVER-002`, `BE-STATUS-001`, `BE-IDEMP-001`, and `BE-COND-001` each say how far. The categories are exactly those the file's header declares:

| Category | Abbrev | Concern |
| --- | --- | --- |
| Schema publication | `SCHEMA` | a machine-readable schema, served and committed; one source of truth between schema and implementation; a committed schema that matches what ships; automating that match check |
| Versioning and deprecation | `APIVER` | a declared versioning strategy applied consistently; `Deprecation` and `Sunset` headers with a schema-level deprecation mark, the mark alone permitted for a deprecated GraphQL root field on an endpoint that is not itself deprecated |
| Error response envelope | `ERRENV` | one documented envelope across endpoints; stable machine-readable error codes; RFC 9457 as the default envelope |
| HTTP status code discipline | `STATUS` | registered status-code semantics, never a `200` carrying an error; RPC protocols over HTTP signal errors their own way |
| Pagination | `PAGE` | paginate unbounded lists; an explicit continuation field; cursors for collections under concurrent writes; a deterministic total order |
| Idempotency | `IDEMP` | `Idempotency-Key` on side-effecting `POST` and non-idempotent `PATCH`, with a side-effecting RPC call carried over HTTP counted as a `POST` — its key may ride in a request field and its rejections in its protocol's error channel; idempotent `PUT` and `DELETE` that never repeat a business side effect |
| Backwards compatibility | `COMPAT` | additive-only change within a major version, with the request/response asymmetry |
| Partial updates | `PATCH` | a declared patch media type with absent-versus-`null` semantics; all-or-nothing application |
| Conditional requests | `COND` | a version the client carries from its read to its write, on resources more than one client can modify — whether the write is a `PUT`, a `PATCH`, an RPC update method, or a GraphQL mutation |
| Long-running operations | `LRO` | a status monitor for `202 Accepted`, with explicit terminal states and failure in the project envelope |
| Representation conventions | `REPR` | instants unambiguous about time zone, in one representation — an RFC 3339 string with an offset, Unix time with a documented unit, or `google.protobuf.Timestamp`; one declared casing convention; a JSON number a binary64 parser cannot hold exactly, such as a 64-bit identifier, sent as a string the schema documents |

Each abbreviation is disjoint from the categories the other `-backend.md` files declare, so a `BE-` ID names one rule across the surface.

### Boundaries (cross-reference, do not duplicate)

- **HTTP-surface security** — security headers, CORS, rate limits, method allowlisting, content-type validation, webhook signing, network exposure — is `security-backend.md` §BE-API, as the file's header says; that file is owned by [008-security-rules](../008-security-rules/spec.md). The error envelope is split the same way: `BE-ERRENV-001` and `BE-ERRENV-002` govern its contract shape and code stability, while `BE-ERR-001` and `BE-ERR-002` govern its security properties (no internal detail in production, a correlation ID), and a sensitive configuration value in any error response is `configuration-cross.md` `CFG-ENV-006`'s. For an API that is not an HTTP API, `BE-ERR-002` keeps the format's consistency, code, message and correlation ID, its code's stability included, and `BE-COMPAT-001` names it as the owner of a changed error code, as it names `BE-ERRENV-002` for an HTTP API. `BE-ERR-004` governs only an API that is not an HTTP API, preferring the error model of the published protocol it adopts, or else a format documented in `specs/system.md` or in the spec that defines the project's own protocol; for an HTTP API it names `BE-ERRENV-003` as the owner of the envelope's format, and `BE-ERRENV-001` as the owner of a project-specific envelope defined outside `specs/system.md` and of an endpoint's own undocumented shape; and an error an RPC protocol carried over HTTP returns in a success response is `BE-STATUS-001`'s, which `BE-ERR-002` and `BE-ERR-004` name. `BE-STATUS-001` defers to `BE-AUTHZ-006` for answering `404` where a resource's existence must stay hidden, and `BE-SCHEMA-001` keeps publishing a GraphQL schema apart from introspection, which `BE-INPUT-014` keeps disabled in production.
- **Lost updates** are split by how many requests the read-modify-write spans. Within one request, `concurrency-backend.md` `BE-TXN-002` requires a lost-update guard — a version check, a row lock, an atomic write, or a conflict-detecting isolation level. Across two — a client's read, then its write — no single transaction sees the window, and `BE-COND-001` closes it. Each rule names the other. `concurrency-backend.md` is owned by [038-concurrency-backend-rules](../038-concurrency-backend-rules/spec.md).
- **Asynchronous work**: `performance-backend.md` `BE-ASYNC-001` decides that slow or unbounded work leaves the request path, acknowledged with `202 Accepted`, and that a client needing the outcome gets a way to observe completion. `BE-LRO-001` gives that way its shape. Each rule names the other. `performance-backend.md` is owned by [034-performance-backend-rules](../034-performance-backend-rules/spec.md).
- **Collection bounds**: pagination is owned here. `performance-backend.md` `BE-QUERY-003` and `BE-PAYLOAD-001` defer client-facing collection bounds to `BE-PAGE`, and `security-backend.md` `BE-INPUT-006` takes its page-size maximum from the one `BE-PAGE-001` names. The default and maximum page sizes are named constants per `configuration-cross.md` `CFG-CONST-003`.
- **Retries**: this file states what makes an HTTP operation, or an RPC call carried over HTTP, safe to retry (`BE-IDEMP`) and what a status code means (`BE-STATUS-001`). The retry mechanics — attempt bounds and backoff with jitter (`BE-RETRY-001`), which failures earn a retry and honoring `Retry-After` (`BE-RETRY-003`) — are `reliability-backend.md`'s, owned by [039-reliability-backend-rules](../039-reliability-backend-rules/spec.md), which cites `BE-IDEMP` and `BE-STATUS-001` rather than restating them. A queue consumer or scheduled job carries no `Idempotency-Key`, so its deduplication is `concurrency-backend.md` `BE-COORD-002`, which builds on `BE-IDEMP` for the HTTP case.

Rules in `security-backend.md`, `performance-backend.md`, `concurrency-backend.md`, `reliability-backend.md`, `quality-cross.md`, and `performance-frontend.md` cite into this file, so its IDs carry weight beyond the file itself.

### Severity posture

The file declares none. The headers of `performance-backend.md`, `concurrency-backend.md`, and `reliability-backend.md` each state when one of their rules is MUST — a denial-of-service or exhaustion risk, a correctness or corruption hazard, an availability or cascading-failure risk, each regardless of scale. `api-backend.md` leaves the split to each rule. Whether it should declare a posture is an Open Question below.

One severity constraint binds this file as it binds every rule file: a MUST never requires continuous integration — neither that a project run CI nor that a check run in it. The rule and its reasoning live in `specs/008-security-rules/data-model.md` §Severity classification, which names `BE-SCHEMA-003` and `BE-SCHEMA-004` as the pattern.

## Enforcement

- The rules verify **design-time commitments** — what a spec, plan, or the project's `system.md` must state — not code patterns, as the file's header declares. `/{project}:analyze` loads every rule file present, regardless of stack or `[rules] surfaces`, and each rule fires only on its Verification trigger, so a project with no programmatic API draws no findings from it.
- `/{project}:review` selects the file under the **backend** surface by its suffix (`discover-rule-files`), and its content is then authoritative review criteria: MUST blocking, SHOULD advisory. How a project narrows that follows constitution §rules, which the file's header points at, and the selection composes with [033-rule-surface-setting](../033-rule-surface-setting/spec.md) and [024-rule-loader](../024-rule-loader/spec.md).
- `ductus` installs and updates the file as a shared file, through its entry in the bootstrap's Shared Files manifest.

## Rule ID format

Rule IDs are `BE-{CATEGORY}-{NNN}`, permanent and never renumbered, under the schema in `specs/008-security-rules/data-model.md`. Which categories the format admits is governed by the file's own header: constitution §rules, the rule tier [016-cross-cutting-rules](../016-cross-cutting-rules/spec.md) established, places a rule file's category abbreviations there, and `framework/commands/analyze.md` (*Which ID format governs a file*) consults an introducing-spec data-model first and the file's header second.

This spec therefore carries no data-model, by design. One here would become the first-tier source for the file's ID format and would have to stay complete — every category the file gains added to it in the same change — or it would govern wrongly. The precedent specs (034, 037, 038, 039) carry none and rely on their files' headers. A new category is registered by adding it to the header, in the change that adds the rule needing it.

## Open Questions

- Should `api-backend.md` declare a severity posture in its header, as `performance-backend.md`, `concurrency-backend.md`, and `reliability-backend.md` do — for instance, MUST only when the absence breaks a client relying on the contract or corrupts data (a silent breaking change, a repeated side effect, a lost update, an instant read hours off), and SHOULD where an alternative serves the same purpose or a departure is inconsistent rather than incorrect? If so, does every current MUST meet that wording, and does every current SHOULD fall outside it? The second rule-file review (2026-10-19) found tiers that look inconsistent with one another or with their sources: `BE-PAGE-003` is SHOULD, and gives no reason of its own for being advisory, though the offset pagination it steers away from repeats or skips items under concurrent writes — while `BE-PAGE-004` and `BE-COND-001`, which guard against the same kind of silent loss, are MUST; `BE-LRO-001` is SHOULD, yet it shapes the way to observe completion that `performance-backend.md` `BE-ASYNC-001` requires as a MUST; `BE-REPR-003` is SHOULD while `BE-REPR-001` is MUST, though both guard against a value a client reads silently wrong — an identifier read as a different integer, an instant read hours off; `BE-APIVER-001`'s declaration in `system.md` and `BE-SCHEMA-001`'s same-origin serving URL are MUST, while `BE-REPR-002`'s declared casing convention is SHOULD; `BE-APIVER-002` requires as a MUST that `Sunset` carry a future date, where RFC 8594 §3 says only that the value SHOULD be a timestamp in the future; and `BE-IDEMP-001` requires its `422` and `409` as MUST, where §2.7 of the IETF `Idempotency-Key` header draft names them at SHOULD.
- Should `BE-APIVER-001` admit a versionless API? It requires every public API to declare one of its versioning strategies and offers no way to declare none, while GraphQL's own guidance (graphql.org, *Schema Design*, §Versioning) says GraphQL "takes a strong opinion on avoiding versioning" and describes "a common practice of always avoiding breaking changes and serving a versionless API". If the rule accepts a declared versionless strategy — for GraphQL, or for any API — what must that declaration commit to, given that `BE-COMPAT-001` ties every breaking change to a major version bump?
- How does `BE-SCHEMA-001`'s same-origin serving URL apply to gRPC and JSON-RPC, whose discovery mechanisms are not URLs? gRPC server reflection is an optional extension defined as gRPC services and served over gRPC itself (gRPC `doc/server-reflection.md`), and an OpenRPC service discovery method MUST be named `rpc.discover` and returns the API's OpenRPC document (OpenRPC Specification). Should the rule accept a protocol's own discovery mechanism in place of a documented URL, keep the URL for every protocol, or require it only of REST and GraphQL?
- Is `ERRENV`'s reach into RPC protocols intended? The Rule set scope table states the category with no protocol limit, but `BE-ERRENV-001`'s Statement governs "error responses from HTTP APIs", the Verifications of `BE-ERRENV-001` and `BE-ERRENV-002` trigger on "an HTTP API endpoint", and `BE-ERRENV-003`'s default envelope is RFC 9457 `application/problem+json`. Whether an RPC protocol carried over HTTP counts as an "HTTP API" none of the three says, and the header's reach sentence names none of them — while `BE-STATUS-001` lets an RPC protocol signal errors through its own channel without saying whether that channel must carry the project envelope. Should `ERRENV` state its RPC reach — for instance, a stable code carried inside the protocol's own error — or should the scope table limit the category to resource-oriented HTTP APIs? `security-backend.md` `BE-ERR-002`'s, `BE-ERR-003`'s and `BE-ERR-004`'s clauses for an API that is not an HTTP API use the same term, so one answer decides whether such a protocol falls under them or under `ERRENV`.
- Does `BE-APIVER-002` require `Deprecation` and `Sunset` on a deprecated gRPC method? Its Statement requires every deprecated endpoint to emit the headers and names protobuf `option deprecated = true` on the method among the schema marks, so a deprecated method reads as falling under it, and its GraphQL root-field MAY does not extend to gRPC. A gRPC server can send the two headers: custom metadata travels in HTTP/2 response headers, and each method has its own `:path` (gRPC *PROTOCOL-HTTP2*), so the resource scope RFC 9745 §2.2 gives `Deprecation` fits a single method. The rule states none of this. Should it say that response metadata satisfies it for gRPC, or release a deprecated gRPC method from the headers as it releases a GraphQL root field?

## Resolved Questions

- **An owning spec for each backfilled file.** Resolved 2026-10-19 (owner): each of the three files `9ccbd0b` shipped gets its own spec — this one, `069-accessibility-frontend-rules`, and `070-performance-frontend-rules` — matching the one-concern-per-spec precedent of 034, 037, 038, and 039.
- **`BE-SCHEMA-002`: code-first only, or design-first too?** Resolved 2026-10-19 (owner): both. The rule had required the schema to be generated from the code; it now requires one source of truth in either direction — a schema generated from the code, or an implementation generated from, compiled against, or validated against a design-first schema. A hand-written schema the implementation neither derives from nor is checked against stays forbidden. The OpenAPI Initiative's best practices recommend design-first and call for a single source of truth whichever approach is taken.
- **May a MUST require CI behavior?** Resolved 2026-10-19 (owner): no; the rule lives in `specs/008-security-rules/data-model.md` §Severity classification. `BE-SCHEMA-003`, which had required the build to fail on schema drift in CI on every pull request, now states the outcome — the committed schema matches what the implementation produces, and a divergent implementation does not ship — and the new SHOULD `BE-SCHEMA-004` recommends automating the check.
- **`BE-IDEMP-001`: responses to a reused or racing key, and `PATCH`.** Resolved 2026-10-19 (owner): a request that reuses a key with a different body is rejected with `422`, and a retry arriving while the original is still in flight with `409`. The rule had answered a divergent body with `409` and left the in-flight case unstated, so an implementation built to the earlier text now departs from it. `422` and `409` are the codes the *Error Handling* section of the IETF `Idempotency-Key` header draft names, at SHOULD strength there (draft-ietf-httpapi-idempotency-key-header-07 §2.7; the draft expired on 18 April 2026). The rule also covers a `PATCH` whose patch is not idempotent, which carries the duplicate-side-effect risk of a side-effecting `POST`. How the rule reaches an RPC call carried over HTTP is the separate question below.
- **`BE-STATUS-001`: `WWW-Authenticate` on `401`?** Resolved 2026-10-19 (owner): required. RFC 9110 §15.5.2 requires a server generating a `401` to send a `WWW-Authenticate` header field containing at least one challenge, and `/{project}:analyze` flags a `401` described without one.
- **The new MUST rules.** Resolved 2026-10-19 (owner): `BE-COND-001` (a client-carried version on writes to resources more than one client can modify), `BE-PAGE-004` (a deterministic total order for paginated lists), and `BE-REPR-001` (instants unambiguous about time zone, in one representation across the API) are kept, as MUST.
- **How far do the rules phrased in HTTP terms reach RPC protocols carried over HTTP?** Resolved 2026-10-19 (owner): as far as each rule's own text says, and the file's header now says so. The question had found every side-effecting gRPC method, and every GraphQL mutation sent by `POST`, inside `BE-IDEMP-001`'s trigger as written, `BE-COND-001` reaching neither though an RPC update method loses an update as a `PUT` does, and only `BE-STATUS-001` carrying an RPC carve-out. The second rule-file review's four extensions are accepted. `BE-IDEMP-001`: a side-effecting RPC call counts as a `POST`; it may carry the key in a request field (the `request_id` of AIP-155) and may signal the reused-key and in-flight rejections through its protocol's own error channel, because gRPC sends an error on an HTTP `:status 200` response with the status in `grpc-status`, so the `422` and `409` the rule required could never be sent; the HTTP path, its `422` and `409`, and the `PATCH` coverage are unchanged. `BE-COND-001`: it covers RPC update methods and GraphQL mutations, and its version-field branch names the `etag` field of AIP-154, with gRPC `ABORTED` as the mismatch error. `BE-REPR-001`: `google.protobuf.Timestamp` is an accepted representation of an instant. `BE-APIVER-002`: a deprecated GraphQL root field served from an endpoint that is not itself deprecated may carry the schema mark alone, since RFC 9745 §2.2 scopes `Deprecation` to the resource the response belongs to, and on that endpoint the header would announce the whole endpoint deprecated. The rule file's Sources carry the citations.
