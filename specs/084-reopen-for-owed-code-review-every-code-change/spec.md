# 084 — Reopen for owed code, review every code change

A `done` spec reopens only when it owes code: an unchecked task or an unticked acceptance criterion. A code change owes a review whatever its spec's status, derived from history and recorded without a status change. The two are one definition: a spec is open only while code is owed, and a review is owed wherever code changed.

## Motivation

- §spec-lifecycle's third back-edge sent a `done` spec to `in-progress` on any edit under its directory that `classify-spec-edit` did not class as `correction` or `mechanical` ([079](../079-review-and-analysis-work-converges/spec.md)'s AC15 and AC25), so a typo in a scenario, any data-model edit and any other file reopened it, and each reopening owed an analysis, and often a review, before `done`.
- **Baseline.** `measure-reopenings --since 2026-11-11 --at 47cae941`, run with the installed runtime on 2026-11-23, reported 154 closed reopenings, 328 review and analysis runs (145 reviews, 183 analyses), 26 reopenings over 079's AC1 bound and 6 waiting, over 1,293 commits (`git rev-list --count --since=2026-11-11 47cae941`): 14.2 analysis runs per 100 commits. 079's Motivation measured 406 `done` → `in-progress` transitions over all history at `7b49fc80`; [081](../081-reviews-and-checks-follow-what-changed/spec.md)'s Motivation found nine of 12 gate-blocked specs first blocked by their own scenario or data-model edit.
- **Estimate of this spec's rule, same run.** 74 of the 154 reopenings held neither an unchecked box in `tasks.md` nor an unticked criterion in `spec.md` at any commit touching the spec's directory from the reopening's start to its end (`git rev-list start^..end -- specs/{feature}`, each file read with `git show` and matched on a line beginning `- [ ]`), so they would not have reopened; they held 34 of the 145 review runs and 79 of the 183 analysis runs. A box added and ticked in one commit is not seen by this method.
- `/{project}:review` was where the rule files were applied to code, and its result was read only by the gate on the way to `done`. Once a `done` spec reopened only for owed code, a fix bringing code in line with an existing criterion, a refactor and a dependency change would leave every spec `done` with nothing asking for their review. 081 already owed a review for code alone, and `framework/commands/review.md` step 1 already ran on a `done` spec, but nothing reported that a `done` spec's code had changed since its review; `compute-review-scope`'s description set the diff base no earlier than the spec's last reopen (079's AC5), past code committed while the spec was `done`; and code naming no spec was held only by specs that were open (081's AC10 and AC13; spec 083 counts a window's commits no spec claimed).

## Behavior

### A spec is open only while code is owed

- A `done` spec is `in-progress` exactly when its `tasks.md` holds an unchecked box (079's AC27 test: under any heading, outside a fence or comment) or its `spec.md` holds an unticked acceptance criterion. The rule reads the spec's state, not an edit's diff.
- So a new criterion reopens a `done` spec, a new scenario reopens it through the unchecked task it appends, and an edit to a scenario's text, a data model, prose or any other file does not. A code change with no spec change reopens no spec. The back-edge to `draft` on a new open question is unchanged.
- **Correcting a ticked criterion.** When a ticked criterion and the code disagree and the code is correct, the criterion's text is corrected, stays ticked, and the spec stays `done`; when the code is wrong it is a bug, and §bug-handling's scenario and task reopen the spec. Which side is correct is asked of the owner before the text changes, by default; an agent given an explicit instruction to decide, such as `--auto`, decides and says so in the commit.
- The command whose write gives a `done` spec owed work writes `in-progress` in the same action: `/{project}:amend`, `/{project}:groom`, `/{project}:fold` and `/{project}:prune` as they do for a scenario or an added task, and `/{project}:review` once it unticks a criterion of the spec it reviews or defers a finding to that spec's own work, the one status it writes on that spec. `/{project}:analyze --fix` reverts a `done` spec a hand edit left holding owed work, and CI fails on one: the adopter CI template, and this repository's audit for the unchecked box as for the unticked criterion.
- A deferral to a `done` spec, from `/{project}:analyze`, `/{project}:review` or `/{project}:implement`, reopens it by the same test, read after the deferral is written.
- A scenario's unresolved open question reopens no `done` spec. It stays a blocking `/{project}:analyze` finding with its two exits, resolving it or recording it in Resolved Questions with its condition, and still holds a spec short of `done` at the gate; `/{project}:analyze --fix` no longer sets the spec back for it. The spec reopens when the answer adds a task or a criterion.
- A fold into a `done` upstream spec reopens it only when the fold leaves it owed work, and resets its review record only when it reopens it. A body-edit fold that leaves neither an unchecked task nor an unticked criterion leaves the upstream spec `done` with its review as it stood. Code a staging spec folded below `done` brought is reported under the upstream spec by the check below, and reviewed without a reopen.
- An edit that does not reopen owes nothing while the spec is `done`: no analysis and no review runs for it. When the spec next reopens, its analysis and review read the changed files, as `analyzed-digest` and `reviewed-digest` already arrange.
- The rule changes before any code is removed: no part of `classify-spec-edit` is deleted while a caller reads it, and once none does it is retired. The mechanical-sweep rule stays, read by the analysis record's freshness and the review record's digest.

### A review is owed wherever code changed

- A code change owes a review that can be run and recorded without changing any spec's status, and what is owed is derived from history, never remembered.
- One deterministic check reports the code nothing is going to review: code a `done` spec claims, or that no spec claims, with no committed review covering it. Code an `in-progress` spec claims passes, since that spec's gate reviews it before `done`, so work in hand owes no review per push.
- Code a `done` spec claims is reviewed under that spec, in its own `review.md`, and the spec stays `done` unless the review finds what reopens it. Code no spec claims is reviewed under one project record, `{specs-root}/review.md`, beside `inbox.md` and `system.md`, in the review record's schema. The project record is regenerated whole on each run, so it holds the latest run and its `reviewed-against` marks how far unclaimed code has been read; it has no status, no gate and no criteria, and the check and the project review itself are its only readers. Code naming no spec no longer needs every open spec to hold it.
- A review of a `done` spec's code is the whole review: the rule passes and the criteria step both run, with no second mode. A ticked criterion judged not met is put to the owner first, by the correction rule above: when the code is correct, the review corrects the criterion and records it judged met with its new text, and the spec stays `done`; when the code is wrong, the review unticks it, and the unticked criterion reopens the spec. Every gating finding takes its disposition in the run: fixed, waived, deferred elsewhere, or deferred to the spec's own work, which appends a task whose unchecked box reopens it.
- A reopen does not move a spec's review window past code it claims that no committed review has read: the window starts where the spec's last review ended. A `done` spec no review has recorded starts its window at the commit that set it `done`, or that added it as `done`.
- A pre-push hook, shipped beside `framework/bootstrap/hooks/ductus-pre-commit`, runs the check and blocks the push by default. Pre-push and not pre-commit, since a review reads commits and its record is committed after the code it read. `[review] unreviewed-push` in `.ductus/config.toml` takes `"block"` or `"warn"`; absent means `block`, and any other value stops the hook with an error naming the key, never falling back to a warning.
- The hook is skippable and exists only where hooks are installed, so `framework/templates/ci/adopter-generators.yml` runs the same check as a step, as it backs the pre-commit hook today, and follows the same key: it fails under `block` and passes with an annotation per path under `warn`. `/{project}:status` shows the check's count.
- An update that installs the hook runs the check once and reports what it finds, with the key and its two values, and writes no configuration: the default is `block` for a project that updates as for a new one.
- A fix to code an existing criterion already describes is reviewed with no scenario, so §bug-handling's fourth route adds a scenario only when the requirement needs more precision.

## Edge Cases

- A push let through as a warning, or with the hook skipped, leaves code unreviewed: the check keeps reporting it, and the window starting where the spec's last review ended still covers it.
- When the check cannot examine its subject, because history stops short of a window, as in a shallow clone, it says so, naming what and why, and the hook and the CI step treat that as they treat reported code: `block` fails, `warn` reports it and exits zero. The CI step checks out full history. A `.ductus/config.toml` that does not parse stops the hook with an error naming the file, as an invalid value does. A missing runtime is no such case: the runtime is required (§runtime-boundary, principle 3), so the hook halts naming it and `--no-verify`, as `ductus-pre-commit` does, whatever the key says.
- A commit whose tree holds no project record places no window for code no spec claims, so the check reports that subject as not examined, naming the seed. A branch cut before the seed is examined once it holds the seed's commit.
- The install or update that seeds the project record is committed after the seed is written, with the hooks and command files it brings, which are code naming no spec. A seed's window therefore starts after the commit that adds the record. Once a review has read its scope, the window starts as a spec's does: after the commit finishing that review, which holds its fixes, or at its `reviewed-against` while its record is held (the agent's recommendation, adopted by the operator, 2026-11-24). A later update's commit is unclaimed code like any other.
- The hook checks each ref a push updates, at the commit it pushes, and nothing for a ref the push deletes.
- A path both a `done` and an `in-progress` spec claim passes, since the `in-progress` spec's gate reviews it.
- The check reads only committed review records, so a record lost to a concurrent write leaves its code reported, never credited.
- A `done` spec holding an unticked criterion or an unchecked box was already review-state drift, which `/{project}:analyze --fix` sets back to `in-progress` (`check_unticked_criteria` and `check_unchecked_boxes` in `runtime/src/primitives/check_artifacts.rs`, read at `47cae941`; neither reads a digest or a criterion's text): this spec's condition. A review of a `done` spec cut off with a gating finding undisposed leaves its record `blocking: true`, which is review-state drift too, which `--fix` reverts and the adopter CI template's audit-record gate already fails on.
- A review under the project record writes `{specs-root}/review.md`, which its own fix rounds would otherwise read as a change, since `fix_rounds::round_paths` leaves out only a feature's record; its rounds leave it out too.
- A later `/{project}:analyze` of a `done` spec still judges the record it writes, so a blocking finding a non-reopening edit introduced is reported then as analyze-state drift, which `--fix` does not revert (`framework/reference/analyze.md` §Analyze state drift (blocking)).
