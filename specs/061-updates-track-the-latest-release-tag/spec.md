# 061 — Updates track the latest release tag

`/ductus` and the installer fetch from the latest release tag by default, so an adopter's update lands on a released state rather than on whatever `main` holds when it runs. Both accept an override to `main` or to a named release tag.

## Motivation

Every fetch `/ductus` made back into this repository named `main`. The framework archive came from `codeload.github.com/stonean/ductus/tar.gz/refs/heads/main` ([015](../015-tarball-fetch/spec.md), §Source). The runtime version pin came from `raw.githubusercontent.com/stonean/ductus/main/version` ([048](../048-govern-acquired-runtime/spec.md)). The bootstrap's own self-update came from `main` too (`framework/bootstrap/ductus.md`, §Small fetch). The installer fetched the bootstrap from `main`, and its header stated there was no release-pinning knob. [003](../003-bootstrap-automation/spec.md)'s `curl-sh-installer` scenario recorded the same.

An update therefore landed on whatever `main` held at the moment it ran. A commit that was correct only as part of an unfinished series reached every adopter who updated before the series finished. One example is a framework change that relied on a runtime change not yet released.

The runtime binary was already release-pinned: `/ductus` installed it from a `ductus-v{version}` release. Only the file that chose that release was read from `main`.

015 deferred a configurable ref to a later spec because no adopter had asked for one (015, Resolved Questions). This is that spec.

## Source selection

A run fetches from exactly one of three sources:

- **The latest release**: the default, used when no source is given. This is the repository's GitHub *latest release*, which is never a draft or a prerelease ([GitHub REST docs, *Get the latest release*](https://docs.github.com/en/rest/releases/releases#get-the-latest-release): "the most recent non-prerelease, non-draft release"). A tag whose release has not been created yet is not a candidate.
- **`main`**: the override that restores the previous behavior.
- **A named release tag**: for staying on, or returning to, a specific release.

**One run, one source.** Every fetch a run makes back into this repository resolves against the same ref: the bootstrap self-update, the runtime version pin, and the framework archive. A run never mixes them. The latest release is resolved once, at the start of the run, and every fetch names the tag it resolved to. A release published partway through a run therefore cannot split that run across two releases. 048's pin and 015's archive agreed only because both named `main`. This spec keeps that agreement for every source rather than for `main` alone.

The runtime binary still comes from the release the pin names. On the latest release or a named tag, that is the release the source resolved to. On `main`, it is whatever version `main`'s `version` file names. The runtime store stays one binary per machine, as 048 established. Two projects on different recorded sources re-acquire it over each other, one `/ductus` run at a time. A project that needs its own binary sets `[runtime] path`.

`/ductus` takes the source as one flag, `--ref=<value>`. The value is `main`, a `ductus-v*` tag name such as `--ref=ductus-v0.54.2`, or `latest`. The flag may appear in any order beside the project name, `--agents`, and `--add-agent`, like every other `/ductus` flag.

**The choice persists in the project's committed configuration.** A run given `--ref=main` or a tag records it as `.ductus/config.toml` `[source] ref`. A run with no `--ref` uses the recorded value, and with none recorded, the latest release. `--ref=latest` removes the recorded value, returning the project to the default. The framework files `/ductus` scaffolds are committed, so the release a project is on is a fact the whole team shares, and it is recorded where the team shares it.

A run reports which source it used and the ref it resolved to. An adopter reading the output can tell which release they are on without re-deriving it.

## Failure behavior

- **The latest release cannot be resolved, or resolves to a tag outside the `ductus-v*` scheme.** The run halts, naming what it tried and what it got. It does not fall back to `main`. A silent fallback would put the adopter on exactly the unreleased state this spec exists to keep them off, and would read identically to a successful resolution (§design-principles, `QUAL-CLAIM-001`).
- **A named tag does not exist.** The run halts, naming the tag, before anything is written.
- **A resolved tag, named or the latest release, is older than the first release that carries this spec.** The run halts, naming the tag and that release, before anything is written. Every earlier release's bootstrap fetches from `main` regardless of any ref, so once its bootstrap was placed, the tag could not be honored. The latest release reaches this floor only before the release carrying this spec is published, when `main`'s bootstrap is the only one that has it. The message says so, and says that re-running once the release exists, or passing `--ref=main`, proceeds.
- **A resolved tag, named or the latest release, is older than a migration the project has already applied.** The run halts, naming the tag and the `introduced_in` of the project's `[migrations]` `last_applied`, before anything is written. Migrations run forward only, so moving below one would lay that release's pre-migration files over the migrated layout. The latest release reaches this floor when a project on `main` applied a migration no release carries yet, and then returns with `--ref=latest`.
- **A `--ref` value, or a recorded `[source] ref`, is none of `latest`, `main`, or a `ductus-v*` tag name.** The run halts, naming the value, where it came from, and the accepted forms, before anything is written. An empty value, `--ref=`, is one of these.
- **`--ref` is given more than once.** The run halts, naming every value given, before anything is written. Picking one would decide silently between two stated intents.

*Before anything is written* is measured from source resolution, the first step that depends on the source. The Permission Setup seed runs before it: that seed is additive, idempotent and identical for every source (`framework/bootstrap/ductus.md`, §Permission Setup).

## Installer

The installer is published as an asset of every release. The documented one-liner fetches the latest release's copy from `https://github.com/stonean/ductus/releases/latest/download/install.sh`, so by default the installer and the bootstrap it places come from the same release. The installer stays in the repository, so `main`'s copy remains fetchable.

The installer defaults to the latest release and takes the same `--ref=<value>` flag as `/ductus`, in any position beside the agent key: `sh -s -- claude --ref=main`. It fetches the bootstrap from the ref it resolved. With `--ref`, the installer itself still comes from whichever release the one-liner named, while the bootstrap comes from the ref. The failure behavior above applies to the installer, except for the two checks that read project configuration: the migration floor and a recorded `[source] ref`. The installer reads no project configuration, so the next `/ductus` run applies both.

The installer writes no project configuration, so its `--ref` is not recorded. When `--ref` was given, its completion message names `/ductus --ref=<value>` as the next command, and that run records the choice. A plain `/ductus` instead lands on the latest release, and says so. The run reports the source it used, and the self-update's pre-flight abort names the source it replaced the installed bootstrap from.

## Edge Cases

- **`--ref` given while a `[source] ref` is recorded.** The flag wins and replaces the recorded value, so the run and every later run use it.
- **`--ref=latest` with nothing recorded.** The run uses the latest release and writes no configuration.
- **A named tag whose release has not been created yet.** This is the window between a tag's push and its release. The tag exists, so it passes the existence check, but its runtime assets do not. Runtime acquisition halts on the missing asset, as 048 defines, and nothing is installed.
- **The `main` source.** Each fetch names `main`, which can move between two fetches within one run, as it could before this spec. `main`'s `version` file can also name a release not yet published, which halts runtime acquisition, as 048 defines. Both are the exposure an adopter opts into with `--ref=main`.
- **The installer re-run in a project with a recorded source.** The installer does not read project configuration, for the same reason it does not write it. So it places the latest release's bootstrap, or its own `--ref`'s. The next `/ductus` run's self-update replaces that bootstrap from the recorded source and aborts pre-flight once, naming the source.
- **A project on a named tag when a newer release ships.** A plain run stays on the recorded tag. Only `--ref` moves it.
- **Two contributors record different sources.** The committed configuration conflicts in the ordinary way, and the merged value governs every later run.

## Resolved Questions

- **How do framework-only changes reach adopters?** **At the next `ductus-v*` release, whatever that release contains.** A release is the unit that reaches an adopter on the default source. The product keeps one version number and one tag scheme. A framework-only release is an ordinary release: `version`, `runtime/Cargo.toml` and the newest `runtime/CHANGELOG.md` heading move together, as `/ductus:audit` Family 20 requires. The release workflow publishes runtime assets for the new version even when the runtime code is unchanged, because the pin must always name a release whose assets exist. An adopter on `main` receives the change as soon as it is committed, as before. This removes the basis of 050's Resolved Question *"Does a constitution-only change need a version bump?"*. A constitution-only change still needs no bump to be committed, but it reaches default-source adopters only when a release is cut. The cost was measured before deciding. Between `ductus-v0.28.0` (2026-08-15) and `ductus-v0.54.2` (2026-09-27), 45 of the 49 intervals between consecutive `ductus-v*` tags contained a `framework/` commit, so most framework changes ride a release that is cut anyway. An extra release costs one release-workflow run and one crates.io version with no code change. Two alternatives were rejected. A separate framework-only tag form would need a second tag grammar, a resolution rule ordering two forms, and a workflow exclusion. Never cutting a release for framework changes alone leaves the delay unbounded whenever no runtime work is pending. Resolved 2026-09-28.
- **What resolves "the latest release"?** **GitHub's latest release, read from the `Location` header of `https://github.com/stonean/ductus/releases/latest` without following the redirect.** Probed 2026-09-28, that URL answered `302` with a `Location` ending in `/releases/tag/ductus-v0.54.2`. GitHub's latest release is never a draft or a prerelease: its REST documentation defines it as "the most recent non-prerelease, non-draft release" (*Get the latest release*, read 2026-09-28). The release workflow creates the release in its `release-assets` job, only after asserting the asset set is complete (`.github/workflows/runtime-release.yml`). So a tag in the roughly eleven minutes between its push and its release is not a candidate: an adopter stays on the previous release rather than fetching assets that do not exist yet. A resolved tag outside the `ductus-v*` scheme, or a response with no `Location`, halts the run (Failure behavior). Two alternatives were rejected. The REST API's `releases/latest` has the same meaning, but unauthenticated calls are limited to 60 an hour (`x-ratelimit-limit: 60`, probed the same day), which shared CI runners can exhaust, and it needs JSON parsing on the markdown path. The highest `ductus-v*` tag by SemVer sees a tag before its release exists, so during that window it picks a tag with no assets, and runtime acquisition halts (048). Resolved 2026-09-28.
- **What is `/ductus`'s argument syntax for the source?** **One flag, `--ref=<value>`, where the value is `main` or a `ductus-v*` tag name. Leaving it out selects the latest release.** The inbox item asked for a first positional parameter. The first non-flag word is already the project name (`framework/bootstrap/ductus.md`, §Inputs), and `README.md` documents `/ductus my-project` for adoption. A positional source would therefore be ambiguous with a project named `main`, or would force the project name onto a new flag and break the documented call. §Inputs already lets flags appear in any order beside the project name, so `--ref` composes with `--agents` and `--add-agent` with no new rule. The name matches git's vocabulary and the `[source] ref` key 015 anticipated. A value that is neither form halts the run (Failure behavior). Rejected: two flags, `--main` and `--tag=<tag>`. They add a mutual-exclusion rule and cover nothing `--ref` does not. Resolved 2026-09-28.
- **What is the installer's syntax, and where does the installer itself come from?** **The same `--ref=<value>` flag as `/ductus`, accepted in any position beside the agent key. The installer is a release asset, and the documented one-liner fetches it from `releases/latest/download/install.sh`.** A ref knob existed once: an environment variable, `GOVERN_REF`. `fc3a832e` dropped it as an illusory pin, because the bootstrap's self-update re-fetched from `main` and overwrote whatever the installer had placed. Under this spec the self-update follows the ref, so the knob is real. It takes the flag form so that both entry points spell the choice one way. An environment variable would have to sit on the `sh` side of the pipe, which is easy to get wrong. The installer moves off `main` because of how it and the bootstrap change together. Between 2026-06-10 and 2026-08-17 the installer changed in 9 commits, none since, and 3 of those commits changed the bootstrap in the same commit. Three of its agent branches carry a *keep in sync with the settings_template in `framework/bootstrap/ductus.md`* comment. An installer fetched from `main` beside a bootstrap from a release would therefore pair mismatched versions in exactly the commits that change both. That is the mixing *One run, one source* forbids for `/ductus`. The costs were accepted: the installer joins the release workflow's complete-asset check, the documented one-liners change, and the one-liner needs `curl -L`, because the download URL redirects to GitHub's asset host. Probed 2026-09-28 with `curl -sSI` on an existing asset, `releases/latest/download/<asset>` answered `302` to `releases/download/ductus-v0.54.2/<asset>`, which answered `302` to `release-assets.githubusercontent.com`. That redirect is followed by the user's own shell, not by an agent host, so 029's permission-prompt concern does not arise. Rejected: keeping the installer on `main`, which changes nothing but leaves that mismatch possible. Resolved 2026-09-28.
- **Does the chosen source persist?** **Yes, in the project's committed configuration: `.ductus/config.toml` `[source] ref`, the key 015 anticipated.** A run given `--ref=main` or a tag records it, a run with no `--ref` uses it, and `--ref=latest` removes it, returning the project to the default. Recording the choice is what makes it real. The bootstrap's self-update compares the installed `ductus.md` with the upstream copy, and on a difference overwrites it and aborts pre-flight (`framework/bootstrap/ductus.md`, §Per-agent comparison). A per-run-only choice would therefore be replaced on the next plain run, which is the illusion `GOVERN_REF` was dropped for, one run later. The record is committed rather than per-contributor, because the framework files `/ductus` scaffolds are committed. Per-contributor sources would swap those shared files between releases depending on who ran `/ductus` last. `latest` joins `main` and a tag name as a `--ref` value, because clearing a recorded choice needs a spelling. Two follow-on questions were opened from this answer: how an installer `--ref` reaches the first `/ductus` run, and whether 048's machine-global store still holds. Resolved 2026-09-28.
- **Which tags are valid named targets, and what does moving to an older release do?** **A named tag is refused below either of two floors, both derived from facts that already exist. Moving back among releases above both is allowed.** The first floor is the first release that carries this spec. Measured 2026-09-28, all 50 `ductus-v*` tags fetch the archive from `refs/heads/main` and the bootstrap self-update from `main` (`framework/bootstrap/ductus.md` at each tag). So naming any of them would place a bootstrap that goes back to `main` from then on, and the named tag could not be honored. The second floor is the `introduced_in` of the project's `[migrations]` `last_applied`. Migrations run forward only: an entry runs when its `introduced_in` exceeds that value (`framework/bootstrap/ductus-procedure.md`, §Pre-run Migrations). Moving below a migration already applied would lay the older release's pre-migration files over the migrated layout. The pin concern the question began with does not arise: every `ductus-v*` tag, from `ductus-v0.28.0` on, carries a `version` file, and the older `gvrn-v*` tags are not `--ref` values. Both refusals halt before anything is written (Failure behavior). Two alternatives were rejected. A release floor alone knowingly permits a mixed layout. Refusing every backward move needs a record of the project's current release, which nothing keeps today, since the default leaves `[source] ref` absent. Resolved 2026-09-28.
- **How does an installer `--ref` reach the first `/ductus` run?** **The installer's completion message names `/ductus --ref=<value>` as the next command, and that run records the choice.** The installer writes no project configuration: its only `.ductus/` strings are permission entries. After `sh -s -- claude --ref=main`, a plain first `/ductus` finds no recorded `[source] ref` and uses the latest release. Its self-update finds the placed `main` bootstrap stale, overwrites it, and aborts pre-flight (`framework/bootstrap/ductus.md`, §Stale → defer to pre-flight abort). That outcome is the default rather than an unreleased state, and it is visible rather than silent: the run reports its source, and the abort names the source it updated from. Two alternatives were rejected. Having the installer write `[source] ref` would make it a second configuration writer. It would copy into POSIX `sh` the three-tier active-file rule the runtime owns (`framework/bootstrap/ductus.md`, §Project Configuration), before any runtime exists to call, and it is re-run in existing projects where a legacy config may be the active file. Stamping the ref into the placed bootstrap, or into a sidecar file, adds state, and the self-update's byte comparison would have to ignore the stamp so a stamped copy never reads as stale. Resolved 2026-09-28.
- **Does 048's machine-global runtime store still hold?** **Yes. The trade stands, and 061's signpost on 048 restates its cost.** The store is one binary per machine, `~/.ductus/bin/ductus`, and every `/ductus` run version-checks it against the project's pin and re-acquires on a mismatch. 048 accepted that a session in one project can run the runtime another project pinned (048, *Version currency, and what the store gives up*). While every project tracked `main`'s single pin, any mismatch lasted only until the next `/ductus` run. With a recorded source per project, two projects on different releases keep re-acquiring the store over each other. A version-keyed store was rejected for now. It could help only the two agents that register the server per project, `claude` and `opencode`. `auggie` registers it once per user and `antigravity` once per home directory (`framework/bootstrap/ductus.md`, the agent table under §Agent Registry), so on those agents one machine runs one server whatever the store holds. It would also change 048's store layout and pointer, need an adopter migration, and need a pruning policy for versions nobody uses any more. How often adopters run projects on different releases on one machine cannot be measured from here. The condition for revisiting is an adopter reporting that re-acquisition cost. Until then `[runtime] path` is the per-project escape hatch. Resolved 2026-09-28.
- **What does the prose-claim sweep cover, and which hits reopen a spec?** **This repository stays trunk-based, with its stated reason restated. Nine done specs are declared in `cross-spec-impact:`. Two more are corrected by a uniform descriptor substitution that reopens neither.** `CLAUDE.md`'s Non-negotiables and the `AGENTS.md` Workflow entry *Commit directly to `main`* justified trunk-based development by *live-on-main*. The workflow does not change: releases are cut from `main` by tag, and `main` is the integration branch an adopter opts into with `--ref=main`. The sweep was measured on 2026-09-28 with `git grep`, excluding review and analysis records and the runtime CHANGELOG's published history. It searched for claims by meaning: *live-on-main*, *tracks `main`*, `refs/heads/main`, `/main/version`, the `main` bootstrap and installer URLs, *no release-pinning*, and the archive's `ductus-main/` directory. A tag's archive extracts to `ductus-<tag>/` (probed: `ductus-ductus-v0.54.2/`), so every path claim naming `ductus-main/` depends on the ref. The done specs whose stated behavior or paths change are declared: 003, 007, 015, 023, 026, 029, 048, 050 and 056. Each is reopened once, when its signpost lands. 023 is declared because its Resolved Question on read-fallback lifetime rests on *"there is no version a project can pin to"*, which this spec makes false. 028 and 032 carry *live-on-main* only as a parenthetical descriptor in their update stories. It is replaced uniformly across both, which is §spec-lifecycle case (a) and reopens neither. 049's hit is a past-tense record of its rename sweep and stays. The files outside `specs/` that carry the claim are swept in place: `CLAUDE.md`, `AGENTS.md`, `README.md`, the installer, the bootstrap, the audit scripts, and a runtime doc comment. Rejected: declaring 028 and 032 too, which costs two more reopen, review and close cycles for the same one-word change. Correcting 007, 023 and 056 without declaring them is not an option: those are meaningful edits to done specs, and they take the back-edge. Resolved 2026-09-28.
