# `ductus`

The `ductus` framework — a pipeline-driven spec-to-implementation flow scaffolded into adopted projects.

> **Agents:** this file is the committed home for rules true of **this project alone**. Before appending, ask who the learning is true for rather than what kind of learning it is — a rule true for every project running this pipeline is constitution material and belongs in [§drift-prevention](framework/constitution.md#drift-prevention)'s *Shared knowledge stays in git*, not here. When it is project-only, append it to the matching section (Workflow, Gotchas, Boundaries, Design Principles) and add a new section only when none fits.

## Constitution

See [constitution.md](framework/constitution.md) — guiding principles, development pipeline, spec lifecycle, and quality standards that govern this project.

## Project Structure

The `framework/` directory is ductus's source — everything that ships to adopted projects via `/ductus`. It is laid out by IA primary purpose, not by file kind:

- `framework/constitution.md` — the constitution shipped to adopted projects (lands at `.ductus/constitution.md` in adopter repos)
- `framework/rules/` — domain rule sets adopted projects can reference (security-backend, security-frontend, …)
- `framework/templates/spec/` — templates consumed by an agent during the pipeline (spec, plan, tasks, data-model, research, scenario)
- `framework/templates/project/` — project document templates consumed once at adoption (agents, claude-md, system, errors, events, project-readme, gitignore, inbox)
- `framework/commands/` — operational slash command sources only
- `framework/bootstrap/` — the `ductus.md` installer plus per-agent permission files at `bootstrap/configure/{key}.md`

When adding files under `framework/`, place them by purpose, not by extension.

## Tech Stack

`ductus` is a text-first framework. The implementation is intentionally narrow:

- **Markdown** — every primary artifact (constitution, specs, plans, tasks, scenarios, rules, slash command sources, templates) is plain markdown; markdown is the source-of-truth *format* per [§text-first-artifacts](framework/constitution.md#text-first-artifacts). Format is not durability: `spec.md`, scenarios, and rules are durable sources of truth (with `plan.md` / `data-model.md` as design records), while `tasks.md` is ephemeral work-tracking — see [§tasks-phase](framework/constitution.md#tasks-phase).
- **Bash scripts** under `scripts/` — generators (`gen-*.sh`), the pre-commit hook installer (`install-hooks.sh`), and lints (`lint-*.sh`). All deterministic; no application logic.
- **GitHub Actions YAML** under `.github/workflows/` — CI configuration only.
- **Node.js / `markdownlint-cli2`** — invoked at lint time only; not a build dependency and never published. Declared in `package.json` and pinned by `package-lock.json` so the requirement is discoverable and the version is recorded — bare `npx markdownlint-cli2` resolves whatever is latest that day, so contributors and CI could disagree with nothing saying which version was meant. `npm ci` installs it; `node_modules/` is gitignored. Either invocation works once Node is on `PATH`, and the runtime's `lint-markdown` primitive prefers the local `node_modules/.bin/markdownlint-cli2` when present. **Node must be resolvable by spawned processes, not just by your shell** — under a lazy-loading nvm setup `node` and `npx` are shell functions that a child process never inherits, so the MCP server, the pre-commit hook's `cargo test`, and `check-review-gate` all fail with `could not launch npx` while your own terminal works fine. Put the real Node `bin` directory on `PATH`.
- **Rust** under `runtime/` — the `ductus` deterministic runtime (spec 022), a bin + lib crate on edition 2024 with an MSRV of `1.89`, using `rmcp` as the MCP SDK. It executes the mechanical half of every pipeline command (parsing frontmatter and markdown structure, walking tasks, atomic writes, gate handshakes) and exposes each capability as an MCP tool per [§runtime-boundary](framework/constitution.md#runtime-boundary) principle 5. It never calls an LLM — semantic judgment stays in the slash commands (principle 2).

The runtime is **required, and acquired by the pipeline** ([§runtime-boundary](framework/constitution.md#runtime-boundary) principle 3): `/ductus` downloads the pinned release asset into a ductus-owned store during adoption, so acquisition failure halts the run rather than degrading to a second execution path. It ships in lockstep with the framework — see the release entry under §Workflow for the three version sites and the `ductus-v<version>` tag that actually delivers a `runtime/` change. Binaries are published for five targets; `PATH` is never consulted. There is still no database and no long-running service, and [§runtime-boundary](framework/constitution.md#runtime-boundary) ("What the runtime is not") forbids adding one without a constitutional amendment.

When further tooling-language decisions arise (a second binary the framework might ship), prefer Rust, as the runtime already does. The recent generation of Rust CLI tooling (`ripgrep`, `fd`, `bat`, `eza`, `helix`, `tokei`, `hyperfine`, etc.) has set the modern baseline for CLI UX patterns (single static binary, fast cold-start, sensible exit codes). Go is the credible alternative if development velocity matters more than production characteristics; other languages typically don't fit (distribution complexity, startup overhead, ecosystem fit).

## Workflow

- **Commit directly to `main` — this repo uses trunk-based development.** Releases are cut from `main` by tag, and `main` is the integration branch an adopter opts into with `--ref=main` ([061](specs/061-updates-track-the-latest-release-tag/spec.md)), so there is no release branch and no feature-branch/PR step. When the user asks to land work, commit to `main` and push — do **not** branch first (the general "branch off the default branch before committing" default does not apply here). Reason: confirmed by the user 2026-06-11 after a `fix(003)` bootstrap fix was committed straight to `main`, and **again on 2026-08-31**, when an agent branched for spec 054 anyway. The cause is worth stating exactly, because it is not that this file is too long. The agent read it with a shell command whose output exceeded the tool's cap; the harness saved the full text to a temp file and returned only the first 2KB as a preview, with an explicit notice saying so. The agent used the preview and never opened the saved file, so it never reached line 40 and fell back to its generic branch-first default. **Two lessons, and the first is the one that generalises: a truncation notice is not a read — follow the pointer or re-read in ranges.** The second is that a rule which only works when a 90KB file is read in full is a diligence dependency, so this one is now restated in `CLAUDE.md` §Non-negotiables, which is small and always loaded whole. How to apply: branch only when the user explicitly asks, or for a risky spike they want isolated; otherwise small commits reviewed in place on `main` are the norm, matching the existing history.
- **Review an external pull request for correctness and simplicity before resolving its conflicts or merging it — a clean merge and a green hook say nothing about whether the change is right.** A contributor's tree passes the checks that were run *on it*, from *their* session, and a merge conflict is a statement about overlapping lines, not about the change. Reason: surfaced 2026-10-05 on PR #5 (Pi support). The agent was asked to resolve "some small merge conflicts" and went straight to conflict resolution and a spec renumber, until the user asked whether it had reviewed the PR first. The review then found that the Pi bridge's missing-binary and respawn paths did not work although the spec's AC6 was checked, that Family 26 went red under a Claude session because the contributor's checks ran under a Pi one, that the generator wrote `.claude` paths into the Pi copies, and that release records claimed a tag this repository never cut. None of these showed up as a conflict. How to apply: read the substantive diff, run the full local gate on the PR tree from this repo's own session, and verify any `done` spec's checked criteria against the tree before touching the conflicts. Report the findings and let the user decide what happens to the PR. External-PR work is the one place this file's trunk-only rule bends, and only when the user asks for it: PR #5's maintainer updates were made on a branch, at the user's request, so the author could review them.
- **Never create a repository named `govern` under this account again, and never reuse a retired project name.** [049](specs/049-rename-govern-to-ductus/spec.md) renamed the project, and GitHub's rename redirect — which is what keeps every adopter's bootstrap fetch working until they next run it — holds *only for as long as the old name is not reused*. Recreating it silently severs that redirect for every adopter who has not yet re-bootstrapped: no error on this side, no signal, and the failure appears only in their next run. Reason: confirmed against GitHub's rename documentation while resolving 049; it is the one failure mode in that rename with no detection. How to apply: treat the retired name as permanently burned. The same reasoning applies to the retired crates.io crate, which is left published-and-deprecated rather than yanked so existing installs keep resolving.
- **A change ships via a `ductus-v<version>` tag — the commit alone reaches no default-source adopter.** The runtime is released (cross-compiled binaries + crates.io publish) by `.github/workflows/runtime-release.yml`, which triggers *only* on a pushed `ductus-v*` tag, and since [061](specs/061-updates-track-the-latest-release-tag/spec.md) `/ductus` and the installer fetch the bootstrap, the pin, and the framework archive from the latest release by default. **A framework-only change reaches default-source adopters at the next `ductus-v*` release, whatever that release contains**; only a project on `--ref=main` sees it on commit. A framework-only release is an ordinary release: it moves the `version` pin, the `runtime/Cargo.toml` version, and the newest `runtime/CHANGELOG.md` heading together like any other, and the release workflow publishes runtime assets for the new version even when the runtime code is unchanged, because the pin must always name a release whose assets exist. So a change is not "landed" until you: (1) bump **all three** of the repo-root `version` file, `runtime/Cargo.toml` `version`, and a matching `runtime/CHANGELOG.md` section, in one commit (tag scheme `ductus-v<MAJOR>.<MINOR>.<PATCH>`, a runtime bug fix is a patch bump) — `/audit` Family 20 fails when they disagree, and `/ductus` reads the `version` file to decide which runtime to acquire, so a stale pin sends every adopter after assets that do not exist. **The commit is what breaks them, not the tag's absence later** — `/ductus` fetches the pin live in pre-flight at the ref its run resolved (`raw.githubusercontent.com/stonean/ductus/{raw-ref}/version`). A default-source project reads it from the latest release, which the release workflow creates only after its asset set is complete, so a bump on `main` cannot reach it. Two populations still read `main`'s pin: every project on `--ref=main`, and every adopter whose installed bootstrap predates 061's release, which fetches `main/version` until its first run self-updates it. For them, the moment a version bump lands on `main`, a store not already at that version fetches `releases/download/ductus-v<pin>/…`, gets a 404, and §Runtime acquisition → Failure **aborts the run** rather than degrading. It hits State A and State B alike; only a project setting `[runtime] path` survives, by taking Branch 1 and warning. **Nothing gates this**: Family 20 compares the three version sites to each other, not to what is published, and the audit is green throughout. Surfaced 2026-09-13 — `2266ed4` bumped the pin to 0.49.1 and deferred the tag on the recorded grounds that "no adopter is blocked," which was true of the change's content and false of acquisition; adopters were halted for about four and a half hours. So bump and tag in the same sitting, or do not bump: an unreleased pin on `main` is not a deferred release, it is an outage; (2) commit to `main` and push; (3) `git tag ductus-v<version>` at that commit and `git push` the tag. The tag pipeline runs the framework self-audit (`scripts/audit/run-all.sh`) as a **hard release gate** — any finding aborts the publish, the asset upload, and the SBOM — so run it locally *before* tagging. **A local pass is weaker evidence than it looks:** `ductus-v0.28.0`'s first attempt was green locally and failed in CI, because Family 7 used a GNU awk extension that BSD awk (every macOS machine) rejects, and the family exited 0 rather than reporting it could not run. See the Design Principles entry on checks that cannot run — that failure mode hit four different surfaces in that one release. The parity goldens store the version as a `{{runtime-version}}` placeholder (`runtime/tests/parity.rs` substitutes `env!("CARGO_PKG_VERSION")` at compare time), so a version bump needs **no golden re-bless**; do not `BLESS=1` for a version change — blessing templates the current version back to the placeholder, so there is nothing for it to write, and a diff it does write is some other change. To re-bless one golden after a deliberate stream change, name its test: `BLESS=1 cargo test --release --locked --test parity <test_name>`, then read the golden's diff. If parity fails on the version line after a bump, the cause is a stale `runtime/target/release/ductus` — `cargo build --release` to refresh it, don't touch the goldens. Reason: surfaced 2026-06-30 — an `apply-manifest` exec-bit fix committed to `main` would have shipped to no adopter without the tag. How to apply: bump + CHANGELOG + commit + `ductus-v<version>` tag + push tag, in that order; never bless goldens to absorb a version delta. **Every affected spec is `done` before the tag is cut — that is the expected state at tag time** (operator decision, 2026-08-28). A release is cut from completed work: each spec's tasks and acceptance criteria are checked, its review is current and non-blocking, and its status reads `done`; only then is the version bumped and the tag pushed. This entry previously said the reverse — that a spec is *not* complete until its tag ships, so `done` came after — which made the two conditions circular and left releases being cut over specs still in flight. The concern that produced the older wording stands and is unchanged: a spec must never sit at `done` with its runtime work unreleased. 042 reached `done` on 2026-07-22 with its `introduced_in = 0.22.0` work untagged, so no adopter could receive the migration and a stale local server binary kept writing legacy paths. Read it as a promise rather than an ordering: closing a spec commits you to tagging in the same session, not later.
- **A pushed tag is not a published release, and `release not found` is the *normal* answer for the ~11 minutes in between.** `.github/workflows/runtime-release.yml` runs its jobs in this order — `audit`, `cargo-audit` and `build` (×5 targets) in parallel → `acquire` (×5) → `sbom` → `publish` (crates.io) → `release-assets` → `verify-published` and `verify-installer` — and the GitHub release is created by **`release-assets`, the last job before the two post-release verifications**, gated on the crates.io publish ahead of it. So `gh release view ductus-v<version>` answers `release not found` for almost the whole run, and that answer on its own says nothing about whether anything is wrong. **Two things make the mid-flight state read like a failure.** The `Acquire <target>` jobs go green early and look like proof the assets are published — they are not: they `download-artifact` the *staged* tarballs from the `build` jobs, so they verify what is about to ship rather than what shipped. The job that tests the real thing is `verify-published` ("Verify the published release is acquirable"), which `needs: release-assets` and runs last, beside `verify-installer`, which does the same for the installer asset. And the outage the entry above records is real, so a not-found is easy to read as that outage when it is only a run in flight. **Read the run before concluding anything**: `gh run view <id> --json status,conclusion` separates `in_progress` from a failed gate in one call, and `--json jobs` names the job still running. **Never delete-and-re-tag a run that is still in progress.** `scripts/lint-release-ordering.sh` forces the crates.io publish *ahead* of the asset upload precisely because that half is irreversible — a version published to crates.io can never be republished — so a premature "recovery" against a run that was about to succeed burns the version number and needs a patch bump rather than a retry. Reason: surfaced 2026-09-13 verifying `ductus-v0.49.1`. The inbox chore enumerated two outcomes — assets present ⇒ done, `release not found` *or* a failed run ⇒ adopter-halting outage — and the true state was a third the list did not name: in flight and on track, with the audit gate and all five builds already green. How to apply: when a release is unconfirmed, check the **run** first and the release second; treat not-found plus `in_progress` as *wait*, and only a `conclusion` of `failure` as the outage.
- **`done` is not the same as *discharged* — the pre-`done` gate and the release audit are both blind to an obligation recorded in prose.** `check-review-gate` reads ten things, in order: whether the spec is already `done`, the feature directory's markdown lint, unresolved scenario open questions, an undischarged `cross-spec-impact:`, the review record in `review.md`, whether that review is still current, the analyze record in `analysis.md`, whether that analysis is still current, whether either record predates finding dispositions, and whether either records an undispositioned finding. It reads nothing else, and `scripts/audit/run-all.sh` never reads `specs/inbox.md` at all. So an obligation recorded anywhere *other* than the `cross-spec-impact:` key, a task, or a record's dispositions — a spec body, a hand-off note, the inbox — passes every gate this project has, while looking exactly like work that was finished. Reason: surfaced 2026-09-11 closing [055](specs/055-shared-constitution/spec.md), which owed [050](specs/050-constitution/spec.md) a cross-spec update under [§cross-spec-impact](framework/constitution.md#cross-spec-impact). It was identified early and written into 055's body as prose, then moved to `specs/inbox.md` when that section was retired at the completion gate — and 055 passed its review, its analysis, the pre-`done` gate and the release audit with the obligation outstanding, so `ductus-v0.47.0` was published before the operator caught it. `diff-cross-spec` reported `cross-spec-paths: []` at that gate, which was true and worthless: it detects the sibling spec you *changed*, never the one you *owe*. The same blindness hid the backlog: at the time nothing reported inbox depth at all, and the two surfaces that showed it were scoped to the current feature's window, so an item older than the feature in hand was invisible by construction. Six items stood in the inbox while that tag was cut. How to apply: before proposing a `done` transition or cutting a tag, re-read the spec body for obligations it names, and read `specs/inbox.md` for anything a person moved there by hand — a green gate is evidence about the ten checks above and nothing more. A pending `folds-into:` is not among them and is not meant to be: a fold is owed *after* `done` ([051](specs/051-branch-scoped-spec-numbering/spec.md)'s `a-pending-fold-never-holds-done`), and `/{project}:status` keeps reporting it until fold-back runs. **All three scenarios that closed these gaps have since shipped**, which narrows this entry rather than retiring it. [`the-cross-spec-impact-gate`](specs/022-deterministic-runtime/scenarios/the-cross-spec-impact-gate.md) put the `cross-spec-impact:` check into the gate, keyed on the **reciprocal back-link** rather than on the key's removal, so deleting the key to unblock yourself enforces nothing (`check_review_gate.rs`'s `a_declared_impact_blocks_while_the_target_does_not_link_back` and `an_undischarged_impact_outranks_a_missing_review`). [`the-inbox-row`](specs/022-deterministic-runtime/scenarios/the-inbox-row.md) made `/{project}:implement` and `/{project}:review` render the standing count on **every** run including a clean one, in four distinct states; [058](specs/058-findings-route-at-discovery/spec.md) then removed the path the 055 obligation took — no command writes a finding to the inbox, every finding a run produces is fixed, routed, or discarded before its spec can reach `done`, and the standing row moved to `/{project}:status`, rendered by `dashboard`. The rule half is [`a-declared-cross-spec-impact-gates-done`](specs/050-constitution/scenarios/a-declared-cross-spec-impact-gates-done.md) under 050. **What stays contributor discipline is the part no check can reach:** nothing detects an impact that was never *declared* — [§cross-spec-impact](framework/constitution.md#cross-spec-impact) says so in as many words rather than implying a mechanism it does not have — a person can still move an obligation into the inbox by hand, and the standing row is a notice and never a gate — `check-review-gate` and the audit families read no inbox depth. Corrected 2026-09-13: this entry had claimed all three were unbuilt for as long as they had in fact been shipped, which is the stale-prose-claim failure it sits three entries away from.
- **A spec does not reach `done` with an outstanding SHOULD — every review finding is resolved or waived first, not only the MUST ones.** The rule is [§implement-phase](framework/constitution.md#implement-phase) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: confirmed by the user 2026-08-16 while closing 010, after I presented a non-blocking `QUAL-CLAIM-001` SHOULD as compatible with the transition; the user noted the rule had been given before, which is the tell that a session-scoped acknowledgement is not enough. How to apply: read `should-violations` at the completion gate the same way you read `must-violations` — non-zero means not done. Fix it, or waive it with a recorded reason and re-run `/{project}:review` so `review.md` and the frontmatter agree; only then propose the transition. When the fix lands under `runtime/`, the release entry above applies in full — the version bump and `ductus-v<version>` tag are part of the same completion gate, so addressing a SHOULD can mean cutting a release. Carry this rule into any hand-off prompt you write: it is a standing project rule, not a preference for one review.
- **Work a recommendation out to its result *before* presenting it.** The rule is [§recommendations](framework/constitution.md#recommendations) — it ships to adopters, so this entry is the contributor-side mirror, not a second copy. Reason: surfaced 2026-08-17 on 048 task 13. Three options were offered for moving the bootstrap's State-B abort, and I recommended the middle one as "the largest gain available"; only after the user accepted did I count the restarts and find it saved **none** — it relocated the abort without removing it, leaving the pre-042 adopter at three sessions, the exact number the scenario exists to reduce. The user had to be told their approval rested on my framing rather than on the facts. The same session then produced the counter-example the rule wants: the acceptance-criterion-supersession check was measured before being recommended (455 pairs tested, 215 would fire, every sample a false positive), and the measurement is what killed it. How to apply here: state the metric the decision turns on, evaluate every option against it, then rank — and when the metric cannot be computed yet, say so and name what would settle it instead of ranking anyway. **A recommendation written into an artifact is the same claim, made durable — the session that resolves it inherits it as analysis.** Measured 2026-09-29 clarifying 041's three scenarios, three times in one pass: a drafted Open Question's *Recommended: (a)* rested on an unmeasured premise and the first measurement withdrew it (one non-artifact file across 120 spec directories, and that one deliberate); a proposal that four plan sections "fold naturally" into the design record was wrong for two of them once they were actually read; and a reopen rule already approved failed §spec-lifecycle's diff-determinable test when it was finally tested against it. The user's ruling: review carefully, and test the options, before proposing. How to apply: dry-run a proposal against the real corpus — read the sections it acts on, count the population, confirm the mechanism it relies on exists — before writing *Recommended* into a question or putting it to the user.
- **Never record anything durable in `review.md` — it is regenerated wholesale.** The rule is [§implement-phase](framework/constitution.md#implement-phase) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-08-17 closing 010, whose AC7/AC8 (the `[simple]` marker, dropped by 017) and AC14 (`framework/workflows/`, sunset by 043) all describe things the repo no longer has; the only record of the 017 removal lived in `review.md`'s Summary and was destroyed an hour later by a re-run. How to apply: the detection already works — `/{project}:implement`'s criterion-verification step is what surfaced all three, by checking criteria against the tree rather than against the review.
- **Record a review's `reviewed-against` as a commit that already contains the artifacts it reviewed — so commit the work first, then review, then commit the review.** The rule is [§implement-phase](framework/constitution.md#implement-phase) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-08-17 — 000's review was recorded at `11ff132d`, its scenarios committed in `ccdd3ac`, the local audit ran green before the commit, and the `ductus-v0.29.7` release gate then failed on the audit and skipped the publish. How to apply: two commits, always — the artifact commit, then `/{project}:review` against that new HEAD, then the review commit. And **run `scripts/audit/run-all.sh` after committing, before tagging**; a green pre-commit audit is not evidence for any family that reads history. This is the same lesson as the `fetch-depth: 0` entry one layer up: a check that reads git history answers about committed state, so it must be *asked* about committed state.
- **When a scenario is recorded after the fix it describes has landed, review it with `--since`. The default window starts after the reopen and holds none of the code.** `compute-review-scope` starts its window at the parent of the commit where the spec entered `in-progress`. On a `done` spec that commit is the `/{project}:amend` reopen, so a fix committed *before* the amend falls outside the window entirely, and the passes are left reviewing nothing but the amendment. Reason: surfaced 2026-10-05 on PR #5, twice in one session. 065's announcement (`e4784497`) and 022's link-exclusion and sweep fixes (`ad0dd002`, `8fea949f`) were committed before the scenarios that record them, and both default windows held only the amendment's spec files. How to apply: pass `--since=<the previous review's reviewed-against>` (or the commit before the fix, when that sha is gone from history, as a rebased fork's can be), and say in the review's Summary why the window was overridden. Recording the scenario first and fixing after it avoids the override altogether.
- **A review is the five passes, not the `write-review` call — never record findings you did not derive by reading the resolved scope.** `write-review` takes `findings` as an argument and records no denominator, so a review that read none of its scope and one that read all of it produce **byte-identical** records: same counts, same `reviewed-digest`, same `blocking: false`. Neither the primitive nor `check-review-gate` nor Family 19 can tell them apart, and Family 31 could not either before spec 057 retired it. Contrast `write-analysis`, which requires `unexamined` precisely so a clean analyze cannot be recorded without stating what it could not reach — `analyze.md` argues that case in full and the reasoning was never carried across to the review half. Reason: surfaced 2026-09-12. `/ductus:review` was "run" against 017 and 048 by calling `compute-review-scope`, `process-waivers` and `write-review` directly — skipping `discover-rule-files` and all five passes — and recording `0/0/0` under a Summary reading *"Reviewed … across all five dimensions"*. Both records were false. Re-running the review properly over the same scope found **fifteen** defects, three of them `QUAL-CLAIM-001` violations in shipped adopter CI, including a review-blocking gate that enumerated nothing on a configured spec root and exited 0. The operator caught it from how fast it returned, not from any artifact. How to apply: steps 3–7 of `framework/commands/review.md` **are** the command; `write-review` is how a result is recorded, not how it is produced. Load the rule files, read the in-scope files, derive every count from what you read. The Summary is a claim about work performed and is held to [§grounding](framework/constitution.md#grounding) like any other claim. When the scope is too large to read in one pass, say what was examined and what was not — in the Summary, where the next reader meets it — which is the disposition [§design-principles](framework/constitution.md#design-principles) already prescribes for residue.
- **`examined` counts the in-scope files the passes *read*. A file you are confident about by other means is named in the Summary, never folded into the numerator.** The rule is [§implement-phase](framework/constitution.md#implement-phase) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-09-13 backfilling [014](specs/014-reclarify-backedge/spec.md), whose 11-file scope included three generated `.claude/commands/ductus/*.md` mirrors; all three `framework/commands/` sources were read in full and `scripts/gen-claude-commands.sh` ran in the same pass reporting every command in sync — good grounds to believe the mirrors correct, and not a read. Recorded `examined: 8` over `scope: 11`, naming the three and the reasoning. How to apply here: this recurs on **every** spec that touches `framework/commands/`, since each such spec pulls its generated copies into scope, so it is a standing judgment rather than a one-off.
- **Never record another project's name in this repository — describe the shape instead.** Specs, scenarios, changelog entries, commit messages and runtime doc comments may say *what kind of project* exercised something (a pre-042 adopter with a legacy root config, an `.mcp.json` naming the bare command) but not *which one*. What a reader needs is the shape they must reproduce; the identity is the maintainer's local context and does not survive outside this machine. The sequencing decision that followed from this — the three corpus-wide sweeps run before the backfill campaign resumes, applied grouped by spec rather than by item — was recorded on the backfill item, which was retired when that campaign closed at 54 of 54; the measured overlap that priced it (17 already-backfilled specs, 7 then-remaining) lives in git history, which is where [§spec-lifecycle](framework/constitution.md#spec-lifecycle) puts a spent record. **(5) Sort a grooming pass by what each fix *touches* before sorting by what it is.** Measured 2026-09-13, grooming 18 items: the queue's depth was not one problem but three, and only one of them was actionable that day. **Five** items were `runtime/` edits, each individually minutes of work and each carrying the version bump and `ductus-v<version>` tag — so they are one release session, not five chores, and batching them is the whole difference between tractable and never. **Four** would have landed inside specs the backfill campaign had already closed; the scenario route is the trap there, because it reopens its matched spec *and* a scenario is a durable contract, so it costs a reopen plus a full five-pass re-review rather than a reopen plus an analyze. **Five** touched only `framework/` — a shipped CI template, two `ductus.md` prose contradictions, a rule file's Rationale, two migration procedures — and those reopened nothing, so they were fixed in the pass and the inbox went 18 → 14. The operational point is that *chore* and *scenario* are the wrong first cut. A finding's cost is set by its **destination**: `framework/` is free, `runtime/` is a release, and a closed spec is a back-edge whose price depends on whether the edit lands in a durable contract. Classify by destination first and the actionable subset falls out immediately; classify by route first and every item looks equally blocked. Before 058 a campaign that found defects grew the inbox faster than grooming shrank it; since 058 a campaign's findings are dispositioned in the runs that find them, so only hand-logged todos grow it. The release batch — the one move that retires several items for one tag — is still the cheapest way to drain what is logged. **(6) When you retire an item, grep the inbox for anything that named it.** An item that records a blocker holds a claim about another item, and retiring the second never revisits the first — so the blocked one is walked, read as *blocked*, and re-deferred on every pass afterwards. Measured 2026-09-14: the `ductus.md` archive-boundary split declared itself blocked on a sibling ordering item that `86a4432b` had fixed as a chore **four hours later the same day**, and it sat blocked through every grooming pass since with the blocker gone. This is [§brownfield-inbox](framework/constitution.md#brownfield-inbox)'s no-hold-state failure arriving through an **internal** dependency rather than an external event, which is the case that rule does not cover: there is no external condition to re-evaluate, only a cross-reference nobody re-read. A `grep -c` over the retired item's subject costs a second and is the whole check.
- **A finding whose fix lands inside a spec the corpus has already closed has exactly two disposals — spend the reopen deliberately, or discard it with its reason; since 058 the inbox is neither.** Standing operator decision, 2026-09-13, re-homed here 2026-09-14 when the `examined`/`scope` backfill campaign closed at 54 of 54 and its inbox item was retired; the per-spec accounts that item carried stay in git history, which is where [§spec-lifecycle](framework/constitution.md#spec-lifecycle) puts a historical record. It offered **three** disposals when it was made: wait for that spec's own later pass, spend the reopen, or route the finding somewhere that is not a spec — the inbox, then. [058](specs/058-findings-route-at-discovery/spec.md) removed that last one: a finding parked in the inbox let a spec reach `done` looking finished, so the second disposal is now a discard with its reason, stored as a decision so the next run does not ask again, or — for a genuinely cross-cutting finding — a route to a rule file the project owns. **The first is gone** — the campaign *was* the schedule of future passes, so with it closed *waits for that spec's own later pass* resolves to *waits indefinitely*, and an item left parked is a third thing that is neither disposal, which is exactly the residue [§design-principles](framework/constitution.md#design-principles) rejects. **Price the reopen by destination before spending it**: an edit to `spec.md` or `plan.md` costs a reopen plus an analyze, while an edit to `scenarios/*.md` or `data-model.md` is a durable contract and costs a reopen **plus a full five-pass re-review** — those two are the only files `write_review.rs` digests, which is the same split the sweep-pricing entry below turns on. **And batch by target rather than routing singly:** one deliberate reopen pays one re-review however many findings ride along, the same arithmetic decision (c) already makes for a release tag. Measured 2026-09-14 while grooming: **six** inbox items routed to `022-deterministic-runtime` and **five** carried a `runtime/` edit, overlapping at four — so one reopen and one tag discharge what five separate sessions could not, and 022's own pre-reopen review scope was 144 modified-since / 167 in scope at 144,932 bytes, over the MCP cap — **re-measured 2026-09-15 at 88 / 112 and 37,922 bytes, comfortably inline**, because 022's base moved forward in the 2026-09-14 batch reopen and every figure here decays the moment the spec reopens. The window is not the cost: a full 022 re-review is still the corpus's largest single unit, because what makes it large is 98 scenarios and a 1,351-line `data-model.md`, not how many files the diff base happens to span. Do not read a narrow window as permission to claim one. **022 is the case to read before pricing any of it, because its record looks like a completed pass and is not**: it reads `examined: 12` of `scope: 87`, written as a *digest repair* after the 0.49.4 canonical sync, and its own `review.md` Summary states in as many words that its **95 scenarios were not re-read**. That is the truthful-small-numerator disposition this file prescribes for a sync that stales a digest mid-release — not evidence that a five-pass review has ever been run over 022's contracts. A full 022 re-review is the largest single unit in the corpus and is its own decision to spend; the `examined`/`scope` backfill campaign deliberately excluded it, and 022's presence in that campaign's Done list never meant otherwise. How to apply: when a finding's fix lands in a closed spec, name the destination *file*, say which of the two disposals you are taking, and check whether a reopen of that spec is already being spent for something else you can ride along with. The grooming stance this sits beside — fix chores in the pass, route scenarios, sort by what a fix touches before sorting by what it is — is the entry above, not a second copy here. **You do not have to judge which of the two you are paying — `check-review-gate` names it.** After the edits are on disk and the spec is reopened, the gate answers `blocked-by: review-stale` when a durable contract moved (reopen **plus** a full five-pass re-review) and `analyze-stale` when only `spec.md` / `plan.md` did (reopen **plus** an analyze, the recorded review staying valid because `reviewed-digest` covers `scenarios/*.md` and `data-model.md` alone). Measured 2026-09-15 across six specs reopened in one pass: four answered `analyze-stale` and two `review-stale`, matching the hand estimate exactly, at the cost of one command each. **And re-derive the item's own destination list before pricing anything off it** — an inbox item's enumeration of *what it touches* decays the same way its counts do, and it decays toward under-estimating: the `/ductus:init` retirement was costed at four closed specs with no digest staled, and re-measuring found six `spec.md` files, three durable contracts, three `runtime/` doc comments, and a whole spec falsified end to end.
- **A finding made during implementation becomes a task on the spec in hand — a fix task inside the spec, a disposition task outside it — never an inbox item.** The rule is [§brownfield-inbox](framework/constitution.md#brownfield-inbox) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: confirmed by the user 2026-08-25, after I proposed landing it in `AGENTS.md` alone; contributor-side practice does not propagate to adopting projects, and this rule governs implementation behavior everywhere, so the constitution is its canonical home. How to apply: read the section for the tier test, and treat reaching for the inbox during implementation as the habit it replaces — that reflex routed a defect through `/ductus:groom` back to the spec that was open the whole time. The machinery-observation entry still applies to the case that *looks* like a defect but is not: an observation about the pipeline's own machinery becomes a disposition task like any other out-of-spec finding, and working it discards it with its reason.
- **An inbox item blocked on an external event is discarded at `/{project}:groom`, not held — the inbox has no hold state.** The rule is [§brownfield-inbox](framework/constitution.md#brownfield-inbox) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: confirmed by the user 2026-08-30. A 2026-05-19 Skills-protocol exploration in `specs/inbox.md` carried an **On hold per user 2026-07-11** marker; by the time both of its stated conditions had quietly cleared, resolving it cost a research session, and every groom pass in between had walked and re-deferred it. How to apply: at the `discard` route, ask whether the item's premise can be evaluated *today*. If it cannot, discard it and make sure the durable half is recorded where it is read at the moment it matters — this file for a maintenance burden, the spec body for a design constraint. If it can, the item is merely undecided, not blocked: route it to a scenario under its covering spec and let the decision live in that scenario's Open Questions. The neighbouring entries cover the two cases that look like this one — an observation about the pipeline's own machinery (discarded, never captured) and a defect in the in-progress spec (its `tasks.md`, never the inbox).
- **`check-artifacts` reports `clean: true` and a non-empty `skipped` array at the same time — the second is the manual worklist, not noise.** The rule is [§implement-phase](framework/constitution.md#implement-phase) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. The two fields answer different questions: `clean` covers what the primitive examined, `skipped` names what it could not reach. The `criterion-path-existence` family skips with `root-absent` (a path outside the repo — a home-directory store, say) and with `not-a-live-claim` (a criterion describing a replacement or a removal rather than a file that must exist), and a criterion in that second bucket has had **nothing** check the substance of its claim, ever — not on this run, not on any previous one. Reason: surfaced 2026-08-18 closing 048. AC17 asserted that every per-step markdown-only fallback had been removed from `framework/commands/*.md`, and `tasks.md` recorded all 26 as removed; two survived in `specify.md` §Instructions with no exemption recorded anywhere, and the criterion had stood ticked across four releases. `check-artifacts` had reported it `skipped` as `not-a-live-claim` the whole time, so its green result was never evidence about that criterion — the family was telling the truth about what it had not looked at, and the omission read as assurance anyway. How to apply: at the completion gate, walk the `skipped` array entry by entry and check each criterion's claim against the tree by hand — a `grep` for the claim's own wording is usually the entire job, and it is the only thing standing between a false claim and a `done` spec. When the claim does not hold, ask which of two things happened: a later spec removed what this one delivered, in which case the earlier spec is **edited in place** through the `done → in-progress` back-edge so its body describes what is true now (or consolidated away, when nothing in it still holds); or the original work was simply incomplete, which is a **sweep to finish** — editing that one to match the tree would record a fiction, since nothing removed it. **There is a third arm, and the campaign found it before it found a name for it: the criterion may never have been true.** Measured 2026-09-14 on 023, whose AC30 claims the Status → next action tables in *both* `target.md` and `status.md` point at `/amend` for the `done` row. `target.md` does. `status.md` reads `done (spec is complete)` — and `git show 670a3181:framework/commands/status.md`, 023's **own** rename commit, already read that, because 022 task 12 had rewritten the table first. The criterion was ticked over a claim about a file the spec did not change, and every gate since has been green. The tell is cheap and nobody runs it: when a criterion names an artifact, `git show <the spec's own merge commit>:<path>` answers whether it was ever true, and it is the only way to tell *superseded later* from *false on arrival*. The disposition differs too — a superseded criterion is annotated with what replaced it, while one that was never true is annotated with what it actually described, and **neither is a licence to sweep the artifact**: 023's divergence is correct (`status` renders a view of every spec, `target` recommends the action on the one just selected), so changing `status.md` to match would have altered shipped behaviour on the strength of a stale claim.

## Gotchas

- **Pi has no MCP client — its tool surface is the `.pi/extensions/ductus.ts` bridge, and never "fix" Pi by registering an MCP server for it.** The bridge (spec 064, shipped from `framework/bootstrap/pi/ductus-bridge.ts`, installed by `/ductus` at State-B wire time, repaired by `/{project}:configure`) spawns `.ductus/bin/ductus mcp` over stdio and re-registers every tool as `ductus__<name>` with the server's own schema. It is deliberately dependency-free — the README promises nothing enters the adopter's dependency manifest, and the live-schema property depends on the bridge staying a thin transport — so adding an npm MCP SDK to it, or replacing it with an MCP-config entry Pi cannot read, breaks the contract twice over. How to apply: when Pi needs a new runtime capability, the bridge needs no edit (the tool list is live from the server); when the bridge itself must change, keep it stdio-only and zero-dependency, and remember the tool names go through pi's `registerTool` which passes plain JSON-Schema through untouched (verified 2026-09-20 against pi 0.86.1 — `registerTool` only checks `parameters` is a non-array object). Verification after changing the bridge comes in two parts. First run `node scripts/tests/pi-bridge-harness.mjs`, which drives the bridge through a mock pi against a real runtime build: registration, a round-tripped call, the missing-binary load path, respawn, and recovery after a failed call. Then do a real `pi` run, the only test of pi's own loader. `scripts/gen-claude-commands.sh` regenerates the dogfooded copy but does not load pi. Reason for the harness: surfaced 2026-10-05 reviewing PR #5. The bridge's happy path had been verified in a real pi run, but every failure path was broken, and nothing exercised them. A missing binary raised an uncaught `ENOENT` in pi's process and stalled for 120 s before any notice, a dead runtime was never respawned, and one failed call poisoned every later one.

- **After changing runtime source, verify through the built binary — not the MCP tools.** The `ductus` MCP server runs the binary it was started with, so every `mcp__ductus__*` result in a session reflects the runtime as of session start, not your working tree. A primitive you just changed will keep reporting its old behavior, and the result looks authoritative. How to apply: after `cargo build --release`, verify with `./runtime/target/release/ductus <primitive> …` and treat MCP results for that primitive as stale until the server is restarted. **This bites hardest when the stale primitive *writes* rather than reads.** A stale read is a wrong answer you may catch; a stale write persists on disk and a later gate trusts it. Running a pipeline command in the same session that changed the primitive backing it is the concrete case — `/{project}:review` invoked after editing `write_review.rs` renders the pre-edit report, and `/{project}:analyze` after editing `write_analysis.rs` records the pre-edit block. Surfaced again 2026-09-11 on spec 055: the review of the very feature that added the `## Unexamined governance` section was written without it. Finish runtime work, restart the session, *then* run the pipeline commands that consume it. Reason: surfaced 2026-08-31 during spec 054 — `read-spec` returned a `supersedes` key the new code cannot emit, which read as a passthrough bug in the struct and was actually the old server answering; an acceptance criterion had already been marked verified on the strength of one of those stale results.
- **`framework/commands/help.md` is generated — hand-edits to it are reverted on the next commit.** `scripts/gen-help-tables.sh` owns its command tables and the pre-commit hook runs it, so removing a command by editing `help.md` puts the row straight back (with an empty description, since the source file it reads is gone). How to apply: change the entry in `scripts/gen-help-tables.sh` and re-run it; treat `help.md` as build output. The same ordering applies to `framework/bootstrap/configure/*.md`, which `scripts/gen-configure-mcp.sh` derives from `framework/runtime-tools.txt`. Reason: surfaced 2026-08-31 during spec 054's command removal — the hand-edited row came back on the very next commit.
- **Registering a runtime primitive is five sites, and two of them are only found by tests — de-registering one is the same five.** The obvious three are the CLI command enum plus its dispatch arm in `runtime/src/main.rs`, the exec-path match arm in `runtime/src/interpreter/mod.rs`, and the `#[tool]` in `runtime/src/mcp/server.rs`. The two that get missed are `framework/runtime-tools.txt` (the shipped manifest) and `runtime/src/schema/registry.rs`'s `PRIMITIVE_REGISTRY` (the canonical set). Reason: surfaced 2026-08-30 adding a primitive whose registry entry was missed, and `runtime/tests/mcp.rs`'s `lists_every_manifest_tool_and_canonical_set` caught it by asserting the manifest is set-**equal** to the registry: a manifest entry with no tool is a phantom, and a tool missing from the manifest escapes both the markdown-only PATH assertion and `scripts/lint-tool-coverage.sh`. How to apply: after adding a primitive run `cargo test --test mcp` before anything else — it names the exact divergence with both sets printed. Then run `scripts/gen-configure-mcp.sh` **followed by** `scripts/gen-claude-commands.sh` (that order; the second renders command copies from what the first writes) or `/{project}:audit`'s check-zero precondition fails on a stale `.claude/commands/ductus/configure.md`. A new arm may also push `dispatch_primitive` past clippy's 100-line ceiling; it carries the same `#[allow(clippy::too_many_lines)]` as `main`'s CLI match, for the same reason — both are flat registries that grow one arm per primitive.
- **`check-artifacts`' `skipped` array names targets that could not be *reached*, never subjects that were empty.** Its reason set is closed and each entry points at a path something tried and failed to examine. A family with nothing to examine — no declared edge, no path claim — reports neither a finding nor a skip. Reason: surfaced 2026-08-30 building a check family whose first implementation recorded a skip on every spec that declared nothing for it to examine, to express that the family only sees declared edges. Six existing tests failed, correctly: they encode the contract. Overloading the set would have put an informational line on every spec in a corpus while telling an operator nothing actionable. How to apply: when a family's coverage is genuinely bounded, state the bound in the family's doc comment and in `framework/commands/analyze.md`'s rendering — where a reader meets it once — rather than emitting a per-spec entry. Removing the skip made all six tests pass untouched, which is the tell that the contract was right and the design was wrong.
- Use `npx markdownlint-cli2` to run markdown linting — do not suggest installing it globally.
- **A prose-only edit to `framework/commands/*.md` can break a Rust test, so run `cargo test` before calling such a change verified.** `runtime/tests/parity.rs`'s `read_parity_spec` prefers the repo-canonical command file over any fixture copy, so that file's *bytes* land in the parity fixture's git tree. `init_git_repo` then commits with a frozen signature — deliberately, because `derive-boundary`'s `first-commit` / `current-head` are threaded into the `writeCode` payload and a drifting sha would make the golden flaky. Frozen time plus a fixed tree fully determine the commit OID, so changing the tree changes the OID *by design*. Only `implement-basic.jsonl` is affected by a prose edit that leaves the step list alone; it is the one golden whose payload carries git-derived values. **A step added, removed, or renumbered moves every golden for that command**, because each progress envelope carries its `step`, and it breaks the tests that pin a command's parsed step list — `runtime/tests/review_command.rs` and `specify_command.rs`. Measured 2026-09-24 on 058: two host-responsibility steps inserted before `write-review` moved `review-basic` from step 9 to 11 and failed `review_command.rs`, and three before `write-analysis` moved `analyze-basic` from 17 to 19. Re-bless with the test **filtered to that one golden** (`BLESS=1 cargo test --release --locked <name>_stream_matches_golden`), never a corpus-wide `BLESS=1`, then confirm the diff is only the sha fields, the renumbered `step`, and the prose the edit changed. Blessing does preserve `{{runtime-version}}` — `parity.rs`'s `run_parity_case` templates the literal back before writing — so the release entry's warning below is about not needing a re-bless for a version bump, not about this path. Reason: surfaced 2026-08-19 — spec 040's `spec-root-rule-stated-once` deleted a blockquote from six command sources; markdownlint, procedure-parseability, the derived indexes, the generators, and the full self-audit were all green locally, the change was reported as markdown-only, and CI then failed on all three platforms. How to apply: treat every file under `framework/commands/` as **runtime-adjacent** — the local gate for any edit there is the full CI surface (see Workflow), not the markdown checks alone.
- **An `assessSpecQuality` step's prose chooses the tier of rules the exec walker asks about, so a `-tier` word added to that prose can change what the step covers.** `severity_from_step_prose` (`runtime/src/interpreter/payload.rs`) lowercases the step text and returns the first of `must-tier`, `should-tier` and `info-tier` it contains, checked in that order, and steps 11 and 12 of `framework/commands/analyze.md` are selected exactly that way. A `SHOULD-tier` phrase added to step 11 is harmless only because MUST is checked first; a `MUST-tier` phrase added to step 12 would make it select MUST-tier rules and leave the SHOULD-tier ones unasked. Describe a rule's keywords in those steps without the suffix — `a MUST or SHOULD keyword`. Reason: surfaced 2026-09-27 on 008, when rewording "no RFC 2119 keyword" to "no MUST- or SHOULD-tier keyword" put `should-tier` into step 11; reading the function before committing caught it. How to apply: before committing an edit to steps 11 or 12 of `analyze.md`, grep the new prose for `-tier`.
- **Two extension points fan out in the exec walker, so neither is a stand-in for "one request, one response" in a test.** An `assessSpecQuality` step sends one request per loaded rule of its tier (spec 060), and with no rule loaded it sends **none** — so a protocol test that feeds it one scripted response now completes without reading it, or dies on stdin EOF. An `askClarifyQuestion` step sends one request per entry of `open-questions` when that key is in the context (022, scenario `exec-clarify-asks-each-open-question`), and exactly one when it is absent. A test of the generic round trip, stray-line tolerance, or EOF handling uses `askClarifyQuestion` **without** `open-questions` in its context. Rule fixtures have a second trap: a rule section is recognized only by `check-rule-ids`' heading grammar (`^#{2,4}\s+[A-Z]{2,5}-[A-Z][A-Z0-9]+-\d{3,4}`, shared through `runtime/src/primitives/rule_sections.rs`), so a fixture heading like `### X-1` or `### X-A-001` is not a rule at all — the walker loads nothing from it and the test asserts against an empty rule set. Use IDs like `TS-MUST-001`, and give the Statement an RFC 2119 keyword, since a keyword-less Statement is recorded unexamined rather than assessed. Reason: surfaced 2026-09-27 implementing 060 — five existing protocol tests used `assessSpecQuality` as a generic extension step and failed once it fanned out, and the first parser tests used `X-A-001` and found zero sections. How to apply: pick the extension point by the request count the test needs, and check a new rule fixture parses with `parse_rule_sections` before asserting on what the walker asked.
- The command generator substitutes `{project}` → `ductus` and `{cli-config-dir}` → `.claude`, and writes the Claude-specific permission file (`framework/bootstrap/configure/claude.md`) as `configure.md` in the `ductus` command directory. The values are `PROJECT` and `CONFIG_DIR` in `scripts/gen-claude-commands.sh`; they read `gov` until 049 renamed the project.
- **An edit to `framework/commands/*.md` is invisible to that slash command until the generator re-runs — including to the command you are editing, in the same session.** The pre-commit hook regenerates `.claude/commands/ductus/` (see Workflow), but that is *commit* time; the agent host loads the installed copy at *invocation* time. So editing a command source and then invoking that command walks the pre-edit text, silently. The same shape applies one layer down, but the loop is shorter than it used to be: this repo sets `[runtime] path = "runtime/target/release/ductus"` and registers the pointer (`.ductus/bin/ductus`) as the MCP command, so a `runtime/` source change is live for MCP tool calls after `cargo build --release` **and** an MCP server restart — which means a new session, since the host spawns the server once. There is no `cargo install` step and `PATH` is not consulted; the pointer resolves straight to the build in the working tree. Reason: surfaced 2026-08-14 — `framework/commands/analyze.md` was corrected to document `--fix`'s second trigger, and the very next `/ductus:analyze` invocation loaded the stale installed copy and displayed the old text; in the same session the `append-*` marker fix was published as `gvrn-v0.27.2` while every MCP call kept using the Aug-3 binary (that half is what `[runtime] path` now prevents — spec 048). How to apply: after editing any `framework/commands/*.md`, run `scripts/gen-claude-commands.sh` before invoking that command (it is idempotent, and the pre-commit hook re-runs it anyway); after a `runtime/` change, do not trust an MCP tool call in the *current* session to exercise it — verify with `cargo test`, and treat the running server as the pre-build binary until the session is restarted.
- **The pre-commit hook regenerates the command mirrors from the working tree and stages them on every commit — so a commit can carry a mirror whose source it does not.** `.githooks/pre-commit` runs `scripts/gen-claude-commands.sh` unconditionally (line 67) and then `git add .claude/commands/ductus/` (line 94), whatever was staged. With an unstaged edit to any `framework/commands/*.md` in the tree, an unrelated commit picks up that command's regenerated copy and leaves its source behind, and the pushed tree fails the self-audit's source-versus-mirror check. Reason: surfaced 2026-09-29 — a one-file `specs/050-constitution/plan.md` fix (`1fc697f3`) committed `.claude/commands/ductus/consolidate.md` without `framework/commands/consolidate.md`, which had to follow in its own commit. How to apply: commit a command-source edit together with (or before) anything else while it sits in the tree, and read `git show --stat` for a `.claude/commands/` path you did not stage.
- **The generator rule has no exceptions — every file under `.claude/commands/ductus/` is generated output, and one with no source is drift for the prune loop rather than a file to hand-maintain.** It carried exactly one exception until 2026-09-15: a `ductus`-specific `init.md` with no `framework/commands/` counterpart, which `scripts/gen-claude-commands.sh` named in `expected` so the prune loop would spare it. Reason: surfaced 2026-09-29 in 062's task 11 — `scripts/audit/lib.sh` calls `ductus dashboard` to enumerate the corpus, and while `dashboard` performed a delivering resolution an audit run silently pinned the maintainer's own session in this repository (062 task 12 makes `dashboard` read-only).

## Boundaries

- **No host-level enforcement of the deterministic (`ductus`) path — it is a deliberate non-goal.** `/ductus`'s State-A execution contract (spec 029, scenario `state-a-deterministic-path-forcing`) uses binding *procedure language* to get a wired runtime actually used. `ductus` does **not** enforce it at the host level — no denying `curl`/`tar` while `ductus` is registered, no State-A-only procedure variant with the shell stripped. Reason: host enforcement would block the legitimate non-primitive shell steps the bootstrap needs (gitignore `curl`, `git config`, `chmod`), is host-specific and a permanent per-host maintenance tax, and breaks [§runtime-boundary](framework/constitution.md#runtime-boundary)'s "neither path wraps the other" parity by demoting the markdown path. A model that ignores the binding contract falls back to the correct-but-pricier markdown path — an accepted outcome, not a gap. How to apply: do not propose or build host enforcement as a follow-up; if the procedure-level contract proves insufficient for a given model, the answer is a more capable model, not coercion.
- **Never edit an installed command file directly — edit the source the generator copies from.** Here that means never editing `.claude/commands/ductus/*.md`; your changes are overwritten the next time the generator runs. Edit the source under `framework/commands/` (or `framework/bootstrap/configure/claude.md` for the `configure` command). The rule is [§drift-prevention](framework/constitution.md#drift-prevention) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-05-23 during the spec-022 `/ductus:status` rewrite — I read the deployed (already-substituted) copy when drafting the rewrite and shipped hardcoded `/ductus:` and `.claude/` literals to the source, which broke the framework-checks CI on Family 4 of `scripts/audit/run-all.sh` (`placeholder-roundtrip`). How to apply: when in doubt, `git show HEAD:framework/commands/{name}.md` to see the source convention before editing; the `placeholder-roundtrip` audit is the post-hoc check, not the first line of defense.
- **Never end a response with a "worth flagging" / "worth noting" / "two things to note" section. Every residue gets a disposition, not a paragraph.** [§design-principles](framework/constitution.md#design-principles) already forbids this and names why it happens: for anything outstanding there are exactly three dispositions — fix it, record it where the pipeline will surface it again, or decide it is out of scope and record the reason — and "disclosing it in prose alongside a completion claim is none of the three, and it is the most tempting failure available because it feels like candour." A trailing notes section is that failure in its purest form. It reads as diligence while making three different states indistinguishable: something already fixed, something recorded and waiting on a command, and something merely observed all get the same bullet, so the reader cannot tell what is owed to them or by whom. Reason: surfaced 2026-09-07 and confirmed by the user, after a report on spec 047 closed with a "worth flagging" list that mixed one designed behavior already recorded in a scenario's Edge Cases, two findings already fixed with tests, and one item logged to `specs/inbox.md`. The user's words: "it's not clear whether things were identified and not addressed versus identified and addressed versus just a note. i don't want notes, it want actionable items otherwise i want relevant, durable information added to the constitution or rules." How to apply: before writing any closing section, give each item its disposition, then write the **disposition** rather than the item. *Fixed* belongs in the account of what was done — past tense, with the test that holds it. *Recorded* names the artifact it now lives in and the command that picks it up (a task on the spec's `tasks.md` → `/{project}:implement`; a scenario; an acceptance criterion) — never `specs/inbox.md`, which no gate reads. *Out of scope* says so with its reason. *Durable and general* is a constitution or rule change — or an entry in this file when it is local to this repo — and the response names the file that changed. An item that fits none of those four is not worth the reader's attention and does not go in the response at all.

## Design Principles

- **Reach for a runtime primitive first; a shell script is the fallback.** The rule is [§runtime-boundary](framework/constitution.md#runtime-boundary) — it ships to adopters, so this entry is the contributor-side record of what it cost *here*. A capability that is deterministic, already mechanical, and specifiable as prose meets the eligibility criteria, and meeting them is a **default, not a permission**: it is implemented in `runtime/` and the shell entry point the framework needs — a pre-commit hook, a CI step, an `/audit` family — resolves the binary and calls the primitive. `scripts/audit/command-flag-hint-parity.sh` (Family 30) is the reference shape: the check *is* the `check-command-flags` primitive and the script is ~40 lines of entry point. Reason: surfaced 2026-08-28, twice in one session, each time as a script written by reflex and corrected only after the user pushed back. The second was `/audit` Family 31 (retired by spec 057), where a hand-rolled `scalar()` helper — copied from `review-freshness.sh`, which still has it — used `\s*` after the key, and because `\s` matches a newline it walked past an empty value onto the next line and returned *that* line's content, producing a confidently-wrong finding against a spec that was correct. The runtime's tested scanners do not have that bug, and the copy that did was the fourth hand-rolled frontmatter parser in a repo whose runtime already parses frontmatter for a living. How to apply: before writing a script, ask what stops this from being a primitive and answer with a criterion that fails, not with "a script is faster to land" — the build is a one-time cost to the author and the parser is a permanent cost to every reader. If the script would parse frontmatter or markdown structure to do its work, that is the signal it belongs in the runtime, regardless of whether it reaches for `awk` or for an embedded `python3` heredoc; the language is not what the principle turns on.

- **A check that cannot run must never look like one that passed.** The rule is [§design-principles](framework/constitution.md#design-principles) — it ships to adopters, so this entry is the contributor-side record of what it cost *here*, not a second statement of it. It is the single most expensive failure mode this repo has produced. It surfaced four separate times while shipping `ductus-v0.28.0`, each time as a green signal that meant nothing: `scripts/audit/sibling-coupling.sh` used a GNU awk extension, so on every macOS machine the extraction aborted, the family found nothing, and it exited 0 — a release gate that was dead locally and alive in CI; `release-assets` in `runtime-release.yml` needed only `build`, so the self-audit gated the crates.io publish while the binaries adopters actually download shipped regardless; the acquisition workflow was triggered by `on: release: [published]`, which GitHub never fires for a release created with the default `GITHUB_TOKEN`, so the invariant the constitution requires would have been cited by name and never once executed; and the `macos-13` runner label no longer resolves, so that leg sat queued with no runner while the others passed — a missing runner reads as a hang, since it produces no step output. Reason: all four were invisible to a passing local check, and three of them were invisible in CI too until something else forced them into the open. How to apply here: the constitution states the rule; what is local to this repo is where it bites. When a job is a gate, check what actually depends on it rather than what its name implies. And treat a green local run of `scripts/audit/run-all.sh` as necessary-but-not-sufficient evidence before a tag — the environments differ in exactly the dimensions the checks depend on.

- **Never close work with a caveat attached — the status is the claim, and a summary is not where residue lives.** The rule is [§design-principles](framework/constitution.md#design-principles) — it ships to adopters, so this entry is the contributor-side record of what it cost *here*. Reason: surfaced 2026-08-19, three times in one session and each time in a different place — a stale prose claim left standing while 022 went to `done`, a detection gap reported as unmeasured while 026 went to `done`, and both narrated in the closing summary as though naming them discharged them. The user's ruling: *"the work is either complete or it isn't. don't change the spec status to done and then say this."* The tell is that each caveat was **true**, which is exactly why the habit survives — it reads as candour and costs nothing to write. What it actually does is move the exception from a channel that is re-read (the status, a task, a scenario) to one that is read once (a summary, a commit message). When the second of those caveats was finally investigated it was 28 broken links, a number thirty seconds of grep would have produced at any point. How to apply: when you notice something outstanding while closing, do not reach for the summary. Fix it; or record it where the pipeline will resurface it and let the status follow that record; or record an out-of-scope decision with its reason. Reopening a `done` spec is cheap and routine — preferring a caveat to a back-edge, to keep a status field looking clean, is the failure in its purest form. And when the residue is only knowable by measuring, measure: an unmeasured gap is a task, not a caveat.
- **Never design framework features that depend on human diligence or discipline.** The rule is [§design-principles](framework/constitution.md#design-principles) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-05-06 when evaluating an optional `## Upgrade Impact` spec section as a way to capture cross-version migration notes; rejected on this principle and the topic was tabled to inbox until a derivable design is found. How to apply: this is a hard filter on framework proposals, not a tiebreaker — if the only viable design relies on author discipline, the right answer is to defer the feature, not to ship the disciplined version "for now."

- **Removing an embedded copy is a corpus sweep, not a deletion — grep for what pointed at it, including the artifacts that *describe* it.** The rule is [§drift-prevention](framework/constitution.md#drift-prevention) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-09-13 replacing 020's §Embedded artifacts (a 561-line frozen copy of `framework/commands/review.md`) with a pointer, which took `spec.md` 803 → 275 lines. One deletion produced three separate corrections and none was in the deleted section. Inside the spec: `data-model.md` named a section that no longer existed, and `plan.md`'s affected-files table called the embedded artifact the canonical content, which is backwards under the canonical-sources rule and is the inversion that produced the snapshot in the first place. Outside it: 050's scenario [`a-canonical-source-is-pointed-at-not-copied`](specs/050-constitution/scenarios/a-canonical-source-is-pointed-at-not-copied.md) recorded that copy in the **present tense**, so removing the copy falsified the scenario that governs copies — correcting it by tense cost a second reopen, which is the real price of the removal and is easy to miss when pricing one. Deliberately **not** swept: a `review.md` naming the section as it stood at that pass, since a review record is pinned to its `reviewed-against` sha and `analyze.md` excludes `review.md` from link-adjacent drift for exactly that reason.

- **A `data-model.md` that claims "authoritative shapes" drifts from the runtime silently — check it against a record the runtime actually wrote, not against the code.** The rule is [§drift-prevention](framework/constitution.md#drift-prevention) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-09-13 re-reviewing 020, whose data-model was then the canonical record for both the `review:` block and `review.md`'s frontmatter (spec 057 has since left it one subject, and correcting that table is 057's task 18). Both tables had fallen behind: the block was missing `examined`, `scope` and `reviewed-digest`, and the frontmatter was missing `captured-issues`, `examined` and `scope` — six fields, all added by 022 and all live for months (058 has since retired `captured-issues` for `dispositions:`). 020's **own AC15** asserts that "`review.md` and the spec's `review:` block both record `examined`", so the authoritative record contradicted its own acceptance criterion, and nothing reported it.

- **Point at the canonical source — never embed a copy of it.** The rule is [§drift-prevention](framework/constitution.md#drift-prevention)'s *Canonical sources*, which states both reasons and the back-edge consequence — it ships to adopters, so this entry is the contributor-side record of what a copy cost *here* rather than a second copy of the rule (which would be the rule's own failure mode). Reason: confirmed by the user 2026-09-13, who directed that the pointer pattern "must be used when available" and that it belongs with adopters, not only here. The instance: `specs/020-code-review/spec.md` §Embedded artifacts is a frozen copy of `framework/commands/review.md` running lines 242–802 of an 802-line spec — **70% of the spec**, against a live source that had grown to 894 lines. Nothing flagged it and nothing could: the snapshot sits in a code fence, so no link check, anchor resolver or audit family reads it, and a scan for the next `##` heading stops 540 lines early on a heading belonging to the copied file. A person reading the spec is the only instrument that has ever found one. How to apply: when a spec needs to record what a command, template, manifest or rule file looked like, write what the spec *delivered* and link the source; the section above governs what replacing an existing copy costs. Rule and worked example: [`a-canonical-source-is-pointed-at-not-copied`](specs/050-constitution/scenarios/a-canonical-source-is-pointed-at-not-copied.md) under 050; 020's own remediation is **done**: its §Embedded artifacts copy was replaced with a pointer, taking that `spec.md` from 803 lines to 280.

- **A conformance test whose subject is drawn from corpus state can go vacuous, and its vacuity guard will then assert that an unhealthy corpus must exist.** The rule is [§design-principles](framework/constitution.md#design-principles) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: measured 2026-09-15 on `runtime/tests/mechanical_sweep_parity.rs`, which compares the Rust staleness rule against Family 19's Python over every `done` spec whose durable contracts differ from its `reviewed-against`. **That subject is thin — one spec, `020`'s `data-model.md`, has ever supplied it** — which is the shape the rule warns about. **The red-build half of this entry was wrong and is corrected 2026-09-16:** reopening 020 does *not* fail the suite. Three derivations agree. The `compared == 0` path is an `eprintln` and an early return, not an assertion, and `git show` at this entry's own commit (`ad7cba1e`) shows that soft path already present — it shipped in `ductus-v0.49.7` (`880e59a0`), eight minutes earlier the same morning. A live probe settles it: `set-status` 020 to `in-progress`, run the test, green, restore. The hard guard is a different one — `specs.is_empty()`, over every done spec with a resolvable `reviewed-against`, which one reopen cannot empty. What that guard *does* catch is a relocation: spec 057 moved the record out of `spec.md` and the subject went to zero, which is how the suite found a reader the sweep had missed. How to apply: the vacuity design here is already correct, so do not avoid reopening 020 on this entry's account — and when a recorded red-build claim blocks an action, re-derive it before believing it, because this one cost nothing to disprove and would have cost a wrong plan to honour.
