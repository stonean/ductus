# `ductus`

The `ductus` framework — a pipeline-driven spec-to-implementation flow scaffolded into adopted projects.

> **Agents:** this file is the committed home for project rules — append durable learnings to the matching section (Gotchas, Workflow, Boundaries, Code Style, Testing). Add a new section only when none fits.

## Constitution

See [constitution.md](framework/constitution.md) — guiding principles, development pipeline, spec lifecycle, and quality standards that ductus this project.

## Project Structure

The `framework/` directory is ductus's source — everything that ships to adopted projects via `/ductus`. It is laid out by IA primary purpose, not by file kind:

- `framework/constitution.md` — the constitution shipped to adopted projects (lands at `.ductus/constitution.md` in adopter repos)
- `framework/rules/` — domain rule sets adopted projects can reference (security-backend, security-frontend, …)
- `framework/templates/spec/` — templates consumed by an agent during the pipeline (spec, plan, tasks, data-model, research, scenario)
- `framework/templates/project/` — project document templates consumed once at adoption (agents, claude-md, system, errors, events, project-readme, gitignore, inbox)
- `framework/commands/` — operational slash command sources only
- `framework/bootstrap/` — the `ductus.md` installer plus per-agent permission files at `bootstrap/configure/{key}.md`

When adding files under `framework/`, place them by purpose, not by extension.

## Tech Stack

`ductus` is a text-first framework. The implementation is intentionally narrow:

- **Markdown** — every primary artifact (constitution, specs, plans, tasks, scenarios, rules, slash command sources, templates) is plain markdown; markdown is the source-of-truth *format* per [§text-first-artifacts](framework/constitution.md#text-first-artifacts). Format is not durability: `spec.md`, scenarios, and rules are durable sources of truth (with `plan.md` / `data-model.md` as design records), while `tasks.md` is ephemeral work-tracking — see [§tasks-phase](framework/constitution.md#tasks-phase).
- **Bash scripts** under `scripts/` — generators (`gen-*.sh`), the pre-commit hook installer (`install-hooks.sh`), and lints (`lint-*.sh`). All deterministic; no application logic.
- **GitHub Actions YAML** under `.github/workflows/` — CI configuration only.
- **Node.js / `npx`** — invoked at lint time for `markdownlint-cli2` only; not a build dependency, no `package.json` or `node_modules`.

There is no compiled language, no application runtime, no database, no service binary. An optional deterministic runtime is permitted under [§runtime-boundary](framework/constitution.md#runtime-boundary) but is not yet implemented (deferred to spec 022).

When tooling-language decisions arise (e.g., the runtime spec'd in 022, future binaries the framework might ship), prefer Rust. The `rmcp` crate is the reference MCP SDK, and the recent generation of Rust CLI tooling (`ripgrep`, `fd`, `bat`, `eza`, `helix`, `tokei`, `hyperfine`, etc.) has set the modern baseline for CLI UX patterns (single static binary, fast cold-start, sensible exit codes). Go is the credible alternative if development velocity matters more than production characteristics; other languages typically don't fit (distribution complexity, startup overhead, ecosystem fit).

## Workflow

- **Commit directly to `main` — this repo uses trunk-based development.** `ductus` is live-on-main: the installer and everything `/ductus` fetches track `main`, so there is no release branch and no feature-branch/PR step. When the user asks to land work, commit to `main` and push — do **not** branch first (the general "branch off the default branch before committing" default does not apply here). Reason: confirmed by the user 2026-06-11 after a `fix(003)` bootstrap fix was committed straight to `main`. How to apply: branch only when the user explicitly asks, or for a risky spike they want isolated; otherwise small commits reviewed in place on `main` are the norm, matching the existing history.
- **Never create a repository named `govern` under this account again, and never reuse a retired project name.** [049](specs/049-rename-govern-to-ductus/spec.md) renamed the project, and GitHub's rename redirect — which is what keeps every adopter's bootstrap fetch working until they next run it — holds *only for as long as the old name is not reused*. Recreating it silently severs that redirect for every adopter who has not yet re-bootstrapped: no error on this side, no signal, and the failure appears only in their next run. Reason: confirmed against GitHub's rename documentation while resolving 049; it is the one failure mode in that rename with no detection. How to apply: treat the retired name as permanently burned. The same reasoning applies to the retired crates.io crate, which is left published-and-deprecated rather than yanked so existing installs keep resolving.
- **A `runtime/` change ships via a `ductus-v<version>` tag — the commit alone reaches nobody.** The runtime is released (cross-compiled binaries + crates.io publish) by `.github/workflows/runtime-release.yml`, which triggers *only* on a pushed `ductus-v*` tag. So a change under `runtime/` is not "landed" until you: (1) bump **all three** of the repo-root `version` file, `runtime/Cargo.toml` `version`, and a matching `runtime/CHANGELOG.md` section, in one commit (tag scheme `ductus-v<MAJOR>.<MINOR>.<PATCH>`, a runtime bug fix is a patch bump) — `/audit` Family 20 fails when they disagree, and `/ductus` reads the `version` file to decide which runtime to acquire, so a stale pin sends every adopter after assets that do not exist; (2) commit to `main` and push; (3) `git tag ductus-v<version>` at that commit and `git push` the tag. The tag pipeline runs the framework self-audit (`scripts/audit/run-all.sh`) as a **hard release gate** — any finding aborts the publish, the asset upload, and the SBOM — so run it locally *before* tagging. **A local pass is weaker evidence than it looks:** `ductus-v0.28.0`'s first attempt was green locally and failed in CI, because Family 7 used a GNU awk extension that BSD awk (every macOS machine) rejects, and the family exited 0 rather than reporting it could not run. See the Design Principles entry on checks that cannot run — that failure mode hit four different surfaces in that one release. The parity goldens store the version as a `{{runtime-version}}` placeholder (`runtime/tests/parity.rs` substitutes `env!("CARGO_PKG_VERSION")` at compare time), so a version bump needs **no golden re-bless**; do not `BLESS=1` for a version change (it would hardcode the literal version and destroy the placeholder). If parity fails on the version line after a bump, the cause is a stale `runtime/target/release/ductus` — `cargo build --release` to refresh it, don't touch the goldens. Reason: surfaced 2026-06-30 — an `apply-manifest` exec-bit fix committed to `main` would have shipped to no adopter without the tag. How to apply: bump + CHANGELOG + commit + `ductus-v<version>` tag + push tag, in that order; never bless goldens to absorb a version delta. The tag is part of the spec's **completion gate**, not a separate release chore: a spec whose work registers a migration with `introduced_in = X` (or otherwise lands `runtime/` changes) is not complete until `ductus-vX` is tagged — surfaced again 2026-07-22, when 042 reached `done` with its `introduced_in = 0.22.0` runtime work untagged, so no adopter could receive the migration and a stale local server binary kept writing legacy paths.
- Read `framework/commands/{name}.md` before recommending, describing, or disambiguating a slash command — don't guess from the name. Source files are authoritative; the generated `.claude/commands/ductus/*.md` copies are produced by the pre-commit hook.
- `.ductus/config.toml` is treated as a shared adopter-side database, not as a schema owned by any single spec. When a new spec adds a section/key (its own "table"), document it in that spec's body and behavior — do not generate a §cross-spec-impact signpost on spec 019 (or any prior `.ductus/config.toml` spec) for the addition. Reason: surfaced 2026-05-10 while clarifying spec 020 — adding `[review] tech-stack-verified` did not warrant reopening 019. How to apply: only treat a `.ductus/config.toml` change as cross-spec impact when it modifies an *existing* key already documented in another spec.
- **No dead references in live artifacts.** When renaming or removing a name (spec slug, capability, command, identifier, parenthetical descriptor, etc.), update every reference across **live artifacts**: `framework/`, `scripts/`, `runtime/` (including `tests/fixtures/`, `tests/golden/`, `tests/parity/`), `.github/`, `docs/`, `README.md`, `AGENTS.md`, and `specs/NNN-*/` (including done-spec bodies). Reason: a reader following a forward-pointer or back-reference in live artifacts must never land on an outdated name; spec bodies are living documents that represent current state. The sweep is mechanical: every change in the diff is the same find-and-replace token substitution applied uniformly across the artifact set above. Because the diff is uniform, it qualifies as a **mechanical sweep** under [§spec-lifecycle](framework/constitution.md#spec-lifecycle) and does NOT trigger the `done → in-progress` back-edge — done specs stay `done` after a rename sweep. How to apply: when renaming X to Y, grep the live-artifact paths above and update every hit in a single commit; do not bundle the sweep with unrelated edits (a non-uniform diff would qualify as a meaningful edit and reopen affected specs). Commit messages and published PR/release notes stay as written (git history is the audit trail of what was named when).
- **A behavior change needs a prose-claim sweep, not just an identifier sweep.** The "No dead references" rule above catches renamed/removed *names*; a change that alters what the system *does* additionally needs a sweep for stale *claims* about the old behavior — and those claims contain none of the changed tokens, so a path/identifier-scoped grep silently passes over them. Reason: surfaced 2026-06-18 — spec 031 split MCP registration per-agent (Auggie/Antigravity now surface a manual `mcp add` command instead of `/ductus` writing a config file), and the spec's dead-reference sweep grepped only `.mcp.json` / `mcp_config.json` and passed, yet `README.md` still claimed `/ductus` "registers it automatically" for every agent — false for two of three. How to apply: when a spec changes behavior (not just a name), enumerate the behavioral claims the change falsifies and grep for them **by meaning** — registration / "automatically" / "by hand" / "writes the file" phrasings, not just the changed path — across the live-artifact set, `README.md` especially since it narrates behavior to users. A prose-claim fix to `README.md` or `docs/` is docs-only and does not reopen the originating spec; a stale behavioral claim *inside a done spec body* is a meaningful edit and does reopen it (route it through `/{project}:amend` / the back-edge).
- **A change to an agent-facing surface must cover every agent in the registry, not just Claude.** The Agent Registry in `framework/bootstrap/ductus.md` is the enumeration: `claude`, `auggie`, `antigravity`, `opencode` — four agents across three `layout` values (`claude-style`, `antigravity`, `opencode`). Because this repo dogfoods Claude, `scripts/gen-claude-commands.sh` regenerates `.claude/commands/ductus/` on every command-source edit and the self-audit's check-zero fails until it is re-run — so the Claude deployment is the one surface a change is *forced* to update. That regeneration passing is **not** evidence the other layouts are covered; it is evidence for exactly one of three. Reason: confirmed by the user 2026-08-14 after the Antigravity native rules mirror (`ductus.md` §Antigravity layout) was found to mirror only the **Shared Files** manifest rows, so a project-authored rule file was enforced by the pipeline for every agent yet invisible to the only agent that loads rules from a native dir. How to apply: before landing an agent-facing change, walk the §Derived values **Layout-derived** table row by row — command/skill path, invocation, `ductus` install path, settings file, permission shape, native rule-loading dir, native rules file, cleanup glob — and ask what the change means for each layout; note the per-agent impact (including "no change needed, reads the shared path") in the commit message. `scripts/audit/installer-registry-parity.sh` and `scripts/audit/host-namespace-parity.sh` enforce installer and namespace parity only — nothing audits per-layout *behavior* parity, so this one is contributor discipline, not a gate that will catch you.
- **Cross-service reference edits are mechanical-class (non-reopening).** Adding, removing, or rewriting a cross-service reference — an inline body link whose target resolves to a registered `.ductus/config.toml` `[services]` entry, plus the `references:` frontmatter that `.ductus/scripts/gen-cross-service-refs.sh` harvests from it — does NOT trigger the `done → in-progress` back-edge under [§spec-lifecycle](framework/constitution.md#spec-lifecycle) (case (b) of the mechanical-edit rule): references are informative cross-service navigation, never dependencies. The `references:` index is generator-managed and **strictly distinct from `dependencies:`** (harvested by `.ductus/scripts/gen-spec-deps.sh`); each generator owns its own frontmatter field and the two never share an index or enter the cycle check. Reason: spec 030. How to apply: a diff that only touches cross-service reference links and their harvested `references:` entries keeps a `done` spec at `done`, the same way a uniform rename sweep does — do not route it through `/{project}:amend`.
- **Criterion-label assignment is mechanical-class (non-reopening).** A diff whose every change inserts an `AC{n}:` label between an acceptance criterion's checkbox and its text — plus the `next-criterion:` counter that backs it — does NOT trigger the `done → in-progress` back-edge under [§spec-lifecycle](framework/constitution.md#spec-lifecycle) (case (c) of the mechanical-edit rule). The labelled text is byte-identical either side of the insert, so the diff is determinable without author judgment, and an identifier names a requirement without stating one — the same reason a rule ID is not the rule. Reason: spec 013's `criterion-identifiers` resolved the corpus backfill as a uniform mechanical sweep, and the sweep landed across 49 specs (47 of them `done`) on 2026-08-14; the constitution enumerated only cases (a) and (b) at the time, so the rule and the practice disagreed until case (c) was added. How to apply: run the sweep through `label-criteria`, never by hand, and confirm from the diff that no criterion's own text moved — a label insert bundled with a wording fix is a **meaningful** edit and does reopen the spec. Assignment is `max(highest label in body, next-criterion)`, never `max(body) + 1`; the counter is what keeps a deleted criterion's label from being reissued.
- **Never hand-write an `AC{n}:` label — add the criterion unlabelled and run `label-criteria`.** The label is `max(highest label in body, next-criterion)`, and `next-criterion` is frontmatter you are not reading while drafting prose, so a hand-written label is a guess that happens to be right until it collides with a retired one. Reason: surfaced twice in one session on 2026-08-15 while clarifying spec 048 — both times the guess matched, which is exactly what makes the habit durable. How to apply: write `- [ ] <criterion text>` with no label, then run the pass (`ductus label-criteria --feature <slug>`, or the MCP tool) and let it assign. If you have already written labels, leave them — stripping them renumbers from the advanced counter and opens a gap for no gain. The same rule is why `/{project}:specify` and `/{project}:clarify` invoke the pass rather than asking the agent to number: citing a criterion must never require counting a list, including in the session that wrote it.
- **Run `/ductus` per its spec — no ad-hoc prompts.** When executing `/ductus` (here or in any adopter), do not insert confirmation prompts beyond those the spec specifies (project inputs, agent-selection prompts on `--add-agent` / first-run, the registry-driven migration prompts from `framework/migrations.toml`). Specifically, do not stop to warn about uncommitted edits to update-strategy files, custom slash commands about to be removed by **Slash command cleanup**, or "data loss" from the `stale` → write-and-abort path. Reason: the spec already encodes safety — `.ductus/config.toml` `[pinned] files` is the documented opt-out; the stale path writes upstream and aborts cleanly (recoverable from git); slash command cleanup is unconditional for unpinned files. Extra prompts duplicate information the spec already gives the user and stall routine runs. How to apply: trust the documented behavior. The canonical statement of this rule lives as a "Procedural fidelity" preamble at the top of §Instructions in `framework/bootstrap/ductus.md` so it travels to every adopter via the self-update path; this AGENTS.md entry is the contributor-side mirror. If a real safety concern seems missing from the spec, raise it as a spec change (inbox entry or discussion) — not as a runtime prompt.
- **Use the `Write` tool, not Bash redirects, for `.ductus/session.toml`.** Spec 023 added explicit `Edit(.ductus/session.toml)` and `Write(.ductus/session.toml)` permission entries so pipeline commands stop prompting on session-file updates. Those entries scope the **Edit** and **Write** tools only — they do not cover Bash redirects (`cat > … <<EOF`, `tee`, etc.), which fall under separate `Bash(...)` permissions. Reason: surfaced 2026-05-17 while running `/ductus:target 025` — used a Bash heredoc and got a permission prompt despite spec 023's allowlist work. How to apply: when an agent writes the session file (or any `ductus`-owned state file with a dedicated `Write(...)` allow entry), use the `Write` tool. Do not widen the Bash allowlist with patterns like `Bash(cat > * *)` to compensate — that grants write-anywhere-via-shell and defeats the per-path scoping. A narrow `Bash(cat > .ductus/session.toml *)` would be safe, but reaching for the right tool is cheaper than maintaining two surfaces.
- **Use repo-relative paths in tool calls.** When invoking `Read`, `Write`, `Edit`, or `Bash` against files in this repo, use repo-relative paths (e.g., `.ductus/session.toml`, `specs/027-bootstrap-migration-registry/spec.md`) — never `/Users/stonean/src/stonean/ductus/...`. Reason: surfaced 2026-05-17 during `/ductus:specify` — agent used an absolute path for the session-file write. Absolute paths leak the maintainer's home directory into transcripts, make diffs and error messages noisier, and break path-pattern matching for `permissions.allow` entries that are written relative. How to apply: every framework artifact (rule files, command sources, scripts, spec links) already uses relative paths; mirror that convention in tool calls. The only places absolutes are appropriate are temp files under `/tmp` or `/private/tmp` and explicit references to files in other working directories listed in the harness environment.
- **Never call specs "frozen archaeology" or use frozen-archaeology phrasing.** Specs are living documents that represent current state. Edits to a `done` spec body trigger the `done → in-progress` back-edge via `/{project}:amend` (or directly via `set-status` per the rule below); rename sweeps stay `done` because they qualify as mechanical edits under §spec-lifecycle. Reason: spec 023's `living-specs` scenario explicitly dropped the "frozen archaeology" exception from constitution §drift-prevention; surfaced 2026-05-24 when I wrote "outside frozen-archaeology specs" into spec 022's task 41 and the user corrected it. How to apply: when describing why a done spec shouldn't be edited, frame it in terms of the back-edge cost (it reopens the spec and goes through the pipeline again), not as "the spec is frozen." When describing a sweep that touches done specs, frame it as a §spec-lifecycle mechanical edit (uniform find-and-replace across live artifacts) that keeps the spec at `done`. Live framework files that still carry frozen-archaeology language (`framework/commands/analyze.md`, `framework/migrations/spec-and-plan-sunset.md`) are drift candidates from before the rule was dropped — flag them when adjacent, but do not bundle the sweep with unrelated work.
- **Re-open a `done` spec via `set-status` when the only intent is to reflect on-disk edits, not via `/{project}:amend`.** When the agent (acting on the user's behalf in conversation) has already added scenario files under `specs/{feature}/scenarios/` or appended lines to `spec.md` / `tasks.md`, and the spec's `status: done` is the only remaining inconsistency, invoke `set-status` (`from: done`, `to: in-progress`) directly and report the on-disk delta. Do not prompt `/{project}:amend` — the refinement loop expects an input to classify, and producing a synthetic re-open input is friction (the classifier will either insist on scenario shape and create a second file, or treat the input as a no-op). Reason: surfaced during the gvrn 0.10.0 session-consolidation cycle (see `specs/014-reclarify-backedge/scenarios/reopen-after-informal-edits.md` — Option A). How to apply: only when there is *no* new input from the user to capture. If the user is also adding new scenario content beyond what is already on disk, route the new content through `/{project}:amend` after flipping status — Option A is a shortcut for the re-open-only case, not a replacement for the scenario-add flow. The command-side safety net (Option B in `framework/commands/amend.md`) covers hosts without an agent in the loop.
- **Add a rule to its surface's home spec via the back-edge — do not spawn a new spec for it.** When a new enforceable rule belongs to an *existing* rule surface (e.g. a new `QUAL-*` category/rule in `quality-cross.md`, owned by spec 036), extend that surface's owning spec through the normal `done → in-progress` back-edge — register the category in its `data-model.md`, add the rule, add a task — rather than creating a new feature spec. Reason: a separate spec per rule fragments the durable record of one concern across many specs, making its purpose harder to follow; this is the drift §spec-lifecycle's anti-proliferation stance ("scenarios evolve the existing spec rather than spawning a new one") exists to prevent. Surfaced 2026-07-18 — I proposed a follow-on spec for the code-side grounding rule (`QUAL-GROUND-001`) and the user corrected it. How to apply: keep the cross-cutting principle in its single canonical home (e.g. constitution §grounding) and have each enforcement point — a rule, a command check — reference it; route a new rule on an existing surface into that surface's spec. Reserve a brand-new spec for a genuinely new rule *file*/surface, per constitution §rules.
- **Route runtime work to spec 022 via the back-edge — 022 is the durable home for runtime rules.** When a new spec's behavior is carried by the `ductus` runtime — a new `check-artifacts` family, a new field on a primitive's result, a change to a shared parser under `runtime/src/` — the primitive-level changes land as **scenarios under `022-deterministic-runtime`**, each back-linking to the requiring spec per §cross-spec-impact, with `specs/022-deterministic-runtime/data-model.md` updated for the new field or family. Recording them on a `done` 022 takes it through the normal `done → in-progress` back-edge. The requiring spec keeps what it actually owns: the requirement, its constitution amendments, its command-source documentation, and its acceptance criteria — which are verified against shipped behavior regardless of which spec's tasks produced it, so the requiring spec cannot reach `done` before the 022 scenarios do. Reason: confirmed by the user 2026-08-02 while planning 045 — 022 owns the runtime and is where runtime rules stay findable, rather than being scattered across every spec that happened to need one. The precedent is 046, which added the fifth `check-artifacts` family exactly this way (`specs/046-scenario-open-question-visibility/spec.md` §Implementation ownership); 022's `data-model.md` is also the canonical registry of primitive result shapes and check families, so a new family has to be recorded there whatever else happens. How to apply: state the ownership split as a plan decision, open the back-edge before any runtime work, and give each scenario a matching task in 022's `tasks.md` so the scenario→task mapping family stays clean. This is the runtime analog of the rule-surface entry above — same principle, different surface.
- **A canonical table living on a `done` spec is synced as a mechanical edit — no back-edge.** When runtime behavior changes and the constitution's canonical-sources map points at a table inside some *other* spec's `data-model.md`, update that table in the same change and leave the spec `done`. The routing rule above sends the *behavior* to 022; it says nothing about a canonical record that happens to be housed elsewhere, and the two obligations do not conflict — 022 gains the scenario, the canonical table gains the row. Reason: surfaced 2026-08-03 — adding three `NON_ASSERTION_MARKERS` phrases required editing 045's data-model marker table, which is designated canonical, and `/ductus:review` flagged the un-back-edged edit as a low-confidence process finding. Leaving the table stale would have made a `done` spec's canonical record contradict shipped behavior, which is the drift §drift-prevention exists to catch — a strictly worse outcome than the reopen it was avoiding. How to apply: treat the sync as a uniform find-and-replace under §spec-lifecycle's mechanical-edit rule, the same class as a rename sweep; record the change in the 022 scenario that caused it so the *why* lives with the behavior. If the edit is more than a factual sync — a contract change, a new decision — it is a meaningful edit and does reopen the spec. When a table needs syncing on more than one occasion, prefer moving it to 022's `data-model.md` and leaving a pointer behind, which removes the question entirely.
- **Backtick a primitive in an `## Instructions` step only when the walker can actually supply its arguments.** The exec parser dispatches any step naming a `PRIMITIVE_NAMES` token in a code span, and it has no per-step argument binding — so a step that needs *per-item* arguments the walker does not hold (a value computed from findings, a loop body) breaks `runtime exec` even though the markdown reads correctly. Mark such a step a host responsibility instead: name the primitive **without backticks** and add `<!-- audit:ignore-promotion -->`. Reason: surfaced 2026-08-03 implementing spec 047 — `/ductus:analyze`'s new capture step backticked `append-inbox`, and the walker dispatched it with no `text` argument, failing `analyze_basic_stream_matches_golden` with a non-zero exit. The parity suite caught it; nothing else would have, since the parseability lint accepts a step naming exactly one primitive. How to apply: before backticking a primitive in a step, ask whether the walker can construct its full argument set from context it already has. If the answer is "once per finding" or "the host computes it", it is host work — the same shape as the render step it sits beside. This is the argument-binding half of the `audit:ignore-promotion` gotcha above, which covers the parser half.
- **Do not invoke `cargo build` twice in one shell command and read only the second output.** The pattern `cargo build 2>&1 | grep -E '^error' -A8; cargo build 2>&1 | tail -2` compiles on the first invocation and reports `Finished` in ~0.07s on the second, so the visible output says nothing was built even though it was. Reason: surfaced 2026-08-03 — I read the no-op line, concluded the target dir was stale, and ran `cargo clean -p ductus` three times (clearing 64.8 GiB, 4.0 GiB, 3.1 GiB) chasing a build problem that did not exist; an earlier version of this entry recorded that phantom as a cargo bug, which was wrong. How to apply: build once and capture the output to a variable or a file, then inspect it — `out=$(cargo build 2>&1); echo "$out" | grep …`. When a change appears to have no effect, verify against the artifact rather than the build log: `strings target/debug/ductus | grep '<a new literal>'` answers definitively whether the binary carries your code.
- **A CI check that reads git history needs `fetch-depth: 0`.** `actions/checkout` defaults to a shallow clone with a single commit, so any check resolving a recorded sha — `git cat-file -e`, `git diff <old>..HEAD`, `git log` beyond HEAD — sees no history and reports every subject as unresolvable. Reason: surfaced 2026-08-03 — `/ductus:audit` Family 19 (`review-freshness`) resolves each spec's `review.reviewed-against`; under the default shallow checkout it emitted "not a commit in this repo" for all 48 specs and failed the `gvrn-v0.27.1` release gate, which skipped the publish. It passed locally on every run because a developer checkout has full history. How to apply: when a check reaches into history, add `with: { fetch-depth: 0 }` to the checkout of **every** job that runs it — in this repo, `runtime-release.yml`'s audit job and `framework-checks.yml`'s — and say why in a comment, because the default is invisible until it bites. A local pass is not evidence the check works in CI; the environments differ in exactly the dimension the check depends on.
- **When an item routes to a chore, fix it — do not park it.** `/ductus:groom`'s chore route leaves the item in `specs/inbox.md` to be "done directly"; in this repo, *done directly* means the agent does it in the same pass, then removes the inbox item because it is resolved. Reason: confirmed by the user 2026-08-14 mid-groom, after I proposed leaving an anchor-notation cleanup in the inbox. A parked chore is re-read and re-routed on every subsequent groom pass, so the recurring cost of carrying it exceeds the one-time cost of the fix, and the inbox stops reflecting real backlog. How to apply: when the route is `chore` and the fix is mechanical and in-scope (lint/formatting, notation, dead text, repo hygiene), make the edit, verify it with whatever check surfaced it (`resolve-anchor`, `markdownlint-cli2`, the relevant audit script), then `remove-inbox-item`. Report it as fixed rather than as a chore left behind. Leave it in the inbox only when the fix is genuinely blocked or turns out not to be mechanical after all — say which. This is contributor practice for this repo; it does not change what `framework/commands/groom.md` ships to adopters.
- **`git checkout -- specs/{feature}/` silently reverts uncommitted pipeline state.** A status flip (`set-status`), a ticked criterion (`mark-criterion`), and a ticked subtask (`mark-task`) are writes to tracked files, so a restore aimed at *content* takes the *bookkeeping* with it — and nothing reports the loss, because the pipeline reads status from the file it just reverted. Reason: surfaced 2026-08-15 during 049's sweep. The sweep damaged 049's own artifacts (its substitution table read `.ductus/ -> .ductus/` and its title became "Rename ductus to ductus"), so I restored the directory from HEAD; that also took back the `planned -> in-progress` flip made earlier in the session but never committed, and the spec sat at `planned` through four subsequent commits until the user noticed. How to apply: before `git checkout --` on a spec directory, note the current `status:` and checkbox state, and re-apply them after — or restore the specific damaged files by path rather than the whole directory. Better, commit the status transition as its own step so a content restore cannot reach it. The same hazard applies to `git stash`, `git restore`, and any `--hard` reset over a spec directory mid-pipeline.
- **Renaming this repository orphans contributor-local state that no migration can reach.** The adopter migration converges state named for the project; it cannot touch state keyed to the project *path*, because that is not in the repo and differs per contributor. Nothing errors when it goes missing — the state is simply never found again, which is why it needs a checklist rather than a check. Reason: [049](specs/049-rename-govern-to-ductus/spec.md) renamed the project and the GitHub repository; the local half was hit immediately, and the agent-memory row was found the hard way. How to apply: after renaming the repository, on **each** machine you work from — (1) rename the local checkout directory to match; (2) repoint `git remote` to the new URL (the redirect works, but a stale remote keeps the retired name in daily use); (3) move any per-project agent state stored under a path-derived slug — Claude Code keeps memory at `~/.claude/projects/<path-slug>/memory/`, so copy that directory to the new slug **and correct the absolute paths recorded inside it**, which a copy alone leaves pointing at the old checkout; (4) fix anything else keyed to the old path — shell aliases, editor workspaces, worktrees. None of this is reachable from a `/ductus` run.

## Gotchas

- Use `npx markdownlint-cli2` to run markdown linting — do not suggest installing it globally.
- The command generator substitutes `{project}` → `gov` and `{cli-config-dir}` → `.claude`, and writes the Claude-specific permission file (`framework/bootstrap/configure/claude.md`) as `configure.md` in the gov command directory.
- **An edit to `framework/commands/*.md` is invisible to that slash command until the generator re-runs — including to the command you are editing, in the same session.** The pre-commit hook regenerates `.claude/commands/ductus/` (see Workflow), but that is *commit* time; the agent host loads the installed copy at *invocation* time. So editing a command source and then invoking that command walks the pre-edit text, silently. The same shape applies one layer down, but the loop is shorter than it used to be: this repo sets `[runtime] path = "runtime/target/release/ductus"` and registers the pointer (`.ductus/bin/ductus`) as the MCP command, so a `runtime/` source change is live for MCP tool calls after `cargo build --release` **and** an MCP server restart — which means a new session, since the host spawns the server once. There is no `cargo install` step and `PATH` is not consulted; the pointer resolves straight to the build in the working tree. Reason: surfaced 2026-08-14 — `framework/commands/analyze.md` was corrected to document `--fix`'s second trigger, and the very next `/ductus:analyze` invocation loaded the stale installed copy and displayed the old text; in the same session the `append-*` marker fix was published as `gvrn-v0.27.2` while every MCP call kept using the Aug-3 binary (that half is what `[runtime] path` now prevents — spec 048). How to apply: after editing any `framework/commands/*.md`, run `scripts/gen-claude-commands.sh` before invoking that command (it is idempotent, and the pre-commit hook re-runs it anyway); after a `runtime/` change, do not trust an MCP tool call in the *current* session to exercise it — verify with `cargo test`, and treat the running server as the pre-build binary until the session is restarted.
- `.claude/commands/ductus/init.md` is the one exception to the generator rule — it is `ductus`-specific (no source counterpart) and is hand-maintained. The generator leaves it untouched.
- Never `git add -A` / `git add .` in this repo — it sweeps untracked `/specify` drafts (e.g. an in-progress `specs/NNN-*/spec.md`) into the commit, which spec 017 (`tracked-specs-not-worktree`) forbids. Stage explicit paths.
- A new adopter-facing `.ductus/scripts/gen-*.sh` generator wires into more than this repo's own `.githooks/pre-commit`. For adopters to actually receive and run it, two more sites are required: (1) a row in the **Shared Files** manifest in `framework/bootstrap/ductus.md` (`update` strategy, `.ductus/scripts/<name>.sh` → `.ductus/scripts/<name>.sh`) so `/ductus` copies it into adopter projects, and (2) an invocation in the adopter hook `framework/bootstrap/hooks/ductus-pre-commit` (run it `--staged` so a commit only rewrites its own specs). Adding it only to this repo's `.githooks/pre-commit` exercises it on `ductus`'s own commits — so CI and local dogfooding stay green while every adopter silently misses the generator until someone notices. Reason: surfaced 2026-06-17 — spec 030's `gen-cross-service-refs.sh` was wired into `.githooks/pre-commit` but not the manifest or adopter hook, so a `/ductus` update in adopter projects never installed or ran it. How to apply: when adding a generator that derives adopter spec frontmatter, wire all three sites (this repo's hook, the manifest row, the adopter hook) in the same change; if it derives per-spec frontmatter independently it can take `--staged` directly, but if it needs a cross-spec view (like `gen-spec-deps.sh`'s cycle check) keep the full read and gate only the disk write on staged membership.
- `write_atomic_bytes` (the create-then-rename helper backing every primitive write) lands the destination at the fresh tempfile's mode — `0600` on Unix — discarding whatever mode the file should carry. For markdown/JSON this is invisible (git tracks only the exec bit), but a primitive that writes a file expected to be **executable** must re-apply the mode itself. `apply-manifest` mirrors the *source* file's `Permissions` onto the dest after each write (`mirror_source_mode`, `cp -p` semantics) because the **Shared Files** manifest ships `.ductus/scripts/gen-*.sh` with `update` strategy and the `ductus-pre-commit` hook must be able to exec them; the staging source carries `+x` because `extract-archive` preserves archive-header modes (`apply_unix_mode`). Reason: surfaced 2026-06-30 — a `/ductus` run rewrote the generators to `0600`, failing the pre-commit hook (and a fresh adopter's `created` write would emit a non-executable generator + broken hook). How to apply: any new primitive writing an executable (or otherwise non-`0600`) file must restore the intended mode after `write_atomic_bytes` — do not assume the helper preserves it; mirror the source's `Permissions` when copying, like `apply-manifest` and `extract-archive` do.
- `runtime/rust-toolchain.toml` pins `components = ["clippy", "rustfmt"]`, and every `cargo` command run under `runtime/` makes rustup honor that file — auto-installing any missing component *mid-build*, a path that hits rustup's `detected conflict: 'bin/cargo-fmt'` bug and aborts the job. So any CI job that runs `cargo` under `runtime/` must pre-install those components via the `dtolnay/rust-toolchain` step's `components: clippy, rustfmt` input, so nothing is left for the runtime auto-install path to do. `runtime.yml` (which lints) always had it; the fix is to keep every other `runtime/`-touching workflow in sync. Reason: surfaced 2026-07-11 — the `gvrn-v0.16.0` release failed because `runtime-release.yml`'s `dtolnay` steps omitted `components:`; the `aarch64-unknown-linux-gnu` cross job's first `cargo` call (`cargo install cargo-zigbuild`) triggered the auto-install conflict. It was the first release tagged after the toolchain pin (commit 19d9229), so no earlier release exposed it. How to apply: when adding or editing a workflow that runs any `cargo` command from `runtime/`, give its `dtolnay/rust-toolchain@<ver>` step `components: clippy, rustfmt` matching `rust-toolchain.toml` — do not rely on rustup's toolchain-file auto-install to supply them.
- A new `ductus` runtime primitive wires into more than `primitives/mod.rs` + `mcp/server.rs`. Building and exposing it over MCP needs `schema/primitives.rs` (Args/Result types), `primitives/<name>.rs` + `primitives/mod.rs` (`pub mod`), and `mcp/server.rs` (`TOOL_NAMES` + a `#[tool]` method). Three more sites are needed the moment a slash command *uses* it: `parser/mod.rs` (`PRIMITIVE_NAMES`) so a command's `## Instructions` can backtick the name without failing `lint-procedure-parseability`; `interpreter/mod.rs` (`dispatch_primitive` match arm) so `runtime exec` can call it (the path the parity tests drive); and `main.rs` (`Command` enum variant + dispatch) for the `ductus <name>` CLI surface. Add the name to `framework/runtime-tools.txt` for `lint-tool-coverage`. Reason: surfaced 2026-06-14 implementing spec 030's `resolve-references` — MCP exposure alone passes `cargo test` and `tests/mcp.rs` (which only checks `TOOL_NAMES ⊇ runtime-tools.txt`), so the gap stays invisible until a command references the primitive. How to apply: decide up front whether a command will reference the primitive; if yes, wire all six Rust sites + `runtime-tools.txt` in the same change.
- `<!-- audit:ignore-promotion -->` silences the framework self-audit's Family-9 (primitive-promotion) check for a prose-only `## Instructions` step, but it does **not** change how the runtime's exec parser reads that step. The parser (`parser/mod.rs`) marks any step naming a `PRIMITIVE_NAMES` token in a backticked code span as a primitive dispatch, and `lint-procedure-parseability` only rejects a step naming *two or more* primitives — a step naming exactly one is legal. So a host-responsibility step marked `audit:ignore-promotion` that mentions a primitive in backticks (e.g. a `--fix` action described "via `set-status`") gets dispatched by `runtime exec`, which then errors or performs an unintended mutation. Reason: surfaced 2026-07-12 — `/ductus:analyze` step 13 (report render, a host responsibility) referenced `set-status` in backticks; the exec walker dispatched it and the `analyze` parity golden failed with a non-zero exit, even though the parseability lint passed and the audit ignored the step. How to apply: in a numbered `## Instructions` step, backtick a primitive name only when the step is meant to *dispatch* it. To reference another primitive without dispatching — a leverage note, a cross-reference — name it without backticks, or move the reference into non-step prose (the command's preamble or its Markdown-only reference), where multiple primitive names can be backticked freely. `audit:ignore-promotion` is about the audit, not the parser.

- **A markdown link in a spec body creates a `dependencies:` edge — cite in prose when you mean a citation.** `.ductus/scripts/gen-spec-deps.sh` harvests every inline link to a sibling `specs/NNN-*/` path and rewrites the frontmatter `dependencies:` union from it, so a link added purely to reference another spec's *review* or *history* silently declares a dependency. Reason: surfaced 2026-08-16 — a link to `013`'s `review.md` from `049`'s body made the generator add `013-text-first-artifacts` to 049's dependencies, which is false (049 does not depend on 013; it merely cites it). The pre-commit hook applied it before anyone looked. How to apply: to cite without an edge, use a backticked slug (`` `013-text-first-artifacts` ``) rather than a link, or place the link under a §See Also region, which spec 017's `skip-prose-cross-references` opt-out already exempts. After editing a spec body, read the `dependencies:` line in the hook's output before committing — the generator reports `Updated …` when it rewrote one.
- **`create-scenario` appends its own Open/Resolved Questions scaffolding — do not author those headings in the body you pass it.** The primitive frames the body with `section:` frontmatter, the H1, *and* `## Open Questions` / `## Resolved Questions`. A body that already carries an `## Open Questions` section produces two, which `npx markdownlint-cli2` rejects as MD024 (duplicate heading). Reason: surfaced 2026-08-16 grooming an inbox item into a scenario carrying one real open question. How to apply: pass Context / Behavior / Edge Cases only, then edit the scaffolded `## Open Questions` section afterwards to add entries — or write the whole file with `Write` if it needs questions at creation time.
- **A version bump needs one build without `--locked`.** Every other runtime command in this repo uses `--locked`, but bumping `runtime/Cargo.toml`'s `version` changes the package's own entry in `Cargo.lock`, and `--locked` exists to forbid exactly that (`error: cannot update the lock file … because --locked was passed`). Run `cargo build --release --offline` once to refresh the lock, after which `--locked` works again. Reason: surfaced 2026-08-16 cutting `ductus-v0.28.1`. How to apply: bump, one `--offline` build, then verify `--locked` succeeds before committing — and remember the release binary must be rebuilt anyway, because `runtime/tests/parity.rs` substitutes `env!("CARGO_PKG_VERSION")` at compare time and a stale binary fails the parity version line. Never `BLESS=1` to absorb that failure; it would replace the `{{runtime-version}}` placeholder with a literal.

## Boundaries

- **No host-level enforcement of the deterministic (`ductus`) path — it is a deliberate non-goal.** `/ductus`'s State-A execution contract (spec 029, scenario `state-a-deterministic-path-forcing`) uses binding *procedure language* to get a wired runtime actually used. `ductus` does **not** enforce it at the host level — no denying `curl`/`tar` while `ductus` is registered, no State-A-only procedure variant with the shell stripped. Reason: host enforcement would block the legitimate non-primitive shell steps the bootstrap needs (gitignore `curl`, `git config`, `chmod`), is host-specific and a permanent per-host maintenance tax, and breaks [§runtime-boundary](framework/constitution.md#runtime-boundary)'s "neither path wraps the other" parity by demoting the markdown path. A model that ignores the binding contract falls back to the correct-but-pricier markdown path — an accepted outcome, not a gap. How to apply: do not propose or build host enforcement as a follow-up; if the procedure-level contract proves insufficient for a given model, the answer is a more capable model, not coercion.
- Never edit `.claude/commands/ductus/*.md` directly — your changes will be overwritten the next time the generator runs. Edit the source under `framework/commands/` (or `framework/bootstrap/configure/claude.md` for the `configure` command). **When writing or rewriting that source, use placeholders, not substituted literals.** Write `{cli-config-dir}/` (not `.claude/`) and `/{project}:` (not `/ductus:`); the generator substitutes them on the way to `.claude/commands/ductus/*.md`. Reason: surfaced 2026-05-23 during the spec-022 `/ductus:status` rewrite — I read the deployed (already-substituted) copy when drafting the rewrite and shipped hardcoded `/ductus:` and `.claude/` literals to the source, which broke the framework-checks CI on Family 4 of `scripts/audit/run-all.sh` (`placeholder-roundtrip`). How to apply: when in doubt, `git show HEAD:framework/commands/{name}.md` to see the source convention before editing; the `placeholder-roundtrip` audit is the post-hoc check, not the first line of defense.

## Design Principles

- **A check that cannot run must never be indistinguishable from a check that passed.** This is `QUAL-CLAIM-001` applied to the project's own machinery, and it is the single most expensive failure mode this repo has produced. It surfaced four separate times while shipping `ductus-v0.28.0`, each time as a green signal that meant nothing: `scripts/audit/sibling-coupling.sh` used a GNU awk extension, so on every macOS machine the extraction aborted, the family found nothing, and it exited 0 — a release gate that was dead locally and alive in CI; `release-assets` in `runtime-release.yml` needed only `build`, so the self-audit gated the crates.io publish while the binaries adopters actually download shipped regardless; the acquisition workflow was triggered by `on: release: [published]`, which GitHub never fires for a release created with the default `GITHUB_TOKEN`, so the invariant the constitution requires would have been cited by name and never once executed; and the `macos-13` runner label no longer resolves, so that leg sat queued with no runner while the others passed — a missing runner reads as a hang, since it produces no step output. Reason: all four were invisible to a passing local check, and three of them were invisible in CI too until something else forced them into the open. How to apply: when you add a gate, prove it **fails** before trusting that it passes — break the thing it guards and watch it go red. When a script can fail to examine its subject (a missing tool, an unsupported extension, an empty derivation), make that a finding rather than a silent zero. When a job is a gate, check what actually depends on it rather than what its name implies. And treat a green local run of `scripts/audit/run-all.sh` as necessary-but-not-sufficient evidence before a tag: the environments differ in exactly the dimensions the checks depend on.

- **Never design framework features that depend on human diligence or discipline.** Any artifact section, frontmatter field, command behavior, or workflow step that requires an author to *remember* to fill it in, set a flag, update a doc alongside code, or otherwise be careful will fail in practice — silently and asymmetrically (the cases where it gets skipped are exactly the cases where it mattered most). When proposing a new input, ask "what happens when an author forgets?" If the answer is "the feature degrades silently," redesign the input as **derived** (extracted from existing artifacts, frontmatter, git history, code analysis) or don't ship it. Reason: surfaced 2026-05-06 when evaluating an optional `## Upgrade Impact` spec section as a way to capture cross-version migration notes; rejected on this principle and the topic was tabled to inbox until a derivable design is found. How to apply: this is a hard filter on framework proposals, not a tiebreaker — if the only viable design relies on author discipline, the right answer is to defer the feature, not to ship the disciplined version "for now."
