# `ductus`

The `ductus` framework — a pipeline-driven spec-to-implementation flow scaffolded into adopted projects.

> **Agents:** this file is the committed home for project rules — append durable learnings to the matching section (Gotchas, Workflow, Boundaries, Code Style, Testing). Add a new section only when none fits.

## Constitution

See [constitution.md](framework/constitution.md) — guiding principles, development pipeline, spec lifecycle, and quality standards that govern this project.

## Project Structure

The `framework/` directory is ductus's source — everything that ships to adopted projects via `/ductus`. It is laid out by IA primary purpose, not by file kind:

- `framework/constitution.md` — the constitution shipped to adopted projects (lands at `.ductus/constitution.md` in adopter repos)
- `framework/rules/` — domain rule sets adopted projects can reference (security-backend, security-frontend, …)
- `framework/templates/spec/` — templates consumed by an agent during the pipeline (spec, plan, tasks, data-model, research, scenario)
- `framework/templates/project/` — project document templates consumed once at adoption (agents, claude-md, system, errors, events, project-readme, gitignore, inbox)
- `framework/commands/` — operational slash command sources only
- `framework/bootstrap/` — the `ductus.md` installer plus per-agent permission files at `bootstrap/configure/{key}.md`

When adding files under `framework/`, place them by purpose, not by extension.

## Tech Stack

`ductus` is a text-first framework. The implementation is intentionally narrow:

- **Markdown** — every primary artifact (constitution, specs, plans, tasks, scenarios, rules, slash command sources, templates) is plain markdown; markdown is the source-of-truth *format* per [§text-first-artifacts](framework/constitution.md#text-first-artifacts). Format is not durability: `spec.md`, scenarios, and rules are durable sources of truth (with `plan.md` / `data-model.md` as design records), while `tasks.md` is ephemeral work-tracking — see [§tasks-phase](framework/constitution.md#tasks-phase).
- **Bash scripts** under `scripts/` — generators (`gen-*.sh`), the pre-commit hook installer (`install-hooks.sh`), and lints (`lint-*.sh`). All deterministic; no application logic.
- **GitHub Actions YAML** under `.github/workflows/` — CI configuration only.
- **Node.js / `npx`** — invoked at lint time for `markdownlint-cli2` only; not a build dependency, no `package.json` or `node_modules`.
- **Rust** under `runtime/` — the `ductus` deterministic runtime (spec 022), a bin + lib crate on edition 2024 with an MSRV of `1.88`, using `rmcp` as the MCP SDK. It executes the mechanical half of every pipeline command (parsing frontmatter and markdown structure, walking tasks, atomic writes, gate handshakes) and exposes each capability as an MCP tool per [§runtime-boundary](framework/constitution.md#runtime-boundary) principle 5. It never calls an LLM — semantic judgment stays in the slash commands (principle 2).

The runtime is **required, and acquired by the pipeline** ([§runtime-boundary](framework/constitution.md#runtime-boundary) principle 3): `/ductus` downloads the pinned release asset into a ductus-owned store during adoption, so acquisition failure halts the run rather than degrading to a second execution path. It ships in lockstep with the framework — see the release entry under §Workflow for the three version sites and the `ductus-v<version>` tag that actually delivers a `runtime/` change. Binaries are published for five targets; `PATH` is never consulted. There is still no database and no long-running service, and [§runtime-boundary](framework/constitution.md#runtime-boundary) ("What the runtime is not") forbids adding one without a constitutional amendment.

When further tooling-language decisions arise (a second binary the framework might ship), prefer Rust, as the runtime already does. The recent generation of Rust CLI tooling (`ripgrep`, `fd`, `bat`, `eza`, `helix`, `tokei`, `hyperfine`, etc.) has set the modern baseline for CLI UX patterns (single static binary, fast cold-start, sensible exit codes). Go is the credible alternative if development velocity matters more than production characteristics; other languages typically don't fit (distribution complexity, startup overhead, ecosystem fit).

## Workflow

- **Commit directly to `main` — this repo uses trunk-based development.** `ductus` is live-on-main: the installer and everything `/ductus` fetches track `main`, so there is no release branch and no feature-branch/PR step. When the user asks to land work, commit to `main` and push — do **not** branch first (the general "branch off the default branch before committing" default does not apply here). Reason: confirmed by the user 2026-06-11 after a `fix(003)` bootstrap fix was committed straight to `main`. How to apply: branch only when the user explicitly asks, or for a risky spike they want isolated; otherwise small commits reviewed in place on `main` are the norm, matching the existing history.
- **Never create a repository named `govern` under this account again, and never reuse a retired project name.** [049](specs/049-rename-govern-to-ductus/spec.md) renamed the project, and GitHub's rename redirect — which is what keeps every adopter's bootstrap fetch working until they next run it — holds *only for as long as the old name is not reused*. Recreating it silently severs that redirect for every adopter who has not yet re-bootstrapped: no error on this side, no signal, and the failure appears only in their next run. Reason: confirmed against GitHub's rename documentation while resolving 049; it is the one failure mode in that rename with no detection. How to apply: treat the retired name as permanently burned. The same reasoning applies to the retired crates.io crate, which is left published-and-deprecated rather than yanked so existing installs keep resolving.
- **A `runtime/` change ships via a `ductus-v<version>` tag — the commit alone reaches nobody.** The runtime is released (cross-compiled binaries + crates.io publish) by `.github/workflows/runtime-release.yml`, which triggers *only* on a pushed `ductus-v*` tag. So a change under `runtime/` is not "landed" until you: (1) bump **all three** of the repo-root `version` file, `runtime/Cargo.toml` `version`, and a matching `runtime/CHANGELOG.md` section, in one commit (tag scheme `ductus-v<MAJOR>.<MINOR>.<PATCH>`, a runtime bug fix is a patch bump) — `/audit` Family 20 fails when they disagree, and `/ductus` reads the `version` file to decide which runtime to acquire, so a stale pin sends every adopter after assets that do not exist; (2) commit to `main` and push; (3) `git tag ductus-v<version>` at that commit and `git push` the tag. The tag pipeline runs the framework self-audit (`scripts/audit/run-all.sh`) as a **hard release gate** — any finding aborts the publish, the asset upload, and the SBOM — so run it locally *before* tagging. **A local pass is weaker evidence than it looks:** `ductus-v0.28.0`'s first attempt was green locally and failed in CI, because Family 7 used a GNU awk extension that BSD awk (every macOS machine) rejects, and the family exited 0 rather than reporting it could not run. See the Design Principles entry on checks that cannot run — that failure mode hit four different surfaces in that one release. The parity goldens store the version as a `{{runtime-version}}` placeholder (`runtime/tests/parity.rs` substitutes `env!("CARGO_PKG_VERSION")` at compare time), so a version bump needs **no golden re-bless**; do not `BLESS=1` for a version change (it would hardcode the literal version and destroy the placeholder). If parity fails on the version line after a bump, the cause is a stale `runtime/target/release/ductus` — `cargo build --release` to refresh it, don't touch the goldens. Reason: surfaced 2026-06-30 — an `apply-manifest` exec-bit fix committed to `main` would have shipped to no adopter without the tag. How to apply: bump + CHANGELOG + commit + `ductus-v<version>` tag + push tag, in that order; never bless goldens to absorb a version delta. The tag is part of the spec's **completion gate**, not a separate release chore: a spec whose work registers a migration with `introduced_in = X` (or otherwise lands `runtime/` changes) is not complete until `ductus-vX` is tagged — surfaced again 2026-07-22, when 042 reached `done` with its `introduced_in = 0.22.0` runtime work untagged, so no adopter could receive the migration and a stale local server binary kept writing legacy paths.
- **A spec does not reach `done` with an outstanding SHOULD — every review finding is resolved or waived first, not only the MUST ones.** The rule is [§implement-phase](framework/constitution.md#implement-phase) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: confirmed by the user 2026-08-16 while closing 010, after I presented a non-blocking `QUAL-CLAIM-001` SHOULD as compatible with the transition; the user noted the rule had been given before, which is the tell that a session-scoped acknowledgement is not enough. How to apply: read `should-violations` at the completion gate the same way you read `must-violations` — non-zero means not done. Fix it, or waive it with a recorded reason and re-run `/{project}:review` so `review.md` and the frontmatter agree; only then propose the transition. When the fix lands under `runtime/`, the release entry above applies in full — the version bump and `ductus-v<version>` tag are part of the same completion gate, so addressing a SHOULD can mean cutting a release. Carry this rule into any hand-off prompt you write: it is a standing project rule, not a preference for one review.
- **Work a recommendation out to its result *before* presenting it.** The rule is [§recommendations](framework/constitution.md#recommendations) — it ships to adopters, so this entry is the contributor-side mirror, not a second copy. Reason: surfaced 2026-08-17 on 048 task 13. Three options were offered for moving the bootstrap's State-B abort, and I recommended the middle one as "the largest gain available"; only after the user accepted did I count the restarts and find it saved **none** — it relocated the abort without removing it, leaving the pre-042 adopter at three sessions, the exact number the scenario exists to reduce. The user had to be told their approval rested on my framing rather than on the facts. The same session then produced the counter-example the rule wants: the acceptance-criterion-supersession check was measured before being recommended (455 pairs tested, 215 would fire, every sample a false positive), and the measurement is what killed it. How to apply here: state the metric the decision turns on, evaluate every option against it, then rank — and when the metric cannot be computed yet, say so and name what would settle it instead of ranking anyway.
- **Record a superseded acceptance criterion in the spec body, on the criterion itself — never in `review.md`.** The rule is [§spec-requirements](framework/constitution.md#spec-requirements) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-08-17 closing 010, whose AC7/AC8 (the `[simple]` marker, dropped by 017) and AC14 (`framework/workflows/`, sunset by 043) all describe things the repo no longer has. The only record of the 017 supersession lived in `review.md`'s Summary — which `write-review` regenerates wholesale, so re-running `/{project}:review` an hour later destroyed it. 017 also declares no dependency on 010, so nothing else linked remover to removed. How to apply: the detection already works — `/{project}:implement`'s criterion-verification step is what surfaced all three, by checking criteria against the tree instead of trusting their checkboxes — so what needs discipline is only *where the outcome is written down*. A deterministic check for this was measured and rejected; see the §recommendations entry above.
- **Record a review's `reviewed-against` as a commit that already contains the artifacts it reviewed — so commit the work first, then review, then commit the review.** The rule is [§implement-phase](framework/constitution.md#implement-phase) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-08-17 — 000's review was recorded at `11ff132d`, its scenarios committed in `ccdd3ac`, the local audit ran green before the commit, and the `ductus-v0.29.7` release gate then failed on the audit and skipped the publish. How to apply: two commits, always — the artifact commit, then `/{project}:review` against that new HEAD, then the review commit. And **run `scripts/audit/run-all.sh` after committing, before tagging**; a green pre-commit audit is not evidence for any family that reads history. This is the same lesson as the `fetch-depth: 0` entry one layer up: a check that reads git history answers about committed state, so it must be *asked* about committed state.
- **Never record another project's name in this repository — describe the shape instead.** Specs, scenarios, changelog entries, commit messages and runtime doc comments may say *what kind of project* exercised something (a pre-042 adopter with a legacy root config, an `.mcp.json` naming the bare command) but not *which one*. What a reader needs is the shape they must reproduce; the identity is the maintainer's local context and does not survive outside this machine. Reason: confirmed by the user 2026-08-17 — the project used to validate 048's AC10 had accumulated 13 references across 8 files including runtime source, and the user's ruling was that *"another project does not need to be recorded in this one."* How to apply: when a defect is found by running against a real adopter, write the reproducing conditions and drop the name; if a fixture is useful, build one under `/tmp` or in `tests/`. Sweeping a name out afterwards is a uniform token substitution, so done specs stay `done` — but the replacement text usually varies by sentence, which means `mechanical_sweep`'s repo-wide test will *not* exempt it and reviews touching those contracts go stale. Expect to re-review; that is the cheap direction of error.
- Read `framework/commands/{name}.md` before recommending, describing, or disambiguating a slash command — don't guess from the name. Source files are authoritative; the generated `.claude/commands/ductus/*.md` copies are produced by the pre-commit hook.
- **A `.ductus/config.toml` change is cross-spec impact only when it modifies a key another spec already documented.** The rule is [§cross-spec-impact](framework/constitution.md#cross-spec-impact) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-05-10 while clarifying spec 020 — adding `[review] tech-stack-verified` did not warrant reopening 019. How to apply: only treat a `.ductus/config.toml` change as cross-spec impact when it modifies an *existing* key already documented in another spec.
- **No dead references in live artifacts.** The rule is [§drift-prevention](framework/constitution.md#drift-prevention) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. **The live-artifact set for this repository** is <!-- audit:sweep-targets:begin --> `framework/`, `scripts/`, `.ductus/scripts/`, `runtime/` (including `tests/fixtures/`, `tests/golden/`, `tests/parity/`), `.github/`, `docs/`, `README.md`, `AGENTS.md`, `.markdownlint-cli2.jsonc`, and `specs/NNN-*/` (including `done` spec bodies) <!-- audit:sweep-targets:end --> — the constitution states the rule in *categories* because it ships to adopters, whose layouts differ, so the literal paths live here rather than there, and [§spec-lifecycle](framework/constitution.md#spec-lifecycle) case (a) resolves its mechanical-edit scope through this enumeration. Family 23 (`scripts/audit/sweep-target-manifest-parity.sh`) holds it against the **Shared Files** manifest so a relocated directory cannot leave it stale the way 042 did; the delimiting comments are what the family extracts, so keep them around the list. Reason: a reader following a forward-pointer or back-reference in live artifacts must never land on an outdated name; spec bodies are living documents that represent current state. `.ductus/scripts/` was added to this list on 2026-08-17, after an adoption run found `config_path_of` in `.ductus/scripts/lib/specs-root.sh` still resolving `.govern/config.toml` → `.govern.toml` with no `.ductus/` tier — 049's sweep had moved the generators' *location* but never grepped inside them, because this enumeration still said `scripts/`, where they lived before 042 relocated them. A converged adopter therefore resolved to a path that does not exist and silently fell through to the default `specs`, so any non-default `[paths] specs-root` derived nothing and exited 0. The lesson generalizes: when a sweep's own target list names a path a previous spec moved, the list is the thing that goes stale first, and it fails silently because a grep over the wrong directory returns clean. The sweep is mechanical: every change in the diff is the same find-and-replace token substitution applied uniformly across the artifact set above. Because the diff is uniform, it qualifies as a **mechanical sweep** under [§spec-lifecycle](framework/constitution.md#spec-lifecycle) and does NOT trigger the `done → in-progress` back-edge — done specs stay `done` after a rename sweep. How to apply: when renaming X to Y, grep the live-artifact set named above and update every hit in a single commit; do not bundle the sweep with unrelated edits (a non-uniform diff would qualify as a meaningful edit and reopen affected specs). Commit messages and published PR/release notes stay as written (git history is the audit trail of what was named when).
- **A behavior change needs a prose-claim sweep, not just an identifier sweep.** The rule is [§drift-prevention](framework/constitution.md#drift-prevention) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-06-18 — spec 031 split MCP registration per-agent (Auggie/Antigravity now surface a manual `mcp add` command instead of `/ductus` writing a config file), and the spec's dead-reference sweep grepped only `.mcp.json` / `mcp_config.json` and passed, yet `README.md` still claimed `/ductus` "registers it automatically" for every agent — false for two of three. How to apply: when a spec changes behavior (not just a name), enumerate the behavioral claims the change falsifies and grep for them **by meaning** — registration / "automatically" / "by hand" / "writes the file" phrasings, not just the changed path — across the live-artifact set, `README.md` especially since it narrates behavior to users. A prose-claim fix to `README.md` or `docs/` is docs-only and does not reopen the originating spec; a stale behavioral claim *inside a done spec body* is a meaningful edit and does reopen it (route it through `/{project}:amend` / the back-edge).
- **A change to an agent-facing surface must cover every agent in the registry, not just Claude.** The Agent Registry in `framework/bootstrap/ductus.md` is the enumeration: `claude`, `auggie`, `antigravity`, `opencode` — four agents across three `layout` values (`claude-style`, `antigravity`, `opencode`). Because this repo dogfoods Claude, `scripts/gen-claude-commands.sh` regenerates `.claude/commands/ductus/` on every command-source edit and the self-audit's check-zero fails until it is re-run — so the Claude deployment is the one surface a change is *forced* to update. That regeneration passing is **not** evidence the other layouts are covered; it is evidence for exactly one of three. Reason: confirmed by the user 2026-08-14 after the Antigravity native rules mirror (`ductus.md` §Antigravity layout) was found to mirror only the **Shared Files** manifest rows, so a project-authored rule file was enforced by the pipeline for every agent yet invisible to the only agent that loads rules from a native dir. How to apply: before landing an agent-facing change, walk the §Derived values **Layout-derived** table row by row — command/skill path, invocation, `ductus` install path, settings file, permission shape, native rule-loading dir, native rules file, cleanup glob — and ask what the change means for each layout; note the per-agent impact (including "no change needed, reads the shared path") in the commit message. `scripts/audit/installer-registry-parity.sh` and `scripts/audit/host-namespace-parity.sh` enforce installer and namespace parity only — nothing audits per-layout *behavior* parity, so this one is contributor discipline, not a gate that will catch you.
- **Cross-service reference edits are mechanical-class (non-reopening).** Adding, removing, or rewriting a cross-service reference — an inline body link whose target resolves to a registered `.ductus/config.toml` `[services]` entry, plus the `references:` frontmatter that `.ductus/scripts/gen-cross-service-refs.sh` harvests from it — does NOT trigger the `done → in-progress` back-edge under [§spec-lifecycle](framework/constitution.md#spec-lifecycle) (case (b) of the mechanical-edit rule): references are informative cross-service navigation, never dependencies. The `references:` index is generator-managed and **strictly distinct from `dependencies:`** (harvested by `.ductus/scripts/gen-spec-deps.sh`); each generator owns its own frontmatter field and the two never share an index or enter the cycle check. Reason: spec 030. How to apply: a diff that only touches cross-service reference links and their harvested `references:` entries keeps a `done` spec at `done`, the same way a uniform rename sweep does — do not route it through `/{project}:amend`.
- **Criterion-label assignment is mechanical-class (non-reopening).** A diff whose every change inserts an `AC{n}:` label between an acceptance criterion's checkbox and its text — plus the `next-criterion:` counter that backs it — does NOT trigger the `done → in-progress` back-edge under [§spec-lifecycle](framework/constitution.md#spec-lifecycle) (case (c) of the mechanical-edit rule). The labelled text is byte-identical either side of the insert, so the diff is determinable without author judgment, and an identifier names a requirement without stating one — the same reason a rule ID is not the rule. Reason: spec 013's `criterion-identifiers` resolved the corpus backfill as a uniform mechanical sweep, and the sweep landed across 49 specs (47 of them `done`) on 2026-08-14; the constitution enumerated only cases (a) and (b) at the time, so the rule and the practice disagreed until case (c) was added. How to apply: run the sweep through `label-criteria`, never by hand, and confirm from the diff that no criterion's own text moved — a label insert bundled with a wording fix is a **meaningful** edit and does reopen the spec. Assignment is `max(highest label in body, next-criterion)`, never `max(body) + 1`; the counter is what keeps a deleted criterion's label from being reissued.
- **Never hand-write an `AC{n}:` label — add the criterion unlabelled and run `label-criteria`.** The rule is [§spec-requirements](framework/constitution.md#spec-requirements) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced twice in one session on 2026-08-15 while clarifying spec 048 — both times the guess matched, which is exactly what makes the habit durable. How to apply: write `- [ ] <criterion text>` with no label, then run the pass (`ductus label-criteria --feature <slug>`, or the MCP tool) and let it assign. If you have already written labels, leave them — stripping them renumbers from the advanced counter and opens a gap for no gain. The same rule is why `/{project}:specify` and `/{project}:clarify` invoke the pass rather than asking the agent to number: citing a criterion must never require counting a list, including in the session that wrote it.
- **Run `/ductus` per its spec — no ad-hoc prompts.** When executing `/ductus` (here or in any adopter), do not insert confirmation prompts beyond those the spec specifies (project inputs, agent-selection prompts on `--add-agent` / first-run, the registry-driven migration prompts from `framework/migrations.toml`). Specifically, do not stop to warn about uncommitted edits to update-strategy files, custom slash commands about to be removed by **Slash command cleanup**, or "data loss" from the `stale` → write-and-abort path. Reason: the spec already encodes safety — `.ductus/config.toml` `[pinned] files` is the documented opt-out; the stale path writes upstream and aborts cleanly (recoverable from git); slash command cleanup is unconditional for unpinned files. Extra prompts duplicate information the spec already gives the user and stall routine runs. How to apply: trust the documented behavior. The canonical statement of this rule lives as a "Procedural fidelity" preamble at the top of §Instructions in `framework/bootstrap/ductus.md` so it travels to every adopter via the self-update path; this AGENTS.md entry is the contributor-side mirror. If a real safety concern seems missing from the spec, raise it as a spec change (inbox entry or discussion) — not as a runtime prompt.
- **Use the `Write` tool, not Bash redirects, for `.ductus/session.toml`.** The rule is [§text-first-artifacts](framework/constitution.md#text-first-artifacts) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-05-17 while running `/ductus:target 025` — used a Bash heredoc and got a permission prompt despite spec 023's allowlist work. How to apply: when an agent writes the session file (or any `ductus`-owned state file with a dedicated `Write(...)` allow entry), use the `Write` tool. Do not widen the Bash allowlist with patterns like `Bash(cat > * *)` to compensate — that grants write-anywhere-via-shell and defeats the per-path scoping. A narrow `Bash(cat > .ductus/session.toml *)` would be safe, but reaching for the right tool is cheaper than maintaining two surfaces.
- **Use repo-relative paths in tool calls.** When invoking `Read`, `Write`, `Edit`, or `Bash` against files in this repo, use repo-relative paths (e.g., `.ductus/session.toml`, `specs/027-bootstrap-migration-registry/spec.md`) — never `/Users/stonean/src/stonean/ductus/...`. Reason: surfaced 2026-05-17 during `/ductus:specify` — agent used an absolute path for the session-file write. Absolute paths leak the maintainer's home directory into transcripts, make diffs and error messages noisier, and break path-pattern matching for `permissions.allow` entries that are written relative. How to apply: every framework artifact (rule files, command sources, scripts, spec links) already uses relative paths; mirror that convention in tool calls. The only places absolutes are appropriate are temp files under `/tmp` or `/private/tmp` and explicit references to files in other working directories listed in the harness environment.
- **Never call specs "frozen archaeology" or use frozen-archaeology phrasing.** Specs are living documents that represent current state. Edits to a `done` spec body trigger the `done → in-progress` back-edge via `/{project}:amend` (or directly via `set-status` per the rule below); rename sweeps stay `done` because they qualify as mechanical edits under §spec-lifecycle. Reason: spec 023's `living-specs` scenario explicitly dropped the "frozen archaeology" exception from constitution §drift-prevention; surfaced 2026-05-24 when I wrote "outside frozen-archaeology specs" into spec 022's task 41 and the user corrected it. How to apply: when describing why a done spec shouldn't be edited, frame it in terms of the back-edge cost (it reopens the spec and goes through the pipeline again), not as "the spec is frozen." When describing a sweep that touches done specs, frame it as a §spec-lifecycle mechanical edit (uniform find-and-replace across live artifacts) that keeps the spec at `done`. Live framework files that still carry frozen-archaeology language (`framework/commands/analyze.md`, `framework/migrations/spec-and-plan-sunset.md`) are drift candidates from before the rule was dropped — flag them when adjacent, but do not bundle the sweep with unrelated work.
- **Re-open a `done` spec via `set-status` when the only intent is to reflect on-disk edits, not via `/{project}:amend`.** The rule is [§spec-lifecycle](framework/constitution.md#spec-lifecycle) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced during the gvrn 0.10.0 session-consolidation cycle (see `specs/014-reclarify-backedge/scenarios/reopen-after-informal-edits.md` — Option A). How to apply: only when there is *no* new input from the user to capture. If the user is also adding new scenario content beyond what is already on disk, route the new content through `/{project}:amend` after flipping status — Option A is a shortcut for the re-open-only case, not a replacement for the scenario-add flow. The command-side safety net (Option B in `framework/commands/amend.md`) covers hosts without an agent in the loop.
- **Add a rule to its surface's home spec via the back-edge — do not spawn a new spec for it.** The rule is [§rules](framework/constitution.md#rules) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: a separate spec per rule fragments the durable record of one concern across many specs, making its purpose harder to follow; this is the drift §spec-lifecycle's anti-proliferation stance ("scenarios evolve the existing spec rather than spawning a new one") exists to prevent. Surfaced 2026-07-18 — I proposed a follow-on spec for the code-side grounding rule (`QUAL-GROUND-001`) and the user corrected it. How to apply: keep the cross-cutting principle in its single canonical home (e.g. constitution §grounding) and have each enforcement point — a rule, a command check — reference it; route a new rule on an existing surface into that surface's spec. Reserve a brand-new spec for a genuinely new rule *file*/surface, per constitution §rules.
- **Route runtime work to spec 022 via the back-edge — 022 is the durable home for runtime rules.** When a new spec's behavior is carried by the `ductus` runtime — a new `check-artifacts` family, a new field on a primitive's result, a change to a shared parser under `runtime/src/` — the primitive-level changes land as **scenarios under `022-deterministic-runtime`**, each back-linking to the requiring spec per §cross-spec-impact, with `specs/022-deterministic-runtime/data-model.md` updated for the new field or family. Recording them on a `done` 022 takes it through the normal `done → in-progress` back-edge. The requiring spec keeps what it actually owns: the requirement, its constitution amendments, its command-source documentation, and its acceptance criteria — which are verified against shipped behavior regardless of which spec's tasks produced it, so the requiring spec cannot reach `done` before the 022 scenarios do. Reason: confirmed by the user 2026-08-02 while planning 045 — 022 owns the runtime and is where runtime rules stay findable, rather than being scattered across every spec that happened to need one. The precedent is 046, which added the fifth `check-artifacts` family exactly this way (`specs/046-scenario-open-question-visibility/spec.md` §Implementation ownership); 022's `data-model.md` is also the canonical registry of primitive result shapes and check families, so a new family has to be recorded there whatever else happens. - **A canonical table living on a `done` spec is synced as a mechanical edit — no back-edge.** The rule is [§spec-lifecycle](framework/constitution.md#spec-lifecycle) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. - **Backtick a primitive in an `## Instructions` step only when the walker can actually supply its arguments.** The exec parser dispatches any step naming a `PRIMITIVE_NAMES` token in a code span, and it has no per-step argument binding — so a step that needs *per-item* arguments the walker does not hold (a value computed from findings, a loop body) breaks `runtime exec` even though the markdown reads correctly. - **Do not invoke `cargo build` twice in one shell command and read only the second output.** The pattern `cargo build 2>&1 | grep -E '^error' -A8; cargo build 2>&1 | tail -2` compiles on the first invocation and reports `Finished` in ~0.07s on the second, so the visible output says nothing was built even though it was. - **Before reporting that a declarative entry misbehaved, read the entry.** The rule is [§grounding](framework/constitution.md#grounding) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. - **A real adopter run is the only test of composition this project has.** Every check here verifies what it was built to verify against *this* repository; none of them exercises a migration chain, a bootstrap, and a runtime acquisition together in a project shaped like an adopter's. - **A run summary is evidence about what that agent wrote, not about what the framework does — verify every other claim against the source.** An adoption run is narrated by a host executing *one* version of the procedure while reporting on *another*, so both its forward-looking predictions and its diagnoses are unverified by construction. Reason: 2026-08-17, twice in one run. A stale-hop host warned that the next run would probe `command -v ductus`, write a broken MCP entry, abort a second time, and degrade to the markdown path — every clause false, because 048 replaced the `PATH` probe with a store filesystem check (`ductus.md` §ductus runtime detection). - **Verify what a commit actually contains before reporting it landed — `git show --stat`, not the absence of an error.** A `git add` of twelve modified paths plus one new file, followed by a commit, produced a commit holding only the new file; the twelve stayed unstaged in the working tree. Nothing errored. Reason: surfaced 2026-08-18 landing the review-scope fix. The pre-commit hook's own evidence pointed the wrong way — it ran the full cargo suite, which it does *only* when staged changes touch `runtime/`, so the hook plainly saw the runtime files the commit did not keep, and every subsequent check passed because `scripts/audit/run-all.sh`, `markdownlint` and `cargo test` all read the **working tree**, where the changes still were. The gap surfaced only when a later reading of `git diff --name-only <parent>..HEAD` returned one file. Re-running the identical `git add` staged all twelve correctly, so it is unreproduced and deliberately **not** filed as a defect (see the frontfill rule below); what is durable is the discipline. How to apply: end every commit with `git show --stat --format="%h %s" HEAD` and read the file list against what you meant to commit — a two-second check that a green audit cannot substitute for, because the audit is not looking at the index. This is the [check that cannot run](#design-principles) principle turned on the verification step itself: passing checks were evidence about the worktree and were silently read as evidence about the commit.
- **Do not capture an observation about the pipeline's own machinery while reviewing framework work — `specs/inbox.md`'s "do not frontfill" rule binds agents too.** A review of framework code is executed *by* the machinery it reviews, so noticing something true about `/{project}:review`, `run-all.sh`, or a primitive is near-certain on every pass. Each note is individually correct and collectively a treadmill: it lands in the inbox, grooms into a scenario, reopens a spec, and that spec's own review produces the next one. Reason: surfaced 2026-08-18 — a single review of 026 captured two machinery observations, and the user named the resulting cycle as work that never ends. The inbox header has said *"do not frontfill bugs that are not being actively worked on"* the whole time; both captures violated it, and one of the two did not survive its own re-reading. How to apply: capture an observation only when it concerns the code under review or blocks the current work. A true-but-unrelated note about tooling is **discarded** unless you would stop and fix it today — mention it in the summary if it matters and let it go if it does not, because a finding worth keeping is worth acting on now and one that is not is inbox debt with a recurring re-routing cost. **One exception, deliberately narrow:** a defect that makes the *current* review's own result wrong is reported, because it bears on whether the gate that just passed can be trusted at all.
- **`check-artifacts` reports `clean: true` and a non-empty `skipped` array at the same time — the second is the manual worklist, not noise.** The rule is [§implement-phase](framework/constitution.md#implement-phase) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. The two fields answer different questions: `clean` covers what the primitive examined, `skipped` names what it could not reach. The `criterion-path-existence` family skips with `root-absent` (a path outside the repo — a home-directory store, say) and with `not-a-live-claim` (a criterion describing a replacement or a removal rather than a file that must exist), and a criterion in that second bucket has had **nothing** check the substance of its claim, ever — not on this run, not on any previous one. Reason: surfaced 2026-08-18 closing 048. AC17 asserted that every per-step markdown-only fallback had been removed from `framework/commands/*.md`, and `tasks.md` recorded all 26 as removed; two survived in `specify.md` §Instructions with no exemption recorded anywhere, and the criterion had stood ticked across four releases. `check-artifacts` had reported it `skipped` as `not-a-live-claim` the whole time, so its green result was never evidence about that criterion — the family was telling the truth about what it had not looked at, and the omission read as assurance anyway. How to apply: at the completion gate, walk the `skipped` array entry by entry and check each criterion's claim against the tree by hand — a `grep` for the claim's own wording is usually the entire job, and it is the only thing standing between a false claim and a `done` spec. When the claim does not hold, ask which of two things happened: a later spec removed what this one delivered, which is a **supersession** to annotate per [§spec-requirements](framework/constitution.md#spec-requirements); or the original work was simply incomplete, which is a **sweep to finish** — annotating that one would record a fiction, since nothing superseded anything.

## Gotchas

- Use `npx markdownlint-cli2` to run markdown linting — do not suggest installing it globally.
- The command generator substitutes `{project}` → `gov` and `{cli-config-dir}` → `.claude`, and writes the Claude-specific permission file (`framework/bootstrap/configure/claude.md`) as `configure.md` in the gov command directory.
- **An edit to `framework/commands/*.md` is invisible to that slash command until the generator re-runs — including to the command you are editing, in the same session.** The pre-commit hook regenerates `.claude/commands/ductus/` (see Workflow), but that is *commit* time; the agent host loads the installed copy at *invocation* time. So editing a command source and then invoking that command walks the pre-edit text, silently. The same shape applies one layer down, but the loop is shorter than it used to be: this repo sets `[runtime] path = "runtime/target/release/ductus"` and registers the pointer (`.ductus/bin/ductus`) as the MCP command, so a `runtime/` source change is live for MCP tool calls after `cargo build --release` **and** an MCP server restart — which means a new session, since the host spawns the server once. There is no `cargo install` step and `PATH` is not consulted; the pointer resolves straight to the build in the working tree. Reason: surfaced 2026-08-14 — `framework/commands/analyze.md` was corrected to document `--fix`'s second trigger, and the very next `/ductus:analyze` invocation loaded the stale installed copy and displayed the old text; in the same session the `append-*` marker fix was published as `gvrn-v0.27.2` while every MCP call kept using the Aug-3 binary (that half is what `[runtime] path` now prevents — spec 048). How to apply: after editing any `framework/commands/*.md`, run `scripts/gen-claude-commands.sh` before invoking that command (it is idempotent, and the pre-commit hook re-runs it anyway); after a `runtime/` change, do not trust an MCP tool call in the *current* session to exercise it — verify with `cargo test`, and treat the running server as the pre-build binary until the session is restarted.
- `.claude/commands/ductus/init.md` is the one exception to the generator rule — it is `ductus`-specific (no source counterpart) and is hand-maintained. The generator leaves it untouched.
- **Never `git add -A` / `git add .` in this repo.** The rule is [§text-first-artifacts](framework/constitution.md#text-first-artifacts) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Here it bites on in-progress `specs/NNN-*/spec.md` drafts from `/ductus:specify`, which spec 017 (`tracked-specs-not-worktree`) forbids sweeping into a commit. Stage explicit paths.
- A new adopter-facing `.ductus/scripts/gen-*.sh` generator wires into more than this repo's own `.githooks/pre-commit`. For adopters to actually receive and run it, two more sites are required: (1) a row in the **Shared Files** manifest in `framework/bootstrap/ductus.md` (`update` strategy, `.ductus/scripts/<name>.sh` → `.ductus/scripts/<name>.sh`) so `/ductus` copies it into adopter projects, and (2) an invocation in the adopter hook `framework/bootstrap/hooks/ductus-pre-commit` (run it `--staged` so a commit only rewrites its own specs). Adding it only to this repo's `.githooks/pre-commit` exercises it on `ductus`'s own commits — so CI and local dogfooding stay green while every adopter silently misses the generator until someone notices. Reason: surfaced 2026-06-17 — spec 030's `gen-cross-service-refs.sh` was wired into `.githooks/pre-commit` but not the manifest or adopter hook, so a `/ductus` update in adopter projects never installed or ran it. How to apply: when adding a generator that derives adopter spec frontmatter, wire all three sites (this repo's hook, the manifest row, the adopter hook) in the same change; if it derives per-spec frontmatter independently it can take `--staged` directly, but if it needs a cross-spec view (like `gen-spec-deps.sh`'s cycle check) keep the full read and gate only the disk write on staged membership.
- `write_atomic_bytes` (the create-then-rename helper backing every primitive write) lands the destination at the fresh tempfile's mode — `0600` on Unix — discarding whatever mode the file should carry. For markdown/JSON this is invisible (git tracks only the exec bit), but a primitive that writes a file expected to be **executable** must re-apply the mode itself. `apply-manifest` mirrors the *source* file's `Permissions` onto the dest after each write (`mirror_source_mode`, `cp -p` semantics) because the **Shared Files** manifest ships `.ductus/scripts/gen-*.sh` with `update` strategy and the `ductus-pre-commit` hook must be able to exec them; the staging source carries `+x` because `extract-archive` preserves archive-header modes (`apply_unix_mode`). Reason: surfaced 2026-06-30 — a `/ductus` run rewrote the generators to `0600`, failing the pre-commit hook (and a fresh adopter's `created` write would emit a non-executable generator + broken hook). How to apply: any new primitive writing an executable (or otherwise non-`0600`) file must restore the intended mode after `write_atomic_bytes` — do not assume the helper preserves it; mirror the source's `Permissions` when copying, like `apply-manifest` and `extract-archive` do.
- `runtime/rust-toolchain.toml` pins `components = ["clippy", "rustfmt"]`, and every `cargo` command run under `runtime/` makes rustup honor that file — auto-installing any missing component *mid-build*, a path that hits rustup's `detected conflict: 'bin/cargo-fmt'` bug and aborts the job. So any CI job that runs `cargo` under `runtime/` must pre-install those components via the `dtolnay/rust-toolchain` step's `components: clippy, rustfmt` input, so nothing is left for the runtime auto-install path to do. `runtime.yml` (which lints) always had it; the fix is to keep every other `runtime/`-touching workflow in sync. Reason: surfaced 2026-07-11 — the `gvrn-v0.16.0` release failed because `runtime-release.yml`'s `dtolnay` steps omitted `components:`; the `aarch64-unknown-linux-gnu` cross job's first `cargo` call (`cargo install cargo-zigbuild`) triggered the auto-install conflict. It was the first release tagged after the toolchain pin (commit 19d9229), so no earlier release exposed it. How to apply: when adding or editing a workflow that runs any `cargo` command from `runtime/`, give its `dtolnay/rust-toolchain@<ver>` step `components: clippy, rustfmt` matching `rust-toolchain.toml` — do not rely on rustup's toolchain-file auto-install to supply them.
- A new `ductus` runtime primitive wires into more than `primitives/mod.rs` + `mcp/server.rs`. Building and exposing it over MCP needs `schema/primitives.rs` (Args/Result types), `primitives/<name>.rs` + `primitives/mod.rs` (`pub mod`), and `mcp/server.rs` (`TOOL_NAMES` + a `#[tool]` method). Three more sites are needed the moment a slash command *uses* it: `parser/mod.rs` (`PRIMITIVE_NAMES`) so a command's `## Instructions` can backtick the name without failing `lint-procedure-parseability`; `interpreter/mod.rs` (`dispatch_primitive` match arm) so `runtime exec` can call it (the path the parity tests drive); and `main.rs` (`Command` enum variant + dispatch) for the `ductus <name>` CLI surface. Add the name to `framework/runtime-tools.txt` for `lint-tool-coverage`. Reason: surfaced 2026-06-14 implementing spec 030's `resolve-references` — MCP exposure alone passes `cargo test` and `tests/mcp.rs` (which only checks `TOOL_NAMES ⊇ runtime-tools.txt`), so the gap stays invisible until a command references the primitive. How to apply: decide up front whether a command will reference the primitive; if yes, wire all six Rust sites + `runtime-tools.txt` in the same change.
- `<!-- audit:ignore-promotion -->` silences the framework self-audit's Family-9 (primitive-promotion) check for a prose-only `## Instructions` step, but it does **not** change how the runtime's exec parser reads that step. The parser (`parser/mod.rs`) marks any step naming a `PRIMITIVE_NAMES` token in a backticked code span as a primitive dispatch, and `lint-procedure-parseability` only rejects a step naming *two or more* primitives — a step naming exactly one is legal. So a host-responsibility step marked `audit:ignore-promotion` that mentions a primitive in backticks (e.g. a `--fix` action described "via `set-status`") gets dispatched by `runtime exec`, which then errors or performs an unintended mutation. Reason: surfaced 2026-07-12 — `/ductus:analyze` step 13 (report render, a host responsibility) referenced `set-status` in backticks; the exec walker dispatched it and the `analyze` parity golden failed with a non-zero exit, even though the parseability lint passed and the audit ignored the step. How to apply: in a numbered `## Instructions` step, backtick a primitive name only when the step is meant to *dispatch* it. To reference another primitive without dispatching — a leverage note, a cross-reference — name it without backticks, or move the reference into non-step prose (the command's preamble or its Markdown-only reference), where multiple primitive names can be backticked freely. `audit:ignore-promotion` is about the audit, not the parser.

- **A markdown link in a spec body creates a `dependencies:` edge — cite in prose when you mean a citation.** The rule is [§text-first-artifacts](framework/constitution.md#text-first-artifacts) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-08-16 — a link to `013`'s `review.md` from `049`'s body made the generator add `013-text-first-artifacts` to 049's dependencies, which is false (049 does not depend on 013; it merely cites it). The pre-commit hook applied it before anyone looked. How to apply: to cite without an edge, use a backticked slug (`` `013-text-first-artifacts` ``) rather than a link, or place the link under a §See Also region, which spec 017's `skip-prose-cross-references` opt-out already exempts. After editing a spec body, read the `dependencies:` line in the hook's output before committing — the generator reports `Updated …` when it rewrote one.
- **`create-scenario` appends its own Open/Resolved Questions scaffolding — do not author those headings in the body you pass it.** The rule is [§scenarios](framework/constitution.md#scenarios) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-08-16 grooming an inbox item into a scenario carrying one real open question. How to apply: pass Context / Behavior / Edge Cases only, then edit the scaffolded `## Open Questions` section afterwards to add entries — or write the whole file with `Write` if it needs questions at creation time.
- **A version bump needs one build without `--locked`.** Every other runtime command in this repo uses `--locked`, but bumping `runtime/Cargo.toml`'s `version` changes the package's own entry in `Cargo.lock`, and `--locked` exists to forbid exactly that (`error: cannot update the lock file … because --locked was passed`). Run `cargo build --release --offline` once to refresh the lock, after which `--locked` works again. Reason: surfaced 2026-08-16 cutting `ductus-v0.28.1`. How to apply: bump, one `--offline` build, then verify `--locked` succeeds before committing — and remember the release binary must be rebuilt anyway, because `runtime/tests/parity.rs` substitutes `env!("CARGO_PKG_VERSION")` at compare time and a stale binary fails the parity version line. Never `BLESS=1` to absorb that failure; it would replace the `{{runtime-version}}` placeholder with a literal.

- **Gitignored adopter state survives a `git` reset, so a "reset" subject is not a fresh one.** Reverting a test adopter restores tracked files and nothing else: `.mcp.json` is gitignored in many projects, `.ductus/bin/` always is, and the runtime store lives outside the repo entirely at `~/.ductus/bin/ductus`. Reason: surfaced 2026-08-17 across two 048 AC10 runs. After the first run was reverted, `.mcp.json` still carried the converged `ductus` entry from that run, so the retired-key collision the second run existed to exercise was absent until it was restored by hand; the store still held the previously acquired binary, turning fresh acquisition into an upgrade. How to apply: before re-running a bootstrap test, list what the scenario needs to be true and check each against the working tree rather than assuming `git` restored it — for a pre-rename subject that means the MCP config's server key and command, the absence of `.ductus/bin/`, and the store's version against the pin. Capture the pre-run shape of any gitignored file you will want back *before* the first run; it cannot be recovered from history afterwards.
- **This repo's dogfooded copy of an adopter file is not the copy adopters get — test the shipped one.** `.githooks/pre-commit` (ours) and `framework/bootstrap/hooks/ductus-pre-commit` (shipped) are *separate files* doing the same job, and the same split exists between `.ductus/scripts/` as this repo runs it and as the manifest installs it. A guard present in the copy this repo executes is invisible to adopters — and worse, the dogfooded copy working is exactly what stops anyone noticing the shipped one is broken. Reason: surfaced 2026-08-17, twice in one adopter run. The shipped hook guarded `label-criteria` on `command -v ductus`, but spec 048 moved the runtime into the ductus-owned store and `/ductus` never puts it on `PATH`, so spec 013's labelling backstop was dead for **every** adopter since 048; our `.githooks/pre-commit` has a `runtime/target/release/ductus` tier ahead of the `PATH` fallback and worked fine, which is why it went unseen for four releases. In the same run, `config_path_of` in the shipped `.ductus/scripts/lib/specs-root.sh` had no `.ductus/` tier and resolved a *converged* adopter to a nonexistent legacy path, silently defaulting their spec root — masked here because this repo uses the default `specs`. Both failed silently and exited 0. How to apply: when touching `framework/bootstrap/hooks/` or `.ductus/scripts/`, ask what the **adopter's** copy does and exercise it against a tree shaped like theirs, not this one — `bash -c 'cd <adopter-checkout>; …'` or a `/tmp` fixture is enough, and takes seconds. A green run in this repo is evidence about this repo. This is the [check that cannot run](#design-principles) principle applied to the gap between what we dogfood and what we ship.
- **`020` and `022` carry diff bases that predate the `0.28.0` cycle, so reviewing either resolves a scope of hundreds of files.** `compute-review-scope` derives the diff base from the commit a spec advanced to `in-progress` at; for these two that is far enough back that the modified-since set was 677 and 551 files respectively on 2026-08-18 — and since `0.29.10` made scope the *union* rather than the larger set, it can only grow. Nothing is wrong: the number reflects real history, not staleness in the reviews, and conflating the two is a mistake 022's own §spec note already records. How to apply: when re-reviewing either spec after a small follow-on change, pass the documented `--since=<ref>` override naming the commit the change started from, and say in the review commit that you did and why. Do not "fix" it by rewriting a diff base, and do not read the file count as evidence the spec is drifted.
- **`path` is a reserved array in zsh and clobbering it destroys `PATH`.** A loop like `for path in a b; do …; done` in a zsh-run script silently unsets every command for the rest of the invocation, and the symptom is `command not found` for `tr`, `cmp`, `basename` — utilities that obviously exist. Reason: surfaced 2026-08-17 verifying what the raw GitHub path served; the fetch reported exit 127 and the diagnosis briefly looked like a network failure. How to apply: never name a shell variable `path` in this repo's tooling or in ad-hoc commands — the harness shell is zsh. `p`, `repo`, `file`, or `target` all work.

## Boundaries

- **No host-level enforcement of the deterministic (`ductus`) path — it is a deliberate non-goal.** `/ductus`'s State-A execution contract (spec 029, scenario `state-a-deterministic-path-forcing`) uses binding *procedure language* to get a wired runtime actually used. `ductus` does **not** enforce it at the host level — no denying `curl`/`tar` while `ductus` is registered, no State-A-only procedure variant with the shell stripped. Reason: host enforcement would block the legitimate non-primitive shell steps the bootstrap needs (gitignore `curl`, `git config`, `chmod`), is host-specific and a permanent per-host maintenance tax, and breaks [§runtime-boundary](framework/constitution.md#runtime-boundary)'s "neither path wraps the other" parity by demoting the markdown path. A model that ignores the binding contract falls back to the correct-but-pricier markdown path — an accepted outcome, not a gap. How to apply: do not propose or build host enforcement as a follow-up; if the procedure-level contract proves insufficient for a given model, the answer is a more capable model, not coercion.
- **Never edit an installed command file directly — edit the source the generator copies from.** Here that means never editing `.claude/commands/ductus/*.md`; your changes are overwritten the next time the generator runs. Edit the source under `framework/commands/` (or `framework/bootstrap/configure/claude.md` for the `configure` command). The rule is [§drift-prevention](framework/constitution.md#drift-prevention) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-05-23 during the spec-022 `/ductus:status` rewrite — I read the deployed (already-substituted) copy when drafting the rewrite and shipped hardcoded `/ductus:` and `.claude/` literals to the source, which broke the framework-checks CI on Family 4 of `scripts/audit/run-all.sh` (`placeholder-roundtrip`). How to apply: when in doubt, `git show HEAD:framework/commands/{name}.md` to see the source convention before editing; the `placeholder-roundtrip` audit is the post-hoc check, not the first line of defense.

## Design Principles

- **A check that cannot run must never look like one that passed.** The rule is [§design-principles](framework/constitution.md#design-principles) — it ships to adopters, so this entry is the contributor-side record of what it cost *here*, not a second statement of it. It is the single most expensive failure mode this repo has produced. It surfaced four separate times while shipping `ductus-v0.28.0`, each time as a green signal that meant nothing: `scripts/audit/sibling-coupling.sh` used a GNU awk extension, so on every macOS machine the extraction aborted, the family found nothing, and it exited 0 — a release gate that was dead locally and alive in CI; `release-assets` in `runtime-release.yml` needed only `build`, so the self-audit gated the crates.io publish while the binaries adopters actually download shipped regardless; the acquisition workflow was triggered by `on: release: [published]`, which GitHub never fires for a release created with the default `GITHUB_TOKEN`, so the invariant the constitution requires would have been cited by name and never once executed; and the `macos-13` runner label no longer resolves, so that leg sat queued with no runner while the others passed — a missing runner reads as a hang, since it produces no step output. Reason: all four were invisible to a passing local check, and three of them were invisible in CI too until something else forced them into the open. How to apply here: the constitution states the rule; what is local to this repo is where it bites. When a job is a gate, check what actually depends on it rather than what its name implies. And treat a green local run of `scripts/audit/run-all.sh` as necessary-but-not-sufficient evidence before a tag — the environments differ in exactly the dimensions the checks depend on.

- **Never close work with a caveat attached — the status is the claim, and a summary is not where residue lives.** The rule is [§design-principles](framework/constitution.md#design-principles) — it ships to adopters, so this entry is the contributor-side record of what it cost *here*. Reason: surfaced 2026-08-19, three times in one session and each time in a different place — a stale prose claim left standing while 022 went to `done`, a detection gap reported as unmeasured while 026 went to `done`, and both narrated in the closing summary as though naming them discharged them. The user's ruling: *"the work is either complete or it isn't. don't change the spec status to done and then say this."* The tell is that each caveat was **true**, which is exactly why the habit survives — it reads as candour and costs nothing to write. What it actually does is move the exception from a channel that is re-read (the status, the inbox, a scenario) to one that is read once (a summary, a commit message). When the second of those caveats was finally investigated it was 28 broken links, a number thirty seconds of grep would have produced at any point. How to apply: when you notice something outstanding while closing, do not reach for the summary. Fix it; or record it where the pipeline will resurface it and let the status follow that record; or record an out-of-scope decision with its reason. Reopening a `done` spec is cheap and routine — preferring a caveat to a back-edge, to keep a status field looking clean, is the failure in its purest form. And when the residue is only knowable by measuring, measure: an unmeasured gap is a task, not a caveat.
- **Never design framework features that depend on human diligence or discipline.** The rule is [§design-principles](framework/constitution.md#design-principles) — it ships to adopters, so this entry is the contributor-side mirror rather than a second copy. Reason: surfaced 2026-05-06 when evaluating an optional `## Upgrade Impact` spec section as a way to capture cross-version migration notes; rejected on this principle and the topic was tabled to inbox until a derivable design is found. How to apply: this is a hard filter on framework proposals, not a tiebreaker — if the only viable design relies on author discipline, the right answer is to defer the feature, not to ship the disciplined version "for now."
