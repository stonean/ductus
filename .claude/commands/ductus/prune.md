# Prune

Invocation arguments: `$ARGUMENTS` (empty when none were supplied)

Reduce the session target's spec directory — or, with `--all`, every spec's, or with `--project`, the four project files and their parts — so each working artifact says only what it should — dropping spent task sections from `tasks.md` (or resetting it to template state), and removing the `plan.md` sections outside the design record once their durable pieces have moved home.

## Purpose

A feature's `tasks.md` accumulates completed work, and a plan accumulates journal, evidence, and handoff sections outside its design record (§plan-phase). `/ductus:prune` reclaims both, each by the rule its durability class allows: `tasks.md` is reduced mechanically; a plan section is removed only once it has been emptied of what lasts, a judgment the operator confirms section by section.

| Artifact | Class | What prune does |
| --- | --- | --- |
| `tasks.md` | Ephemeral | Drops spent sections (keep-pending) or resets (`--reset`) |
| `plan.md` | Design record | Removes each section outside the design record, after its durable content has been moved home |
| `spec.md` | Durable | Body never touched; its `status` changes only to reopen a `done` spec |
| `scenarios/*.md`, `data-model.md` | Durable | Never touched |
| `research.md` | Reference | Never touched |
| `review.md`, `analysis.md` | Regenerated | Never written; prune reads only `analysis.md`'s stored decisions |

Any other file in the directory is the project's, not the pipeline's: prune neither reads nor reports it.

`--project` reduces the four project files instead — `AGENTS.md`, `system.md`, `events.md` and `errors.md` — and their parts, moving each entry the operator confirms to its home or removing it (**Project files (`--project`)**).

## Scope Boundaries

- Prune writes `tasks.md` (its reduction, and owed work a plan section moves onto a pending task), `plan.md` (a moved decision edited into its design-record entry, and the removal of sections outside the record), and the home a plan section's project-only knowledge moves to by §drift-prevention's *Shared knowledge stays in git*, which is `AGENTS.md` only for what every session needs. Knowledge that holds more widely is named for the operator to route where §drift-prevention's *Shared knowledge stays in git* sends it; prune writes no shipped artifact.
- Prune changes status only to reopen a `done` spec, and names each reopen before the write that causes it. A spec below `done` is never moved.
- `--project` writes the four project files, their parts, and the home each confirmed entry moves to — a project file or a part of one, a spec, `docs/` or a README, or a comment or test at the site — and reads the project's source only for the catalog search. It writes nothing outside the project, files nothing upstream, needs no session target, and leaves any target that is set unchanged.
- `--all` repeats the one-spec reduction for every spec in the corpus; it is a batch of one-spec operations, never one operation spanning two specs. It needs no session target and leaves any target that is set unchanged.
- Recovery is git history: prune writes no backup file and no gitignored sidecar.
- Reference: §plan-phase (a plan records the design as it stands), §tasks-phase (`tasks.md` is an ephemeral work-tracking artifact — not a durable source of truth), §spec-lifecycle (a `done` spec reopens while it owes work), §pipeline-boundaries ("don't backtrack silently"), §text-first-artifacts, §runtime-boundary, plus [041 — Spec Directory Pruning](https://github.com/stonean/ductus/blob/main/specs/041-task-pruning/spec.md) for the reduction semantics and [data-model](https://github.com/stonean/ductus/blob/main/specs/041-task-pruning/data-model.md) for both segmentations and classifications.

## Instructions

> **For agent runtimes**: the Invoke steps below call the ductus runtime's MCP tools; without the server, stop and say to restart or re-run `/ductus` (§runtime-host-integration).
>
> **Claude Code:** load this command's `ductus` tools in one `ToolSearch` call, and send the command's first `ductus` call in that same message, since a tool can be called beside the search that loads it: `select:mcp__ductus__check-owed-work,mcp__ductus__gate-confirm,mcp__ductus__prune-plan,mcp__ductus__prune-project,mcp__ductus__prune-tasks,mcp__ductus__read-section,mcp__ductus__set-status`

**Where a named section lives.** This command's reference is `.ductus/reference/prune.md`. A section named here, or cited elsewhere as part of this command, that has no heading in this file is there. When a step points at one, invoke `read-section` with that path and every section the step names, in one call, rather than reading the whole file.

<!-- audit:ignore-promotion -->
1. Invoke `resolve-session` to resolve the session target, and display any notices and unreadable session files it returns. If no target is set and neither `--all` nor `--project` is given, stop and tell the user to run `/ductus:target` first; `--all` and `--project` need no target and use none. Parse the invocation flags: `--all` walks every spec in the corpus, in corpus order; `--reset` selects a full reset of `tasks.md` (default is a keep-pending prune); `--force` overrides the reset status gate on a non-`done` spec, and without `--reset` is ignored. `--force` with `--all` is refused before anything is read, whether or not `--reset` is given: a forced reset across the corpus would discard every in-flight todo under one confirmation, which §pipeline-boundaries forbids. `--project` is refused with `--all`, `--reset` or `--force`, before anything is read, since it walks no spec directory. Under `--project`, work **Project files (`--project`)** below instead of steps 2–10.

2. Invoke `prune-tasks` against the target feature — or with `all` under `--all` — in preview mode (`apply: false`), passing the `reset` and `force` flags. Read `sections` — under `--all`, `features` and `skipped` — from the file `lists-file` names when `form` is `file`. When the feature directory does not exist (a `feature directory not found: …` error), stop and direct the user to `/ductus:target`. When the target has no `tasks.md` (a `tasks.md not found: …` error), note it and continue: the plan decides whether there is anything to prune. Continuing is the host's decision — the `ductus exec` walker halts on any primitive error, this one included, so an exec run stops here on a spec with no `tasks.md`. A result carrying `unexamined-tail`, or, under `--all`, a non-zero `unexamined-count`, ends inside an open fenced block or HTML comment: report that file as *not examined from line N*, never as clean, read those lines with the host's file tools, and tell the user an apply of it writes nothing (`applied: false`) until the region is closed.

3. Invoke `prune-plan` against the target feature — or with `all` under `--all` — as a preview, with no `apply`; a walk is preview-only, since each plan section is a judgment about one spec's content. Read `sections` — under `--all`, `features` and `skipped` — from the file `lists-file` names when `form` is `file`. An `analysis.md` whose `decisions:` list does not parse is refused, so the run stops there — under `--all`, at that spec — and on a `done` spec whose HEAD cannot be read the preview errors and the run stops before anything is written. `reopen-required` on a `done` spec means edits made before this run already add an unchecked checkbox to `tasks.md`, so the spec reopens with whatever this run writes. A result with `missing` set means the feature has no `plan.md`; with no `tasks.md` either (the `draft` and `clarified` case, since `/ductus:plan` writes both), stop and direct the user to run `/ductus:plan`. Under `--reset` no plan section is proposed, but the preview still runs, for `reopen-required`. The same `unexamined-tail` holds for `plan.md`; an apply naming a section of it removes nothing.

<!-- audit:ignore-promotion -->
4. Settle which plan sections to propose (host responsibility), spec by spec under `--all`. A `decided` section, one a person's stored waiver keeps, is kept, and listed as *kept — decided in `analysis.md`*. For each undecided one, read `analysis.md`'s `decisions:` list and match it to a stored `plan-record` waiver by a person, never one with `decided-by: rule`, the way `/ductus:analyze`'s stored-decision step matches a finding — by judgment, because a finding that step re-matched after its wording drifted keeps its original key — and treat a match as decided too. Every other section is proposed.

<!-- audit:ignore-promotion -->
5. Render the preview from both summaries, so the whole reduction is visible before any of it happens: the spec's status, and — when the plan preview reports `reopen-required` — that the spec reopens once the run has written to it unless step 9's fresh reading finds the cause gone: a reopen named here, before anything is written, and repeated in every confirmation that writes to that spec; for `tasks.md`, the mode, the size before → after, and one line per task section with its classification and action, or that there is no task list; for `plan.md`, one line per section outside the record with its size and whether it is proposed or kept, and the size before → after, the after being the size were every proposed section removed. Under `--all`, render one table instead: a row per spec that has anything to reduce, or that is `done` and listed only because its tree already requires a reopen — its status, whether edits made before the run already reopen it, what each artifact would lose, and the plan sections kept because `analysis.md` decided them — then a total, and the number of specs examined, so a clean corpus reads as *examined N, nothing to prune* rather than as silence. A reopen the tree already carries is named on its row now; one a spec's moves would cause is named at that spec's plan confirmation, once its moves are known. Two early exits, neither of which writes or changes a status: when nothing anywhere has anything to reduce — `nothing-to-prune` on `tasks.md` or no task list, and no proposed plan section — report that there is nothing to prune and stop, but never for a result carrying `unexamined-tail` (step 2); when the gate is `blocked-needs-force` (a `--reset` on a non-`done` spec), name the current status, point at the default keep-pending `/ductus:prune` as the likely intent, note `--reset --force` as the explicit escape hatch, and stop. Under `--all --reset` a blocked spec is not an exit: name each spec the reset skips, with its status, and reset the rest.

6. When `tasks.md` has something to reduce, invoke `gate-confirm` with a prompt that names the destructive write (the mode and how much the file shrinks — under `--all`, how many specs and the total). One confirmation covers every `tasks.md` reduction of a walk. A `tasks.md` reduction never causes a reopen, though on a spec whose preview reported `reopen-required` the prompt names that reopen, which step 9 performs, or not, after the run's writes to that spec. On a declined gate, leave every `tasks.md` unchanged and go on to the plan sections.

7. On confirmation, invoke `prune-tasks` again with `apply: true` (same `feature` or `all`, and the same `reset` / `force` flags), and note each file's new size and the sections removed from the returned summary. A single feature's apply refused with the changed-since-read error wrote nothing: another writer changed `tasks.md` after the apply read it, so preview again from step 2 and confirm afresh. Under `--all`, a spec in `skipped` with the reason `changed-since-read` was not written while the others were: name it in the report, and run it again.

<!-- audit:ignore-promotion -->
8. Work each proposed plan section in turn (host responsibility) — under `--all`, one spec at a time, each apply naming that spec's feature, since a plan apply never spans specs. Read it with the host's file tools and propose, piece by piece, where each durable piece goes: a changed decision into the Technical Decisions entry it amends, edited in place to say what is now true; knowledge that holds for this project alone into its home by the same routing **Project files (`--project`)** applies, which sends it to `AGENTS.md` only when every session needs it; owed work, including an in-flight task's handoff notes, onto its pending task in `tasks.md`. Name what is dropped because git already holds it — evidence, pass counts, scratch paths — and name any knowledge that holds more widely for the operator to route where §drift-prevention's *Shared knowledge stays in git* sends it. On a `done` spec, name the reopen before anything is written whenever a move adds an unchecked checkbox to `tasks.md`, since the spec then owes that work; a move into a design-record section owes nothing, so it reopens nothing (§spec-lifecycle). Confirm the section's moves and its removal together through the gate-confirm primitive. On a declined section, leave it byte-for-byte and say so in the prompt: declining keeps it for this run only, and the lasting keep is folding it under a design-record heading. On confirmation, write the moves first, then call the prune-plan primitive with `apply: true` and `remove` naming that section's heading and digest. On `stale-sections`, nothing was removed: preview again and propose the section afresh against the entry that already holds its piece. On the changed-since-read error, `plan.md` changed after the apply read it and nothing was removed: preview again and propose the section afresh.

<!-- audit:ignore-promotion -->
9. Reopen a `done` spec only as its state requires (host responsibility), decided on a fresh reading. Once the run has finished writing to a `done` spec — under `--all`, spec by spec — invoke the check-owed-work primitive for that feature: it answers for the tree as the run left it, where the preview's `reopen-required` was a prediction made before anything was written. Flip the spec with the set-status primitive, `from: done`, `to: in-progress`, only when that result reports `owes: true`, naming each unchecked box and unticked criterion it lists. When that reopen was named — in the preview, for edits made before the run, or at a section's confirmation, for its moves — perform it; when it was not, ask before flipping, and never reopen silently. A reopen the preview named that the fresh reading no longer requires is not performed, and the report says so. A spec the run wrote nothing to keeps its status. When the guarded write refuses because the status is no longer `done`, stop and name the status found rather than overwriting it.

<!-- audit:ignore-promotion -->
10. Report what changed — per spec under `--all`: the `tasks.md` reduction written, each plan section removed and where each of its pieces went, each section kept and why, and every spec reopened. An interrupted `--all` resumes by running it again: each write is atomic and each reduction idempotent, so what was already removed is simply not found. The reopen costs a fresh `/ductus:analyze` and the completion gate back to `done`; an edit to `plan.md` or `tasks.md` owes no review, while a piece moved into code owes one (spec 081).

## Project files (`--project`)

`--project` walks `AGENTS.md` at the project root and `system.md`, `events.md` and `errors.md` under the spec root, then each of their parts: the markdown files directly under `.ductus/docs/agents/`, `system/`, `events/` and `errors/`, each walked as its own project file is and holding what that file holds (spec 087). What each holds, and where everything else goes, is the constitution's: the test in §drift-prevention's *Shared knowledge stays in git*, and the §spec-phase tree. Every entry's home is a judgment, so the walk is host-mediated, and the operator confirms each write. The entry grammar and the primitive's schema are in [data-model](https://github.com/stonean/ductus/blob/main/specs/041-task-pruning/data-model.md) §`prune-project`.

- **Preview.** Invoke `prune-project` with no `apply`. Render each file's state and size against `[artifacts] read-size-bytes`, and each part's from `part-files` beside its project file, named by its `part-of`: an `absent` file is reported as absent, an `unreadable` one as not examined, and an `outside-project` one (a symbolic link leaving the project, never read or written) as not examined and its path named, never as clean, and a walk with no entry to judge reads *nothing to prune* beside each file's state. Show each `part-findings` entry with its `message`, a fault in a project file that holds nothing here, and name each directory in `parts-unlisted` as not examined, its parts unknown, never as none. The result locates entries and never carries their text, so read each entry's lines with the host's file tools. Read `entries`, `part-files`, `part-findings` and `parts-unlisted` from the file its `lists-file` names when its `form` is `file`. A file whose record carries `unexamined-tail` was walked only above its `from-line`: report it as *not examined from line N* (an open comment, or a managed region with no END), never as clean, and read those lines with the host's file tools to judge them, since none is an entry the result lists.
- **Judge each entry**, in the order returned, and propose one disposition:
  - **Stays.** An `AGENTS.md` entry stays when every session needs it before acting, nothing the work reads would say it, and no check, test or hook reports its failure. Any other file's entry stays when it fits that file's §spec-phase definition, and a part's entry when it fits its project file's definition and the part it is in.
  - **Moves** to its home: architecture, configuration or deployment to `system.md`, or to the part of it the entry belongs in; an event to `events.md` or its part; an error convention or code to `errors.md` or its part; a one-feature decision to that spec's Resolved Questions, or to an existing scenario the operator names, never a new one; a procedure to `docs/` or a README beside the code, while a skill is named, never written; a trap in one file to a comment or test at the site. How a lesson was learned is dropped, since its commit holds it. An entry leaving `AGENTS.md` for a home read on demand leaves one pointer line naming the home and when to read it.
  - **Every adopter's.** An `AGENTS.md` entry true for every project running the pipeline is checked against what the project has installed: `.ductus/constitution.md`, `.ductus/reference/` and the runtime. One already stated there becomes a one-line pointer to that section; one no longer true at the installed version is removed with its reason; one still true stays, trimmed to one line, and the report carries a drafted upstream report with the project's names and details removed. Prune files nothing upstream.
  - **The organization's.** A rule true across the organization's projects is named with its shared constitution's `repo`, and leaves `AGENTS.md` only once the operator confirms it has landed there.
  - **No longer true.** For an `events.md` or `errors.md` entry, show the preview's literal search with any proposal to remove it: the files searched and each one holding the identifier. Zero hits reads *no literal occurrence found*, never proof the code no longer has it, since an identifier built at runtime does not appear literally; a search reported `unavailable` did not run, and says so; name each file in the search's `outside-project` (read it from the file `lists-file` names when `form` is `file`) as not searched, since a hit in it, if any, is not in the zero. A removal carries its reason into the report.
- **Confirm** each entry's disposition, and every file it writes, through `gate-confirm`. A write that leaves a `done` spec an unchecked box or an unticked criterion reopens it (§spec-lifecycle), so name the reopen in the prompt; one into its Resolved Questions or an existing scenario's text owes nothing and leaves it `done`. An entry whose home is in another repository is named, and nothing is written there.
- **Write the home first, then apply.** A home that is a missing `system.md`, `events.md` or `errors.md` is created first, by an apply naming only `create`; a new part is written by the host as any home is, and its project file gains the pointer naming it and when to read it. Write the entry into its home, then invoke `prune-project` with `apply: true`, naming the entry under `remove`, or under `replace` with its pointer or trimmed line. On `stale-entries`, nothing was written: preview again and judge the entry afresh. A file in `refused` changed after the apply read it and was not written, while each in `written` was: preview again and judge that file's entries afresh. Flip a `done` spec a move wrote to with `set-status`, `from: done`, `to: in-progress`, only when `check-owed-work`, read after the write, reports owed work.
- **Report** each entry moved and its home, each removed with its reason, each kept, each file's and each part's size before and after against the limit, each `part-findings` entry and each directory in `parts-unlisted`, every spec reopened, and each drafted upstream report.
