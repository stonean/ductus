# Security Rules — Cross-Surface

Enforceable security rules that hold wherever code runs: a server, a browser, a mobile or desktop app, a command-line tool or a library. This file installs in every project shape. These rules verify **design-time commitments** — what a spec or plan must state — and `/{project}:analyze` enforces them against feature artifacts; `/{project}:review`'s security pass also checks the code in scope against them. Where `security-backend.md` or `security-frontend.md` is also loaded, a rule here names the case that file's rule owns. Rule IDs follow the format `SEC-{CATEGORY}-{NNN}`. Categories: `LOG` (logging, error reporting and telemetry), `DEPS` (build inputs and dependencies), `AUTHN` (authentication). Severity, ID permanence, and how review selects or excludes this file follow constitution §rules.

## SEC-LOG — Logging, Error Reporting and Telemetry

### SEC-LOG-001

> Logs, error-reporting payloads, trace span attributes and events, metric labels, and propagated trace context (W3C `tracestate` and OpenTelemetry baggage entries) MUST NOT carry passwords, full authentication tokens, session IDs, encryption keys, one-time codes (OTP, TOTP, SMS codes), recovery codes, security-question answers, raw PII, full payment card numbers, or other sensitive field values, wherever the code that records them runs. A field that must be referenced MUST be recorded by its name, in a redacted, truncated or masked form, or as an opaque internal identifier, never by its value.

**Verification:** Any spec or plan that introduces logging, error reporting, tracing, metrics or baggage, in client code or server code, MUST commit to excluding or redacting passwords, tokens, session IDs, keys, one-time and recovery codes, PII and other sensitive field values from each of those carriers. `/{project}:analyze` flags specs that log or report request or response bodies in raw form, that mention "log everything" without a redaction commitment, that send an error reporter raw request or form data without scrubbing it, or that record tokens or PII as span attributes, metric labels, baggage or `tracestate`. **Not flagged:** a sensitive configuration value, alone or in a configuration object, which `configuration-cross.md` `CFG-ENV-006` owns; and, where `security-backend.md` is also loaded, the exclusion or redaction commitment for logging and any other such value in a log line, which its `BE-LOG-002` owns, and the commitment for error reporting, tracing, metrics or baggage and any other such value in an error-reporting payload, a span, a metric label or propagated trace context, which its `BE-LOG-008` owns.

**Source:** OWASP Logging Cheat Sheet ("Data to exclude"; its event sources include "Client software" and a "JavaScript exception handler"), W3C Trace Context §6 (Privacy Considerations), OpenTelemetry documentation — Baggage (Baggage security considerations)

## SEC-DEPS — Build Inputs and Dependencies

### SEC-DEPS-001

> Build and release inputs that the package lockfile does not cover — CI/CD actions and reusable workflows, container base images, and tools or scripts downloaded during the build — MUST be pinned to an immutable reference: a full commit SHA, an image digest, or a checksum the build verifies. An action in a workflow onboarded to a GitHub Actions workflow dependency lockfile (`.github/workflows/actions.lock`) is pinned by the commit the lockfile records for it; a reusable workflow called by `{owner}/{repo}/…@{ref}`, from another repository or this one, is not, and takes a full commit SHA, while one called by `./` or `$/` runs from the caller's commit, which pins it; and nor is a container image a workflow runs (`uses: docker://…`, a job's `container:` or `services:` image), which takes an image digest. Mutable references (branch names, version tags, `latest`) MUST NOT select what runs in the build. A pinned reference MUST change only through a documented update process.

**Verification:** Any spec or plan covering CI/CD pipelines, container builds, or build tooling MUST commit to immutable pinning for each of these input kinds and to an update process for the pins (e.g., Dependabot or Renovate digest updates). `/{project}:analyze` flags build specs that reference actions by tag or branch (`uses: org/action@v4`) outside a workflow onboarded to a workflow dependency lockfile, a tag an immutable release backs included since nothing in the repository shows one, that call a reusable workflow by `{owner}/{repo}` and a tag or branch in any workflow, that run a container image by tag alone in any workflow (`uses: docker://hadolint/hadolint:v2.12.0`, a job's `container: node:22`), that reference base images by tag alone (`FROM node:22`), or that run download-and-execute steps without checksum verification. **Not flagged:** a floating version of a dependency the lockfile covers, which, where `security-backend.md` is also loaded, its `BE-DEPS-002` owns or, for a frontend production build where `security-frontend.md` is also loaded, its `FE-DEPS-004`; a package a build step's command runs by a mutable reference, such as `npx tool@latest`, stays this rule's.

**Source:** OpenSSF Scorecard (Pinned-Dependencies check), GitHub Docs — Secure use reference (GitHub Actions), Workflow dependency lockfiles and Workflow syntax (`jobs.<job_id>.uses`), `github/gh-actions-lock` README (Limitations), OWASP Top 10:2025 (A03 — Software Supply Chain Failures)

## SEC-AUTHN — Authentication

### SEC-AUTHN-001

> Comparison of secrets, tokens, MACs, signatures, and password hashes MUST use a constant-time comparison primitive.

**Verification:** Any spec or plan that introduces secret/token/HMAC/signature comparison MUST commit to a constant-time primitive (e.g., `crypto.timingSafeEqual`, `hmac.compare_digest`, `subtle.ConstantTimeCompare`, `MessageDigest.isEqual`). `/{project}:analyze` flags specs that compare secrets with `==`, `===`, `equals`, `strcmp`, or any short-circuiting comparison. **Not flagged:** where `security-backend.md` is also loaded, a comparison an outbound webhook's receiver contract documents for its receivers, or its naming none, in a spec or plan that introduces the webhook, which its `BE-API-010` (d) owns.

**Source:** OWASP Authentication Cheat Sheet, OWASP Webhook Security Cheat Sheet, OWASP Cross-Site Request Forgery Prevention Cheat Sheet

### SEC-AUTHN-002

> OAuth 2.0 and OIDC client flows MUST (a) include and verify a unique `state` parameter on every authorization request; (b) use PKCE (`code_challenge` / `code_verifier`) for every authorization-code flow, including confidential clients; (c) validate the `nonce` claim on OIDC ID tokens; and (d) validate redirect URIs against an exact-match allowlist registered with the authorization server, the port of a native app's loopback redirection URI (`127.0.0.1`, `[::1]` or `localhost`) aside. A client that authenticates to the authorization server MAY instead send a `redirect_uri` it has not registered, and does not take from the request, in a pushed authorization request (RFC 9126) or a signed request object (RFC 9101).

**Verification:** Any spec or plan that introduces an OAuth client, OIDC client, or third-party login integration MUST commit to all four requirements, and one that changes the redirect URIs such a client registers or sends without introducing the client MUST commit to (d). `/{project}:analyze` flags OAuth/OIDC specs that omit `state` (neither PKCE nor the OIDC `nonce` stands in for it), that omit PKCE or limit it to public clients, that omit ID-token `nonce` validation, that pass a `redirect_uri` taken from a request parameter, in a pushed authorization request or a signed request object included, or name neither a fixed registered `redirect_uri` nor its exact-match validation, the port of a native app's loopback redirection URI (`127.0.0.1`, `[::1]` or `localhost`) aside, and one a client that authenticates to the server sends in a pushed authorization request or a signed request object without taking it from the request, the spec naming that mechanism, aside, or that describe `redirect_uri` matching using `startsWith`/`contains`/regex instead of exact equality, a spec that changes those redirect URIs without introducing the client flagged for (d) alone. **Not flagged:** a forbidden grant or response type, or the `plain` PKCE method, which `SEC-AUTHN-003` owns; and, where `security-backend.md` is also loaded, the matching of a `redirect_uri` that an authorization server the project serves receives, which its `BE-API-009` owns; a client's registration with any authorization server stays this rule's.

**Source:** RFC 9700 §2.1, §2.1.1, §4.1.3 (OAuth 2.0 Security Best Current Practice), RFC 9126 §2.4, §7.2 (Pushed Authorization Requests), RFC 8252 §7.3, RFC 7636 (PKCE), OpenID Connect Core 1.0

### SEC-AUTHN-003

> OAuth 2.0 clients and authorization servers MUST NOT use the resource owner password credentials grant, the implicit grant, or any other response type that returns an access token in the authorization response. PKCE MUST use the `S256` code challenge method; the `plain` method MUST NOT be used. Refresh tokens issued to public clients MUST be sender-constrained (e.g., DPoP per RFC 9449, mutual TLS per RFC 8705) or rotated on every use.

**Verification:** Any spec or plan that introduces an OAuth 2.0 client or authorization server MUST name the grant types it uses or supports, the PKCE challenge method, and, for public clients, the refresh-token protection; one that changes the grant or response types a client uses or a server supports without introducing the client or server MUST name the grant and response types it uses or supports, the PKCE challenge method where the change adds an authorization-code flow, and the refresh-token protection where it gives a public client refresh tokens. `/{project}:analyze` flags OAuth specs that use or enable the password grant, the implicit grant (`response_type=token`), or another response type that returns an access token in the authorization response, that allow the `plain` PKCE method, or that issue refresh tokens to public clients without sender-constraining or rotation. **Not flagged:** a spec or plan that introduces an OAuth client and commits to no PKCE, which `SEC-AUTHN-002` (b) owns; the challenge method once PKCE is named stays this rule's, and so does PKCE's omission from an authorization server's spec or from a change that adds an authorization-code flow.

**Source:** RFC 9700 §2.1.1, §2.1.2, §2.2.2, §2.4 (OAuth 2.0 Security Best Current Practice), RFC 7636 (PKCE), RFC 9449 (DPoP), RFC 8705 (OAuth 2.0 Mutual-TLS Client Authentication and Certificate-Bound Access Tokens)
