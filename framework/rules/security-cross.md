# Security Rules — Cross-Surface

Enforceable security rules that hold wherever code runs: a server, a browser, a mobile or desktop app, a command-line tool or a library. This file installs in every project shape. These rules verify **design-time commitments** — what a spec or plan must state — and `/{project}:analyze` enforces them against feature artifacts; `/{project}:review`'s security pass also checks the code in scope against them. Where `security-backend.md` or `security-frontend.md` is also loaded, a rule here names the case that file's rule owns. Rule IDs follow the format `SEC-{CATEGORY}-{NNN}`. Categories: `LOG` (logging, error reporting and telemetry), `DEPS` (build inputs and dependencies), `AUTHN` (authentication), `DATA` (sensitive values in URLs). Severity, ID permanence, and how review selects or excludes this file follow constitution §rules.

## SEC-LOG — Logging, Error Reporting and Telemetry

### SEC-LOG-001

> Logs, error-reporting payloads, trace span attributes and events, metric labels, propagated trace context (W3C `tracestate` and OpenTelemetry baggage entries), product-analytics event payloads and user properties, and session-replay recordings MUST NOT carry passwords, full authentication tokens, session IDs, encryption keys, one-time codes (OTP, TOTP, SMS codes), recovery codes, security-question answers, raw PII, full payment card numbers, or other sensitive field values, wherever the code that records them runs. A field that must be referenced MUST be recorded by its name, in a redacted, truncated or masked form, or as an opaque internal identifier, never by its value.

**Verification:** Any spec or plan that introduces logging, error reporting, tracing, metrics, baggage, product analytics or session replay, in client code or server code, MUST commit to excluding or redacting passwords, tokens, session IDs, keys, one-time and recovery codes, PII and other sensitive field values from each of those carriers. `/{project}:analyze` flags specs that log or report request or response bodies in raw form, that mention "log everything" without a redaction commitment, that send an error reporter raw request or form data without scrubbing it, that record tokens or PII as span attributes, metric labels, baggage or `tracestate`, that send them in a product-analytics event or user property, as `analytics.identify(user.id, { email, accessToken })` does, or that record sessions without masking the input fields and page text that hold them. **Not flagged:** a sensitive configuration value, alone or in a configuration object, which `configuration-cross.md` `CFG-ENV-006` owns; and, where `security-backend.md` is also loaded, the exclusion or redaction commitment for logging and any other such value in a log line, which its `BE-LOG-002` owns, and the commitment for error reporting, tracing, metrics, baggage, product analytics or session replay and any other such value in an error-reporting payload, a span, a metric label, propagated trace context, a product-analytics event or a session-replay recording, which its `BE-LOG-008` owns.

**Source:** OWASP Logging Cheat Sheet ("Data to exclude"; its event sources include "Client software" and a "JavaScript exception handler"), W3C Trace Context §6 (Privacy Considerations), OpenTelemetry documentation — Baggage (Baggage security considerations), Google Analytics Help — Best practices to avoid sending Personally Identifiable Information (PII)

## SEC-DEPS — Build Inputs and Dependencies

### SEC-DEPS-001

> Build and release inputs that the package lockfile does not cover — CI/CD actions and reusable workflows, container base images, and tools or scripts downloaded during the build — MUST be pinned to an immutable reference: a full commit SHA, an image digest, or a checksum the build verifies. An action in a workflow onboarded to a GitHub Actions workflow dependency lockfile (`.github/workflows/actions.lock`) is pinned by the commit the lockfile records for it; a reusable workflow called by `{owner}/{repo}/…@{ref}`, from another repository or this one, is not, and takes a full commit SHA, while one called by `./` or `$/` runs from the caller's commit, which pins it; a local action called by `$/` runs from the running commit, which pins it, while one called by `./` resolves against the runner's workspace and is pinned only when the job checks out the running commit; and nor is a container image a workflow runs (`uses: docker://…`, a job's `container:` or `services:` image), or a container action's own image (`image: docker://…` in its `action.yml`), whatever pins the action, which takes an image digest. An action or reusable workflow pinned by a full commit SHA whose own steps or jobs reference an action by tag or branch, a composite action's steps for one, is selected by those references too, unless the calling workflow is onboarded to a workflow dependency lockfile, which pins the actions its workflows depend on, transitive ones included, a reusable workflow's being pinned only by the lockfile of the repository that defines it. Mutable references (branch names, version tags, `latest`) MUST NOT select what runs in the build. A GitHub-hosted runner label (`runs-on: ubuntu-latest`, `ubuntu-24.04`) MAY select the runner, since no label names an immutable image: GitHub updates its images' software weekly, and a lockfile does not control the runner image. A pinned reference MUST change only through a documented update process.

**Verification:** Any spec or plan covering CI/CD pipelines, container builds, or build tooling, or `system.md` where it describes the build or its CI, MUST commit to immutable pinning for each of these input kinds and to an update process for the pins (e.g., Dependabot or Renovate digest updates). `/{project}:analyze` flags build specs that reference actions by tag or branch (`uses: org/action@v4`) outside a workflow onboarded to a workflow dependency lockfile, a tag an immutable release backs included since nothing in the repository shows one, that call a reusable workflow by `{owner}/{repo}` and a tag or branch in any workflow, that run a container image by tag alone in any workflow (`uses: docker://hadolint/hadolint:v2.12.0`, a job's `container: node:22`), or a container action the spec or plan shows naming its own image by tag in its `action.yml`, that run a SHA-pinned action or reusable workflow the spec or plan shows referencing an action by tag or branch outside a workflow onboarded to a lockfile, naming the lockfile as the fix where it would pin the reference, that run a `./` local action in a job that checks out anything but the running commit, that reference base images by tag alone (`FROM node:22`), or that run download-and-execute steps without checksum verification. **Not flagged:** a GitHub-hosted runner label, which the Statement's MAY sets aside, a self-hosted runner's image staying this rule's where the spec builds it; a floating version of a dependency the lockfile covers, which, where `security-backend.md` is also loaded, its `BE-DEPS-002` owns or, for a frontend production build where `security-frontend.md` is also loaded, its `FE-DEPS-004`; a package a build step's command runs by a mutable reference, such as `npx tool@latest`, stays this rule's.

**Source:** OpenSSF Scorecard (Pinned-Dependencies check), GitHub Docs — Secure use reference (GitHub Actions), Workflow dependency lockfiles, Workflow syntax (`jobs.<job_id>.uses`, `jobs.<job_id>.steps[*].uses`) and About GitHub-hosted runners (Preinstalled software for GitHub-owned images), `github/gh-actions-lock` README (Limitations), OWASP Top 10:2025 (A03 — Software Supply Chain Failures)

## SEC-AUTHN — Authentication

### SEC-AUTHN-001

> Comparison of secrets, tokens, MACs, signatures, and password hashes MUST use a constant-time comparison primitive.

**Verification:** Any spec or plan that introduces secret/token/HMAC/signature comparison MUST commit to a constant-time primitive (e.g., `crypto.timingSafeEqual`, `hmac.compare_digest`, `subtle.ConstantTimeCompare`, `MessageDigest.isEqual`). `/{project}:analyze` flags specs that compare secrets with `==`, `===`, `equals`, `strcmp`, or any short-circuiting comparison. **Not flagged:** where `security-backend.md` is also loaded, a comparison an outbound webhook's receiver contract documents for its receivers, or its naming none, in a spec or plan that introduces the webhook, which its `BE-API-010` (d) owns.

**Source:** OWASP Authentication Cheat Sheet, OWASP Webhook Security Cheat Sheet, OWASP Cross-Site Request Forgery Prevention Cheat Sheet

### SEC-AUTHN-002

> OAuth 2.0 and OIDC client flows MUST (a) include a unique, one-time `state` parameter on every authorization request, bound to the user agent that started the flow, and verify it against that binding; (b) use PKCE (`code_challenge` / `code_verifier`) for every authorization-code flow, including confidential clients; (c) validate an OIDC ID token's `nonce`, and its `iss`, `aud`, `exp` and signature as OpenID Connect Core 1.0 §3.1.3.7 requires; (d) validate redirect URIs against an exact-match allowlist registered with the authorization server, the port of a native app's loopback redirection URI (`127.0.0.1`, `[::1]` or `localhost`) aside; (e) generate `state`, the PKCE `code_verifier` and the OIDC `nonce` with a cryptographically secure pseudorandom generator, the `code_verifier` and the `nonce` each specific to one transaction and bound to the client and the user agent that started it; (f) where the client can interact with more than one authorization server, defend against mix-up attacks by comparing the issuer an authorization response identifies, by the `iss` parameter (RFC 9207) or an `iss` value such as an ID token's, with the issuer the request was sent to, or, where neither is available, by a distinct redirection URI per authorization server; and (g) in a native app, send authorization requests through an external user-agent, never an embedded one such as a web view. A client that authenticates to the authorization server MAY instead send a `redirect_uri` it has not registered, and does not take from the request, in a pushed authorization request (RFC 9126) or a signed request object (RFC 9101).

**Verification:** Any spec or plan that introduces an OAuth client, OIDC client, or third-party login integration MUST commit to each requirement, (f) where the client can interact with more than one authorization server and (g) where it is a native app, and one that changes the redirect URIs such a client registers or sends without introducing the client MUST commit to (d). `/{project}:analyze` flags OAuth/OIDC specs that omit `state` (neither PKCE nor the OIDC `nonce` stands in for it), or verify it against no binding to the user agent, such as a store of issued values shared across user agents, that omit PKCE or limit it to public clients, that omit ID-token `nonce` validation or any of its `iss`, `aud`, `exp` and signature checks, that pass a `redirect_uri` taken from a request parameter, in a pushed authorization request or a signed request object included, or name neither a fixed registered `redirect_uri` nor its exact-match validation, the port of a native app's loopback redirection URI (`127.0.0.1`, `[::1]` or `localhost`) aside, and one a client that authenticates to the server sends in a pushed authorization request or a signed request object without taking it from the request, the spec naming that mechanism, aside, or that describe `redirect_uri` matching using `startsWith`/`contains`/regex instead of exact equality, that generate `state`, a `code_verifier` or a `nonce` with a non-cryptographic generator such as `Math.random`, or reuse a `code_verifier` or a `nonce` across transactions, that let a client of more than one authorization server accept an authorization response with no mix-up defence, or that have a native app send its authorization requests through an embedded user-agent, a spec that changes those redirect URIs without introducing the client flagged for (d) alone. **Not flagged:** a forbidden grant or response type, or the `plain` PKCE method, which `SEC-AUTHN-003` owns; the matching of a `redirect_uri` that an authorization server the project serves or provides receives, which `SEC-AUTHN-004` owns; a client's registration with any authorization server stays this rule's; and, where `security-backend.md` is also loaded, the generator of `state`, a `code_verifier` or a `nonce`, which its `BE-DATA-009` owns, and an ID token's `iss`, `aud`, `exp` and signature validation, which its `BE-AUTHN-012` owns, the source of the key that verifies the signature being its `BE-AUTHN-019`'s.

**Source:** RFC 9700 §2.1, §2.1.1, §4.1.3, §4.4 (OAuth 2.0 Security Best Current Practice), RFC 9126 §2.4, §7.2 (Pushed Authorization Requests), RFC 9207 (OAuth 2.0 Authorization Server Issuer Identification), RFC 8252 §7.3, §8.12, RFC 6749 §10.12, RFC 7636 §4.1 (PKCE), OpenID Connect Core 1.0 §3.1.2.1, §3.1.3.7

### SEC-AUTHN-003

> OAuth 2.0 clients and authorization servers MUST NOT use the resource owner password credentials grant, the implicit grant, or any other response type that returns an access token in the authorization response. PKCE MUST use the `S256` code challenge method; the `plain` method MUST NOT be used. Refresh tokens issued to public clients MUST be sender-constrained (e.g., DPoP per RFC 9449, mutual TLS per RFC 8705) or rotated on every use. An authorization server MUST bind a `code_challenge` it receives to the authorization code it issues, accept a token request for that code only with a `code_verifier` that matches it, and reject a token request carrying a `code_verifier` for a code issued without a challenge, which one that requires PKCE of every client does by construction. An authorization server that redirects a request that may contain the user's credentials MUST NOT use HTTP status code 307.

**Verification:** Any spec or plan that introduces an OAuth 2.0 client or authorization server MUST name the grant types it uses or supports, the PKCE challenge method, for public clients, the refresh-token protection, and, for an authorization server, how its token endpoint enforces PKCE and the status code with which it redirects a request that may carry the user's credentials, such as a sign-in form's `POST`; one that changes the grant or response types a client uses or a server supports without introducing the client or server MUST name the grant and response types it uses or supports, the PKCE challenge method and, for a server, its PKCE enforcement where the change adds an authorization-code flow, and the refresh-token protection where it gives a public client refresh tokens. `/{project}:analyze` flags OAuth specs that use or enable the password grant, the implicit grant (`response_type=token`), or another response type that returns an access token in the authorization response, that allow the `plain` PKCE method, that issue refresh tokens to public clients without sender-constraining or rotation, that have an authorization server accept a token request without checking its `code_verifier` against the `code_challenge` bound to the code, or, unless it requires PKCE of every client, accept a `code_verifier` for a code issued without a challenge, or that have an authorization server redirect a request that may carry the user's credentials with 307. **Not flagged:** a spec or plan that introduces an OAuth client and commits to no PKCE, which `SEC-AUTHN-002` (b) owns; the challenge method once PKCE is named stays this rule's, and so does PKCE's omission from an authorization server's spec or from a change that adds an authorization-code flow.

**Source:** RFC 9700 §2.1, §2.1.1, §2.1.2, §2.2.2, §2.4, §4.8.2, §4.12 (OAuth 2.0 Security Best Current Practice), RFC 7636 (PKCE), RFC 9449 (DPoP), RFC 8705 (OAuth 2.0 Mutual-TLS Client Authentication and Certificate-Bound Access Tokens)

### SEC-AUTHN-004

> An OAuth 2.0 authorization server the project serves or provides MUST compare a `redirect_uri` it receives with a registered one by exact string matching, except for the port of a native app's loopback redirection URI (`127.0.0.1`, `[::1]` or `localhost`); it MAY accept an unregistered one that a client authenticating to it sends in a pushed authorization request (RFC 9126) or a signed request object (RFC 9101).

**Verification:** Any spec or plan that introduces or describes an OAuth authorization server the project serves or provides, as a service or a library, MUST commit to exact string matching of each `redirect_uri` it receives against the registered ones, the port of a native app's loopback redirection URI (`127.0.0.1`, `[::1]` or `localhost`) aside, and an unregistered one it accepts in a pushed authorization request or a signed request object from a client that authenticates to it aside, and to naming that mechanism where it accepts one. `/{project}:analyze` flags such a server without the exact-matching commitment, that matches a `redirect_uri` by prefix, substring or pattern, the port of a native app's loopback redirection URI (`127.0.0.1`, `[::1]` or `localhost`) aside and a restriction it places on an unregistered one accepted in such a request from such a client aside, or that accepts an unregistered one other than in such a request from such a client. The rule keeps a `redirect_uri` such a server receives, its matching and client-side code's navigation to it included. **Not flagged:** an OAuth or OIDC client's `redirect_uri`, its registration with any authorization server included, which `SEC-AUTHN-002` (d) owns.

**Source:** RFC 9700 §2.1, §4.1.3 (OAuth 2.0 Security Best Current Practice), RFC 9126 §2.4 (Pushed Authorization Requests), RFC 8252 §7.3

### SEC-DATA-001

> Passwords, session identifiers, access, refresh and ID tokens, API keys, and personally identifiable information (PII) MUST NOT be placed in the query, path or fragment of a URL the project's code requests, sends or renders, a link it sends in an email or another message included; they MUST travel in a request header or body. Single-use, short-lived values a protocol carries in the URL by design — OAuth authorization codes, password-reset and email-verification tokens — MAY appear in a URL's query or path when their issuer invalidates them on first use and they expire within a bounded lifetime, and a pre-signed object-storage URL MAY carry its authorization when it is scoped to one object and one method and expires within a lifetime the spec states. A key its issuer designs to be public MAY appear in a URL a third party's browser API, embed or image takes it in, as that API requires.

**Verification:** Any spec or plan that has the project's code send a credential or PII to an endpoint, the project's own or another party's, issue or send a link or URL that carries one, or issue a pre-signed URL MUST name where each such value is carried, and, for a single-use value or a pre-signed URL the project issues, its first-use invalidation and lifetime, or its lifetime and the object and method it is scoped to. `/{project}:analyze` flags a spec or plan whose code puts such a value in a URL's query (`?access_token=`, `?api_key=`, `?email=`), path or fragment outside the carve-outs, such as a command-line tool or a server calling another party's API with its key in the query, a single-use value the project issues in a URL whose spec states no first-use invalidation or expiry, and a pre-signed URL the project issues whose spec states no expiry or whose scope reaches more than one object or method. **Not flagged:** a sensitive configuration value, alone or in a configuration object, which `configuration-cross.md` `CFG-ENV-006` owns or, injected by the build into an artifact delivered to end users, its `CFG-ENV-010`; an access token an OAuth authorization response returns in a URL, which `SEC-AUTHN-003` owns; where `security-backend.md` is also loaded, a value in the URL of an endpoint the project serves, whether the spec describes the server accepting it or code sending it there, a value the server sends to a client in a URL, a redirect's `Location` or a link it renders or sends included, a single-use value or a pre-signed URL the project issues, and a value in a WebSocket opening handshake's URL, which its `BE-API-013` owns or, for that handshake, its `BE-API-015`; and, where `security-frontend.md` is also loaded, a value client-side code binds into a URL, which its `FE-STORAGE-003` owns. A value the project's server-side or command-line code sends in the URL of a request to an endpoint the project does not serve stays this rule's in every shape.

**Source:** OWASP REST Security Cheat Sheet (Sensitive information in HTTP requests), CWE-598 (Use of HTTP Request With Sensitive Query String), RFC 6749 §4.1.2, Amazon S3 User Guide (Download and upload objects with presigned URLs), Google Maps Platform security guidance
