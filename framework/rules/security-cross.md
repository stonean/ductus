# Security Rules — Cross-Surface

Enforceable security rules that hold wherever code runs: a server, a browser, a mobile or desktop app, a command-line tool or a library. This file installs in every project shape. These rules verify **design-time commitments** — what a spec or plan must state — and `/{project}:analyze` enforces them against feature artifacts; `/{project}:review`'s security pass also checks the code in scope against them. Where `security-backend.md` or `security-frontend.md` is also loaded, a rule here names the case that file's rule owns. Rule IDs follow the format `SEC-{CATEGORY}-{NNN}`. Categories: `LOG` (logging, error reporting and telemetry), `DEPS` (build inputs and dependencies), `AUTHN` (authentication). Severity, ID permanence, and how review selects or excludes this file follow constitution §rules.

## SEC-LOG — Logging, error reporting and telemetry

### SEC-LOG-001

> Logs, error-reporting payloads, trace span attributes and events, metric labels, and propagated trace context (W3C `tracestate` and OpenTelemetry baggage entries) MUST NOT carry passwords, full authentication tokens, session IDs, encryption keys, one-time codes (OTP, TOTP, SMS codes), recovery codes, security-question answers, raw PII, full payment card numbers, or other sensitive field values, wherever the code that records them runs. A field that must be referenced MUST be recorded by its name, in a redacted, truncated or masked form, or as an opaque internal identifier, never by its value.

**Verification:** Any spec or plan that introduces logging, error reporting, tracing, metrics or baggage, in client code or server code, MUST commit to excluding or redacting passwords, tokens, session IDs, keys, one-time and recovery codes, PII and other sensitive field values from each of those carriers. `/{project}:analyze` flags specs that log or report request or response bodies in raw form, that mention "log everything" without a redaction commitment, that send an error reporter raw request or form data without scrubbing it, or that record tokens or PII as span attributes, metric labels, baggage or `tracestate`. **Not flagged:** a sensitive configuration value, alone or in a configuration object, which `configuration-cross.md` `CFG-ENV-006` owns; and, where `security-backend.md` is also loaded, any other such value in a log line, which its `BE-LOG-002` owns, or in an error-reporting payload, a span, a metric label or propagated trace context, which its `BE-LOG-008` owns.

**Source:** OWASP Logging Cheat Sheet ("Data to exclude"; its event sources include "Client software" and a "JavaScript exception handler"), W3C Trace Context §6 (Privacy Considerations), OpenTelemetry documentation — Baggage (Baggage security considerations)

## SEC-DEPS — Build inputs and dependencies

### SEC-DEPS-001

> Build and release inputs that the package lockfile does not cover — CI/CD actions and reusable workflows, container base images, and tools or scripts downloaded during the build — MUST be pinned to an immutable reference: a full commit SHA, an image digest, or a checksum the build verifies. An action in a workflow onboarded to a GitHub Actions workflow dependency lockfile (`.github/workflows/actions.lock`) is pinned by the commit the lockfile records for it; a reusable workflow call is not, and takes a full commit SHA, and nor is a container image a workflow runs (`uses: docker://…`, a job's `container:` or `services:` image), which takes an image digest. Mutable references (branch names, version tags, `latest`) MUST NOT select what runs in the build. A pinned reference MUST change only through a documented update process.

**Verification:** Any spec or plan covering CI/CD pipelines, container builds, or build tooling MUST commit to immutable pinning for each of these input kinds and to an update process for the pins (e.g., Dependabot or Renovate digest updates). `/{project}:analyze` flags build specs that reference actions by tag or branch (`uses: org/action@v4`) outside a workflow onboarded to a workflow dependency lockfile, a tag an immutable release backs included since nothing in the repository shows one, that call a reusable workflow by tag or branch in any workflow, that run a container image by tag alone in any workflow (`uses: docker://hadolint/hadolint:v2.12.0`, a job's `container: node:22`), that reference base images by tag alone (`FROM node:22`), or that run download-and-execute steps without checksum verification. **Not flagged:** a floating version of a dependency the lockfile covers, which, where `security-backend.md` is also loaded, its `BE-DEPS-002` owns or, for a frontend production build where `security-frontend.md` is also loaded, its `FE-DEPS-004`.

**Source:** OpenSSF Scorecard (Pinned-Dependencies check), GitHub Docs — Secure use reference (GitHub Actions) and Workflow dependency lockfiles, `github/gh-actions-lock` README (Limitations), OWASP Top 10:2025 (A03 — Software Supply Chain Failures)
