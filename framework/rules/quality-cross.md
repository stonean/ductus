# Code Quality Rules

Enforceable code-quality rules that are not specific to a surface. These rules apply to all projects adopting `ductus` regardless of stack — code-quality discipline is the same problem on backend workers, domain methods, middleware, and frontend stores alike.

Rules use RFC 2119 language: **MUST** / **MUST NOT** are enforced as errors; **SHOULD** / **SHOULD NOT** are flagged as warnings.

Rule IDs follow the format `QUAL-{CATEGORY}-{NNN}` and are permanent — once assigned, an ID is never renumbered, even if the rule is moved within the file or deprecated. Categories: `STUB` (silent stubs), `GROUND` (unverified contracts), `CLAIM` (unsubstantiated clean results), `DELEG` (unenumerated delegation to shared code), `TEST` (tests that cannot fail). See `specs/036-quality-cross-rules/data-model.md` for the `QUAL` surface registration and `specs/008-security-rules/data-model.md` for the full rule schema.

These rules verify **code patterns** rather than design-time commitments; `/{project}:review`'s quality pass enforces them against source in scope.

Cross-cutting (`-cross.md`) rule files load for every stack: `[rules] surfaces` cannot exclude them, and `/{project}:analyze` loads every rule file present. A project can exclude this file from `/{project}:review` with a `.ductus/config.toml` `[[review.disabled-rule-files]]` entry and its mandatory `reason`; listing it under `[pinned] files` only stops `ductus` updates from overwriting a customized copy, which still loads for review and analyze.

## QUAL-STUB — Silent stubs

### QUAL-STUB-001

> A partial or unimplemented code path whose surrounding contract implies it performs work MUST fail loudly — via a panic, an explicit error return, or a failing/skipped test fixture — rather than silently passing through. Returning a zero value, returning `next` unchanged from middleware, returning early from a handler without an error, or returning `nil, nil` from such a method is a silent pass-through and does not satisfy this rule.

**Rationale:** Silent stubs ship indistinguishably from working implementations — a no-op rate-limiter, an always-allow permission check, a publisher that drops events on the floor — and the gap surfaces only when the missing behavior is needed, which is precisely when the system is under stress. In an adopter project running a backend service, a passthrough stub left in a rate limiter's enabled-mode would have silently disabled rate limiting in production had the follow-on task been skipped; failing loudly turns that latent production incident into an immediate, visible failure at the point the stub is exercised (or built/tested).

**Verification:** `/{project}:review`'s quality pass flags a code path in scope when **all three** hold: (1) it is **reachable** under the current spec; (2) its **surrounding contract implies work** — it is named for a behavior, documented to do something, or called by code that depends on its effect; and (3) it returns a success / zero / pass-through value with **no loud signal**. The following are compliant and are **not** flagged: an explicit incompleteness marker (`panic`/`todo!`/`unimplemented!`, a raised not-implemented error, or a failing/skipped test fixture) — that *is* failing loudly; intentional pass-through middleware documented as deliberate; a default or interface implementation meant to be empty; and a not-yet-reachable branch behind a feature flag or guard. The **API-schema** fail-loud case — a published schema bound to its implementation, so that the two cannot diverge silently — is already governed by `api-backend.md` `BE-SCHEMA-002`; this rule covers the broader runtime/contract case across all surfaces rather than restating it.

**Source:** Fail-fast principle (Jim Shore, "Fail Fast", IEEE Software, September/October 2004, pp. 21–25).

## QUAL-GROUND — Verify contracts

### QUAL-GROUND-001

> Code whose correctness depends on a contract defined outside that code — a database schema, another service's API shape, a file or wire format, or a list, schema, or format defined elsewhere in the repository — SHOULD bind to that contract in a way that fails loudly when the assumption is wrong (a typed or generated binding, a schema or migration reference that the build or a test checks, a startup or first-use validation, or a test that exercises the real shape) rather than silently encoding an unverified assumption.

**Rationale:** An unverified assumption about a contract defined elsewhere fails silently and asymmetrically — the code works until the assumed column, field, or member differs from reality, at which point it breaks in production with no early signal. Grounding the assumption at the point it enters the code (constitution §grounding) turns a latent production incident into a build-time or test-time failure. This is the code-side counterpart to the artifact-grounding check `/{project}:analyze` runs against spec and plan claims, and it applies `QUAL-STUB-001`'s fail-loud principle to contracts rather than unimplemented paths. A contract defined elsewhere in the same repository drifts the same way an external one does: the code that hard-codes its shape is not the code that changes it. Configuration keys and values are deliberately not this rule's subject — `configuration-cross.md` `CFG-ENV-003` (required environment variables present at startup) and `CFG-ENV-008` (every value parsed into its declared type at startup, failing fast) govern them at MUST, so a configuration defect is never reported under two IDs; where those rules apply, it is reported under theirs.

**Verification:** `/{project}:review`'s quality pass flags a code path in scope when **all three** hold: (1) its correctness depends on a contract defined **outside that code** — a database schema, an external service's API, a file/wire format, or a list, schema, or format defined elsewhere in the repository; (2) the assumed shape is **encoded directly** — a literal column/table/field/key name, or an assumed response structure — rather than through a binding that would surface a mismatch; and (3) there is **no fail-loud guard** — no generated or typed binding (ORM model, generated client, a type the compiler checks), no schema or migration reference that the build or a test checks, no startup or first-use validation, and no test that exercises the real contract. The following are compliant and **not** flagged: a typed or generated client/ORM binding; a documented assumption paired with a validating guard that fails loudly; a value covered by a test against the real contract; and a contract used through its own definition, so that the compiler or type checker enforces it (an internal type referenced rather than restated). Configuration keys and values are not flagged here; `CFG-ENV-003` and `CFG-ENV-008` own them. Advisory (SHOULD) — the finding asks the author to ground or guard the assumption. It never sets the review's `blocking` flag, and like any outstanding SHOULD it is fixed or waived before the spec reaches `done`.

**Source:** Constitution §grounding (evidence discipline); fail-fast principle (Jim Shore, "Fail Fast", IEEE Software, September/October 2004, pp. 21–25), as applied by `QUAL-STUB-001` — the article's worked example, a property missing from a configuration file and returned as a default rather than raised, is configuration, which this rule leaves to `configuration-cross.md` (the article's cause, a key mistyped in the file, is `CFG-ENV-012`'s unrecognized key); this rule applies the same principle to every other contract.

## QUAL-CLAIM — Unsubstantiated clean results

### QUAL-CLAIM-001

> A result that reports a clean, empty, or in-sync state SHOULD distinguish *"examined the subject and found nothing"* from *"could not examine the subject"*, rather than emitting the same value for both. When a code path skips part of its subject, cannot reach it, or has no basis to inspect it, its output SHOULD say so — through a distinct return variant, an accompanying status or guidance field, or a message naming what was not examined — instead of a bare zero, empty collection, or success string that a caller will read as positive assurance.

**Rationale:** Absence of evidence rendered as evidence of absence. A caller cannot tell a verified-clean result from an unverifiable one when both are the empty list, and will act on the reassuring reading — which is the dangerous one, because the states where a tool *cannot* check are disproportionately the states where something is wrong. The failure is asymmetric and silent: nothing errors, a gate passes, and the missing check is discovered later by someone re-deriving the result by hand. This differs from `QUAL-STUB-001`, which governs *unimplemented* paths returning success, and from `QUAL-GROUND-001`, which governs unverified assumptions inside logic; this rule governs a fully-implemented path whose *output* overstates what it verified.

**Verification:** `/{project}:review`'s quality pass flags a code path in scope when **all three** hold: (1) it emits a clean / empty / zero / success result; (2) that result is reachable in a state where the code did **not** examine some part of its nominal subject — a skipped input, an unavailable precondition, an empty or underivable window, a filtered-out set; and (3) the output does not let a caller distinguish that state from a genuinely-examined clean one. The following are compliant and **not** flagged: a distinct return variant or sentinel for the unknown case; an accompanying field naming what was skipped or why (a `guidance` string, a `skipped` list, a count of what *was* examined); a message that quantifies the subject examined rather than asserting a global property; and a documented total function whose subject is always fully examinable. Advisory (SHOULD) — the finding asks for a distinguishable result, and blanket-flagging every empty return would be noise. It never sets the review's `blocking` flag, and like any outstanding SHOULD it is fixed or waived before the spec reaches `done`. **Promotion criterion:** promote to MUST when a single `/{project}:review --all` run reports 5 or more instances across a repo on two consecutive runs, matching the promotion path `/{project}:analyze`'s advisory checks use.

**Source:** Constitution §grounding (evidence discipline). Surfaced 2026-08-01/02 in `ductus`'s own tooling, where the shape recurred four times in one session: `derive-boundary` and `diff-cross-spec` each raised an error on an underivable git window, and the fix's first form degraded them to an empty result that reads as clean — for `diff-cross-spec`, bare empty lists its contract defines as *no cross-spec impact* — before each was given an explicit `guidance` field; `scripts/audit/run-all.sh` exited 0 both when a family passed and when it never ran, so registration of a new family had to be proven by deliberately breaking it; and the since-retired `.ductus/scripts/gen-spec-deps.sh` printed `No changes (all specs in sync)` on a zero rewrite count, asserting a property of files it never enumerated — `list_specs()` scopes to `git ls-files`, which excludes untracked specs by design (spec 017's `tracked-specs-not-worktree`), so a freshly-created spec is invisible to the very message claiming it is in sync. Its sibling `gen-cross-service-refs.sh` shared both the enumeration and the message shape. Both derivations are now the `derive-dependencies` / `derive-references` primitives, which report `examined`, `untracked-skipped`, `unwritten`, `absent`, and `unparseable` explicitly so the claim names its own scope; the rule is what shaped those fields. `unwritten` reached `derive-references` late, on 2026-08-27: the scenario had reasoned that only the dependency derivation could examine a spec and decline to write it, which held for a field derived from the spec body alone but not for one derived from the body *and* the `[services]` registry — a service rename drifts specs nobody edited, and an unedited spec is never staged. An adopter carried dead references for nine commits behind that gap while the hook reported the tree in sync. The lesson is the rule's own: the reference derivation had narrowed its enumeration until "examined" and "written" coincided, which reads as a sound claim and is instead a smaller subject nobody stated. `gen-help-tables.sh` and `gen-configure-mcp.sh` share only the message shape, and both have since been assessed against this rule (the assessment [017's `generator-sync-claim-honesty`](https://github.com/stonean/ductus/blob/main/specs/017-derive-dont-ask/scenarios/generator-sync-claim-honesty.md) requires of them): `gen-configure-mcp.sh` is sound — it processes a fixed set of four files unconditionally, compares each, and exits non-zero when the tool list is empty, so its subject is always fully examined. `gen-help-tables.sh` was **not** — it built its tables from a hardcoded command list, so a command added under `framework/commands/` was absent from `help.md` while the generator still reported it in sync. It now asserts its coverage against the directory and fails loudly on an unlisted command, so the claim is verified rather than merely reworded.

## QUAL-DELEG — Delegation to shared code

### QUAL-DELEG-001

> Replacing a hand-rolled predicate, parser, validator, or comparator with a shared one SHOULD be preceded by enumerating what the local version enforced **by construction** — its accepted character set, its length or form constraints, where it decided the candidate ended, its ordering, and the trust level of the input it was written for — rather than only what its name or doc comment declares. Any property the shared implementation does not provide SHOULD be kept local, with the reason recorded at the call site and at the shared implementation.

**Rationale:** An inline predicate usually enforces several properties at once and names one of them, so delegating adopts all of the shared rule's behavior and silently drops every unnamed property the local version happened to supply. A change made to fix one defect therefore widens or narrows the others, and the two failures point in opposite directions: a widened predicate accepts input the caller then writes verbatim into somewhere structured, while a narrowed one silently discards input it used to accept — which is the same silent-drop class the delegation was often introduced to fix, reintroduced while fixing it. Neither is visible in a repository that happens to contain no instance of the affected shape, so an unchanged result before and after is not evidence. The **trust context** is the property most often unshareable: a predicate recognizing names that already exist on disk can safely leave its character set open, while one parsing untrusted text destined for a structured file cannot — one rule, opposite ends. This differs from `QUAL-CLAIM-001`, which governs a result that overstates what it verified, and from `QUAL-GROUND-001`, which governs an unverified assumption about a contract defined outside the code that depends on it; this rule governs a correct-looking substitution of one implementation for another.

**Verification:** `/{project}:review`'s quality pass flags a change in scope when **all three** hold: (1) it replaces a local predicate, parser, validator, or comparator with a shared one; (2) the local version enforced at least one property the change does not name — character set, length or form, termination, ordering, or input trust level; and (3) neither the call site nor the shared implementation records which properties were checked against the shared rule and which were deliberately kept local. The following are compliant and **not** flagged: a delegation whose comment, commit message, or test names both the properties enumerated and the ones retained locally; a shared implementation documented as the single definition of the property in question, with its call sites cited; and a delegation covered by tests exercising **both** the widened and the narrowed direction, since one direction proves half. Advisory (SHOULD) — the finding asks the author to enumerate and record. It never sets the review's `blocking` flag, and like any outstanding SHOULD it is fixed or waived before the spec reaches `done`.

**Source:** Constitution §drift-prevention (one authoritative source, referenced rather than restated — in code, one definition called rather than re-implemented) and §grounding (prefer the source to the recollection — here, the code's behavior over its declaration). Both are named in prose rather than linked, as `QUAL-GROUND-001` and `QUAL-CLAIM-001` name §grounding: this file ships to `specs/rules/quality-cross.md` in an adopter tree while the constitution lands at `.ductus/constitution.md`, so a repo-relative link resolves here and dangles there. Surfaced 2026-09-14 in `ductus`'s own runtime, where two link-slug predicates were delegated to a shared feature-directory parser to fix a digit-count bug. The parser deliberately leaves a sequential directory's slug outside the slug grammar, which is sound for directory names already on disk, so a crafted link target spliced a second key onto a spec's `dependencies:` frontmatter line; and terminating the candidate on `/` alone lost where the old predicate had ended it, so a directory-only sibling link harvested nothing. Probes found both. `derive-dependencies` reported no drift across all 54 specs before and after.

## QUAL-TEST — Tests that cannot fail

### QUAL-TEST-001

> A test SHOULD fail when the behavior it names is removed or broken. A test that passes whether or not the code under test behaves as named SHOULD NOT be added or counted as coverage. That includes a test that exercises a path without asserting its result, one that pins only a value incidental to the behavior, and one whose assertion a fallback or default path satisfies as well as the primary path does.

**Rationale:** A test that cannot fail is counted as coverage by every measure a project has: the suite grows, the run is green, and the task that asked for the test reads as done. Yet it proves nothing about the behavior it names, so the first sign that the behavior broke is the failure the test existed to catch. The fallback case is the one that survives review. When the code under test has a fallback, an input on which the primary path and the fallback agree lets the fallback satisfy the assertion, and the test stays green with the primary path deleted. Only breaking the code shows it. This differs from `QUAL-CLAIM-001`, which governs a code path whose *output* overstates what it examined, and from `QUAL-STUB-001`, which governs an unimplemented path that returns success. This rule governs the test itself: a check that reports a pass it could never withhold.

**Verification:** `/{project}:review`'s quality pass flags a test in scope when **any** of these holds: (1) it exercises a path without asserting on the result the test is named for; (2) its assertions pin only values incidental to that behavior, such as a length, a type, or that something is non-empty, where the content is what the behavior produces; (3) the code under test has a fallback or default path, and the test's input makes the primary path and the fallback produce the same observable result, so the assertion would hold with the primary path broken; (4) whether it can fail depends on a condition the test does not establish — its assertions are compiled or branched away inside the test body on some platform or feature set, or its outcome differs only when an environment variable the test never sets happens to be present — so in a configuration the suite runs in it passes with the behavior broken; or (5) it never reaches the code it names, because the unit under test is mocked, stubbed, re-implemented inside the test, or not called at all. The following are compliant and **not** flagged: a test whose report, commit message or comment records how it was shown to fail, by reverting the fix or mutating the code; a test whose assertion is on the named behavior's own output, with inputs that separate it from any fallback; a test that establishes the condition it depends on, by setting the variable itself or re-running in a child process that does; a test gated as a whole, by a test-level attribute or skip marker, to the configurations where the named behavior applies, since elsewhere it reports no pass; a test that replaces the unit's collaborators with doubles but calls the unit itself; and a test explicitly named as a smoke test, which asserts only that a path runs and claims nothing more. Advisory (SHOULD): the finding asks the author to make the test able to fail and to record how that was shown. It never sets the review's `blocking` flag, and like any outstanding SHOULD it is fixed or waived before the spec reaches `done`.

**Source:** Constitution §design-principles (a check that cannot run is never indistinguishable from one that passed, and a new gate is shown to fail before it is trusted to pass), applied to tests rather than to the pipeline's own checks. Named in prose rather than linked, for the reason `QUAL-DELEG-001` gives. Surfaced 2026-09-26 in `ductus`'s own runtime tests. A test for an exec tally claimed to pin case-insensitive tier parsing, yet it passed with the parsing made case-sensitive. Its capitalized MUST finding answered a MUST-tier request, so when the finding's tier failed to parse, the fallback to the requested tier produced the same count. Mutating the code was the only thing that showed it. Verification shapes (4) and (5) were added after reviews filed them under this rule's Statement while none of the first three described them. On 2026-09-29, 062's review found a test asserting that no session identity was captured, which a per-call environment read also returns wherever no identity variable is set, so the test could fail only in a shell carrying one and never in CI. On 2026-09-30, 048's review found a test whose `cfg(unix)` inside its body left it asserting nothing on Windows, and one that called no `ductus` code at all.
