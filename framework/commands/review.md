# /{project}:review

Run a comprehensive code review against the targeted feature's implementation,
covering reuse, quality, security, efficiency, and simplicity, and judges
every acceptance criterion against the code, wherever that code lies, ticking
or unticking each to match. Produces a `review.md` artifact alongside the spec.
**Blocks the spec from reaching `done` when MUST violations are present, or a
criterion is judged not met.**

`/{project}:review` audits **code against rules**. It is complementary to `/{project}:analyze`,
which audits **artifacts against each other**. Both should pass before a spec
advances to `done`.

## Purpose

Quality gate before `done`: audit the feature's implementation against the project's rule files across five dimensions (security, reuse, quality, efficiency, simplicity) and judge every acceptance criterion (the criteria step, step 7's sub-steps), record the findings in `specs/NNN/review.md` — each observation with its disposition — and set `blocking` in that file's own frontmatter record so `/{project}:implement`, `/{project}:analyze`, and the CI hook can hold the spec out of `done` while MUST violations stand. Waivers (with recorded justification) and deferrals that release a violation (**§Deferrals** in `.ductus/reference/review.md`) are the sanctioned exits.

## Context

Use the session target: invoke `resolve-session` and display any notices and unreadable session files it returns. If `$ARGUMENTS` carries a feature identifier, use it to override the session target, resolved through `resolve-feature` (`ambiguous` and `not-found` are domain outcomes to surface). With `--all` the target is every spec at `in-progress` or `done`, then the code no spec claims, and a feature identifier is redundant; report it rather than silently ignoring it. With `--project` the target is the code no spec claims alone (**A project review** under Instructions): no session target is needed, and a feature identifier beside it is an operator error to report, never ignored. If no session target is set and no feature argument or `--project` is provided, stop and tell the user to run `/{project}:target` first.

### Parsing `$ARGUMENTS`

Parse `$ARGUMENTS` for flags in any position, then treat the remaining text as the optional feature identifier. No flag is persisted to the session file. [Flags](#flags) below is the authoritative table of what each one _does_; this step is how each is _recognized_:

- **`--all`**, **`--project`**, **`--fix`**, **`--security`**, **`--simplicity`**, **`--quality`** — bare toggles, no value.
- **`--since=<ref>`** — takes its value in `--since=<ref>` form; pass it to `compute-review-scope` as `since` (step 1). A bare `--since` with no value is an operator error: report it and stop. Do not fall back to the default diff base, which reviews a different window than the one asked for.
- **`--waive <rule-id> --reason "<text>"`** — a pair; each is an operator error without the other. Repeatable to waive more than one finding in a single invocation.
- **`--defer <rule-id>`** — with `--target <path>` (plus `--task <n>` when the target is a `tasks.md`), `--work-item <id>`, or both, and an optional `--reason "<text>"`. Each `--target`, `--task`, `--work-item` and `--reason` belongs to the `--waive` or `--defer` before it. A `--defer` naming no work, a `--task` without a `tasks.md` target, a `--waive` carrying a `--target`, `--task` or `--work-item` (a waiver names no future work), and one rule both waived and deferred in one invocation are operator errors. Repeatable.

Report an unrecognized `--flag` and stop. Never absorb it into the feature identifier, where it can resolve to a real feature whose review then covers the wrong scope.

## Scope Boundaries

- Reads the target spec, its `plan.md` (for Affected Files), the in-scope source files, the code each acceptance criterion's claim names wherever it lies (the criteria step), the selected rule files' rules as step 2's `discover-rule-files` result gives them, `AGENTS.md`, `.ductus/config.toml`, and the `decisions:` list in its own `review.md`. The fix-and-route step (step 10) additionally reads what a disposition needs: a candidate covering spec's `spec.md` and `tasks.md` for the **§Groom decision tree** in `.ductus/reference/groom.md`, as `/{project}:groom` does. Do NOT review files outside the resolved scope beyond what the criteria step reads to judge a criterion, and do NOT introduce review criteria from outside the project's rule files and `AGENTS.md`.
- Writes `specs/NNN/review.md` — the whole record, in that file's own frontmatter (via `write-review`). `spec.md` is written only by step 7.3: its `mark-criterion` calls, one acceptance-criterion checkbox per verdict, and a `done` spec's ticked criterion whose text the owner says the code bears out. With `--waive`, appends a waiver entry; with `--defer`, records a deferral under `decisions:`, including, once confirmed, a `done → in-progress` reopen of a `done` spec a violation is deferred to, when the check-owed-work primitive then reports owed work; with `--fix`, applies auto-fixable findings to the working tree; and step 10 writes each observation's disposition — a chore fix by the rule, or, only after `gate-confirm` returns a confirmed decision, a deferral of a broken contract to the spec's own task or the home the **§Groom decision tree** in `.ductus/reference/groom.md` chooses, including a `done → in-progress` reopen of the spec deferred to, when the check-owed-work primitive then reports owed work. The fix-round loop (steps 10 and 12) writes its round files under `.ductus/review-rounds/{feature}/`, `.ductus/review-rounds/.gitignore`, and its snapshots as git objects no ref points at. A project review writes `{specs-root}/review.md` in place of `specs/NNN/review.md` and `.ductus/review-rounds/project/` in place of the feature's round directory, and writes no `spec.md` and no status. Past the read size, steps 1, 2, 8, 9, 11 and 12's primitives, `dashboard` under `--all`, and `read-section` write lists files under `.ductus/results/`. No other files are modified, and nothing is written to `specs/inbox.md` — the reviewed spec's status transitions belong to `/{project}:implement`, but for the one this command writes on it, `done → in-progress` once it unticks a criterion (step 7.3) or defers a finding to the spec's own work (step 10), read from the check-owed-work primitive (§spec-lifecycle).
- Reference: §runtime-host-integration, §bug-handling, §brownfield-inbox (Finding dispositions), §text-first-artifacts, §spec-phase (spec-root resolution) (constitution loaded by `/{project}:target` — do not re-read).

## Inputs

- **Target** — the current `/{project}:target` feature, or every feature with
  status `in-progress` or `done` and then the code no spec claims when invoked
  with `--all`, or that code alone with `--project`.
- **Rules** — every file under the project's rule-file directory
  (`framework/rules/` in ductus's own repo, `specs/rules/` in adopter
  projects) selected in step 2 (`discover-rule-files`); their content is the
  authoritative review criteria. RFC 2119 language is authoritative:
  **MUST/MUST NOT** are blocking violations, **SHOULD/SHOULD NOT** are
  advisory.
- **Scope** — the spec's own change since its window's start, committed or not:
  `compute-review-scope`'s description states the rule, and what it leaves out
  is named in the record — see step 1.
- **Config** — five `.ductus/config.toml` keys influence this command:
  - `[review] tech-stack-verified` (boolean, default `false`): when `true`,
    step 1's tech-stack alignment check is skipped until the operator clears
    the key. Set, with operator confirmation, on the first successful check. A present
    value that is not a boolean halts step 1 before any pass, naming the key,
    the file and the value, and is never read as `false`.
  - `[[review.disabled-rule-files]]` (array-of-tables, default empty): each
    entry has a required `file` (a basename in the rule-file directory, e.g.,
    `"accessibility-frontend.md"`) and a required `reason` (free text, the
    override's audit trail; trimmed length ≥ 16 Unicode codepoints), and is
    excluded from step 2's selection regardless of stack detection. A
    malformed entry fails fast in step 2.
  - `[rules] surfaces` (array of strings, default unset): the project's rule
    surfaces, members in `{"backend", "frontend"}` (`*-cross.md` files are
    unconditional and not members). When set, it replaces stack detection in
    step 2; when unset, step 2 falls back to the detected stack (and with no
    detected surfaces supplied, the primitive loads **all** recognized
    surfaces). The **empty list** (`[]`) is valid and means cross-only, not
    the same as unset; an unrecognized member (including `"cross"`) or a
    non-list value fails fast in step 2. Collected and persisted by `/ductus`
    (`ductus.md`, **Collect Project Inputs**).
  - `[review] re-reads-off` (string, default unset): switches step 12's
    fix-round loop off; the value is the reason, at least 16 characters
    once trimmed. Each round that needed a re-read is then recorded as not
    re-read and waived with it, and each run prints it. An empty value
    counts as unset. A malformed value halts the run at step 10, before any
    fix, naming the setting and the file.
  - `[artifacts] read-size-bytes` (integer, default 50,000): the size past
    which a step's result moves its lists to the file `lists-file` names, as
    each primitive's description states. A malformed value halts the call
    that reads it.

## Flags

| Flag | Behavior |
| --- | --- |
| _(none)_ | Review the current target across all dimensions |
| `--all` | Review every feature with status `in-progress` or `done`, then the code no spec claims as `--project` does. Composes with every other flag but `--project`, which it includes. |
| `--project` | Review the code no spec claims, under `{specs-root}/review.md` (**A project review** under Instructions). Takes no feature and no `--since`. |
| `--security` | Run only the security pass |
| `--simplicity` | Run only the reuse / quality / efficiency / simplicity passes |
| `--quality` | Run only the correctness / bug-detection pass |
| `--fix` | Apply auto-fixable findings (see **§Auto-fix scope** in `.ductus/reference/review.md`) |
| `--since=<ref>` | Override where the window starts; the scope rule still applies (default: where the spec's last review ended, whether or not it reopened since; with no review, the spec's last reopen, `HEAD` while that reopen is uncommitted, or for a `done` spec the commit that set it `done`) |
| `--waive <rule-id> --reason "<text>"` | Record a waiver for a MUST or SHOULD violation, anchored at each site its rule fires (see **§Waivers** in `.ductus/reference/review.md`) |
| `--defer <rule-id>` `--target <path>` `--task <n>` `--work-item <id>` | Defer a MUST or SHOULD violation, at each site its rule fires, to the work that will address it (see **§Deferrals** in `.ductus/reference/review.md`) |

## Pipeline position

`/{project}:review` runs after `/{project}:implement` has produced code and before the spec
can advance to `done`. The recommended sequence is:

```text
/{project}:implement   →   /{project}:review   →   /{project}:analyze   →   spec status: done
```

`/{project}:implement` MUST NOT mark a spec `done` while the target's `review.md`
records `must-violations: > 0`. See **§Blocking semantics** in `.ductus/reference/review.md`.

## Instructions

> **For agent runtimes**: the Invoke steps below call the ductus runtime's MCP tools; without the server, stop and say to restart or re-run `/ductus` (§runtime-host-integration).

**Where a named section lives.** This command's reference is `.ductus/reference/review.md`. A section named here, or cited elsewhere as part of this command, that has no heading in this file is there. When a step points at one, invoke `read-section` with that path and every section the step names, in one call, rather than reading the whole file.

Run once per targeted feature, in order. Resolve a `[feature]` argument through `resolve-feature`, and enumerate the `--all` set from `dashboard`'s per-spec status inventory (`specs[].status ∈ {in-progress, done}`, read from the file its `lists-file` names when its `form` is `file`) rather than a directory scan. Before step 3, read **§Load rules** and **§Run review passes** in `.ductus/reference/review.md`, which hold the review's inputs and each pass's definition and severity.

**A project review.** With `--project`, and as the last run of `--all`, the review is of the code no spec claims, recorded in `{specs-root}/review.md`: the review record's schema, with no status, no gate and no criteria. It is the steps below with these differences, and no other:

- **Step 1** makes none of its checks of a spec's status or `tasks.md`, and in place of the scope primitive calls the check-unreviewed-code primitive with no argument, which reads `HEAD`'s commit and never the working tree, so uncommitted work joins no project review. In the file form read `not-examined` and `unclaimed` from the file `lists-file` names before either test below, since neither list is inline there and an absent list is not an empty one. When its `not-examined` names `project`, halt this run with that reason: a commit holding no project record is seeded first, by the write-review primitive with `seed` alone, and the seed committed. When `unclaimed` is absent, report that no code no spec claims is owed a review and stop this run, writing nothing. Otherwise `unclaimed` is the window: its `window-start` is step 11's `diff-base`, the result's `at` its `reviewed-against`, and its `paths` the scope the passes read, each path the record leaves open or left unread among them. Its `deleted` paths cannot be read: the Summary names each, and a window holding deleted paths alone skips the passes as any empty scope does. `--since` does not combine with `--project`, since the primitive reports one window: report the pair as an operator error and stop.
- **Steps 7.1 to 7.3** do not run: the record has no criteria, and step 11 passes no `criteria`.
- **Steps 8 to 12** call each primitive with no `feature`, which names the project: the process-waivers, process-decisions, start-fix-rounds, brief-re-read, read-re-read, check-prescriptions and write-review primitives. A departure entry belongs to a spec, so none applies.
- **Step 10** has no spec whose own task could take a deferral: a broken contract is fixed in the run, or deferred to the home the **§Groom decision tree** in `.ductus/reference/groom.md` chooses.
- **Under `--all`** a project run that halts or finds nothing owed is reported beside the features' results and fails none of them.
- **Under `ductus exec`** no project review is walked: `project=true` drops the session's target from the walk, so no step reviews the targeted feature in the project's name, and the walk stops at step 1, which says to run the review through the host.

Invoke `compute-review-scope`; the primitive's description states how the diff base, `base-source`, the scope and `review-owed` are decided, and a `diff-base` that is empty, or a window wider or narrower than the change under review, is settled by the base-override rules of **§Window and coverage** in `.ductus/reference/review.md` before any pass runs. When `review-owed` is false and neither `--since` nor the operator asks for a review, report `review-owed: false` — this reopening changed no code, and every criterion is ticked and judged met with its current text, so it owes `/{project}:analyze` and no review — and stop this feature's run, writing nothing. When `scope-count` is zero, skip the passes and waivers, but not the criteria step (steps 7.1 to 7.3), which judges every criterion whatever the window holds, and go on at step 9 — an observation the reviewer supplies is still dispositioned — and step 11 emits the nothing-to-review-yet report, blocking only through a criterion judged not met; when `deleted-count` is above zero the scope is empty because every path it would hold was deleted, so that report and the record's Summary name each path in `deleted` and say no pass could read it, and a review owed for deletions never reads as a window that changed nothing; when that write refuses, since the record counts a finding it would clear unread, report the refusal and stop this feature's run. **A failed call is not an empty scope, and neither is an absent list.** Never route a failed call or a file-form result to the empty-scope branch, which records a non-blocking 0-findings review byte-identical to a genuinely clean one. Otherwise confirm tech-stack alignment first (host judgment, not a primitive): read the active config file; when its `[review] tech-stack-verified` flag is true, skip the check (a present value that is not a boolean halts here, naming the key, the file and the value); else compare the AGENTS.md Tech Stack section against the code in scope, halting with the tech-stack-misalignment message (**§Blocking message** in `.ductus/reference/review.md`) on a mismatch, and — on success — confirm before persisting the flag (see the tech-stack alignment check under **§Resolve target and scope** in `.ductus/reference/review.md`) and write `[review] tech-stack-verified = true` to the **active config file** (the newest existing of `.ductus/config.toml`, `.govern/config.toml`, or the legacy root `.govern.toml`, else `.ductus/config.toml`; specs 042 and 049 — a write outside the `/ductus` migrations never creates a partial `.ductus/config.toml` alongside a lingering older file).

10. Fix and route (host responsibility). Before anything is written, take the run's first fix-round base: call the start-fix-rounds primitive with the feature and keep its `base` and its `budget` for step 12; a failed call leaves no base, and step 12 records any fix the run writes as one round not re-read. A malformed `[review] re-reads-off` fails it before anything is written: report the error and stop the run. Then apply the disposition rule to each observation no stored decision disposed of, asking nobody and marking each `by-rule`: a chore is fixed in the run, and anything else is waived with its reason, except as follows. A defect that makes this review's own result wrong is never waived: it is fixed in the run or deferred as a broken contract is. An observation showing the spec's own code breaks its contract is marked `contract-break`, and is fixed in the run or deferred to the spec's own task, which the append-task primitive appends: such a deferral is the only write that reaches the operator, and it is written only after the gate-confirm primitive returns a confirmed decision, with the operator free to name another home by the **§Groom decision tree** in `.ductus/reference/groom.md`, an external work-item ID beside it or in its place, or a waiver with their reason. A deferral to a `done` spec, this run's own spec included, names in its confirmation the `done → in-progress` reopen its home causes, and once the deferral is written, invokes the check-owed-work primitive on that spec and performs the reopen through the set-status primitive with `from: done` only when it reports owed work; a home that leaves none, such as a spec edit, reopens nothing, and the report says no gate reads it. When a chore fix wrote, re-run the affected passes before step 11, as `--fix` does, so the record describes the fixed tree. A fix that fails or proves not to be mechanical is reverted, then waived by the rule, or on a broken contract proposed as a deferral; a declined deferral leaves the observation waived with the operator's reason, or undispositioned; a confirmed deferral whose write fails is undispositioned, and the failure is reported beside the observation. **With no operator to confirm**, a host that cannot ask still applies the rule, leaving each broken contract undispositioned, which holds `done` until a run with an operator decides it, and `ductus exec`, whose walker no-ops this step by design, writes nothing: each unmatched observation is recorded undispositioned. MUST and SHOULD violations are not dispositioned here: each is fixed, waived with `--waive`, or deferred with `--defer` (**§Deferrals** in `.ductus/reference/review.md`). On a spec that was `done` when the run began, though, no gating finding is recorded without a disposition: each MUST or SHOULD violation no flag or stored decision disposes of is put to the operator through the gate-confirm primitive, one at a time, to be fixed in the run, waived with their reason, or deferred, to a task of the spec's own, which the append-task primitive appends, or to the home the **§Groom decision tree** in `.ductus/reference/groom.md` chooses, and the answer is recorded as that `--waive` or `--defer` would record it, the reopen of a deferral to the spec's own work included. With nobody to ask it is recorded undispositioned, and a `done` spec whose record then holds a MUST, an outstanding SHOULD or an open broken contract is the review-state drift `/{project}:analyze --fix` reverts. Nor is a criterion step 7.2 judged not met, which is no observation and is never waived or deferred: it is fixed in the run when the fix is mechanical, and judged again, and otherwise stays not met in the record, which blocks, until the code is fixed or the criterion corrected or moved to the spec that owns the work (**§Criteria step** in `.ductus/reference/review.md`).
    The detail is under **Observations** in **§Write `review.md`** in `.ductus/reference/review.md`.

11. Invoke `write-review`, passing `loop-open` so the record marks the fix-round loop open, with the accumulated pass findings, the accumulated pass **observations** — each with its `disposition` (`outcome`, plus a deferral's `target`, `task` and `work-item`, or a waiver's `reason`), its `path`, which a broken contract left open must name, and, when step 9 matched it, its `decision-key`; each finding `--defer` named, or step 9 matched to a stored deferral, carries its deferral the same way — the waiver results (`applied` / `expired`, read from `lists-file` when step 8 returned the file form, with the anchor of a stored waiver a `--defer` replaces moved from `applied` to `expired`), `expired-decisions` — step 9's expired and lapsed decisions, a rule's waiver of a broken contract, plus a stored deferral a `--waive` replaces — `new-waivers`, the rule and reason of each `--waive`, whose anchors the primitive derives from the findings' files and sites, refusing one whose rule fires at a finding naming no site, as it refuses such a finding deferred, the scope, and `criteria`, step 7.2's verdicts, each by `label` (by `index` for a criterion with none) with `met` and its evidence as `note`. A departure entry in the spec's `## Applicable Rules` needs no `--waive`: the primitive derives its waiver itself (**§Waivers** in `.ductus/reference/review.md`), and the result's `malformed-departures` is reported beside the record, one line each, since an entry listed there waived nothing; in the file form (`form` is `file`) the list is under that name in `lists-file`, and `malformed-departures-count` says how many. Its `departure-notices` are reported there too, one line each: each names a scoped entry's `spec.md` line and a covered site whose file is gone or leaves the project, or in whose file the rule fires at a site the entry does not cover or at none, so the entry does not waive the finding there; in the file form they are under that name, with `departure-notices-count`. Supply the required scalars the primitives don't produce — `reviewed-at` (the current UTC timestamp) and `reviewed-against` (step 1's `head`, the commit the passes' scope was resolved against); `diff-base` from step 1; **`examined`, how many of the in-scope files the passes above actually read**, a numerator against the `scope` the primitive resolves itself; **`unread`, the scope entries the passes did not read**, `[]` when they read every one, since another spec's window takes each entry it leaves out as read (**§Window and coverage** in `.ductus/reference/review.md`); and `decided-by` (`git config user.email`), which the primitive requires when any observation or violation is newly deferred or waived. With `--fix`, apply the auto-fixable findings (**§Apply `--fix` (optional)** in `.ductus/reference/review.md`, within **§Auto-fix scope** in `.ductus/reference/review.md`), re-run the affected passes, and invoke `write-review` a second time, `loop-open` included, for the post-fix counts. A write refused with the changed-since-read error wrote nothing: another writer changed `review.md` after the primitive read it, so report the conflict and run the write again from the same arguments, which reads the record as it now is. A write refused because a commit after `reviewed-against` changed a path the scope holds wrote nothing either: invoke the compute-review-scope primitive again, read each moved path (the refusal names up to three, and the `git log --relative --name-only` command it gives lists every one) and each path the new scope adds, or list it in `unread`, and write again with its `head`: a moved path the scope already held is not added by the re-run. Render the result's `dispositions` as the `observations` row and its `analyze-freshness` as the `analyze` row (**§Output** in `.ductus/reference/review.md` lays out the summary; **§The `observations` row** in `.ductus/reference/review.md` and **§The `analyze` row** in `.ductus/reference/review.md` are its rows). Neither affects the exit code.
