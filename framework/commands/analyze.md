# Analyze

Audit a feature's artifacts against each other and against the framework's rule set.

## Purpose

Audit a feature's spec, plan, tasks, and data model for consistency, then give every live finding a disposition before recording the run. Use this to catch problems before the next pipeline gate fires. **Detection (steps 1–17) writes nothing.** Step 19 then gives each live finding one disposition by the rule — fixed, deferred, or waived with its reason (§brownfield-inbox, Finding dispositions) — and writes a gating finding's deferral only after the operator confirms it; when anything was written, detection runs again (step 20). `analysis.md` records the run in that file's own frontmatter (step 21). No finding is written to the inbox. The `--fix` flag reverts a status-`done` spec back to `in-progress` on either of two triggers: review state drift in any of its forms (see **§Review state drift (blocking)** in `.ductus/reference/analyze.md`), or unresolved open questions carried by the spec's scenarios (see **§Scenario open questions (blocking at `done`, advisory otherwise)** in `.ductus/reference/analyze.md`). A record carrying undispositioned findings is reported, never reverted (see **§Disposition drift (advisory)** in `.ductus/reference/analyze.md`). `--fix` never edits content, and each revert emits a notice naming the spec and what drifted.

Complementary to `/{project}:review`, which audits **code** against rules.

## Context

Parse `$ARGUMENTS` for flags and an optional feature identifier:

- **Feature identifier** — a feature number, partial name, or full directory name. Overrides the session target.
- **`--all`** — scan all feature directories under `specs/` instead of a single target. Report results grouped by feature.

If `--all` is not present, use the feature identifier if provided, otherwise fall back to the session target — invoke `resolve-session` and display any notices and unreadable session files it returns. If no target can be resolved, stop and tell the user to run `/{project}:target` first or use `--all`.

## Scope Boundaries

- Detection (steps 1–17) never modifies an artifact under audit. Besides the session state `resolve-session` keeps for this process, three kinds of write are in scope and no others: step 19's, a mechanical fix to an artifact the run audited, or a gating finding's deferral to the home **§Groom decision tree** in `.ductus/reference/groom.md` chooses, including a `done → in-progress` reopen of the spec deferred to, only after `gate-confirm` returns a confirmed decision; the feature's `analysis.md` (step 21); and, only with `--fix`, step 22's revert of a drifted `done` spec via `set-status`. Under `ductus exec` step 19 writes nothing, and `analysis.md` is the only write; a host that cannot ask applies the rule and writes no deferral. No finding is written to `{specs-root}/inbox.md`.
- Read only files within the target feature's directory, the cross-spec files needed for reference checks (`specs/system.md`, `specs/events.md`, `specs/errors.md`, dependency spec files), and the project's installed command-source frontmatter for **§Project-level consistency (advisory)** in `.ductus/reference/analyze.md` (frontmatter only, located as that section describes). May invoke `scripts/gen-help-tables.sh --dry-run` to surface generator drift, only when that script exists in the project. Step 19 additionally reads what a disposition needs: a candidate covering spec's `spec.md` and `tasks.md` for the **§Groom decision tree** in `.ductus/reference/groom.md`, and the artifact a chore fix edits. Do NOT read source code or test files.
- Resolving the target spec's cross-service `references:` index (step 13) additionally reads `.ductus/config.toml` (the `[services]` registry) and the registered local checkouts' linked `spec.md` files, and nothing else; the canonical repo URL is **never fetched**.
- Reference: §spec-requirements, §grounding, §plan-phase, §tasks-phase, §readiness-check, §scenarios, §cross-spec-impact, §bug-handling, §brownfield-inbox (Finding dispositions), §text-first-artifacts, §markdown-standards, §drift-prevention (constitution loaded by `/{project}:target` — do not re-read). See [030 — Cross-Service References](https://github.com/stonean/ductus/blob/main/specs/030-cross-service-references/spec.md) for the reference semantics surfaced here.

## Instructions

> **For agent runtimes**: the Invoke steps below call the ductus runtime's MCP tools; without the server, stop and say to restart or re-run `/ductus` (§runtime-host-integration).

**Where a named section lives.** This command's reference is `.ductus/reference/analyze.md`. A section named here, or cited elsewhere as part of this command, that has no heading in this file is there; read it when a step points at it.

1. Invoke `read-spec` (with `include-body`) against the targeted feature. When the spec's `tasks.md` holds an unchecked box under any heading, stop naming the boxes: an analysis runs once implementation is complete, since nothing can say whether a task still open would change what it reads, and the write-analysis primitive refuses before then, but for a box under a task this run's own deferral names. Its status governs which artifact-completeness checks apply, and its parsed `sections` feed step 14's `## Applicable Rules` scan, so the body needs no re-read.

2. Invoke `validate-frontmatter` against the spec path. Each finding carries the severity §text-first-artifacts (Validation Severity) assigns to **that** condition, so render each finding in the tier it names — never map the family to one fixed tier. The rest of the procedure still runs to surface every issue in a single pass. The host judges each scenario's frontmatter (**§Frontmatter schema (hard fail)** in `.ductus/reference/analyze.md`).

3. Invoke `traverse-deps` against the feature. A missing dependency is blocking. An incompatible status (the edge's `compatible: false` — the dependency is below `planned`) is blocking when this spec is at `clarified` or later: the primitive reports each edge without reading the consumer's status, so apply that condition host-side from the returned data rather than mapping the top-level `compatible` flag straight to a blocking finding. Any non-empty `cycles` entry — multi-node SCC or self-loop — is blocking.

4. Invoke `resolve-anchor` against the spec path **with `markers-path` set to the constitution file** (`framework/constitution.md` in ductus's own repo; `.ductus/constitution.md` at the adopter repo root), since a spec carries no markers of its own. Unresolved anchors are advisory.

5. Invoke `check-rule-ids` against the spec path with the files **§Rules (blocking and advisory)** in `.ductus/reference/analyze.md` discovers. Cited rule IDs that are missing are blocking; cited rule IDs marked deprecated are advisory. **Read `examined` before acting on `missing`**: the known-ID set is built from the `rule-files` argument, so an `examined` of **0** makes every citation `missing` and means *nothing was checked against*. Raise no finding from that state, since "fixing" it deletes a valid citation: the spec's citations are unexamined, never missing (`rule-citations-not-checked`, under **§Unexamined targets (informational)** in `.ductus/reference/analyze.md`), and on a project that has rule files it is a caller defect.

6. Invoke `derive-dependencies`, whose default reports without writing, so this step is read-only. A non-empty `updated` is an advisory drift finding between the body's inline links and the frontmatter `dependencies:`, which the pre-commit hook resolves on the next commit.

7. Invoke `lint-markdown` against the markdown files in the feature directory. Each returned violation is surfaced as an advisory finding.

8. Invoke `check-artifacts` against the feature to run the residual deterministic check families its description lists. Render each finding in the tier it carries and each target in its `skipped` list in the Informational tier, never as a finding. `analysis.md`, its dispositions and its own state alike, is judged after step 21 from the record this run writes, never here (**§Analyze state drift (blocking)** in `.ductus/reference/analyze.md`). The semantic items stay with the host: data-model necessity, whether tasks reference the plan, a scenario's own Context/Behavior sections, and Command-frontmatter completeness, which reads the host's command directory the runtime does not own. What each family asks of the host is in `.ductus/reference/analyze.md`: **§Artifact completeness (blocking)**, **§Task consistency (blocking if tasks exist)**, **§Scenario consistency (advisory)**, **§Scenario open questions (blocking at `done`, advisory otherwise)**, **§Review state drift (blocking)**, **§Disposition drift (advisory)**, **§Link-adjacent decision drift (advisory)**, **§Acceptance-criterion path existence (advisory)**, **§Body path existence (advisory)**, **§Acceptance-criterion labels (advisory)**, **§Cross-spec references (advisory)** and **§Project-level consistency (advisory)**.

9. Invoke `check-orphaned-references` (advisory; see **§Project-level consistency (advisory)** in `.ductus/reference/analyze.md`). Its subject is the project, not the spec, so with `--all` run it once, not per feature. The result's `attribution` governs the render and must not be flattened: under `registry` an empty `migration` means the registry *was* read and no entry claims that path; under `watermark` no registry was available to ask, and `last-applied` is the only migration context there is. Referrers in `skipped` belong in the Informational tier (`referrer-unreadable`). Report, never repair.

10. Invoke `check-unfolded-specs` (advisory; see **§Project-level consistency (advisory)** in `.ductus/reference/analyze.md`). Its subject is the corpus, not the spec, so with `--all` run it once, not per feature. The finding **stays** advisory: the check cannot tell a spec whose branch is still open from one whose branch merged weeks ago, so it reports the set and leaves that judgement to the operator. Report a `folds-into` naming a spec absent from this tree as *unresolved here*, never as broken. Report, never repair: which upstream section a spec's content belongs in is the routing decision `/{project}:fold` puts to the operator.

11. <!-- llm:assessSpecQuality --> For every loaded MUST-tier rule whose Verification trigger fires against the spec, request a semantic assessment via the extension point. The host responds with a structured finding carrying severity, rule-id, location, and message. MUST-tier findings join the Blocking tier in the rendered report. A rule's tier is the RFC 2119 keyword in its Statement, never the step's: MUST or MUST NOT makes it MUST-tier, including a Statement that also carries SHOULD, so no rule is assessed at both this step and the next. Under `ductus exec` the walker sends one request per loaded MUST-tier rule, each carrying that one rule, and evaluates no trigger itself: the host judges whether the rule's trigger fires against the spec and answers `passed: true` when it does not. A rule whose Statement carries no MUST or SHOULD keyword (MAY alone sets no tier), or that has no Verification, is recorded unexamined rather than assessed, as is a rule file that could not be read (see **§Unexamined targets (informational)** in `.ductus/reference/analyze.md`). A Verification that yields a case to another rule "where `{file}` is also loaded" yields it only when `{file}` is among the rule files this run loaded, so the yielding rule keeps the case in a project without that file: under `ductus exec` each request lists the loaded files' basenames under `loaded-rule-files`, and a file the list lacks, or a request carrying no list, makes the condition false; a host walking the steps applies it from the rule files it loaded, a file it could not read or treated as unloadable excluded.

12. <!-- llm:assessSpecQuality --> For every loaded SHOULD-tier rule whose Verification trigger fires against the spec, request a semantic assessment via the extension point. SHOULD-tier findings join the Advisory tier in the rendered report. A rule is SHOULD-tier when its Statement carries SHOULD or SHOULD NOT and no MUST. Under `ductus exec` the walker sends one request per loaded SHOULD-tier rule, as at step 11, and the host judges the trigger, answering `passed: true` when it does not fire. A load-conditioned yield is applied as at step 11, on either path.

<!-- audit:ignore-promotion -->
13. Resolve the target spec's cross-service **references** (deterministic; advisory). When the spec's derived `references:` index is non-empty, resolve each entry with the resolve-references primitive (**§Cross-service references (advisory)** in `.ductus/reference/analyze.md`). A **broken** outcome is an **Advisory** finding, as is each repo in the result's `duplicate-repos`; a result whose `form` is `file` carries each list's count and no list, so read both from the file `lists-file` names. The informational unknowns are **not** findings: **unregistered** (surface a pointer to `/{project}:link` to register the service), **not checked out**, and **status unreadable** each record what could not be proven. Skip this step when the target spec declares no references.

<!-- audit:ignore-promotion -->
14. Parse the spec body for a `## Applicable Rules` section and collect every rule ID cited there. For each cited ID that did **not** appear in the set of rules whose Verification triggers fired in steps 11 or 12, emit an advisory finding: `Applicable Rules citation does not fire: {rule-id} is listed under ## Applicable Rules, but the rule's Verification trigger did not fire against any spec artifact. Either remove the citation, or extend the spec to bring the cited surface into scope.` Skip this step when the spec has no `## Applicable Rules` section. A citation whose ID resolves to no loaded rule is step 5's, not reprocessed here. A cited rule whose rule file declares that it verifies code patterns rather than design-time commitments, as `quality-cross.md` does, is not flagged, since `/{project}:review` enforces it against the code whatever the spec cites. See **§Applicable Rules citation consistency (advisory)** in `.ductus/reference/analyze.md`.

<!-- audit:ignore-promotion -->
15. Scan the spec body (loaded in step 1) and `plan.md` (read it if present) for **ungrounded factual claims about the existing system** — assertions about how current code behaves, what a schema or interface contains, or what an external system returns, stated as fact but carrying neither a citation to a primary source (a `path:line` reference, a named query, a command, or a link to a substantiating artifact) nor an explicit assumption / Open Question marker. Descriptive claims about existing reality need grounding; **prescriptive requirements** about the feature under design (what it MUST do) are contracts, not claims, and are never flagged — the descriptive-vs-prescriptive call is the semantic judgment this step turns on. This is a *form* check: do NOT read source code to confirm a claim (out of scope; see Scope Boundaries), only verify the artifact sources or hedges it. Apply to the spec body at status `clarified` or later and to `plan.md` at `planned` or later; skip on a `draft` spec. Emit each as an **Advisory** finding per **§Grounding (advisory)** in `.ductus/reference/analyze.md`.

16. Invoke `prune-plan` against the feature, as a preview — it passes no `apply` — to find the `plan.md` sections outside the design record (§plan-phase; **§Plan record (advisory)** in `.ductus/reference/analyze.md`). On a spec at `planned` or later, record **every** section the result lists as an **Advisory** finding under the result's own `finding`, whether or not the section is `decided`: firing a decided one lets step 18 match it to its stored waiver, so nothing is asked, where leaving it out would expire the waiver and have `/{project}:prune` propose the section again. Below `planned` nothing is recorded. A result with `missing` set names a feature with no `plan.md`, which step 8 judges. The primitive errors on an `analysis.md` whose `decisions:` list does not parse and, on a `done` spec, a HEAD it cannot read: under `ductus exec` the walk halts here on either, and an interactive host reports the error and stops the run too. This step ignores `reopen-required`.

17. Invoke `check-artifact-size` against the feature (**§Artifact size (advisory)** in `.ductus/reference/analyze.md`). At every status, record each entry in `oversized` as an **Advisory** finding — family `artifact-size`, its `message`, its `path` — and render its `warning`. In this command a waiver with its reason is the further fix, which step 19's rule applies like any other advisory waiver. Record an entry the result marks `decided` too, firing its `decision-key` at step 18: a stored waiver covers it, so nothing is asked, where leaving it out would expire the waiver. Render each `skipped` subject in the Informational tier as unexamined under `artifact-unreadable`, and each of the result's `notices` in the Informational tier too. A malformed read size is a configuration error the primitive fails on, not a finding, and the command halts there rather than measuring at the default.

<!-- audit:ignore-promotion -->
18. Process stored decisions (host responsibility): read the `decisions:` list in `analysis.md` and match each finding still live after detection to the stored decision describing the same issue — many messages are worded by the host and do not reproduce byte for byte, so the match is the host's judgment, as `/{project}:review`'s is for observations. An `artifact-size` finding is the exception: a decided one fires the `decision-key` step 17's result returned and an undecided one fires its own key, never matched by judgment to a stored waiver that covers fewer read pages. Then call the process-decisions primitive with the feature, `record: analysis`, `fired` — for each live finding, in every tier, the stored key it matched, or else its own `{family} — {message}` — and `restricted` set only when the run could not read something it meant to examine — a skipped target whose reason is in the **could not be read** class (see **§Unexamined targets (informational)** in `.ductus/reference/analyze.md`), or a registered shared constitution it could not resolve. A target **excluded by construction** never restricts: it recurs on every run, so restricting would retain a stored decision forever. The Informational tier is not findings and carries no key. When the result's `form` is `file`, read its lists from the file `lists-file` names. Each `matched` decision disposes of its finding under the stored outcome, and nothing is asked about it — the finding carries that key to step 21 as its `decision-key`; each `expired` decision goes to step 21 to be dropped; each `lapsed` decision (spec 076) goes to step 21 to be dropped with them, and its finding takes a new disposition at step 19, or is recorded undispositioned; `retained` decisions stay in the record untouched. Render the result's `notices` in the Informational tier. When the primitive refuses because the list does not parse, report that, disposition each finding as though nothing were stored, and tell the operator the record cannot be written until the list is repaired. Two findings with the same key are one finding and get one disposition.

<!-- audit:ignore-promotion -->
19. Fix and route (host responsibility): apply the disposition rule to each live finding no stored decision matched, marking what it decides `by-rule`. **Fixed**, asking nobody: a chore — a mechanical edit to an artifact this run audited, adding no durable requirement (§bug-handling's durability test). **Waived**, asking nobody: an advisory finding that is no chore, with its reason, which step 21 records. **Deferred**: the only write that reaches the operator, for a `hard-fail` or `blocking` finding that is no chore, written only after the gate-confirm primitive returns a confirmed decision: to the home **§Groom decision tree** in `.ductus/reference/groom.md` chooses, with an external work-item ID beside it or in its place when the operator gives one; a deferral to a spec that is `done` — the spec in hand included — names the `done → in-progress` reopen in its confirmation and performs it through the set-status primitive with `from: done`. A `hard-fail` or `blocking` finding its deferral releases (**§Deferrals** in `.ductus/reference/review.md`) leaves the record's gating counts; any other deferred one keeps blocking until the re-check no longer produces it (spec 076). A `hard-fail` or `blocking` finding is **never waived**. A declined deferral leaves the finding undispositioned. A fix that fails or proves not to be mechanical is reverted, then waived by the rule when advisory, and otherwise proposed as a deferral; a confirmed deferral whose write fails is undispositioned, and the failure is reported beside the finding. With `--all`, group the proposals by spec, and let each prompt leave the rest of that spec's findings undispositioned. **With no operator to confirm**, a host that cannot ask still applies the rule, leaving each hard-fail or blocking finding undispositioned, which holds `done` through the record's `blocking`, and `ductus exec`, whose walker no-ops this step by design, writes nothing: every live finding is recorded as undispositioned, since the walker no-ops step 18 too and matches nothing against the stored decisions, which it leaves in place. The detail is in **§Finding dispositions** in `.ductus/reference/analyze.md`.

<!-- audit:ignore-promotion -->
20. Re-check (host responsibility): when step 19 wrote anything, run the detection steps (1–17) again, and take the tier counts and the live findings from the re-check. A finding the re-check no longer produces is carried to step 21 with `live: false` and recorded `fixed`, whether a chore or a confirmed deferral removed it; a finding that first appears in the re-check is recorded undispositioned, for the next run to decide. When nothing was written, the first pass is the re-check.

<!-- audit:ignore-promotion -->
21. Record the run (host responsibility): invoke `write-analysis` with the feature, the current UTC timestamp, the HEAD sha, and the re-check's tier counts — `hard-fail`, `blocking-findings`, `advisory`, and `unexamined` (the size of the Informational tier's unexamined-target set, written even when it is zero, since a zero that was computed and a field never written are not the same claim) — plus `findings`: every finding the run dispositioned or left owed, each with its `tier`, `family`, `message`, `path`, `live`, and `disposition` (`outcome`, plus a deferral's `target`, `task` and `work-item`, or a waiver's `reason`; a finding a stored decision matched carries that decision's outcome, and its key as `decision-key`). Pass `expired-decisions` — step 18's expired and lapsed decisions — and `decided-by` (`git config user.email`), which the writer requires when any live finding is newly deferred or waived. The writer derives the rest. **Always**, including on a clean run and on a run whose scope was empty: the record's *absence* means the run never happened, and `/{project}:implement`'s pre-done gate reads it.

<!-- audit:ignore-promotion -->
22. Render the report (host responsibility): list hard-fail and blocking findings first, advisory findings next, then informational. For each finding, include what failed, what was expected, what was found, a suggested fix, and its disposition — the fixed file, the work it was deferred to, or the waiver's reason — or that it is undispositioned. When the spec is `done`, judge the record step 21 wrote: when the write-analysis primitive returns `blocking`, report analyze-state drift (**§Analyze state drift (blocking)** in `.ductus/reference/analyze.md`); when its `dispositions` map counts undispositioned findings, report disposition drift for `analysis.md` (**§Disposition drift (advisory)** in `.ductus/reference/analyze.md`). With `--fix` set, additionally revert any status-done spec a check found drifted — review state drift in any of its forms, or unresolved open questions in the spec's scenarios — through the guarded set-status revert (`from: done`, `to: in-progress`), detailed in **§Review state drift (blocking)** in `.ductus/reference/analyze.md` and **§Scenario open questions (blocking at `done`, advisory otherwise)** in `.ductus/reference/analyze.md`; disposition drift is reported and never reverted. Each revert emits its own non-silent notice.
