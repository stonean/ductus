# implement — markdown-only reference

The full setup, walk-through, completion gate, and stuck-detection details are documented below for the markdown-only path. The numbered steps in `implement.md`'s Instructions invoke the mechanical primitives that automate each phase; the host applies the same procedure against the markdown-only path when the runtime is unavailable.

**Where a named section lives.** This file is read alongside its command, `implement.md`, which is already loaded whenever this one is. A section named below that has no heading in this file is in the command file, along with the numbered Instructions steps this file cites. A bare `§name` is a heading in this file or a constitution marker; a `§name` with another file's path on the same line is a heading in that file.

## Setup details

- Read the shared default `.ductus/session.toml` for the session target, including optional `scenario` and `scenario-path` fields. Without the runtime the host cannot read its session identity, so this path always uses the shared default (§concurrent-features).
- Read `specs/{feature}/tasks.md` for the ordered task list (primitive: `read-tasks`).
- Read `specs/{feature}/plan.md` for technical decisions and affected files.
- Read the spec file for acceptance criteria and contracts.
- If a scenario is targeted, read the scenario file for scenario-specific context, behavior, and edge cases. The scenario scopes which part of the feature is the primary focus for this implementation session.
- **Recompute dependencies (safety net).** Invoke `derive-dependencies` (report-only by default; it walks every spec — there is no per-spec mode). If it reports drift, the `dependencies:` frontmatter is stale from uncommitted body edits; surface that and recommend committing (the pre-commit hook syncs it) or running `ductus derive-dependencies --write` manually. Do not pass `--write` from this command.

## Stuck-detection details

If the spec's status is already in-progress, run `git log --oneline -- specs/{feature}/tasks.md` and count commits since the spec entered in-progress. Identify the first incomplete task (first `- [ ]` checkbox group) in `tasks.md`. If `git log` shows ≥ 3 commits on `tasks.md` AND the same task is still the first incomplete one (no checkbox flipped to `- [x]` between those commits for that task), surface the cycle to the user with this message: `Task {N} ({title}) has been touched in {count} prior implement runs without completing. Consider decomposing it into smaller subtasks before continuing.` Pause and wait for user direction; do not auto-decompose. The threshold of 3 is fixed (not configurable in v1) — smallest count that distinguishes routine multi-session work from a cycle.

## Progressive context loading

- **At setup:** read only the spec, plan, tasks, and scenario file (if targeted). Do NOT read `system.md`, `events.md`, `errors.md`, or source code yet.
- **Per task:** read only the source files relevant to that task from the plan's affected files list.
- **At completion:** tally the `tasks.md` checkboxes (primitive: `read-tasks`) and re-read the acceptance criteria from the spec (primitive: `read-spec`) to verify. Do NOT re-read the full plan.

## Walk through tasks (per task, in order)

1. Display the task number, description, and "done when" condition.
2. Read the relevant technical decisions from the plan.
3. Read only the existing code files relevant to this task from the plan's affected files.
4. Implement the task: write code, tests, and migrations as needed. Follow conventions in `AGENTS.md` and `specs/system.md`; respect the contracts defined in the spec. If a write would land outside the runtime boundary, notify the user, explain why, and wait for confirmation before proceeding. Once accepted, the file is part of the boundary for the rest of the session.
5. **Route an incidental issue by scope.** When implementing this task surfaces an issue — a security weakness, a memory or resource leak, a violated convention, a latent bug in adjacent code — the scope it falls in decides where it goes (§brownfield-inbox, Finding dispositions). An issue *inside this task's* scope is fixed as part of the task, not logged. Anything else becomes an unchecked task on the targeted spec's `tasks.md` the moment it surfaces (deterministic path: the `append-task` primitive; without the runtime, append the task block with the host's file tools):

   - **Inside the targeted spec**, outside this task — a task that implements the fix. A finding that is a requirement gap rather than a defect routes through `/ductus:amend` per §bug-handling, with the task as the work item that implements it.
   - **Outside the spec** — a **disposition task**, titled `Disposition out-of-spec finding: {summary}`, with the body item `{path} — {detail}` and the done-when *the finding is fixed, routed, or discarded, with a discard's reason written on the task*. Append it with `dedup-title` set, so a re-run of an interrupted walk returns the pending task rather than recording the same finding twice. It is never written to `specs/inbox.md`.

   In every case, record and keep working — do not derail to fix a finding outside this task. The task is on disk as soon as the finding surfaces, so an interrupted run loses nothing, and as an unchecked task it already holds the spec out of `done`. The cost is deliberate: a finding unrelated to the spec holds it until the finding is decided, because this spec's work surfaced it.

   **Working a disposition task.** When the walk reaches one, the finding takes exactly one of three dispositions, and the task is checked only once one of them has happened. **Fix** it when it is a chore — mechanical, adding no durable requirement (§bug-handling's durability test); a fix that fails or proves not to be mechanical is reverted and is not a chore. **Route** it, with confirmation, to the home the **§Groom decision tree** in `.ductus/reference/groom.md` chooses — its single canonical statement; do not restate it here — naming a `done → in-progress` reopen in the confirmation when the spec routed to is `done`, and performing it with `set-status` (`from: done`); a route to a spec that is not `done` follows `/ductus:amend`'s rules for its status and reopens nothing. Or **discard** it with its reason. Record the outcome on the task's body item — `— fixed`, `— routed to {target}`, or `— discarded: {reason}` — then check it; the discard's reason written there is the finding's record. A confirmed route whose write fails leaves the task unchecked, with the failure reported.
6. Verify the "done when" condition is met.
7. Mark the task as complete in `tasks.md` — update each checkbox to `- [x]`, including nested sub-item checkboxes and a checkbox-form "Done when" clause (`- [ ] Done when: …`), before proceeding. The clause is not an addressable subtask, but leaving it unticked shows an unchecked box under a task the tally calls complete.
8. Prompt the user to commit and push changes. With `--auto` set, skip the prompt: commit on your own, do not push.
9. **Offer the next step.** When at least one task is still unchecked, name the next one and how many remain after it, then ask whether to continue: `Next: task {N} — {heading} ({M} remaining). Continue? (Y/n)`. Yes continues the walk onto that task in the same run; no exits cleanly; free-text instructions redirect ("do task 12 first"), which is a reply rather than a rejection. Name **one** task, not a menu — the count is what lets the operator judge the queue without re-reading `tasks.md`, and looking further ahead is itself a redirect. Suppress the offer when nothing is unchecked, so it never renders as "no next step"; the run continues into the completion gate as it does today. With `--auto` the walk already continues without asking. Nothing here writes, and the offer never advances spec status — the `in-progress → done` transition keeps its own confirmation.

   Edge cases: a task whose "done when" failed halts the run as today (the offer is for a *completed* task, not a way past a failure); every subtask checked with an unticked checkbox-form "Done when" clause is the completion gate's state to surface, not a next-step offer; and a reply targeting a different spec exits cleanly rather than retargeting mid-walk — retargeting is `/ductus:target`'s job, and a walk that silently changed feature would be worse than one that stopped.

10. Before starting the next task, assess whether sufficient context remains to complete it. If context is low, suggest starting a new session.

## Completion gate (after all tasks)

Same order as Instructions steps 9–16, with the same primitives named as fallbacks.

1. **Task tally.** Re-read `specs/{feature}/tasks.md` and tally every checkbox (primitive: `read-tasks`) — top-level tasks, nested sub-items, and scenario-linked tasks. Distinguish "all subtasks checked" from "task block fully checked": a checkbox-form "Done when" clause (`- [ ] Done when: …`) is not an addressable subtask, so a task can have every subtask checked while an unchecked box is still visible in its block (`done-when-checked` is `false`). Surface that rather than rounding it up. If any remains unchecked, report the specific incomplete tasks and stop — the gate ends here, before criteria verification. The user finishes them and re-runs the command.
2. **Load acceptance criteria.** Re-read the spec's Acceptance Criteria checkboxes (primitive: `read-spec`); the review record is read from `review.md` by the gate below.
3. **Verify each criterion.** Walk through each acceptance criterion from the spec and verify it is met against the implementation — semantic judgment, one criterion at a time (the verifyCriteria extension seam on the runtime path). Mark each passing criterion `- [x]` in the spec file at the time of verification (primitive: `mark-criterion`, one call per passing criterion, addressed by 0-based body-order index). If a criterion fails, leave it unchecked and report the failure. Do not batch-mark — verify each individually. If any criterion remains unchecked, report the specific failures and do not propose the transition; the user fixes the issues and re-runs the command.
4. **Cross-spec impact check.** Run `git diff --name-only --relative <first-commit>..HEAD -- specs/` from the project root, filtered to paths outside `specs/{feature}/`. If any sibling spec dir shows changes, surface the list to the user and ask whether the changes were intentional cross-spec updates per §cross-spec-impact. Informational; does not block. (Primitive: `diff-cross-spec`, which diffs against the working tree so uncommitted edits surface too; the git command above is the markdown-only path.) This detects the cross-spec update you **made**; the one you **owe** is the `cross-spec-impact:` declaration the pre-done gate checks in step 5. An empty result here says nothing about that — the two answer opposite questions, and reading a clean diff as a clear obligation is how a release has shipped with an obligation outstanding.
5. **Pre-done gate** (primitive: `check-review-gate`, which evaluates every check below in this order and returns the verdict with the canonical blocked message — the name is historical; it gates both `/ductus:review` and `/ductus:analyze`).

   **First, whether there is a transition to gate at all.** A spec already at `status: done` has made the `in-progress → done` transition this gate authorizes, so no check below it can matter and none runs. Halt with `not gated: spec is already at status done — the in-progress → done transition this gate authorizes has already happened`, plus guidance that nothing is owed and that changing the spec means reopening it first through `/ductus:amend`. The result is deliberately **not** `passed: true`: a gate reporting a pass for a spec it did not examine is `QUAL-CLAIM-001` applied to itself, and a caller could read it as authorization to transition a spec that is already transitioned.

   It is ordered ahead of the lint for two reasons. A completed spec should not be held against a markdown violation introduced long after it closed. And the analyze-freshness check below would answer *wrongly* here rather than pointlessly: the completing `set-status` rewrites `spec.md`, which is one of the analysis's own subjects, so a spec's record is stale the instant it reaches `done`. Re-running this gate on finished work therefore reported a stale analysis and sent the operator to re-run it — advice that then appeared to work, which is worse than advice that plainly fails. Only the exact value `done` short-circuits; an unrecognized status falls through and the checks run, since `validate-frontmatter` owns reporting a bad value.

   Then confirm all `.md` files in the feature directory pass `npx markdownlint-cli2`; on failure, report the specific violations and do not propose the transition. Then confirm no scenario under the feature carries unresolved open questions: a scenario is an organizational split of the spec, so its questions are the spec's questions for completeness and the spec is not `done` while any remain (§spec-lifecycle; spec 046). On failure, halt with `blocked: {N} unresolved open question(s) in scenario(s) {names} — resolve them before completing`, followed by guidance to run `/ductus:target {feature}/<scenario>` then `/ductus:clarify` on each — or, when a question is deferred rather than undecided ("not now; revisit when X lands"), to record it in that scenario's `## Resolved Questions` with its trigger, since a deferral is a resolution with a condition and only `## Open Questions` entries count. This check is ordered ahead of the review record because an unresolved design question is the more upstream defect: reviewing a design that is about to change wastes the review.

   No check reads `folds-into:`. **A pending fold never holds `done`** — the order is done first, then fold. A branch-scoped spec completes its own pipeline like any other, and fold-back then consolidates its durable content into the upstream spec it names; the work is complete once that has run. The owed fold is carried past `done` by the surfaces built for it — `check-unfolded-specs`, and `/ductus:status`, which qualifies the row `(fold pending)` and offers `/ductus:fold` as the next action once the spec is `done` — so the gate has nothing to add ([051](https://github.com/stonean/ductus/blob/main/specs/051-branch-scoped-spec-numbering/spec.md), scenario `a-pending-fold-never-holds-done`).

   Then confirm every `cross-spec-impact:` entry is discharged. The key is a hand-authored list of the specs this one owes a change to under §cross-spec-impact, and each entry is outstanding work until the named spec carries the change — the same category as the unresolved scenario questions above, which is why it sits beside them rather than with the review checks. Unlike a pending fold it blocks, because nothing but this gate carries an undischarged impact past `done`. **Discharge is the reciprocal link, not the key's removal:** an entry is discharged when the named spec's body, or a scenario under it, links back to this spec — the signpost §cross-spec-impact already requires — because a key an author deletes to unblock themselves enforces nothing. On failure, halt with `blocked: undischarged cross-spec impact — {details}`, followed by guidance to record the change in each affected spec with a back-link and re-run, using `/ductus:amend` against a spec that is already `done` so the back-edge is taken. An entry naming no spec directory is reported as a typo rather than treated as discharged, and an entry naming this spec itself is reported too — a spec cannot owe itself a change. Absent and empty are the same state and report nothing; most specs affect no other spec. The check reports per entry, because partially discharged is the normal state of a multi-entry declaration, and it never writes: which section of the affected spec should carry the signpost is a routing judgment, and a wrong auto-write into another spec is worse than a precise refusal. Nothing detects an impact that was never *declared* — that is semantic judgment the author and reviewer own, and §cross-spec-impact says so rather than implying a mechanism that does not exist.

   Then read the review record from `review.md` before asking for the done transition. **The absent file is the never-run state**: if there is no `review.md`, or its `last-run` is missing or null, halt with `blocked: spec has not been reviewed — run /ductus:review before completing`. A `review.md` that exists but carries no parseable record is a third state — **undeterminable** — and is reported as such rather than as never-reviewed. If the record carries `blocking: true`, halt with: `blocked: spec has {must-violations} MUST violation(s) — see specs/NNN-feature/review.md` followed by guidance to either resolve the violations and re-run `/ductus:review`, or run `/ductus:review --waive <rule-id> --reason "..."` for each waivable finding.

   Finally, confirm the recorded review still describes the current code — and, as with the analysis, by comparing **content rather than commits**. The record carries `reviewed-digest`, a per-path digest of the spec's **durable contracts** — `scenarios/*.md` and `data-model.md`, the artifacts a review actually reads — as the review read them from disk. When any differ now, halt with `blocked: review is stale — {N} durable contract(s) changed since it ran: {paths}` followed by guidance to re-run `/ductus:review`. `reviewed-against` is provenance and is read for one thing: the mechanical-sweep rename exemption, so a contract that changed only by a repo-wide rename says what it said before and is not stale. This check is ordered last among the `review:` checks because it is the weakest claim — the others say a review is missing or failing, this one says a passing review is out of date.

   `tasks.md` and `plan.md` are outside the contract set — the first is ephemeral by construction (§tasks-phase), the second churns as Affected Files are revised — and so are `review.md` and `spec.md`. `review.md` is this command's own output, so counting it would stale every review the instant it was recorded; `spec.md` was excluded for the same reason until spec 057 stopped `write-review` touching it, and the set is deliberately left unchanged rather than widened, since adding it would stale every review on any spec-body edit. That is the exact opposite of the analyze subject set below, and correctly so: those two files are this command's *outputs*, and the analysis's *inputs*.

   **Why content and not the recorded sha, here too.** `/ductus:review`'s scope is the working tree — the union of the plan's Affected Files and the files modified since the diff base — while `reviewed-against` records a *commit*. So a scenario written during the session was reviewed, then committed, and came back as a durable contract that had changed since the review; it had changed only since the commit the review was labelled with. This gate previously carried a notice for the other half of that gap, naming durable contracts it could not examine because they were uncommitted. **That notice is gone**: the digest reads the working tree directly, so the state it described is now answered rather than reported, and a check that can no longer fire is indistinguishable from one that passed.

   A record carrying no `reviewed-digest` — every review recorded before this — is **undeterminable**, not stale and not current, and does not block. It clears on the next review. A spec with no scenarios and no data model records an *empty* digest, which is distinct from an absent one and reads as current.

   **Then the analyze record in `analysis.md`, and this is the gate's other half.** The pipeline is `/ductus:review → /ductus:analyze → done`, and until spec 047 recorded it, only the first half left a trace: a spec that had passed both gates and one that had passed only the review were byte-identical on disk, so nothing could enforce the second. If `analysis.md` is absent, or its `last-run` is missing or null, halt with `blocked: spec has not been analyzed — run /ductus:analyze before completing`; a present-but-unparseable `analysis.md` is undeterminable and reported as such. If the record carries `blocking: true`, halt with `blocked: spec has {hard-fail} hard-fail and {blocking-findings} blocking analyze finding(s) — run /ductus:analyze to see them`, followed by guidance naming the run's advisory and unexamined counts, so a blocked gate still says what the analysis did not look at.

   **Finally, whether that analysis still describes the current artifacts.** The presence check above asks only whether `analyze.last-run` is *set*, so `review → fix → done` passed the gate on an analysis recorded before the fixes — the identical shape to the stale-review hole the previous check exists to close, stated in its own words: a passing analysis that predates the artifacts it nominally covers satisfies every other check.

   The comparison is of **content, not commits**. The record carries `analyzed-digest`, a per-path digest of the spec's **analyze subjects** — every `.md` under `specs/{feature}/` except `analysis.md` itself, `review.md` included — as the analysis actually read them from disk. `analysis.md` is excluded whole, not merely its frontmatter: `write-analysis` rewrites the record and the report body in the same call, after the subjects are read, so a digest covering either half could never match. `spec.md` is digested whole. Staleness is a digest mismatch, and it names the mismatching paths: halt with `blocked: analysis is stale — {N} artifact(s) changed since it ran: {paths}` followed by guidance to re-run `/ductus:analyze`. Ordered last because it is the weakest of the three analyze claims, the same reason review staleness sits behind the MUST-violations check.

   **Why content and not the recorded sha.** `analyzed-against` records where `HEAD` was; `/ductus:analyze` reads the working tree. Those are the same subject only when the tree is clean, and at the moment analyze runs it usually is not — `/ductus:review` has just written `review.md`, and `mark-task` and `mark-criterion` rewrote `tasks.md` and `spec.md` before that. Comparing the sha therefore blocked records whose analysis had genuinely read the current content, as soon as that content was committed. A gate with false positives is the one people route around. `analyzed-against` survives as provenance and is read for exactly one thing: the mechanical-sweep rename exemption, which genuinely needs two trees, and whose candidates are reported rather than dropped when those trees are unavailable.

   The subject set is wider than the review's durable contracts because analyze's subject is wider — its families read `spec.md`'s frontmatter and criteria, `tasks.md`'s numbering, the scenarios' questions, and `review.md` itself through `review-state-drift`. Excluding `review.md`, as the review's own staleness check correctly does for *its* purpose, would exempt the single edit that most often invalidates an analyze record.

   A record carrying **no** `analyzed-digest` — every record written before this check — is reported as **undeterminable**, not current and not stale: nothing on disk says what those runs examined. It does not block, so the gate stops enforcing freshness for that spec until its next `/ductus:analyze` writes a digest. That is self-healing rather than a hole, and deliberately not a grandfather clause: the record is not exempt, it is unreadable, and the passing verdict's guidance says which.

   The analyze checks come **after** every review check because the pipeline runs in that order: a spec whose review is missing or failing has not reached the point where analysis is the next thing owed, and naming the later gate for an earlier defect sends a contributor to the wrong command. Unlike the review half, an **advisory** analyze finding does not block — analyze's advisory tier is advisory by design: some of its checks were introduced advisory with their own published promotion criteria (grounding, Applicable-Rules citations, decision drift), and the rest — the plan record and un-folded branch specs among them — stay advisory for good, so gating on them here would promote every one of them at once, past the criteria some declare and against the design of the rest. There is deliberately **no grandfather clause** at this gate, though the CI template's record check and `/ductus:audit` Family 37 have one: they read a corpus written before the field existed, while this gate runs when a spec is being completed now, so the record is always writable and an exemption would be a permanent hole rather than a bounded transitional one.

   **Last, whether every finding has a disposition** (§brownfield-inbox, Finding dispositions). Both records carry a `dispositions:` map — `fixed`, `routed`, `discarded`, `undispositioned` — counting the review's observations and the analysis's findings in every tier. Two checks, in this order. First, a record with **no map**: it was written before findings were dispositioned, so its run's findings may sit in the inbox unrouted, and absence is not zero. Halt with `blocked: {files} predate(s) finding dispositions — re-run {commands}`, naming the review record before the analysis, followed by guidance that re-running writes the map. There is no exemption, for the reason the analyze record has none: the record is always writable at the moment a spec is being completed. Then a record whose **`undispositioned` is above zero**: halt with `blocked: {N} undispositioned finding(s) — {file}: {n}, …`, followed by guidance to re-run the named command and fix, route, or discard each finding. The block asks for a decision, not a fix — discarding a false positive with its reason clears it — so an advisory analyze finding still never has to be *fixed* to reach `done`, and the advisory tier's promotion criteria are untouched. Both come after every other review and analyze check, because each of those names a more upstream defect, and the map-less record comes first because a count from a record that predates the field means nothing.

6. If all checks pass, present a summary — including every disposition task this feature's implementation appended, each with the outcome recorded on it (fixed, routed with its target, or discarded with its reason) — then ask the user to approve the transition to done. Do not update the status until the user confirms. No inbox row renders here; see step 15 of the command's Instructions.
7. On confirmation, update the spec's frontmatter status from in-progress to done (primitive: `set-status`, guarding against a stale "from" value).
