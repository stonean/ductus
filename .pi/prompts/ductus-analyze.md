# Analyze

Audit a feature's artifacts against each other and against the framework's rule set.

## Purpose

Audit a feature's spec, plan, tasks, and data model for consistency, then give every live finding a disposition before recording the run. Use this to catch problems before the next pipeline gate fires. **Detection (steps 1–17) writes nothing**: the read-only contract is a promise about detection, and analyze never mutates an artifact while it is deciding what is wrong with it. After detection, the fix-and-route step (step 19) proposes one disposition per live finding — fixed, routed, or discarded with its reason (§brownfield-inbox, Finding dispositions) — and writes each fix or route only after the operator confirms it; when anything was written, detection runs again (step 20), so what is recorded is the state the dispositions left. Then `analysis.md` records the run in that file's own frontmatter (step 21) — the durable record that this run happened, what it found, and what it did with each finding. Recording that the audit ran is what `/ductus:review` has always done through `review.md`, and precisely why that gate was enforceable while this one was not: until the record existed, a spec that had passed both gates and one that had passed only the review were byte-identical on disk. No finding is written to the inbox. The `--fix` flag reverts a status-`done` spec back to `in-progress` on either of two triggers: a review record drifted to blocking (see **§Review state drift (blocking)** in `.ductus/reference/analyze.md`), or unresolved open questions carried by the spec's scenarios (see **§Scenario open questions (blocking at `done`, advisory otherwise)** in `.ductus/reference/analyze.md`). A record carrying undispositioned findings is reported, never reverted (see **§Disposition drift (advisory)** in `.ductus/reference/analyze.md`). `--fix` never edits content, and no revert is silent — each emits a notice naming the spec and what drifted.

Renamed from `/validate` in spec 023 to align with the emerging spec-driven-development standard (GitHub Spec Kit uses `/analyze` for the same artifact-vs-artifact audit role). Complementary to `/ductus:review`, which audits **code** against rules.

## Context

Parse `$ARGUMENTS` for flags and an optional feature identifier:

- **Feature identifier** — a feature number, partial name, or full directory name. Overrides the session target.
- **`--all`** — scan all feature directories under `specs/` instead of a single target. Report results grouped by feature.

If `--all` is not present, use the feature identifier if provided, otherwise fall back to the session target — invoke `resolve-session` and display any notices and unreadable session files it returns (on the markdown-only path, read the shared default `.ductus/session.toml` — §concurrent-features). If no target can be resolved, stop and tell the user to run `/ductus:target` first or use `--all`.

## Scope Boundaries

- Detection (steps 1–17) never modifies an artifact under audit. Besides the session state `resolve-session` keeps for this process (Context — an adoption pinned, `used-at` refreshed), three kinds of write are in scope and no others: the fix-and-route step's confirmed writes (step 19) — a mechanical fix to an artifact the run audited, or a route to the home **§Groom decision tree** in `.ductus/reference/groom.md` chooses, including a `done → in-progress` reopen of the spec routed to — each only after `gate-confirm` returns a confirmed decision; the feature's `analysis.md` (step 21); and — only with `--fix` — the revert of a drifted `done` spec from `done` to `in-progress` via `set-status` on either of two triggers: review-state drift or unresolved scenario open questions (see **§Review state drift (blocking)** in `.ductus/reference/analyze.md` and **§Scenario open questions (blocking at `done`, advisory otherwise)** in `.ductus/reference/analyze.md`). With no operator to confirm — `ductus exec`, or any host that cannot ask — step 19 writes nothing, and `analysis.md` is the only write. No finding is written to `{specs-root}/inbox.md`.
- Read only files within the target feature's directory, the cross-spec files needed for reference checks (`specs/system.md`, `specs/events.md`, `specs/errors.md`, dependency spec files), the project's plan template `specs/templates/plan.md` (its `##` headings only, on the markdown-only path, for the Plan record check — the runtime compiles them into `prune-plan`), and the project's installed command-source frontmatter for **§Project-level consistency (advisory)** in `.ductus/reference/analyze.md` (frontmatter only: the installed command set at the agent layout's **Command/skill path**, plus the bootstrap installer at its **`ductus` install path** **if that file exists** — both layout-derived, located as that section describes). May invoke `scripts/gen-help-tables.sh --dry-run` to surface generator drift, only when that script exists in the project (it is a ductus-repo-only generator and is absent from adopters), and `derive-dependencies` in its report-only default to surface frontmatter drift. The fix-and-route step (step 19) additionally reads what a disposition needs: a candidate covering spec's `spec.md` and `tasks.md` for the **§Groom decision tree** in `.ductus/reference/groom.md`, as `/ductus:groom` does, and the artifact a chore fix edits. Do NOT read source code or test files.
- Resolving the target spec's cross-service `references:` index additionally reads `.ductus/config.toml` (the `[services]` registry) and the registered local checkouts' linked `spec.md` files — and nothing else; the canonical repo URL is **never fetched**. On the runtime path the host calls the resolve-references primitive per referencing spec; on the markdown-only path it reads those files with host file tools (see **§Cross-service references (advisory)** in `.ductus/reference/analyze.md`). This stays read-only.
- Reference: §spec-requirements, §grounding, §plan-phase, §tasks-phase, §readiness-check, §scenarios, §cross-spec-impact, §bug-handling, §brownfield-inbox (Finding dispositions), §text-first-artifacts, §markdown-standards, §drift-prevention (constitution loaded by `/ductus:target` — do not re-read). See [030 — Cross-Service References](https://github.com/stonean/ductus/blob/main/specs/030-cross-service-references/spec.md) for the reference semantics surfaced here.

## Instructions

> **For agent runtimes**: the Invoke steps below call the MCP tools of the ductus runtime; the host-integration contract — bare↔prefixed tool names, lazy ToolSearch schema fetch, the no-shell-utilities rule, and the two-paths guarantee — lives once in the constitution, §runtime-host-integration. Before the server is registered — the window between acquisition and the restart that loads it — walk the same prose using the host file-reading tools (Read, Edit, Write).

**Where a named section lives.** This command's markdown-only reference — the procedure for the path without the runtime, and the policy these steps apply — is `.ductus/reference/analyze.md`. A section named here, or cited elsewhere as part of this command, that has no heading in this file is there; read it when a step points at it.

1. Invoke `read-spec` (with `include-body`) against the targeted feature to load frontmatter, sections, and the open-question count from the body. The result drives subsequent steps' tier classification (status governs which artifact-completeness checks apply); its parsed `sections` also feed step 14's `## Applicable Rules` scan, so no separate re-read of the body is needed.

2. Invoke `validate-frontmatter` against the spec path to check that the YAML block parses and that the required fields (status, dependencies) are present with valid values. Each finding carries the severity §text-first-artifacts (Validation Severity) assigns to **that** condition, so render each finding in the tier it names — never map the family to one fixed tier. The distinction is load-bearing in both directions: a malformed block or a missing or invalid required field is Hard fail, while a residual `review:`/`analyze:` record block is **Blocking** precisely because the spec file itself parses. A family flattened up to hard-fail overstates the second; one flattened down to blocking understates the first. The rest of the procedure still runs to surface every issue in a single pass.

3. Invoke `traverse-deps` against the feature to verify each dependency directory exists, carries a compatible status, and that the reachable dep subgraph is acyclic. Missing dependencies are blocking; an incompatible status (the edge's `compatible: false` — the dependency is below `planned`) is blocking when this spec is at `clarified` or later. `traverse-deps` reports per-edge `compatible` and `status` **unconditionally** (it never reads the consumer's own status), so apply that consumer-status conditioning host-side from the returned data rather than mapping the top-level `compatible` flag straight to a blocking finding. Any non-empty `cycles` entry — multi-node SCC or self-loop — is blocking. The cycle check is defense-in-depth that fires when the upstream derive-dependencies check (spec 017) was bypassed or stale frontmatter re-introduces an edge.

4. Invoke `resolve-anchor` against the spec path **with `markers-path` set to the constitution file** (`framework/constitution.md` in ductus's own repo; `.ductus/constitution.md` at the adopter repo root) to confirm every `§<name>` reference in the spec resolves to a `<!-- §name -->` marker in the constitution. The `markers-path` is essential: a spec carries no markers of its own, so resolving against the spec itself would flag *every* reference as unresolved; resolving against the constitution flags only a reference to a section that was renamed or restructured without updating callers. Unresolved anchors are advisory. With no ductus runtime, walk the markdown-only path.

5. Invoke `check-rule-ids` against the spec path with the project's rule files. Cited rule IDs that are missing are blocking; cited rule IDs marked deprecated are advisory. **Read `examined` before acting on `missing`.** It reports how many rule files were read, and `missing` is only meaningful against it: the known-ID set is built from the `rule-files` argument, so an `examined` of **0** makes every citation `missing` and means *nothing was checked against*, not *these IDs do not exist*. A blocking finding raised from that state is against a correct spec, and "fixing" it deletes a valid citation. Pass the files the rule-file discovery step selected, and treat `examined: 0` on a project that has rule files as a caller defect rather than a result. Either way, with `examined: 0` the spec's citations are unexamined, never missing (`rule-citations-not-checked`, under **§Unexamined targets (informational)** in `.ductus/reference/analyze.md`).

6. Invoke `derive-dependencies` to detect drift between the body inline links and the frontmatter `dependencies:`. It reports without writing unless `--write` is passed, so this step is read-only; a non-empty `updated` surfaces as an advisory drift finding — the pre-commit hook resolves these on the next commit.

7. Invoke `lint-markdown` against the markdown files in the feature directory. Each returned violation is surfaced as an advisory finding.

8. Invoke `check-artifacts` against the feature to run the ten residual deterministic check families: artifact completeness per status tier (plan.md/tasks.md required at planned+ — the *conditional* data-model.md requirement is a semantic judgment and stays on the markdown-only path), task numbering and done-when consistency (the "tasks reference the plan" link is a semantic judgment and stays on the markdown-only path), scenario→task mapping (a scenario is flagged only when no revision of `tasks.md` ever named it, at every status, so a spent task pruned per §tasks-phase never counts against its scenario), review-state drift on done specs, disposition drift on done specs (advisory — a `review.md` recording undispositioned findings — `analysis.md`, its dispositions and its own state alike, is judged after step 21 from the record this run writes, never here: see **§Analyze state drift (blocking)** in `.ductus/reference/analyze.md` and **§Disposition drift (advisory)** in `.ductus/reference/analyze.md`; a record with no `dispositions:` map predates dispositions and is not drift), scenario open questions (blocking at `done`, advisory otherwise — no grandfather rule), link-adjacent decision drift (advisory — prose asserting an open state that its own sibling link's target contradicts), acceptance-criterion path existence (advisory — a filesystem path named in a `done` spec's acceptance criterion that no longer resolves), body path existence (advisory — a path named elsewhere in a `done` spec's artifacts that existed in this project and no longer resolves), and acceptance-criterion labels (advisory — a duplicate `AC{n}` within one spec, a `next-criterion` that no longer exceeds the body, and an unlabelled criterion in a spec that carries a counter). Each returned finding carries its family, severity tier, and location. The result additionally carries a `skipped` list naming each target a family could not examine; render those in the Informational tier, never as findings — a zero-finding result must not read as assurance the primitive cannot give. The primitive mechanizes the **deterministic subset** of **§Artifact completeness (blocking)** in `.ductus/reference/analyze.md`, **§Task consistency (blocking if tasks exist)** in `.ductus/reference/analyze.md`, **§Scenario consistency (advisory)** in `.ductus/reference/analyze.md`, **§Scenario open questions (blocking at `done`, advisory otherwise)** in `.ductus/reference/analyze.md`, **§Review state drift (blocking)** in `.ductus/reference/analyze.md`, **§Disposition drift (advisory)** in `.ductus/reference/analyze.md`, **§Link-adjacent decision drift (advisory)** in `.ductus/reference/analyze.md`, **§Acceptance-criterion path existence (advisory)** in `.ductus/reference/analyze.md`, **§Body path existence (advisory)** in `.ductus/reference/analyze.md` and **§Acceptance-criterion labels (advisory)** in `.ductus/reference/analyze.md`; the semantic items noted above (data-model necessity, tasks-reference-plan, and a scenario's own Context/Behavior sections) stay on the markdown-only path, as does Command-frontmatter completeness (**§Project-level consistency (advisory)** in `.ductus/reference/analyze.md`), which reads the host's command directory the runtime does not own.

9. Invoke `check-orphaned-references` to report adopter-owned files whose references to ductus-managed paths no longer resolve (advisory; see **§Project-level consistency (advisory)** in `.ductus/reference/analyze.md`). Runs once per invocation regardless of which feature is targeted — its subject is the project, not the spec — so with `--all` run it once, not per feature. Each finding names the referring file, the missing path, and the line. The result's `attribution` field governs the render and must not be flattened: `registry` means `framework/migrations.toml` was readable, and a finding's `migration` names the entry whose move most likely orphaned the reference (empty there means the registry *was* read and no entry claims that path); `watermark` means no registry was available to ask, so an empty `migration` means something different and `last-applied` is the only migration context there is. Rendering the two identically asserts an attribution nobody computed. Referrers that could not be read arrive in `skipped` and belong in the Informational tier (`referrer-unreadable`), so an empty `findings` reads as clean only when `skipped` is empty; `examined` names the files the result actually describes. Report, never repair — the adopter may have hand-edited the reference, and a wrong rewrite is worse than a precise report. See 027's `migration-chain-reference-integrity` for the rule and `/ductus`'s Pre-run Migrations for the second call site, where the registry is in hand.

10. Invoke `check-unfolded-specs` to report branch-scoped specs (`{identifier}.{n}-{slug}`) still present in the working tree (advisory; see **§Project-level consistency (advisory)** in `.ductus/reference/analyze.md`). Runs once per invocation regardless of which feature is targeted — its subject is the corpus, not the spec — so with `--all` run it once, not per feature. Each entry names the directory, its branch identifier, its declared `folds-into` target, and its status. A branch-scoped directory is a staging form discharged by fold-back, and nothing runs on the merge itself, so a merged branch leaves its staging directories behind silently — this is what notices. The finding is advisory and **stays** advisory: the check cannot tell a spec whose branch is still open, where the directory is exactly where it belongs, from one whose branch merged weeks ago, so it reports the set and leaves that judgement to the operator. Report a `folds-into` naming a spec absent from this tree as *unresolved here*, never as broken — before the merge the target normally lives on the upstream branch, and existence is enforced at fold-back, in the first tree holding both. `examined` counts every feature directory scanned, so an empty `unfolded` reads as clean only against that count. Report, never repair: which upstream section a spec's content belongs in is the routing decision `/ductus:fold` puts to the operator. See [051 — Branch-scoped spec numbering](https://github.com/stonean/ductus/blob/main/specs/051-branch-scoped-spec-numbering/spec.md) for the directory form and the fold target.

11. <!-- llm:assessSpecQuality --> For every loaded MUST-tier rule whose Verification trigger fires against the spec, request a semantic assessment via the extension point. The host responds with a structured finding carrying severity, rule-id, location, and message. MUST-tier findings join the Blocking tier in the rendered report. A rule's tier is the RFC 2119 keyword in its Statement, never the step's: MUST or MUST NOT makes it MUST-tier, including a Statement that also carries SHOULD, so no rule is assessed at both this step and the next. Under `ductus exec` the walker sends one request per loaded MUST-tier rule, each carrying that one rule, and evaluates no trigger itself: the host judges whether the rule's trigger fires against the spec and answers `passed: true` when it does not. A rule whose Statement carries no MUST or SHOULD keyword (MAY alone sets no tier), or that has no Verification, is recorded unexamined rather than assessed, as is a rule file that could not be read (see **§Unexamined targets (informational)** in `.ductus/reference/analyze.md`). A Verification that yields a case to another rule "where `{file}` is also loaded" yields it only when `{file}` is among the rule files this run loaded, so the yielding rule keeps the case in a project without that file: under `ductus exec` each request lists the loaded files' basenames under `loaded-rule-files`, and a file the list lacks, or a request carrying no list, makes the condition false; on the markdown-only path the host applies it from the rule files it loaded, a file it could not read or treated as unloadable excluded.

12. <!-- llm:assessSpecQuality --> For every loaded SHOULD-tier rule whose Verification trigger fires against the spec, request a semantic assessment via the extension point. SHOULD-tier findings join the Advisory tier in the rendered report. A rule is SHOULD-tier when its Statement carries SHOULD or SHOULD NOT and no MUST. Under `ductus exec` the walker sends one request per loaded SHOULD-tier rule, as at step 11, and the host judges the trigger, answering `passed: true` when it does not fire. A load-conditioned yield is applied as at step 11, on either path.

13. Resolve the target spec's cross-service **references** (deterministic; advisory). When the spec's derived `references:` index is non-empty, resolve each entry by the procedure in **§Cross-service references (advisory)** in `.ductus/reference/analyze.md` — the resolve-references primitive on the runtime path; host file tools (read `.ductus/config.toml` and the linked checkout) on the markdown-only path. A **broken** outcome — the service is registered and its checkout reachable, but the target spec does not resolve (renamed, moved, deleted, or mistyped upstream, or a malformed URL) — is an **Advisory** finding, the cross-repo analog of a broken sibling link. The informational unknowns are **not** findings: **unregistered** (the repo matches no `[services]` entry — surface a pointer to `/ductus:link` to register the service), **not checked out**, and **status unreadable** each record what could not be proven, without flagging a defect. Skip this step when the target spec declares no references.

<!-- audit:ignore-promotion -->
14. Parse the spec body for a `## Applicable Rules` section and collect every rule ID cited there. For each cited ID that did **not** appear in the set of rules whose Verification triggers fired in steps 11 or 12, emit an advisory finding: `Applicable Rules citation does not fire: {rule-id} is listed under ## Applicable Rules, but the rule's Verification trigger did not fire against any spec artifact. Either remove the citation, or extend the spec to bring the cited surface into scope.` Skip this step when the spec has no `## Applicable Rules` section. Citations whose IDs do not resolve to any loaded rule are handled earlier in step 5 and not reprocessed here. A cited rule whose rule file declares that it verifies code patterns rather than design-time commitments, as `quality-cross.md` does, is not flagged. Its Verification is `/ductus:review`'s quality pass over code, which has no trigger against spec artifacts, and `/ductus:review` enforces the rule against the code whatever the spec cites. See **§Applicable Rules citation consistency (advisory)** in `.ductus/reference/analyze.md` for the full semantics and the promotion criterion that governs when this check graduates from advisory to blocking.

<!-- audit:ignore-promotion -->
15. Scan the spec body (loaded in step 1) and `plan.md` (read it if present) for **ungrounded factual claims about the existing system** — assertions about how current code behaves, what a schema or interface contains, or what an external system returns, stated as fact but carrying neither a citation to a primary source (a `path:line` reference, a named query, a command, or a link to a substantiating artifact) nor an explicit assumption / Open Question marker. Descriptive claims about existing reality need grounding; **prescriptive requirements** about the feature under design (what it MUST do) are contracts, not claims, and are never flagged — the descriptive-vs-prescriptive call is the semantic judgment this step turns on. This is a *form* check: do NOT read source code to confirm a claim (out of scope; see Scope Boundaries), only verify the artifact sources or hedges it. Apply to the spec body at status `clarified` or later and to `plan.md` at `planned` or later; skip on a `draft` spec. Emit each as an **Advisory** finding per **§Grounding (advisory)** in `.ductus/reference/analyze.md`.

16. Invoke `prune-plan` against the feature, as a preview — it passes no `apply` — to find the `plan.md` sections outside the design record (§plan-phase), segmented and compared as **§Plan record (advisory)** in `.ductus/reference/analyze.md` defines. On a spec at `planned` or later, record **every** section the result lists as an **Advisory** finding under the result's own `finding` — family `plan-record`, message `plan.md §{heading} is outside the design record` — whether or not the section is `decided`. A decided section is one whose finding `analysis.md` already stores a discard for; firing it lets step 18 match it to that discard, so it counts as discarded and nothing is asked, where leaving it out would expire the discard and have `/ductus:prune` propose the section again. Below `planned` nothing is recorded, because the rule is applied once the spec has reached `planned`; a result with `missing` set names a feature with no `plan.md`, which step 8's artifact completeness already judges. The primitive errors rather than guess on two inputs, and under `ductus exec` the walk halts here on either: an `analysis.md` whose `decisions:` list does not parse, which read as empty would mark every decided section undecided; and, on a `done` spec, a HEAD it cannot read, since it computes the `reopen-required` field `/ductus:prune` uses — this step ignores that field. An interactive host reports the error and stops the run too.

17. Invoke `check-artifact-size` against the feature to measure its subject artifacts — `spec.md`, `plan.md`, `tasks.md`, `data-model.md` and each scenario — against the configured read size (`[artifacts] read-size-bytes`, 50,000 bytes by default), as **§Artifact size (advisory)** in `.ductus/reference/analyze.md` defines. At every status, record each entry in `oversized` as an **Advisory** finding — family `artifact-size`, its `message`, its `path` — and render its `warning`, which says the file may not be read in one call and names the fixes for its kind and, on a `done` spec, which of them reopen it. In this command a discard with its reason is the further fix, offered at step 19 like any other advisory discard. Record an entry the result marks `decided` too, firing its `decision-key` at step 18: a stored discard covers it, so it counts as discarded and nothing is asked, where leaving it out would expire the discard. Render each `skipped` subject in the Informational tier as unexamined under `artifact-unreadable`, and each of the result's `notices` — stored decisions it could not read, and each key in `[artifacts]` that no reader recognizes — in the Informational tier too. A `read-size-bytes` that is not a positive whole number of bytes, or an `artifacts` that is not a table, is a configuration error, not a finding: the primitive fails naming the setting, the value, the file and the accepted form, and the command halts there rather than measuring at the default. On the markdown-only path, measure each subject's size with the host's file tools, halt the same way on such a value, and name any key in `[artifacts]` other than `read-size-bytes` as the primitive's notice does; a subject whose size those tools cannot report is unexamined, never under the threshold.

<!-- audit:ignore-promotion -->
18. Process stored decisions (host responsibility): read the `decisions:` list in `analysis.md` and match each finding still live after detection to the stored decision describing the same issue — many messages are worded by the host (grounding, rule assessments, rendered primitive results) and do not reproduce byte for byte, so the match is the host's judgment, as `/ductus:review`'s is for observations. An `artifact-size` finding is the exception: step 17's primitive has already matched it by the read-page rule judgment cannot hold, so a decided one fires the `decision-key` the result returned and an undecided one fires its own key, never matched by judgment to a stored discard that covers fewer read pages. Then call the process-decisions primitive with the feature, `record: analysis`, `fired` — for each live finding, in every tier, the stored key it matched, or else its own `{family} — {message}` — and `restricted` set only when the run could not read something it meant to examine — a skipped target whose reason is in the **could not be read** class (see **§Unexamined targets (informational)** in `.ductus/reference/analyze.md`), or a registered shared constitution it could not resolve — because a stored decision whose finding did not fire may then simply not have been looked at. A target **excluded by construction** never restricts: the run decided not to examine it, it recurs on every run, and letting it restrict would retain a stored decision forever on every spec that carries one. The Informational tier is not findings: unexamined targets and cross-service reference unknowns state what could not be examined, and carry no key. Each `matched` decision disposes of its finding under the stored outcome, and nothing is asked about it — the finding carries that key to step 21 as its `decision-key`; each `expired` decision goes to step 21 to be dropped — for a routed finding, this is the moment its routed work landed; `retained` decisions stay in the record untouched. Render the result's `notices`, malformed and duplicate entries among them, in the Informational tier. When the primitive refuses because the list does not parse, report that, ask about each finding as though nothing were stored, and tell the operator the record cannot be written until the list is repaired. Two findings with the same key are one finding and get one disposition.

<!-- audit:ignore-promotion -->
19. Fix and route (host responsibility): for each live finding no stored decision matched, propose one disposition, and write it only after the gate-confirm primitive returns a confirmed decision. **Fixed**: a chore — a mechanical edit to an artifact this run audited, adding no durable requirement (§bug-handling's durability test). **Routed**: written to the home **§Groom decision tree** in `.ductus/reference/groom.md` chooses — its single canonical statement; do not restate it here — whether a task, a scenario with its task, a body edit, a new spec created through `/ductus:specify`'s procedure, or an amendment to a rule file the project owns; a route to a spec that is `done` — the spec in hand included, since a run can examine a finished spec — names the `done → in-progress` reopen in its confirmation and performs it through the set-status primitive with `from: done`. **Discarded**: the finding and the operator's reason, which step 21 records — **never offered for a `hard-fail` or `blocking` finding**, which is fixed or routed and keeps blocking until the re-check no longer produces it. A declined proposal leaves the finding discarded with the operator's reason, or undispositioned. A fix that fails or proves not to be mechanical is reverted and re-proposed as a route or a discard; a confirmed route whose write fails is undispositioned, and the failure is reported beside the finding. With `--all`, group the proposals by spec, and let each prompt leave the rest of that spec's findings undispositioned. **With no operator to confirm** — `ductus exec`, whose walker no-ops this step by design, or any host that cannot ask — propose nothing and write nothing: each unmatched live finding is recorded as undispositioned, for an interactive run to decide; a hard-fail or blocking one holds `done` through the record's `blocking` whatever its disposition. Under `ductus exec` that is every live finding, since the walker no-ops step 18 too and matches nothing against the stored decisions, which it leaves in place. The detail is in **§Finding dispositions** in `.ductus/reference/analyze.md`.

<!-- audit:ignore-promotion -->
20. Re-check (host responsibility): when step 19 wrote anything, run the detection steps (1–17) again, and take the tier counts and the live findings from the re-check. A finding the re-check no longer produces is carried to step 21 with `live: false` and recorded `fixed`, whether a chore or a confirmed route removed it; a finding that first appears in the re-check is recorded undispositioned, for the next run to decide. When nothing was written, the first pass is the re-check. This is what keeps a run from making its own record stale: the record is written from the state the dispositions left.

21. Record the run (host responsibility): invoke `write-analysis` with the feature, the current UTC timestamp, the HEAD sha, and the re-check's tier counts — `hard-fail`, `blocking-findings`, `advisory`, and `unexamined` (the size of the Informational tier's unexamined-target set) — plus `findings`: every finding the run dispositioned or left owed, each with its `tier`, `family`, `message`, `path`, `live`, and `disposition` (`outcome`, plus `target` for a route or `reason` for a discard; a finding a stored decision matched carries that decision's outcome, and its key as `decision-key`). Pass `expired-decisions` from step 18 and `decided-by` (`git config user.email`), which the writer requires when any live finding is newly routed or discarded. The writer derives the rest: the `dispositions:` map, and the `decisions:` list — each newly routed or discarded live finding stored under its key, a re-matched decision keeping its original stamp, and each expired one dropped. It writes `specs/{feature}/analysis.md` — the run's record in that file's frontmatter, plus the report body's fixed skeleton — the durable record that this command ran, what it found, and what it did with each finding. `spec.md` is not written: the record lives in the artifact this command owns (spec 057). **Always**, including on a clean run and on a run whose scope was empty: the record's whole purpose is that its *absence* means something, so a run that declines to write one is indistinguishable from a run that never happened.

    This is what `/ductus:implement`'s pre-done gate reads to hold a spec out of `done` until this command has actually run, and it exists because it did not. The pipeline is `/ductus:review → /ductus:analyze → done`, and only the first half left a trace: that gate read the review record, Family 19 checked its freshness, a reconciliation family held it against `review.md`, and analyze wrote nothing at all. A spec that had passed both gates and one that had passed only the review were byte-identical on disk, so nothing could enforce the second — the only thing holding it was whoever remembered, which is the diligence dependency §design-principles rejects. On 2026-09-05 two specs were advanced to `done` on the review gate alone and one was published to crates.io, irreversibly, before anything noticed, because nothing could.

    **`unexamined` is not optional and not decorative.** A clean analyze is two different states — every target examined and clean, or some target unexaminable and the rest clean — and **§Unexamined targets (informational)** in `.ductus/reference/analyze.md` says so in as many words. A record carrying only the finding counts would collapse exactly that distinction into the reassuring reading, inside the artifact a later gate trusts, which is the worst possible place for `QUAL-CLAIM-001`. Write the count even when it is zero; a zero that was computed and a field that was never written are not the same claim.

    **`dispositions:` is the pair to the tier counts, and it is derived, never authored.** The tier counts say how many findings are live; the map — `fixed`, `routed`, `discarded`, `undispositioned` — says what the run did about them. A run that found five findings and decided none must not be byte-identical to one that decided all five. The writer computes `undispositioned` as the live tier total less the live findings routed or discarded, so a finding the call omits from `findings` counts as undispositioned and can never read as handled — which is also how an exec run, which itemizes nothing, records every live finding honestly. The pre-done gate does not read `undispositioned` — the map does not split its counts by tier, and only a gating finding holds `done` — but it blocks on a record with no map at all, which predates dispositions: absence is not zero.

    `blocking` is derived by the primitive from `hard-fail` and `blocking-findings` — advisory findings are recorded and never gate. That asymmetry with the review record is deliberate: an outstanding SHOULD blocks `done` at the review gate because §implement-phase says advisory is not ignorable there, while analyze's advisory tier is advisory by design: some of its checks were introduced advisory **with their own published promotion criteria** (grounding, Applicable-Rules citations, decision drift), and the rest — the plan record and unfolded specs among them — stay advisory for good. Gating on them here would promote every one of them at once, past the criteria some declare and against the design of the rest. An undispositioned advisory finding is recorded in the `dispositions:` map and does not hold `done` either.

    Order matters: this runs **after** the dispositions and the re-check, so the record describes the state they left and a run cannot make its own record stale, and **before** the render, so a run interrupted between recording and reporting leaves the record, not the report. On the markdown-only path, write `analysis.md` by hand with the same field set and the same section skeleton. A spec whose frontmatter does not parse gets **no** record: the analysis would have hard-failed on it, and writing a clean record into it inverts the whole mechanism.

22. Render the report (host responsibility): list hard-fail and blocking findings first, advisory findings next, then informational. For each finding, include what failed, what was expected, what was found, a suggested fix, and its disposition — the fixed file, the artifact it was routed to, or the discard reason — or that it is undispositioned. When the spec is `done`, judge the record step 21 wrote: when it is blocking (the write-analysis primitive returns `blocking`), report analyze-state drift from it, as **§Analyze state drift (blocking)** in `.ductus/reference/analyze.md` describes; and when it counts undispositioned findings (it returns the `dispositions` map), report disposition drift for `analysis.md` from it, as **§Disposition drift (advisory)** in `.ductus/reference/analyze.md` describes. With `--fix` set, additionally revert any status-done spec a check found drifted — a review record drifted to blocking, or unresolved open questions in the spec's scenarios — through the guarded set-status revert (`from: done`, `to: in-progress`), detailed in **§Review state drift (blocking)** in `.ductus/reference/analyze.md` and **§Scenario open questions (blocking at `done`, advisory otherwise)** in `.ductus/reference/analyze.md`; disposition drift is reported and never reverted. Each revert emits its own non-silent notice.
