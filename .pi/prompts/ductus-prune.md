# Prune

Invocation arguments: `$ARGUMENTS` (empty when none were supplied)

Reduce the session target's spec directory — or, with `--all`, every spec's — so each working artifact says only what it should — dropping spent task sections from `tasks.md` (or resetting it to template state), and removing the `plan.md` sections outside the design record once their durable pieces have moved home.

## Purpose

A feature's `tasks.md` accumulates completed work across the whole life of the feature, and a task's value is spent the moment it is complete. A plan accumulates something worse: journal, evidence, and handoff sections outside its design record, where a decision corrected during implementation can sit thousands of lines below the entry it contradicts (§plan-phase). `/ductus:prune` reclaims both — each artifact by the rule its durability class allows. `tasks.md` is reduced mechanically; a plan section is removed only once it has been emptied of what lasts, which is a judgment the operator confirms section by section.

| Artifact | Class | What prune does |
| --- | --- | --- |
| `tasks.md` | Ephemeral | Drops spent sections (keep-pending) or resets (`--reset`) |
| `plan.md` | Design record | Removes each section outside the design record, after its durable content has been moved home |
| `spec.md` | Durable | Body never touched; its `status` changes only to reopen a `done` spec |
| `scenarios/*.md`, `data-model.md` | Durable | Never touched |
| `research.md` | Reference | Never touched |
| `review.md`, `analysis.md` | Regenerated | Never written; prune reads only `analysis.md`'s stored decisions |

Any other file in the directory is the project's, not the pipeline's: prune neither reads nor reports it.

## Scope Boundaries

- Prune writes `tasks.md` (its reduction, and owed work a plan section moves onto a pending task), `plan.md` (a moved decision edited into its design-record entry, and the removal of sections outside the record), and the project's `AGENTS.md` (contributor knowledge moved out of a plan section that holds for this project alone). Knowledge that holds more widely is named for the operator to route where §drift-prevention's *Shared knowledge stays in git* sends it; prune writes no shipped artifact.
- Prune changes status only to reopen a `done` spec, and names each reopen before the write that causes it. A spec below `done` is never moved.
- `--all` repeats the one-spec reduction for every spec in the corpus; it is a batch of one-spec operations, never one operation spanning two specs. It needs no session target and leaves any target that is set unchanged.
- Recovery is git history: prune writes no backup file and no gitignored sidecar.
- Reference: §plan-phase (a plan records the design as it stands), §tasks-phase (`tasks.md` is an ephemeral work-tracking artifact — not a durable source of truth), §spec-lifecycle (the diff-determinable reopen), §pipeline-boundaries ("don't backtrack silently"), §text-first-artifacts, §runtime-boundary, plus [041 — Spec Directory Pruning](https://github.com/stonean/ductus/blob/main/specs/041-task-pruning/spec.md) for the reduction semantics and [data-model](https://github.com/stonean/ductus/blob/main/specs/041-task-pruning/data-model.md) for both segmentations and classifications.

## Instructions

> **For agent runtimes**: the Invoke steps below call the MCP tools of the ductus runtime; the host-integration contract — bare↔prefixed tool names, lazy ToolSearch schema fetch, the no-shell-utilities rule, and the two-paths guarantee — lives once in the constitution, §runtime-host-integration. Before the server is registered — the window between acquisition and the restart that loads it — walk the same prose using the host file-reading tools (Read, Edit, Write) per the markdown-only reference below.

<!-- audit:ignore-promotion -->
1. Invoke `resolve-session` to resolve the session target, and display any notices and unreadable session files it returns (markdown-only: read the shared default `.ductus/session.toml`). If no target is set and `--all` is not given, stop and tell the user to run `/ductus:target` first; `--all` needs no target and uses none. Parse the invocation flags: `--all` walks every spec in the corpus, in corpus order; `--reset` selects a full reset of `tasks.md` (default is a keep-pending prune); `--force` overrides the reset status gate on a non-`done` spec. `--force` without `--reset` is ignored (it only gates reset) — except alongside `--all`. `--force` with `--all` is refused before anything is read, whether or not `--reset` is given: a forced reset across the corpus would discard every in-flight todo under one confirmation, which §pipeline-boundaries forbids; a deliberate forced reset stays available one spec at a time.

2. Invoke `prune-tasks` against the target feature — or with `all` under `--all` — in preview mode (`apply: false`), passing the `reset` and `force` flags. Under `--all` the result is a walk: `examined`, the number of specs walked; one line per spec with something to reduce, carrying its status, its reset gate, its removed and kept counts, and its size before and after; and `skipped`, naming each spec with no `tasks.md`. For one spec it is a compact summary — mode, the `--reset` gate outcome, the per-section classification (`spent` / `pending` / `no-checkbox`), the removed/kept counts, and the size before/after — and never carries the file body. When the feature directory does not exist, stop and direct the user to `/ductus:target` (a `feature directory not found: …` error). When the target has no `tasks.md` (a `tasks.md not found: …` error), note it and continue: the plan decides whether there is anything to prune. Continuing is the host's decision — the `ductus exec` walker halts on any primitive error, this one included, so an exec run stops here on a spec with no `tasks.md`. These are operational errors carrying a Display message — the `tasks-file-missing` / `feature-not-found` names label the error variants, they are not literal tokens in the payload.

3. Invoke `prune-plan` against the target feature — or with `all` under `--all` — as a preview, with no `apply`; a walk is preview-only, since each plan section is a judgment about one spec's content. Under `--all` the result is a walk: `examined`; one summary per spec whose plan holds a section outside the design record, or whose tree already requires a reopen — a `done` spec is listed for its `reopen-required` alone, even with no such section or no `plan.md`; and `skipped`, naming each spec with no `plan.md` and nothing else to report. For one spec, the result names the spec's `status` and lists every `plan.md` section outside the design record with its heading, size, digest, and `decided` — whether `analysis.md` stores a discard for that section's `plan-record` advisory. It never carries a section's text. An `analysis.md` whose `decisions:` list does not parse is refused rather than read as empty, which would propose every section it already decided, so the run stops there — under `--all`, at that spec. On a `done` spec it also carries `reopen-required`, computed against HEAD for the tree as it stands: `true` means edits made before this run already change a design-record section or add an unchecked checkbox to `tasks.md`, so the spec reopens with whatever this run writes. Computing it reads HEAD, so on a `done` spec whose HEAD cannot be read the preview errors and the run stops before anything is written. A result with `missing` set means the feature has no `plan.md`; with no `tasks.md` either (the `draft` and `clarified` case, since `/ductus:plan` writes both), stop and direct the user to run `/ductus:plan`. Under `--reset` no plan section is proposed — a reset resets `tasks.md` and never touches the plan — but the preview still runs, for `reopen-required`.

<!-- audit:ignore-promotion -->
4. Settle which plan sections to propose (host responsibility), spec by spec under `--all`. A `decided` section is kept, and listed as *kept — decided in `analysis.md`*. For each undecided one, read `analysis.md`'s `decisions:` list and match it to a stored `plan-record` discard the way `/ductus:analyze`'s stored-decision step matches a finding — by judgment, because a finding that step re-matched after its wording drifted keeps its original key — and treat a match as decided too. Every other section is proposed.

<!-- audit:ignore-promotion -->
5. Render the preview from both summaries, so the whole reduction is visible before any of it happens: the spec's status, and — when the plan preview reports `reopen-required` — that edits made before the run already require the spec to reopen, so it reopens once the run has written to it unless step 9's fresh reading finds the cause gone: a reopen named here, before anything is written, and repeated in every confirmation that writes to that spec; for `tasks.md`, the mode, the size before → after, and one line per task section with its classification and action, or that there is no task list; for `plan.md`, one line per section outside the record with its size and whether it is proposed or kept, and the size before → after, the after being the size were every proposed section removed (under `--reset`, which proposes none, the plan is unchanged). Under `--all`, render one table instead: a row per spec that has anything to reduce, or that is `done` and listed only because its tree already requires a reopen — its status, whether edits made before the run already reopen it, what each artifact would lose, and the plan sections kept because `analysis.md` decided them — then a total, and the number of specs examined, so a clean corpus reads as *examined N, nothing to prune* rather than as silence. Status is what prices a reopen: only a `done` spec can be reopened. A reopen the tree already carries is named on its row now; one a spec's moves would cause is named at that spec's plan confirmation, once its moves are known. Two early exits, neither of which writes or changes a status, whatever the preview reported: when nothing anywhere has anything to reduce — `nothing-to-prune` on `tasks.md` or no task list, and no proposed plan section — report that there is nothing to prune and stop; when the gate is `blocked-needs-force` (a `--reset` on a non-`done` spec), name the current status, point at the default keep-pending `/ductus:prune` as the likely intent, note `--reset --force` as the explicit escape hatch, and stop. Under `--all --reset` a blocked spec is not an exit: name each spec the reset skips, with its status, and reset the rest.

6. When `tasks.md` has something to reduce, invoke `gate-confirm` with a prompt that names the destructive write (the mode and how much the file shrinks — under `--all`, how many specs and the total). One confirmation covers every `tasks.md` reduction of a walk: they are deterministic and hold nothing durable. A `tasks.md` reduction never causes a reopen — dropping a spent section adds no owed work — though on a spec whose preview reported `reopen-required` the prompt names that reopen, which step 9 performs, or not, after the run's writes to that spec. On a declined gate, leave every `tasks.md` unchanged and go on to the plan sections.

7. On confirmation, invoke `prune-tasks` again with `apply: true` (same `feature` or `all`, and the same `reset` / `force` flags) to perform the atomic writes — under `--all`, one per spec whose reduction its gate permits — and note each file's new size and the sections removed from the returned summary.

<!-- audit:ignore-promotion -->
8. Work each proposed plan section in turn (host responsibility) — under `--all`, one spec at a time, each apply naming that spec's feature, since a plan apply never spans specs. Read it with the host's file tools and propose, piece by piece, where each durable piece goes: a changed decision into the Technical Decisions entry it amends, edited in place to say what is now true; contributor knowledge into `AGENTS.md` when it holds for this project alone; owed work, including an in-flight task's handoff notes, onto its pending task in `tasks.md`. Name what is dropped because git already holds it — evidence, pass counts, scratch paths — and name any knowledge that holds more widely for the operator to route where §drift-prevention's *Shared knowledge stays in git* sends it. On a `done` spec, name the reopen before anything is written whenever a move edits a design-record section or adds an unchecked checkbox to `tasks.md`, since that is what the diff will show. Confirm the section's moves and its removal together through the gate-confirm primitive. On a declined section, leave it byte-for-byte and say so in the prompt: declining keeps it for this run only, and the lasting keep is discarding its `/ductus:analyze` advisory with a reason. On confirmation, write the moves first, then call the prune-plan primitive with `apply: true` and `remove` naming that section's heading and digest. A result with `stale-sections` means the section changed since the preview: nothing was removed, so preview again and propose it afresh against the entry that already holds its piece.

<!-- audit:ignore-promotion -->
9. Reopen a `done` spec only as the diff requires (host responsibility), decided on a fresh reading. Once the run has finished writing to a `done` spec — under `--all`, spec by spec — invoke the prune-plan primitive's preview for that feature again: it answers for the tree as the run left it. Flip the spec with the set-status primitive, `from: done`, `to: in-progress`, only when that fresh result reports `reopen-required`. When that reopen was named — in the preview, for edits made before the run, or at a section's confirmation, for its moves — perform it; when it was not, ask before flipping, and never reopen silently. A reopen the preview named that the fresh reading no longer requires — say, a `--reset` removed the unchecked boxes it came from — is not performed, and the report says so. A spec the run wrote nothing to keeps its status. When the guarded write refuses because the status is no longer `done`, stop and name the status found rather than overwriting it.

<!-- audit:ignore-promotion -->
10. Report what changed — per spec under `--all`: the `tasks.md` reduction written, each plan section removed and where each of its pieces went, each section kept and why, and every spec reopened. An interrupted `--all` resumes by running it again: each write is atomic and each reduction idempotent, so what was already removed is simply not found. The reopen costs a fresh `/ductus:analyze` and the completion gate back to `done`; `plan.md` and `tasks.md` are not durable contracts, so the review record stays valid.

## Markdown-only reference

With no ductus runtime registered, the host reaches the same result with its own file tools — no shell-pipeline substitution — producing byte-for-byte the output the primitives would write (the two-paths guarantee, §runtime-host-integration) — with one bound, stated under **reset** and **the design record** below: the reset body and the design-record heading set are compiled into the primitives from the framework templates, so a project that has customized its own tasks or plan template diverges there, and only there.

**`tasks.md`.** Segment it with the same grammar every tasks command uses (see [data-model](https://github.com/stonean/ductus/blob/main/specs/041-task-pruning/data-model.md)): detect flat (`## N.`) versus phased (`### N.` under `## …` containers), then split the file into its preamble, phase containers, and task sections. Classify each task section by its checkboxes — **spent** (≥ 1 checkbox, all checked), **pending** (any unchecked), or **no-checkbox** (zero checkboxes) — counting only real task-list checkboxes (a `- **Done when**:` line is not one).

- **keep-pending** (default): preserve the preamble and every pending / no-checkbox section verbatim; drop every spent section; in a phased file drop a phase container all of whose task sections were dropped, and keep one that governs no task section. When nothing is spent, leave the file byte-for-byte unchanged. Normalize seams to a single blank line with one trailing newline.
- **reset** (`--reset`): preserve the file's existing `# …` heading and replace everything below it with the template's initial tasks body (the intro line plus the guidance comment). On the runtime path this body is **compiled into** `prune-tasks`, pinned to `framework/templates/spec/tasks.md`, so an adopter who customizes `specs/templates/tasks.md` gets the framework body on the runtime path and their own template only on this markdown-only path. Refuse unless the spec status is `done` or `--force` is supplied; a file with no `# …` heading is malformed and is left untouched.

**`plan.md`.** A section is a `##` heading and every line up to the next heading at level 2 or above; a `###` stays inside its section, and a heading inside a fenced block or an HTML comment is not a heading. The lines before the first `##` are the preamble and are always kept.

- **The design record** is the `##` headings of the project's plan template, `specs/templates/plan.md`, compared case-insensitively and with nothing else forgiven, so *Tradeoffs* does not match *Trade-offs*. On the runtime path the set is compiled into `prune-plan` from the framework's own template, `framework/templates/spec/plan.md`, so an adopter who customizes theirs sees their own set only on this markdown-only path. A design-record section is never removed.
- **Decided** — a section is kept without being proposed when `analysis.md`'s `decisions:` list stores a `discarded` decision under `plan-record — plan.md §{heading} is outside the design record`, or one the host matches to it by judgment.
- **Removal** — delete the confirmed section, then normalize every seam in the file to a single blank line with one trailing newline, as keep-pending does. Re-read the section immediately before removing it; if it changed since it was judged, judge it again.
- **Reopen** — on a `done` spec, compare against HEAD (`git diff HEAD -- "specs/{feature}/"`): the spec reopens when its design-record sections differ from HEAD's — compared in order, each by its lowercased heading and its text, which runs from its heading to its last non-blank line — or `tasks.md` adds an unchecked checkbox — holds an unchecked checkbox line, trimmed and outside fenced blocks and HTML comments, more times than HEAD's does, so a line moved or re-indented adds nothing. Compare once before the first write, for the preview, again over each removal before writing it, and once more after the run's writes to the spec, which decides the reopen (step 9). An artifact absent at HEAD triggers nothing. Anything else is mechanical and the spec stays `done`.

**`--all`.** Walk every feature directory under the spec root in corpus order — sequential directories by number, then branch-scoped ones grouped by identifier and ordered by their counter numerically, so `1234.2-` precedes `1234.10-` — and apply the reductions above to each. Count every directory walked; list each spec with something to reduce, and each `done` spec whose tree requires a reopen, with its status; and name each spec with no `tasks.md` or no `plan.md`. Refuse `--force` alongside `--all`.

Confirm with the user before every write, write atomically (a temp file then rename), and leave no backup — recovery is git history.
